## 2. 问题清单

### S-01【严重】填充几何更新从未生效：`setDeferredDispatcher` 全仓 0 调用

**现象**
`FillGeometryUpdater` 在移动/撤销后需要把增量重算推迟到当前调用栈之后；它要求宿主注入 `DeferredDispatcher`。代码在未注入时的行为是：只把待处理 ID 入队，然后 `return`，不做任何重算。

**证据**
- `Engine/2D/Src/Algorithm/FillGeometryUpdater.cpp:122-133`
  ```cpp
  if (!m_pendingScheduled)
  {
      if (!m_deferredDispatcher)
      {
          // 后果是填充色块不会跟随本次移动更新，直到宿主接线或调用 flushPending()。
          APR_DEBUG("[FillGeometryUpdater] no deferred dispatcher installed; "
                   "incremental fill update is skipped.");
          return;
      }
  ```
- 注入接口仅在 `Engine/2D/Src/Algorithm/FillGeometryUpdater.cpp:143-146` 定义，全仓 **0 个调用点**（`rg "setDeferredDispatcher"` 只命中定义与头文件注释）。
- 兜底入口 `flushPending()`（同文件 `:149`）同样 **0 个调用点**。
- 头文件把注入列为宿主启动责任：`Engine/2D/Include/Engine2D/Algorithm/FillGeometryUpdater.h:41`。
- 宿主只做了 `initialize()`，没有注入派发器：`Main/Src/Composition/ApplicationCompositionRoot.cpp:397`。

**影响**
按代码自身注释，移动/撤销填充图层图元后，填充色块不会跟随更新；日志级别是 DEBUG，正常日志配置下完全静默。这是“半成品 + 静默失败”的组合，用户看到的是几何与填充错位。
（若另有整场景全量重刷路径掩盖了该问题，则影响降级为性能问题；见第 4 节待确认 2。）

**修复方向**
最小修复：在组合根用 Qt 事件循环实现派发器并在 `initialize()` 后立即注入，例如
`instance().setDeferredDispatcher([](std::function<void()> t){ QTimer::singleShot(0, qApp, std::move(t)); });`
并补一条“移动填充图元 → 填充包围盒更新”的自动化测试。若不打算接事件循环，则改为 `initialize()` 内自行注册 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`，不要依赖宿主。

### S-02【严重（潜在阻断）】PythonHost 工作线程擦除自己的 `std::thread` → `std::terminate`；取消标志 map 无锁读

**现象**
1. `TaskExecutor::run()` 把工作线程 move 进 `m_threads[handle]`；工作线程函数结尾又执行 `m_threads.erase(handle)`，即在自己仍运行时销毁代表自己的 `std::thread` 对象。
2. `isCancelled()` 直接对 `std::unordered_map` 做 `find()`，调用点不在 `m_mutex` 保护内，而同一张表会被其它线程 `erase`。

**证据**
- 自擦除：`PythonHost/PythonHost/Src/TaskExecutor.cpp:156-161`
  ```cpp
  {
      std::lock_guard<std::mutex> lock(m_mutex);
      m_runningFlags[handle].store(false);
      m_cancelFlags.erase(handle);
      m_runningFlags.erase(handle);
      m_threads.erase(handle);      // ← 线程仍在运行，erase 会析构 joinable 的 std::thread
  }
  ```
  插入点：同文件 `:170-174`（`m_threads[handle] = std::move(worker);`）。
  容器声明：`PythonHost/PythonHost/Include/PythonHost/TaskExecutor.h:39`（`std::unordered_map<TaskHandle, std::thread> m_threads`）。
- 无锁读：`TaskExecutor.cpp:28-32`
  ```cpp
  bool isCancelled(const std::unordered_map<TaskHandle, std::atomic<bool>>& flags, TaskHandle handle)
  {
      const auto it = flags.find(handle);   // 无锁
      return it != flags.end() && it->second.load();
  }
  ```
  调用点 `:139`、`:216`、`:308` 均在锁外；`m_cancelFlags.erase()` 在 `:159`（工作线程）与 `shutdownAll()` 的 `:117` 发生。
- `TaskExecutor.h:39` 的 `m_runningFlags` 与 `m_cancelFlags` 在 `:158` 使用 `operator[]`，若 `shutdownAll()` 已 `clear()`，会重新插入条目，语义上也与“正在关闭”冲突。

**影响**
- 只要任务真正跑起来并完成，`m_threads.erase(handle)` 析构 joinable 线程即调用 `std::terminate`，进程直接退出（不是异常，不可捕获）。在“任务极短、worker 先于 `:173` 完成”的窄窗口内表现为偶发；正常 Python 子进程任务耗时秒级，插入一定先发生，因此是**确定性崩溃**。
- 无锁读 map 与并发 erase 是数据竞争（UB），在 ASan/TSan 下必然报错，Release 下可能读到已释放节点。
- 当前可达性：`PythonHost` 的唯一产品侧引用是 `UI/2D/Src/Option/FaceRecognitionProcessor.cpp:53`，而该类在全仓 **0 个构造点**（见 G-11）。因此当前版本不会触发；一旦把人脸识别/脚本化接上，即为阻断。

**修复方向**
- 工作线程不要碰 `m_threads`：只清 `m_cancelFlags`/`m_runningFlags`；线程对象统一由 `shutdownAll()` 或完成回调在主线程 `join()` 后移除。
- 若必须自清理，改为 `m_threads[handle].detach()`（配合完成标志）或改用 `std::jthread`/线程池。
- `isCancelled()` 增加 `std::lock_guard`，或把取消标志做成 `std::shared_ptr<std::atomic<bool>>` 副本交给 worker，彻底移出共享 map。
- 为 PythonHost 的 `Example` 增加一个“任务完成后进程仍存活”的用例，防止回归。

### S-03【严重】PythonHost 任务回调捕获裸 `this`，且在 worker 线程直接触达 QObject

**现象**
`runTask()` 的回调由 `TaskExecutor` 工作线程直接调用；`FaceRecognitionProcessor` 用 `[this]` 捕获并直接 `emit` Qt 信号。

**证据**
- `UI/2D/Src/Option/FaceRecognitionProcessor.cpp:53-55`
  ```cpp
  PyHost::PythonHost::instance().runTask(request, [this](const PyHost::TaskResult& result) {
      handleTaskResult(result);
  });
  ```
- 回调在 worker 线程直接执行：`PythonHost/PythonHost/Src/TaskExecutor.cpp:164-167`
  ```cpp
  if (callback)
  {
      callback(result);   // 当前线程 = worker
  }
  ```
- `handleTaskResult()` 内直接 `emit faceDetectionError/Completed`：`FaceRecognitionProcessor.cpp:73`、`:81`。

**影响**
1. 生命周期：处理器对象（对话框/文档级）先于任务结束被销毁时，回调访问已释放对象 → UAF。
2. 线程：信号在非对象所属线程发出；`AutoConnection` 到主线程接收者会排队（侥幸安全），但任何 `Qt::DirectConnection` 或槽内直接触碰 `QWidget` 都是跨线程访问 UI。
3. 与 S-02 叠加：完成回调本身即触发 terminate，链路不可用。

**修复方向**
在 `PythonHost` 层统一把回调 marshal 回主线程（保存 `QMetaObject::invokeMethod(qApp, ..., Qt::QueuedConnection)`），或在调用方用 `QPointer<FaceRecognitionProcessor>` 守卫；两者至少做一项，推荐前者作为模块契约。

### S-04【严重】每次异步导入/导出都在主线程无条件 `sleep_for(3s)`

**现象**
`shutdownAsyncThread()` 只要线程对象 `joinable()` 就固定睡 3 秒再 join。线程自然结束后 `std::thread` 仍是 joinable 的（直到 join），因此**从第二次操作开始，每次导入/导出都会先卡 3 秒**；退出程序时只要执行过导入/导出也会卡 3 秒。

**证据**
- `Main/Src/Import/ImportService.cpp:258-277`（sleep 在 `:271`）
  ```cpp
  if (!m_asyncThread.joinable()) { return; }
  m_asyncCancelFlag.store(true);
  ...
  std::this_thread::sleep_for(std::chrono::seconds(3));   // 无条件
  if (m_asyncThread.joinable()) { ... m_asyncThread.join(); }
  ```
  调用点：`ImportService.cpp:487`（每次 `importAsync` 开头）。
- `Main/Src/Export/ExportService.cpp:73-92`（sleep 在 `:86`），同款无条件 sleep；调用点 `:144`（每次 `exportAsync` 开头）。
- 正常完成路径没有 join：导入的 `finishOnMainThread`（`ImportService.cpp:509-536`）只投递 UI 收尾，不 join 线程。

**影响**
主线程（UI 线程）阻塞 3 秒：菜单/窗口无响应、进度条静止；批量导入 N 个文件累计 3N 秒；关闭应用时多等 3 秒。这是明确的用户可感知性能缺陷，且与是否有任务在跑无关。

**修复方向**
不要用“先睡再 join”推测线程状态。用 `std::future`/`std::atomic<bool> finished` + `wait_for(3s)`；更简单的方式是在 worker 尾部设置完成标志，`shutdownAsyncThread()` 先 `wait_for` 该标志（正常毫秒级返回），仅超时才告警并 `join()`。或者把 join 放到完成回调（主线程收尾时顺手 join）。

### S-05【严重】Engine3D ↔ FileIO 存在类型级循环依赖，且用 PUBLIC include 规避链接环

**现象**
`FileIO` 私有链接 `Engine2D/Engine3D`；`Engine3D` 的公共头 `FioEntityConverter.h` 又公开使用 `Fio::*` 类型，因此 `Engine3D` 把 `FileIO/Include` 放进 `PUBLIC_INCLUDE_DIRS` 但**不链接** FileIO。CMake 注释直接承认“形成链接环……只靠头文件 + POD 类型做契约”。

**证据**
- `Engine/3D/CMakeLists.txt:46-55`
  ```
  # 关键：Engine3D **不链接** FileIO（PUBLIC_LINK_LIBRARIES 里没有 FileIO）。
  # FileIO 反过来 link Engine2D/Engine3D，形成链接环；我们只靠头文件 + POD 类型做契约，
  # 避免 ABI 泄漏，也规避链接环。
  ```
- `Engine/3D/CMakeLists.txt:65`（`PUBLIC_INCLUDE_DIRS`）、`:74`：`"${APR_FILEIO_DIR}/Include"` 被公开传播。
- `FileIO/FileIO/CMakeLists.txt:108-114`：`PRIVATE_LINK_LIBRARIES EngineCommon Engine2D Engine3D`。
- 公共头实例：`Engine/3D/Include/Engine3D/Import/FioEntityConverter.h`（公开签名使用 `Fio::*`）。

**影响**
- 依赖方向不成立：Engine 层在**源码契约**上依赖 FileIO，FileIO 在**链接**上依赖 Engine，二者互为上游。任何一方独立发布/独立测试都会失败。
- 因为不链接，消费方 include 后若调用到非内联的 `Fio::*` 符号，会在链接期才炸（而不是编译期），错误定位成本高。
- 与 S-06 叠加：`FileIO/Include` 被 PUBLIC 传播后，UI3D/Main 的 include 面被进一步放大。

**修复方向**
把 `FioEntityConverter` 依赖的纯 POD（`FioTypes.h`）抽到独立的中立契约目标（如 `FioContract`，仅头文件/POD，零 DLL 依赖），Engine3D 对该契约 PUBLIC，FileIO 实现该契约；或把转换器下沉到 FileIO 侧（FileIO 已依赖 Engine，方向天然正确）。**不要**在 Engine3D 里继续扩大 `FioEntityConverter` 的 API 面。

### S-06【严重】UI3D 公共头直接暴露 Engraving / GeoModelCore 类型，导致依赖 PUBLIC 全量传播

**现象**
`UI3D` 的公共头文件直接 `#include "Engraving/..."` 与 `"GeoModelCore/GmcStepAssembly.h"`，因此 CMake 只能 `PUBLIC` 链接这两个模块；而 `GeoModelCore` 又 `PUBLIC` 链接 15 个 OCCT 库。结果是：任何链接 UI3D 的目标（Main、测试）都继承 OCCT + Engraving 的 include 与链接面。

**证据**
- 公共头 include：
  - `UI/3D/Include/UI3D/Service/BRepModelService3D.h:15` → `#include "GeoModelCore/GmcStepAssembly.h"`
  - `UI/3D/Include/UI3D/Adapter/EngravingMeshBridge3D.h:9`、`Relief/ReliefEngravingProcessor3D.h:9-10`、`Relief/ReliefEngravingJob3D.h:12`、`Relief/ReliefEngravingParams3D.h:8`、`Relief/ReliefToolpathPreview3D.h:14`（5 个头文件、6 行 include，`rg` 实测）
- 传播：
  - `UI/3D/CMakeLists.txt:169` `target_link_libraries(${LIB_NAME} PUBLIC GeoModelCore)`
  - `UI/3D/CMakeLists.txt:175` `target_link_libraries(${LIB_NAME} PUBLIC Engraving)`
  - `GeoModelCore/GeoModelCore/CMakeLists.txt:63-69`：15 个 OCCT target 全部 `PUBLIC`
- 运行时也承认该传播：`UI/3D/CMakeLists.txt:301` 注释“UI3D.dll 链 GeoModelCore，加载时需要 OCCT 运行时在 PATH 上”。

**影响**
- 导出面/依赖面过大：只想要 3D 视口或 2D 工作台的下游，也被迫携带 OCCT/Engraving 依赖与部署体积。
- 头文件泄漏内部类型：`GmcStepAssembly`、`LaserStrategy`、`VolumeProcessing` 都是算法内部概念，被提升为 UI 公共契约，后续无法独立演进。
- 与 S-05 一起构成“公共头 → PRIVATE 依赖”的同一类问题，只是这里被迫 PUBLIC 化。

**修复方向**
把这 7 个类改为 PIMPL/前置声明（`struct Impl; std::unique_ptr<Impl>`），或把雕刻/B-Rep 相关 UI 拆成独立适配 target（`UI3DEngravingAdapter`、`UI3DBRepAdapter`），UI3D 核心只依赖窄接口；这样 `Engraving`、`GeoModelCore` 可降为 PRIVATE。

### S-07【严重】QSettings 身份在三处硬编码 "April"/"April"，与品牌身份分叉

应用启动时由品牌配置设置 `QCoreApplication::organizationName/applicationName`；但 Network 与急停控制器各自用硬编码 `"April","April"` 构造 `QSettings`。默认品牌恰好也是 April，所以现在“看起来正常”；切到 `client_a`（appId=AcmeCut）/`client_b`（OrionCAD）后，三方读写的 ini 路径不同。

  ...
  QCoreApplication::setApplicationName(m_config.effectiveAppId());

- 品牌值：`Main/Src/UI/ClientConfig/branding/client_a/brand.json:5` `"appId": "AcmeCut"`；`client_b/brand.json:5` `"appId": "OrionCAD"`。
- 硬编码：
  - `Network/Network/Src/ConfigManager.cpp:19`
    `new QSettings(QSettings::IniFormat, QSettings::UserScope, "April", "April", this)`
  - `Main/Src/UI/Safety/EmergencyStopController.cpp:15` 与 `:21`
    `QSettings(..., QStringLiteral("April"), QStringLiteral("April"))`
- 相关文件里还有一条自述风险注释：`Network/Network/Src/ConfigManager.cpp:17` 提到“避免路径不一致（如写到 AppData\Roaming\April）”。

**影响**

**处理状态（2026-11-11）**
已修复。`Network/Network/Src/ConfigManager.cpp` 与 `Main/Src/UI/Safety/EmergencyStopController.cpp` 已统一改用 `QCoreApplication::organizationName()/applicationName()`。升级时从旧 `April/April.ini` 一次性导入新位置缺失的键（`meta/legacyIdentityMigrated` 标记防重复，旧 ini 文件保留可回滚）；急停闭锁状态优先从旧位置迁移，避免安全状态丢失。configure 期门禁（A-04/G6）尚未落地。

### G-01【一般】UI2D 直接链接 5 个算法/支撑 DLL，其中 Network、PythonHost 为死链；条件目标存在性检查不一致

**现象**
`UI2D` 通过 `UiEngineAccess` 收口了 Engine，但仍直接 `PRIVATE` 链接 `Nesting/Vision/Network/Engraving/Raster/PythonHost`。其中 Network 在 UI2D 源码中 **0 引用**；Network 在整个产品中 **0 消费者**（Main 甚至没有链接它）。

**证据**
- `UI/2D/CMakeLists.txt:181`（Nesting）、`:202`（Vision）、`:212`（Network）、`:223`（Engraving）、`:228`（Raster）、`:234`（PythonHost）。
- 死链证据：`rg "Network/|Network::|WebSocket" UI/2D` → 0 命中；`rg "NetworkManager|WebSocketClient"`（排除 `Network/**`）→ 仅文档/README。
- `Main/Src` 中 `Network` 0 命中（Main 未链接该 DLL）。
- 条件检查不一致：Nesting 有 `if(NOT TARGET Nesting) FATAL_ERROR`（`UI/2D/CMakeLists.txt:174-176`），而 Vision/Network/Engraving/Raster/PythonHost 均无 `TARGET` 守卫（`:197-234`）。
- 根顺序：`UI/2D` 在 `CMakeLists.txt:220` 加入，而 Hardware/Network/Vision/Raster（`:230/:237/:244/:253`）在其后；靠 CMake 的“生成期解析目标名”隐式成立，standalone 构建 UI2D 必然失败。

**影响**

- `unregisterDynamicSection` 全仓 0 调用（仅声明/定义）。
- 生命周期现状：2D/3D 工作台对象在应用生命周期内基本常驻（`Main/Src/Bootstrap/AppBootstrapper.cpp:186,190`；`Main/Src/UI/Services/UiShellHost.cpp:132`），所以当前不会立刻悬垂；但 2D/3D 先后注册同一 `sectionId` 时后者静默覆盖前者。

**影响**

**修复方向**

### A-04【建议】两个规划中的门禁从未落地：公共头自包含性、设置身份一致性

**现象**
旧文档提出的 `CheckPublicHeaders.cmake`、`CheckSettingsIdentity.cmake` 在 `CMake/` 下均不存在；而本次审计的 G-02/G-03/G-04/S-07 恰好都是这两类门禁能自动拦住的问题。

**证据**
- `CMake/` 目录仅含 6 个门禁脚本（列表见 G-07）；无上述两个文件。
- 现存门禁能拦“新增依赖”，但拦不住“PUBLIC include 目录里多塞了第三方路径”（G-02）或“QSettings 硬编码身份”（S-07）。

**影响**
同类问题会在新模块反复出现，只能靠人工复查。

**修复方向**
1. `CheckPublicHeaders.cmake`：对每个公共头做一次“仅带本目标 PUBLIC include + 标准库”的编译探测；顺带校验 `PUBLIC_INCLUDE_DIRS` 中每一条至少被一个公共头使用。
2. `CheckSettingsIdentity.cmake`：`rg` 扫描 `QSettings(` 后两个字符串字面量参数，命中即失败。

### A-05【建议】UI→Engine include 棘轮白名单存在已失效条目，且无法验证“只减不增”

**现象**
`CMake/UiEngineAccessRatchet.cmake:38-119` 冻结了 UI/Common、UI/2D、UI/3D 三份允许的 Engine 头。白名单是“只减不增”的人工维护表，但脚本只检查“不在表内即失败”（`:176`），不检查“表内条目是否仍被使用”，因此条目只会沉淀不会收缩。

**证据**
- 白名单定义：`CMake/UiEngineAccessRatchet.cmake:39-119`。
- 校验逻辑只做 `if(NOT _hdr IN_LIST _allowed)`（`:176`），没有反向的“白名单未使用”检查。
- 已知仍在使用的例子：`Engine2D/Text/TextConverter.h`（白名单 `:98`，实际被 `UI/2D/Src/Option/TextProcessor.h:5` 使用）。

**影响**
依赖面无法真正缩小；后人无法区分“历史豁免”与“当前真实依赖”。

**修复方向**
在脚本里同时输出“白名单中 0 使用的条目”并设为 WARNING（或 CI 中失败），推动逐轮收缩；每次收缩后同步删表项。

**处理结果（2026-11-11）**：已加入“0 使用即 configure 失败”的反向检查。扫描前先剔除注释与字面量 `#if 0` 分支（`#if/#ifdef/#ifndef` 其余条件编译保守视为参与编译，`#else/#elif` 重新放行），避免把仍在用的条目误报为未使用；同时识别 `#include <...>` 写法。对当前 75 条白名单逐条复核（UI/Common 13、UI/2D 45、UI/3D 17）全部仍被真实代码引用，因此本轮没有可删除的失效条目；未放宽任何阈值或新增豁免。

### A-06【建议】渲染三层（RenderAbstraction / RenderBridge / Renderx）缺“零实现/零引用”自动检查

**现象**
`RenderAbstraction` 是纯头文件接口层，`RenderBridge` 是唯一实现方，`Renderx` 是后端；文档已说明这是“ABI/头文件隔离层，不是可插拔后端抽象”。结构本身合理，但没有机制阻止再冒出第二套并行抽象。

- `RenderBridge/CMakeLists.txt:103-107`：导出接口不包含 RenderX。
- `Docs/01-当前架构/框架冗余与复杂度审查.md:1212` 记录已加“唯一实现”注释。

**影响**
现状可控；风险是“再加一个 IRenderXXX 接口/适配器”无人拦截，重复旧文档里清理过的同类冗余。

**修复方向**
