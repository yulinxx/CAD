# 开发说明

## 1. 目的

本文用于统一项目开发过程中的基础规范、编码约定和文档约定，方便后续新功能开发、代码维护、问题排查和多人协作。

> 本文是开发执行层面的约定，不是架构设计文档。若与具体模块设计冲突，应以该模块的架构文档和代码事实为准。

---

## 2. 总体原则

1. 代码先保证可读性，再保证可扩展性，再考虑局部性能。
2. 新增功能优先遵循现有架构，不要为单个需求随意打破分层边界。
3. 重要逻辑必须可追踪、可定位、可回溯。
4. 变更必须尽量局部化，避免无关重构混入业务修改。
5. 所有新增代码都要考虑后续维护者能否快速看懂。

---

## 3. 编码规范

### 3.1 语言与风格

- 代码命名尽量保持统一风格，不要在同一模块里混用多套命名习惯。
- 函数、类、文件的命名应能表达职责，允许出现过度缩写, 但要在注释中说明其含义。
- 不要写只有作者本人能理解的变量名,不要使用拼音命名变量。
- 单个函数尽量只做一件事，逻辑过长时应拆分为更小的辅助函数。

### 3.2 注释规范

- **注释必须使用中文。**
- 注释只写必要信息，重点说明“为什么这么做”“这里有什么约束”“有什么坑”。
- 不要写翻译代码本身含义的重复注释。
- 对于复杂流程、边界条件、兼容逻辑、历史遗留处理，必须补充中文说明。
- 对于临时保留的兼容代码，应写清楚保留原因和后续处理方向。
- 简单的函数注释使用 // 开头，避免使用 /* 开头。

### 3.3 日志规范

- **日志内容必须使用纯英文。**
- 日志建议采用统一前缀或统一类别，便于检索和过滤。
- 日志要尽量短，但要包含关键上下文信息，例如对象名、命令名、状态值、返回值、错误码等。
- 关键函数入口、关键分支、异常路径、资源创建与释放点，建议补充日志。
- 日志不要写成大段自然语言描述，避免影响检索和性能。
- 避免在高频循环、逐帧渲染等热点路径里打印过多日志，必要时使用条件日志或调试开关。

建议原则：

- 入口日志：说明函数进入和主要参数
- 结果日志：说明执行结果和关键返回值
- 错误日志：说明失败原因和上下文
- 状态变更日志：说明从什么状态变到什么状态

### 3.4 关键函数要求

以下函数建议至少具备可追踪能力：

- 模块初始化与反初始化
- 命令分发、命令切换、命令结束
- 视口输入处理与事件路由
- UI 配置加载与应用
- 菜单构建、工具栏构建、布局切换
- DLL 导出接口、跨模块调用接口
- 资源加载、文件读写、外部依赖调用

## 4. DLL 开发规范

### 4.1 导出边界必须明确

在 DLL 中编写代码时，必须先确认哪些内容需要导出，哪些内容只在 DLL 内部使用。

- 只给外部模块调用的类、函数、接口，必须明确导出。
- 仅供 DLL 内部使用的实现细节，不要暴露到导出接口中。
- 不要把内部辅助类、内部工具函数、临时实现细节混入导出头文件。

### 4.2 导出头文件与实现文件的组织

- **DLL 中不导出的头文件和对应 cpp，建议放在一起。**
- 导出接口头文件与内部实现头文件应尽量分层放置，避免误用。
- 如果某个头文件只服务于当前 DLL 的实现，就不要把它放到会被外部直接引用的公开位置。
- 对外接口应尽量小而稳定，内部实现可以灵活调整。
- 导出宏定义要统一，避免在不同头文件中使用不同的宏定义。
- 导出宏定义风格使用大写，避免与 C++ 代码冲突,建议为 `XXX_API`。

### 4.3 跨 DLL 数据类型注意事项

- 跨 DLL 传递的对象生命周期必须清晰。
- 跨模块传递的内存谁分配、谁释放必须明确。
- 尽量避免跨 DLL 直接传递复杂 STL 容器、临时对象和内部私有类型。
- 如果必须跨 DLL 传递类型，应保证 ABI 风险可控，并在文档中说明。
- 单例模式的类，必须在 DLL 内部实现，外部只能通过接口调用。

### 4.4 导出接口稳定性

- 导出接口一旦被外部依赖，修改前要评估兼容性。
- 破坏性改动优先通过新增接口或保留旧接口过渡。
- 对外接口参数尽量少、语义尽量清晰、错误返回方式尽量统一。

## 5. 模块编写规范

### 5.1 UI 模块

- UI 代码要和业务逻辑尽量分离。
- 视图负责展示，状态管理负责同步，命令系统负责行为。
- UI 组件新增功能时，要同步考虑命令映射、菜单入口、快捷入口和状态反馈。
- 新增控件要关注重用性，不要把业务逻辑直接写死在控件内部。

### 5.2 渲染与视口模块

- 视口输入、交互命令、渲染刷新要明确边界。
- 输入路由层只做分发，不要混入复杂业务判断。
- 渲染层尽量保持独立，避免直接依赖过多 UI 细节。
- 涉及高频调用路径时，优先考虑性能和调用次数。

### 5.3 命令与状态模块

- 命令状态切换要清晰，避免隐式状态跳转。
- 状态修改要尽量统一入口，减少到处写状态变量。
- 支持撤销、重做或恢复的逻辑，必须把状态变化记录清楚。
- 命令完成、取消、失败三种路径要分别考虑。

### 5.4 配置与资源模块

- 配置文件应保持结构稳定，字段新增要考虑旧配置兼容。
- 资源命名要统一，避免同类资源出现多套命名规则。
- 资源加载失败时要给出清晰日志，便于定位缺失项。

---

## 6. 日志与调试约定

### 6.1 建议打印的内容

- 函数入口与出口
- 关键参数值
- 状态切换前后值
- 资源加载结果
- 失败原因和异常分支
- 关键对象创建和销毁

### 6.2 不建议打印的内容

- 高频循环内的无意义重复日志
- 与问题无关的冗长描述
- 过大的对象全部展开输出
- 会明显影响性能的逐次调用日志

### 6.3 调试原则

- 先保证能定位问题，再考虑日志是否精简。
- 日志应服务于排查，不应成为噪声源。
- 如果某类问题经常出现，应把日志补在真正的关键节点，而不是到处临时散点打印。

---

## 7. 文档编写规范

- 新增功能前，先确认是否已有对应架构文档。
- 代码行为发生变化时，相关文档应同步更新。
- 文档中应区分“现状”“设计方案”“待核实内容”“历史记录”。
- 设计文档不要冒充已实现事实。
- 如果代码与文档不一致，应先以代码事实为准，再补齐文档修订计划。
- 新增文档尽量放在对应索引目录，并在索引页同步更新入口。

---

## 8. 提交前自检清单

开发完成后，建议至少检查以下内容：

1. 关键路径是否已经补充英文日志。
2. 复杂逻辑是否已经补充中文注释。
3. 是否误把内部实现暴露到了 DLL 导出接口。
4. 非导出头文件与 cpp 是否按模块放置合理。
5. 是否存在无关改动混入本次提交。
6. 是否需要同步更新相关文档。
7. 是否能通过现有编译和测试流程。

---

## 9. 推荐工作方式

1. 先确认需求边界和影响范围。
2. 再确认涉及哪些模块、接口和文档。
3. 实现时优先保持小步修改。
4. 关键函数补日志，复杂逻辑补中文注释。
5. 涉及 DLL 时先想清楚导出边界。
6. 最后回头检查文档与代码是否一致。

---

## 10. 命名规范

### 10.1 总体要求

- 命名应以“看名字就能猜到职责”为目标。
- 不要使用过度缩写，除非它是项目内约定俗成的术语。
- 同一层级、同一模块内的命名风格要一致。
- 对外暴露的命名要稳定、清晰，内部私有命名可以更偏实现细节。

### 10.2 类、函数、变量命名

- 类名建议使用明确的名词或名词短语。
- 函数名建议使用动词或动词短语，表达行为。
- 设置器函数建议使用 'set','get' 前缀，例如 `setIsReady`、`getIsReady`。
- 布尔变量建议使用能直接读懂的语义，例如 `isReady`、`hasValue`、`shouldRefresh`。
- 集合类型变量应表达集合的内容，而不是仅写 `list`、`data` 这类泛化名称。

### 10.3 文件与目录命名

- 文件名应尽量反映模块职责。
- 同类文件尽量使用统一后缀和统一前缀。
- 新增文档和配置文件尽量保持项目现有命名风格。

### 文件夹命名
- 不同功能的类文件若有较多，应放在不同的文件夹中。
- 文件夹名应使用名词或名词短语，表达模块职责。
- 同一层级、同一模块内的文件夹要保持命名规则。


### 10.4 常量与枚举命名

- 常量、枚举值、命令 ID 应保持统一前缀或统一分类方式。
- 不要让不同模块的常量命名互相冲突。
- 对外常量应避免频繁改名，以减少下游修改成本。

## 11. 日志等级与格式

### 11.1 日志等级建议

- `DEBUG`：仅用于调试细节，默认不应大量输出。
- `INFO`：用于关键流程记录、状态变化和正常业务结果。
- `WARN`：用于可恢复异常、边界风险、兼容行为。
- `ERROR`：用于明确失败、不可继续执行或需要重点排查的问题。

### 11.2 日志写法建议

- 日志内容要使用纯英文。
- 日志句式尽量统一，便于全文检索。
- 关键字段建议固定顺序输出，避免同类日志格式混乱。
- 日志中尽量包含模块名、函数名、对象名、状态值、错误码等上下文。

示例：

```text
[WorkbenchMenuManager] Build menu start, client=SanYi
[ViewportInputRouter] Route mouse press, tool=DrawLine
[UiConfigLoader] Load config failed, path=base.json, error=missing key
```

### 11.3 日志使用边界

- 热点路径只保留必要日志。
- 大对象内容不要直接整段输出。
- 如需打印复杂结构，优先打印关键字段而不是完整对象。

## 12. Git 与提交规范

### 12.1 提交前要求

- 提交前先确认本次修改范围是否清晰。
- 不要把无关文件混入本次提交。
- 代码修改、文档修改、配置修改尽量按目的拆分。
- 如果修改涉及多个模块，提交说明里要能看出主线目的。

### 12.2 提交信息建议

- 提交信息应简洁、明确，能表达“为什么改”。
- 优先使用“新增 / 修复 / 调整 / 重构 / 文档”等可读性高的表达。
- 如果一次提交包含多个点，应以主目标为主，次要内容从属说明。

### 12.3 分支与协作建议

- 大范围改动优先在独立分支完成。
- 影响多人的公共接口改动要提前说明。
- 如果文档与代码同步变更，建议在同一开发周期内完成核对。

---

## 13. 测试与验证规范

### 13.1 基本验证

每次完成开发后，建议至少完成以下验证：

1. 编译是否通过。
2. 关键流程是否能正常运行。
3. 新增功能是否能覆盖到预期入口。
4. 相关配置、资源、菜单、布局是否同步生效。
5. 是否引入新的崩溃、空指针、越界或异常路径。

### 13.2 功能验证

- UI 改动后要检查显示、交互、状态刷新是否一致。
- 命令改动后要检查触发路径、取消路径、结束路径是否正确。
- DLL 改动后要检查导出符号、链接、调用约定是否稳定。
- 配置改动后要检查旧配置兼容性。

### 13.3 问题回归

- 修复问题后应尽量补充回归验证。
- 能自动化验证的内容尽量自动化。
- 对于容易复发的问题，应把验证点固定下来。

---

## 14. 资源与配置规范

### 14.1 资源命名

- 图标、图片、样式、配置文件命名应保持一致风格。
- 同类资源建议按目录或功能分组。
- 资源名应尽量能看出用途，不要使用无意义编号。

### 14.2 配置文件

- 配置字段新增时要考虑旧版本兼容。
- 配置读取失败时要给出明确英文日志。
- 默认值策略要统一，避免各处随意兜底。

### 14.3 QRC 与资源引用

- 资源引用路径应保持稳定，避免因为目录调整引起连锁修改。
- 新增资源后要确认编译系统和打包流程能够正确包含。
