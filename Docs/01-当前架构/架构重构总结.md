# 架构收口原则

本文只描述当前架构需要遵守的约束，以及后续继续收口的方向，不保留阶段性历史记录。

---

## 1. 当前架构目标

当前工程的目标是把 UI、引擎、渲染、文件、扩展模块拆成清晰边界：

- `Main` 负责应用启动、工作台装配、窗口生命周期
- `UICommon`、`UI2D`、`UI3D` 负责界面入口、交互和工作台组织
- `EngineCommon`、`Engine2D`、`Engine3D`、`EnginePersistence` 负责几何与文档能力
- `Renderx` 目录承载渲染源码，构建目标为 `RenderX`
- `Utility`、`Log`、`CrashHandler`、`License` 负责基础设施

---

## 2. 现行收口结果

### 2.1 渲染路径

当前生产渲染统一走 `Renderx` / `RenderX`，不再使用独立的 `RenderCommon`、`Render2D`、`Render3D`、`RenderNext` 目录链路。

### 2.2 2D 视图

2D 视图当前以 `RenderViewport2D`、`RenderWidget`、`RenderSceneBuilder` (GeometryStore + DrawList) 为主，数据层通过 `SceneManager` 向渲染层推送几何。

### 2.3 3D 视图

3D 视图当前以 `Workbench3D`、`Viewport3D`、`Renderer3DFactory`、`RenderWidget3DAdapter`、`RenderWidget3D` 组成唯一链路。曾经并存的软件渲染链 `SimpleRenderer3D` / `ViewCamera3D` 已于 2026-08-26 删除（产品运行时无触发点，只有测试在用，且自带一套与 `RenderWidget3D` 冲突的相机键位约定）。

### 2.4 命令系统

命令系统统一通过 `OperationBus` 调度，命令入口由菜单、工具栏、快捷键共享，不再保留旧的中间分发层。

### 2.5 死代码清理（2026-08-23）

已删除以下生产目录中的死代码：

- `Engine2D/Render/DisplayCache.h/.cpp` — 无生产调用者的显示缓存
- `Engine2D/Render/DisplayMeshBuilder.h/.cpp` — DisplayCache 的唯一消费者
- `Engine2D/Algorithm/Test/TestEntityGenerator.h/.cpp` — 无调用者且误放在公开 include 路径
- `UiServices::withFrameworkServices()` — 空实现，全代码库零次调用
- `IInteractionDispatcher::setUiServices()` / `setLayoutService()` — 存储但从不读取
- `CMakeLists.txt` 中 `# EngineCommon Engine2D` / `# RenderCommon Render2D` 旧模块名注释

### 2.6 接口统一（2026-08-23）

**IUiServices 接口**：
- 新增 `Main/Src/UI/Services/IUiServices.h`，暴露 `getSelectionService()`、`getUndoManager()`、`getInteractionDispatcher()`
- `UiServices` 继承 `IUiServices`，保持向后兼容
- 消费者可逐步从依赖具体类型转向依赖接口

**ISceneDocument 统一**：
- 扩展 `UI::SceneDocumentBase` 添加元数据方法（`documentName`、`filePath`、`isModified`）和选择方法（`selectedEntityId`、`clearSelection`）
- `SceneDocument3D` 改为继承 `SceneDocumentBase`，实现所有虚方法
- 2D/3D 场景文档共享同一基类，支持多态访问

**OperationSourceKind 统一**：
- 消除 `Cmd::OperationSourceKind` 与 `Cmd::OperationSource` 重复枚举
- `OperationSourceKind` 改为 `OperationSource` 的类型别名（向后兼容）
- `OperationSourceBridge` 简化为 identity 函数

### 2.7 接口化与去单例（2026-08-24）

**14 个服务接口**：
- 新增 `IUiStateCenter`、`IOperationBus`、`ISceneDocument`、`ISceneEditService`、`ILayerManager`、`ILayerEditService`、`IPersistenceService`、`IImportService`、`IExportService`、`IRecentFileService`、`ISettingsService`、`IViewportActionHub`、`IUnitManager`、`IClipboard`
- `UiServices` 实现 `IUiServices`，成员变量改为接口指针
- `ApplicationCompositionRoot` 注入接口，消费者逐步迁移

> **2026-08-27 复核并清理：这批接口里 13 个是空壳，已物理删除。**
> 逐个核对后，`UI/Common/Include/UI/Services/` 下只有 `IRecentFileService` 真被实现
> （Main 的 `RecentFileService`，本轮最近文件收敛时落地）。其余 13 个
> （`IUiStateCenter`/`IOperationBus`/`ISceneDocument`/`ISceneEditService`/`ILayerManager`/
> `ILayerEditService`/`IPersistenceService`/`IImportService`/`IExportService`/
> `ISettingsService`/`IViewportActionHub`/`IUnitManager`/`IClipboard`）零实现者、
> 零引用、也从未被 CMake 的 glob 收进构建，已全部删除。
>
> 同时纠正两个曾被写错的说法：
> - "`UiServices` 成员变量改为接口指针"**不成立**。`Main/Src/UI/Services/UiServices.h`
>   的 20 个成员里只有 4 个是接口指针（`IInteractionDispatcher`/`IUndoRedoManager`/
>   `ISelectionService`/`IRecentFileService`），其余全是具体类型；当时只新建了接口头文件，
>   没有改过成员类型。头文件自己的注释反而写了实话（"当前暴露具体类型指针，违反…原则"）。
> - "`ILayerManager` 有实现者" 指的是**另一个同名类** ——
>   `Engine/2D/Include/Engine2D/Interaction/ILayerManager.h`（被 `LayerManager` 实现，
>   有 `LayerPersistenceBridge` / `QtLayerManagerBridge` 两个真实消费者，必须保留）。
>   它与被删掉的 `UI/Services/ILayerManager.h` 毫无关系。两者同名且都在全局命名空间，
>   一旦被同一个 TU 同时 include 就是重定义错误 —— 删掉空壳那份正好消除隐患。
>
> 教训：接口先行但迟迟没有实现者，比没有接口更糟 —— 它会让人照着签名写调用方代码。
> `IPersistenceService` 就这样卡住过 `IRecentFileService` 的持久化访问器。



**OperationBus 2D 去单例**：
- 14 处 `OperationBus::instance()` 调用点全部迁移为构造注入
- `SelectTool`/`CommandActionHub`/`OperationRouting` 新增 `setOperationBus()` 方法
- `ToolContext`/`ToolInitializer`/`RenderViewport2D`/`UiWorkbench` 传递 bus 指针
- 删除 `OperationBus::instance()`、`setActiveInstance()`、`s_activeInstance` 静态成员

**OperationRouting 统一**：
- `OperationRouting::dispatch()` 改用 `Cmd::dispatchFromCatalog` 模板
- 与 3D 侧路由逻辑一致，消除手写重复代码

**消除 14 个单例**：
- 引擎层：`EntityIdGenerator`、`FontManager`、`FormatRegistry`
- UI 层：`ServiceLocator3D`、`EntityEditorFactory`、`AlgorithmTaskUiHost2D`、`AlgorithmTaskUiHost3D`、`ReliefEngravingService3D`、`TextInputSettingsStore`、`UiInteractionGate`、`LanguageManager`、`ThemeManager`、`SystemThemeDetector`、`CommandPluginRegistry`
- 均改为通过 `ApplicationCompositionRoot` 依赖注入

**SceneDocument2D 元数据补全**：
- 添加 `m_documentName`、`m_filePath`、`m_isModified` 成员
- 覆盖 6 个虚方法（`documentName`/`filePath`/`isModified` 及 setter）
- 所有修改操作（create/remove/clear）自动标记 `m_isModified = true`

**CMake 修复**：
- 扁平化输出目录（移除按配置分目录），修复 RenderX 链接
- 移除 7 个子模块重复的 `Log/Log` 添加，避免目标名冲突
- UI/2D/Common 条件化 RenderX 依赖（`$<$<BOOL:${BUILD_RENDERX}>:...>`）

**RenderX 修复**：
- `overlayQueue.h` 语法错误（注释行误触发语法）
- `renderCApiFrame.cpp` 调用参数数量不匹配

## 3. 现行约束

1. 所有模块只保留自己的职责，不把历史兼容逻辑继续向主线扩散。
2. 业务逻辑不放在渲染层，渲染层只负责绘制和状态消费。
3. UI 只保留入口、交互和状态同步，不承担核心模型和渲染编排。
4. C ABI 边界只暴露 POD、句柄和明确错误码，不暴露 STL 作为外部契约。
5. 已删除路径只作为“不可再使用”的说明，不再扩展成新接口。

---

## 4. 当前需要继续收口的方向

- 继续统一各模块的 C ABI 风格、版本查询和错误码命名
- 继续减少 UI 层对内部实现细节的直接依赖
- 继续收紧 `RenderWidget3DAdapter` 只做桥接的职责边界（3D 已只剩一条渲染链）
- 继续清理文档中的旧目录名、旧模块名和旧实现名

---

## 5. 当前结论

当前架构已经进入“以现状为基线、以约束为主”的阶段。后续所有文档都应优先描述：

- 当前可用的模块
- 当前有效的边界
- 当前推荐的调用方式
- 当前仍需继续收口的点

不再保留阶段性回顾、时间线式变更记录或旧路径展开。
