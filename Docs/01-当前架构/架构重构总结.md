# 架构收口原则

本文只描述当前架构需要遵守的约束，以及后续继续收口的方向，不保留阶段性历史记录。

---

## 1. 当前架构目标

当前工程的目标是把 UI、引擎、渲染、文件、扩展模块拆成清晰边界：

- `Main` 负责应用启动、工作台装配、窗口生命周期
- `UICommon`、`UI2D`、`UI3D` 负责界面入口、交互和工作台组织
- `EngineCommon`、`Engine2D`、`Engine3D`、`EnginePersistence` 负责几何与文档能力
- `Renderx` 目录承载渲染源码，构建目标为 `RenderX`
- `Utility`、`Log`、`CrashHandler`、`License` 负责基础设施

---

## 2. 现行收口结果

### 2.1 渲染路径

当前生产渲染统一走 `Renderx` / `RenderX`，不再使用独立的 `RenderCommon`、`Render2D`、`Render3D`、`RenderNext` 目录链路。

### 2.2 2D 视图

2D 视图当前以 `RenderViewport2D`、`RenderWidget`、`SceneGeometrySinkAdapter` 为主，数据层通过 `SceneManager` 向渲染层推送几何。

### 2.3 3D 视图

3D 视图当前以 `Workbench3D`、`Viewport3D`、`Renderer3DFactory`、`RenderWidget3DAdapter`、`RenderWidget3D` 组成当前链路。`SimpleRenderer3D` 只用于验证或兼容用途，不作为唯一主链。

### 2.4 命令系统

命令系统统一通过 `OperationBus` 调度，命令入口由菜单、工具栏、快捷键共享，不再保留旧的中间分发层。

---

## 3. 现行约束

1. 所有模块只保留自己的职责，不把历史兼容逻辑继续向主线扩散。
2. 业务逻辑不放在渲染层，渲染层只负责绘制和状态消费。
3. UI 只保留入口、交互和状态同步，不承担核心模型和渲染编排。
4. C ABI 边界只暴露 POD、句柄和明确错误码，不暴露 STL 作为外部契约。
5. 已删除路径只作为“不可再使用”的说明，不再扩展成新接口。

---

## 4. 当前需要继续收口的方向

- 继续统一各模块的 C ABI 风格、版本查询和错误码命名
- 继续减少 UI 层对内部实现细节的直接依赖
- 继续收紧 3D 兼容层与主链之间的职责边界
- 继续清理文档中的旧目录名、旧模块名和旧实现名

---

## 5. 当前结论

当前架构已经进入“以现状为基线、以约束为主”的阶段。后续所有文档都应优先描述：

- 当前可用的模块
- 当前有效的边界
- 当前推荐的调用方式
- 当前仍需继续收口的点

不再保留阶段性回顾、时间线式变更记录或旧路径展开。
