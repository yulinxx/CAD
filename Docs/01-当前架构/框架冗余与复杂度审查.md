## 3. 详解

### 3.1 零调用方的死层

#### 3.1.1 `ServiceLocator3D`：只写不读的全局单例 ★

**结论**：写入侧完整、读取侧为零。15 个 getter 在生产代码中**没有任何调用者**。

**证据链**

1. `UI/3D/Include/UI3D/Service/ServiceLocator3D.h:15-113` 定义单例 + 15 个 accessor（`sceneManager()` / `renderWidget()` / `operationBus()` / `documentManager()` / `undoRedoManager()` / `sceneEditService()` / `sceneMonitor()` / `commandActionHub()` / `settingsCoordinator()` / `algorithmRunner()` / `algorithmService()` / `sceneDocument()` / `cameraController()` / `settingsService()` / `brepModelService()`）+ 1 个 setter。
2. 生产代码中 `ServiceLocator3D` 的**全部出现点**：
   - `Main/Src/UI/Workbench/Workbench3D.cpp:285` → `ServiceLocator3D::adopt(m_services3D);`（写）
   - `Main/Src/UI/Workbench/Workbench3D.cpp:1515` → `ServiceLocator3D::shutdown();`（清）
   - 3 处注释（`Workbench3D.h:30`、`Workbench3D.cpp:99/237/359`）
3. `ServiceLocator3D::instance()` 除被 `adopt()` / `shutdown()` 内部调用外，**0 处生产调用**。
4. 15 个 accessor **全部 0 调用**。
5. `UI/3D/Src/Service/ServiceLocator3D.cpp` 自身只有 45 行，内容为 `instance()` / `adopt()` / `shutdown()` 三个函数。

**成因**：`Workbench3D` 自己持有一份同样的 `ServicePack3D`（`Workbench3D.h:130` 的 `m_services3D`），所有消费都走 `MainWindow3D` 的 14 个 getter，从来没有回头读这个全局单例。

**规模**：`ServiceLocator3D.h` 116 行 + `.cpp` 45 行 = **161 行**，外加 2 处调用点与 3 处误导性注释。

**改造方案**

| 项 | 内容 |
|---|---|
| 动作 | 删除 `UI/3D/Include/UI3D/Service/ServiceLocator3D.h`、`UI/3D/Src/Service/ServiceLocator3D.cpp`；删除 `Workbench3D.cpp:285`、`:1515`；同步删除 `Main/Src/Stubs/UI3D/Service/ServiceLocator3D.h`；更新 3 处注释 |
| 影响面 | `UI/3D/CMakeLists.txt`（源/头文件列表）、`Main/Src/UI/Workbench/Workbench3D.{h,cpp}` |
| 验证 | `grep -rn "ServiceLocator3D" --include="*.cpp" --include="*.h" .` 返回 0；`BUILD_UI_DIMENSION=BOTH` 与 `2D` 两种配置各全量编译一次 |
| 风险 | **低**。零读取方 → 删除不改变任何运行时行为 |
| 回滚 | 单 commit，`git revert` |

#### 3.1.4 2D `OperationContext` 恒空：三处死分支

**结论**：2D 的 `OperationContext` 在生产代码中**从未被赋值**，`refresh()` 空转、`canExecute()` 分支恒真、`postExecute()` 的场景刷新分支永不执行。这些代码不是「没写完」，而是「写完后被 provider 模式取代了」，但旧路径没清理。

**证据链**

1. `grep -rn "setContext" UI/2D/Src/Operation/ Main/Src/Composition/` → **0 结果**。
   对比 3D：`Main/Src/UI/Workbench/Workbench3D.cpp` 中有 `setContext(OperationContext3D)` 调用。
2. `UI/Common/Include/UI/Command/OperationBusBase.h:70` 的 `runImpl` 每次 dispatch 都调用 `m_context.refresh()`；2D 的 `OperationContext::refresh()` 是**空实现**。
3. `UI/2D/Src/Operation/CommandActionHubActions2D.cpp:586-610` 的 `captureSnapshot()`：先读 `m_bus->context()`（恒空），再被 `m_clipboardProvider` / `m_undoRedoProvider` 的结果覆盖。源码注释原文自认：**「OperationContext 在生产中为死代码」**。
4. `UI/2D/Src/Operation/OperationBus.cpp:58` 的 `postExecute`：`if (ctx.sceneManager) ctx.sceneManager->notifySceneChanged();` —— `ctx` 恒空 → 该分支**永不执行**。

**改造方案**（P1，先不碰签名）

| 步骤 | 动作 | 风险 |

| 1 | 删除 `captureSnapshot` 中对 `m_bus->context()` 的读取（保留 provider 覆盖部分） | 低 |

#### 3.2.4 收敛方案（P2，不合并代码）

**明确不做的事**：不把 2D 和 3D 的 `Operation`/`Bus`/`Catalog`/`Hub` 合并成模板实例化的单一类型。理由：

1. 类型名不同（`OperationId` vs `OperationId3D`）是**有意的 DLL 边界隔离**（`UI2DAPI` / `UI3DAPI` 分开导出）。
2. 3D 的 5,248 行里有大量 3D 专属逻辑（`TransformGizmo`、`Camera`、`BRep`、浮雕刀路），强行抽象只会引入空方法。

**建议做的事**：

| 步骤 | 动作 | 收益 |
|---|---|---|
| 1 | 把 `CommandUiSnapshot` 与 `CommandUiSnapshot3D` 的**共有字段**（canUndo/canRedo/hasSelection/selectionCount）抽到 `CommandUiSnapshotBase`，扩展字段留在派生结构 | 快照语义对齐，`refreshActionsFromSnapshot` 可共用更多代码 |

| 4 | 给 2D/3D 各自的 `Operation*` 类加「为什么不能合并」的说明注释 | 防止后来者再试图合并或再长出第三份 |

### 3.4 查表实现：线性扫描与字符串比较

**`CommandCatalogBase` 的两个查询都是线性扫描**（`UI/Common/Include/UI/Command/CommandCatalogBase.h`）：

```cpp
findByMenuId(menuId, commands)   // O(N)
findByOperation(opId, commands)  // O(N)
```

**2D `CommandCatalog.cpp` 的三段查找（最坏叠加）**

| 函数 | 内容 | 最坏比较次数 |
|---|---|---:|
| `operationForCommandId` | 125 条 static 表线性扫描 + 90 条目录线性扫描（比 `entry.shortcutId`） | 125 + 90 = 215 |
| `menuIdForCommandId` | 22 条 precise 表 + 90 条目录 → 调 `operationForCommandId`（215）→ 调 `findByOperation`（90） | 22 + 90 + 215 + 90 = **417** |

**3D `CommandCatalog3D.cpp` 的 `operationForCommandId`**：66 条目录线性扫描，且比较写法是

```cpp
QString::fromUtf8(entry.shortcutId) == cmdId   // 每条都构造一个 QString
```

→ **每次调用分配 0~66 个 QString**。而 `CommandActionHub3D::refreshFromSnapshot`（`CommandActionHub3D.cpp:80`）与 `retranslateActions` 每次快照刷新都会遍历 `CommandCatalog3D::commands()` → 每次刷新至少 66 次分配。

**改造方案（P1，收益最高的一处微优化）**

| 步骤 | 动作 |
|---|---|
| 1 | 2D/3D 各建一张 `QHash<commandId, index>` 与 `QHash<operationId, index>`，在 `kCommands` 静态初始化后一次性构建（`std::call_once` 或静态局部对象） |
| 2 | `operationForCommandId` / `menuIdForCommandId` / `findByOperation` / `findByMenuId` 全部改哈希查表；**删除 125 条 static 映射表与 22 条 precise 表**（它们的存在只是因为没有索引） |
| 3 | 3D 的比较改 `QLatin1String` 或 `QStringView`，消除 `fromUtf8` 分配 |
| 4 | 插件追加时重建哈希（配合 §3.1.6 的缓存改造） |

| 项 | 内容 |
|---|---|
| 影响面 | `CommandCatalog.cpp`、`CommandCatalog3D.cpp`、`CommandCatalogBase.h` |
| 验证 | 相关单测 + 菜单点击手测 + 单次刷新耗时对比（建议在 `refreshEditActionStates` 前后打点） |
| 风险 | **低**。纯查找结构替换，不改语义 |

### 3.6 渲染分层：`RenderAbstraction` 的价值与成本

**链路**

```
UI (RenderWidget / RenderViewport2D / RenderWidget3D)
  → IRenderScene / IRenderDevice              (RenderAbstraction, 797 行)
    → RenderXSceneAdapter / RenderXDeviceAdapter  (RenderBridge, 5484 行)
      → renderx C API (rxGeometryAlloc / rxGeometryWrite / rx*, POD + C ABI)
        → Renderx 后端 (16499 行, OpenGL)
```

**关键事实**：`IRenderScene` / `IRenderDevice` 全仓**只有 1 个实现**（`RenderXSceneAdapter` / `RenderXDeviceAdapter`）。测试也不自己实现它们，而是走 RenderX 的 null backend。

**评价**

- **不是死代码**：`RenderXDeviceAdapter.cpp`（647 行）被真实调用。
- **也不是纯冗余**：`RenderAbstraction` 797 行的价值是**头文件隔离**——UI 层不需要 include `rx*` 头，也不会在 ABI 上依赖 RenderX 的 POD 布局。
- **但它不是「可切换的多态层」**：`I` 前缀（`IRenderScene` / `IRenderDevice`）暗示可以替换后端，而事实是 RenderBridge 直接绑死 RenderX。这会误导后来者以为「换个 `IRenderScene` 实现就能换后端」，而实际上 RenderX 适配器 647 行转发 + `RenderSessionHost` 的生命周期管理都得跟着重写。

**改造方案（P2，主要是「说清楚」而非「改代码」）**

| 步骤 | 动作 |
|---|---|
| 1 | 在 `RenderAbstraction` 或 `IRenderScene.h` 顶部注释明确：**「本层是 ABI/头文件隔离层，不是可插拔后端抽象。当前唯一实现是 RenderBridge/RenderXAdapter。」** |
| 2 | 评估 `IRenderScene` / `IRenderDevice` 是否改名（如 `RenderSceneApi`），避免「接口可替换」的误导（可选，属命名治理） |
| 3 | **不建议删除**该层。UI 与 RenderX 的编译期解耦是真实的（Renderx 16,499 行不必参与 UI 编译单元）；删除会让 UI 直接依赖 C API 头 |

### 3.9 命名与类数量

§1.3 列出 138 个含 `Service/Manager/Registry/Bus/Dispatcher/Bridge/Hub/Coordinator/Center` 的类名。命名问题的实际危害：

1. **同一职责多种后缀**：「把 A 转给 B」在本仓库里可能是 `Dispatcher`（`MenuDispatcher`）、`Bridge`（`QtLayerManagerBridge`）、`Coordinator`（`SceneRefreshCoordinator`）、`Hub`（`CommandActionHub`）、`Adapter`（`RenderXDeviceAdapter`）。新人无法从名字判断哪个是「事件驱动的扇出」、哪个是「同步的参数转发」。
2. **`I` 前缀的含义不统一**：`IRenderScene` 是「唯一实现的 ABI 隔离层」（§3.6），`IUIServices` 是「迁移中的临时窄接口」，`IOperation` 是「真正的可扩展接口」。三者性质完全不同却用同一个前缀。

**改造方案（P2，渐进，不强行重命名）**

## 7. 边界与不做的事

**明确不做**

1. **不合并 2D/3D 命令系统的代码实现**（§3.2.4）。类型名不同是 DLL 边界隔离的有意设计；强行抽象会引入空方法。
2. **不删除 `UiStateCenter`**（§3.3.1）。253 处 token 引用，删除等于重写 UI 层。只做内部结构化。
3. **不删除 `RenderAbstraction`**（§3.6）。编译期/ABI 解耦是真实的。
4. **不做全仓类名重命名**（§3.9）。数千行 diff 会掩盖语义变更并破坏 `git blame`。
5. **不为了行数目标拆分职责单一的大文件**（§3.8）。
6. **不动 `SceneRefreshCoordinator`**（§3.5.4）。它是本仓库设计最好的一块。
7. **不在 P0/P1 中改 `IOperation` / `LambdaOperation` 的签名**。删 `OperationContext` 参数属于 P2 的架构决策。

**边界情况与需要人工确认的点**

| 点 | 为什么需要人工确认 |
|---|---|
| `IInteractionDispatcher` 的删除 | 所有方法 0 调用方，但它是 `Workbench2D/3D::initialize` 的**非空判据**。删除后需确认没有外部插件/脚本依赖这个符号（当前仓库内已核查无） |
| 2D `appendPluginCommands` 的删除 | 若未来计划给 2D 加命令插件，应改为「保留 API 但标注未接线」而非删除。**需要产品/架构决策** |
| `UiStateCenter` 分组 | 40+ 字段的分组边界会影响所有写入点，**建议先出分组草案评审再动手** |
| `SceneNotifier` 优先级 | 引入排序会改变现有（偶然的）触发顺序，**需要先确认当前顺序没有被隐式依赖** |
| 8 个 `*OperationRegistry` 声明式化 | 涉及 2,498 行样板（8 个 `.cpp` 2,067 行），**改造面大**，建议单独排期 |

**回滚策略总则**

- 每个 P0 commit 独立、可 `git revert`
- P1 的 5 个 commit 各自独立，**不做相互依赖的串联提交**
- P2 每项单独评估，不在一个批次里混做
