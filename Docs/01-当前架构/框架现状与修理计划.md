## 1. 当前状态

### 1.1 总判断
框架结构性重构已完成主要阶段，但当前文档与代码仍存在明显不同步，项目不应简单标记为“全部完成”或“纯维护期”。

## 2. 框架冗余排查清单

> 这一节只记录“值不值得动”的判断，后续开发按这里逐项收口。

### 2.1 组合根与操作分发

- **冗余点**：`OperationBus` + `OperationRegistry` + `LambdaOperation`，大量简单操作也要走完整分发链。
- **为什么冗余**：很多场景只是按钮点击后切换状态或调用单个服务，没有撤销/重做、事务编排或多阶段流程，却仍然经过统一命令体系。
- **是否建议保留**：**部分保留**。适合保留给真正需要命令语义的操作，不适合覆盖所有轻量切换。
- **如果优化，优先怎么改**：先把工具切换、部分视图开关、简单菜单动作从 `OperationBus` 中收回，改成 UI 直接调用对应控制器或服务；保留 `OperationBus` 给文件、编辑、撤销类重操作。

### 2.2 绘图与工具激活链路

- **冗余点**：工具栏 → `OperationBus` → `LambdaOperation` → `findActiveViewport2D()` → `ToolManager::setActiveTool()`。
- **为什么冗余**：工具激活本质是状态切换，但链路中夹了注册、分发、视口查找等多层中转。
- **是否建议保留**：**可压缩**。多视口查找可保留，分发中转可简化。
- **如果优化，优先怎么改**：工具栏直接持有轻量工具控制入口；视口查找保留在需要多窗口支持的场景；减少 `LambdaOperation` 包裹。

### 2.3 场景编辑与撤销封装

- **冗余点**：`SceneEditService` 再包一层 `UndoRedoManager`、`AddEntitiesCommand`、`SceneManager`。
- **为什么冗余**：如果某些绘图/导入动作并不需要撤销语义，这条链路会显得过重；每次提交都先走命令对象，会增加理解成本。
- **是否建议保留**：**条件保留**。只要产品明确需要撤销/重做，就应保留。
- **如果优化，优先怎么改**：将“需要撤销”的路径和“直接落场”的路径分开；保留统一入口，但内部区分命令提交和直接提交。
- **当前状态**：✅ 已完成。新增 `CommitMode` 枚举（`Undoable`/`Direct`），`addEntity`/`addEntities`/`addEntityFromPointer` 支持 `CommitMode` 参数；`ImportService` 导入走 `CommitMode::Direct` 直接提交。

### 2.4 通知与刷新链路

- **当前链路**：`SceneNotifier::notifySceneChanged()` → 遍历 `IObserver::onSceneChanged()` → `RenderViewport2D::onSceneChanged()` 收集脏图元 ID → `scheduleSceneUpdate()`（视口内节流定时器）→ `updateSceneRender()` 按 `RefreshLevel` 分发。
- **实际价值**：`SceneNotifier` 承担观察者生命周期管理和批量更新延迟通知（`beginBatch` / `endBatch`），`RenderViewport2D::scheduleSceneUpdate()` 承担节流合并。两层各有明确价值。
- **是否建议保留**：**建议保留**。
- **如果优化，优先怎么改**：不要直接删通知层，而是让它继续承担批量变更合并、延迟刷新和多视图同步职责；只清理重复触发和无效重绘。

### 2.5 渲染提交链路

- **当前状态**：增量渲染接口**已实现**。`RenderWidget` 已具备 `addRenderEntity()` / `modifyRenderEntity()` / `removeRenderEntity()` 三个增量 API；`RenderViewport2D` 已通过 `RefreshLevel::LightUpdate` 路径使用它们，配合 `m_pendingDirtyIds` / `m_pendingDeletedIds` / `m_renderedEntityIds` 实现增量提交。
- **剩余问题**：`submitSceneFromDataSource()` 全量路径仍在首次加载和强制重建时使用，~~`applyOverlayUpdate()` 单函数分支过多（162 行 / 10 分支）~~ **已拆分**，`submitDefaultSceneEnv()` 每帧重算场景环境。
- **是否建议保留**：**全量路径保留为初始化/重建入口，增量路径已为主路径**。
- **如果优化，优先怎么改**：~~拆分 `applyOverlayUpdate()` 按 overlay 类型独立处理~~ 已完成；引入环境缓存或脏标记减少 `submitDefaultSceneEnv()` 每帧重复计算。

### 2.6 导入导出与文件操作注册

- **冗余点**：`FileOperationRegistry`、`ImportDispatcher`、`ExportDispatcher`、多个格式映射函数和重复状态同步逻辑。
- **为什么冗余**：同一类流程里存在大量格式映射、对话框、服务调用、状态更新的重复模板。
- **是否建议保留**：**保留分发器，压缩重复模板**。
- **如果优化，优先怎么改**：统一抽出“选择文件 → 调用服务 → 处理结果 → 更新状态”的公共模板；格式映射保持集中管理，减少散落分支。

### 2.7 图层与持久化桥接

- **冗余点**：`LayerManager`、`QtLayerManagerBridge`、`LayerPersistenceBridge`、`LayerEditService` 之间存在多层桥接。
- **为什么冗余**：如果只是同步运行态图层、UI 显示和持久化状态，这些层会显得链路偏长。
- **是否建议保留**：**保留**。
- **如果优化，优先怎么改**：不要先砍桥接层，而是确认每层只做一件事：运行态管理、UI 同步、持久化同步、编辑命令，不要互相侵入。

### 2.8 旧路径与兼容层

- **冗余点**：主路径之外仍可能残留一些旧注册入口、旧适配器或可编译但不再推荐的调用方式。
- **为什么冗余**：它们通常不影响运行，但会让框架边界变模糊，增加后续维护成本。
- **是否建议保留**：**不建议长期保留**。
- **如果优化，优先怎么改**：按模块逐个清理旧入口；凡是主路径之外还在使用的并行实现，优先合并或删除。

  - **为什么冗余**：环境数据往往变化不频繁，但它仍被放在每帧路径中，容易形成重复计算。
  - **是否建议保留**：建议保留，但应尽可能缓存或按需重算。
  - **如果优化，优先怎么改**：引入环境缓存或脏标记，减少每帧重复组装；只有视图或环境变更时才重算。

- `loadScreenFont()` / `renderScreenTexts()`
  - **冗余点**：本质是对渲染层文本接口的薄封装。
  - **为什么冗余**：如果没有额外业务逻辑，它们更像适配入口而不是独立能力。
  - **是否建议保留**：建议保留。
  - **如果优化，优先怎么改**：保持轻量封装即可，不要再向外扩展额外语义。

#### `RenderWidget` 的综合判断

- 这个模块当前的主要问题不是“有无功能”，而是**全量提交路径过重、overlay 入口分支过多、清理函数重复**。
- 它是当前最典型的“性能冗余”集中区。
- 优先级上应高于一般结构整理，因为它直接影响高频交互体验。

### 3.14 `FileOperationRegistry` 与文件操作模板

> 这一节把文件打开、保存、导入、导出这条链路按函数级拆开。它和工具注册一样，属于"统一入口太多、模板重复太明显"的模块，但相比工具链，它保留的理由更充分一些，因为文件操作天然需要对话框、格式映射、状态同步和持久化。
