## 1. 框架

---

### 1.1 FileIO → Engine2D/Engine3D 依赖倒置

#### 问题描述

`FileIO.dll` 链接了 `Engine2D.dll` 和 `Engine3D.dll`。原因是 FileIO 的各个 Parser（DxfParser、SvgParser、PltParser、StepParser 等）在解析文件时**直接实例化 `Eg::SyEntity`、`Eg::SyLine`、`Eg::SyCircle`、`Eg::SyArc` 等引擎类型**。

文件解析是低层实用模块，理论上只该关心"字节流 → 几何数据"，但它却知道"场景对象模型"的细节。这不仅产生了不必要的 DLL 依赖，还使得 FileIO 无法在没有 Engine2D 的项目中复用。

**涉及的数据范围**：
- 所有 2D 图元类型（Line、Arc、Circle、Ellipse、Bezier、NURBS、Text、Image 等）
- 所有 3D 网格类型
- 图层信息（LayerInfo：id、name、color、visible、locked、customProperties）
- 图元-图层映射关系（每个图元通过 layerId 指向所属图层）
- **群组嵌套关系**（群组可包含子群组，通过 subGroupIds 形成树形结构）
- 文档元信息（DocumentMetadata：author、version、timestamps 等）
- 硬件信息（HardwareInfo：laserType、workArea 等）
- 图元属性（name、visible、locked、lineWidth、closed、ccw）

#### 代码体现

```cmake
# FileIO/FileIO/CMakeLists.txt:128-129
target_link_libraries(FileIO
    PRIVATE
        Engine2D    # ← 问题：文件解析器链接了 2D 引擎
        Engine3D    # ← 问题：文件解析器链接了 3D 引擎
)
```

公共 API 的类型别名暴露了耦合：

```cpp
// FileIO/FileIO/Include/FileIO/FileFormat.h
using VecSyEntityPtr = std::vector<std::unique_ptr<Eg::SyEntity>>;
//                                           ^^^^^^^^^^
//                          FileIO 的公共 API 直接使用 Engine 类型
```

Parser 内部直接 new 引擎对象：

```cpp
// FileIO/FileIO/Src/Parsers/DxfParser.cpp
#include "Engine2D/SyEntity/SyLine.h"    // ← 直接包含引擎头文件
#include "Engine2D/SyEntity/SyArc.h"

Eg::SyLine* line = new Eg::SyLine();      // ← 直接实例化引擎对象
line->vPoints = {startPt, endPt};
line->pLayer = someLayer;                 // ← 直接操作引擎的图层指针
```

#### 改造方案

**核心思路**：FileIO 只产生纯几何数据（POD structs），Engine2D 提供转换器将这些数据转换为场景实体。Parser 的职责止于"从字节流到几何数据"，不延伸到"从几何数据到场景对象"。

**第一步**：在 FileIO 中定义纯数据结构（`ParsedGeometry.h`）

关于 ID 的处理策略：
- FileIO 的 Parser 不负责生成图元最终 ID
- `ParsedGeometry.sourceId` 记录源文件中的原始 ID（用于实体-图层映射引用），**不是最终场景 ID**
- 最终 ID 由转换器（GeometryConverter）在添加到 SceneManager 时通过 `EntityIdGenerator` 分配
- 图层和群组的 ID 同理，使用 `sourceId` 追踪源文件中的引用关系，转换到 Engine 时重新分配

关于颜色的处理策略：
- 图元没有覆盖色，颜色完全由所属图层决定
- 如果图元没有明确的 layerId，使用默认图层
- 转换器在建立图元-图层映射后，Engine 层的 `getColor()` 通过图层颜色计算

```cpp
// ★ 新增 FileIO/Include/FileIO/ParsedGeometry.h
// 纯 POD 数据，不依赖任何 Engine 类型，不含虚函数，不含指针

namespace Fio {

// ===================== 基础类型 =====================

struct ParsedPoint2D { double x = 0, y = 0; };
struct ParsedPoint3D { double x = 0, y = 0, z = 0; };
using ParsedPropertyMap = std::map<std::string, std::string>;

// ===================== 图元类型枚举 =====================
```

**设计要点说明**：

| 设计决策 | 说明 |
|----------|------|
| **`sourceId` 而非 `id`** | FileIO 不负责分配最终 ID。`sourceId` 仅用于：
  1) 图元到图层的引用（`layerSourceId`）
  2) 群组到成员图元的引用（`entitySourceIds`）
  3) 群组到子群组的引用（`subGroupSourceIds`）
  最终 ID 在转换阶段由 `EntityIdGenerator` 分配，避免与现有场景 ID 冲突 |
| **无覆盖色** | 颜色完全由图层决定。`everrideColor` 字段不存在。图元 `getColor()` 通过 `pLayer->color` 计算 |
| **群组嵌套** | `subGroupSourceIds` + `parentGroupSourceId` 支持任意深度的群组树 |
| **图层属性完整性** | `visible`/`locked`/`color`/`customProperties` 与现有 `LayerInfo` 一致 |
| **`SmartLineData` 递归** | `SySmartLine` 是子实体容器，使用 `vector<ParsedGeometry>` 自然表达嵌套 |

```cpp
    ParseData data;
};

Fio::FileImporter::FileImporter() : pImpl(new Impl()) {}

bool Fio::FileImporter::Open(const char* path)
{
    auto parser = ParserRegistry::instance().createParser(path);
    if (!parser) return false;
    pImpl->data = parser->parse(path);
    return pImpl->data.success;
}

int Fio::FileImporter::LayerCount() const
{
    return static_cast<int>(pImpl->data.layers.size());
}

bool Fio::FileImporter::GetLayer(int index, LayerInfo* out) const
{
    if (!out || index < 0 || index >= LayerCount()) return false;
    const auto& src = pImpl->data.layers[index];
    out->sourceId = src.sourceId;
    std::strncpy(out->name, src.name.c_str(), sizeof(out->name) - 1);
    out->color   = src.color;
    out->visible = src.visible;
    out->locked  = src.locked;
    return true;
}

bool Fio::FileImporter::GetEntity(int index, EntityInfo* out) const
{
    if (!out || index < 0 || index >= EntityCount()) return false;
    const auto& src = pImpl->data.geometries[index];
    out->sourceId = src.sourceId;
    out->type     = static_cast<EntityType>(src.type);
    std::strncpy(out->name, src.name.c_str(), sizeof(out->name) - 1);
    out->layerSourceId = src.layerSourceId;
    out->lineWidth = src.lineWidth;
    out->visible   = src.visible;
    out->locked    = src.locked;
    // 按 type 拷贝几何参数（示例）
    if (src.type == ParsedGeometryType::Line) {
        out->type = EntityType::Line;
        out->line = { src.line.start.x, src.line.start.y,
                      src.line.end.x,   src.line.end.y };
    }
    // ... 其他类型略 ...
    return true;
}

Fio::BinaryBlob Fio::FileImporter::ExportBlob() const
{
    BlobWriter writer;
    writer.writeLayers(pImpl->data.layers);
    writer.writeGeometries(pImpl->data.geometries);
    writer.writeGroups(pImpl->data.groups);
    return writer.release();
```

#### DLL ABI 注意事项（更新）

由于采用 PIMPL 将 `std::vector`/`std::string` 封在 FileIO.dll 内部，跨 DLL 边界只传递 POD 类型：

| 注意事项 | 说明 |
|----------|------|
| **编译器一致性** | 同一编译器下完全安全；即使不一致，POD 接口（`BinaryBlob`、`EntityInfo`、`LayerInfo`）也能正常工作 |
| **CRT 一致性** | 不再需要，POD 类型不依赖任何 CRT 内部布局 |
| **容器导出** | `ParsedGeometry.h` 降级为内部头文件，不再需要 `FILEIO_API` 导出宏 |
| **谁分配谁释放** | `BinaryBlob` 由 `FileImporter::ExportBlob()` 在 FileIO.dll 中分配，通过 `FreeBlob()` 释放；Engine2D 只读不写 |
| **PIMPL 析构** | `FileImporter::~FileImporter()` 在 `.cpp` 中实现，`delete pImpl` 在 FileIO.dll 内完成 |
| **跨编译器未来** | 如需支持不同编译器，只需在现有 PIMPL 层上加一层 C ABI 函数包装，无需改动内部逻辑 |

#### 相比之前的提升与优势

| 维度 | 改造前 | 改造后 | 优势说明 |
|------|--------|--------|----------|
| **DLL 依赖** | FileIO 链接 Engine2D.dll + Engine3D.dll | FileIO 是独立 DLL，零 Engine 依赖 | ✅ FileIO 可独立发布和测试 |

| **复用场景** | 只能在有 Engine2D 的项目中使用 | CLI 工具、Web 后端、移动端均可直接用 FileIO | ✅ 打开了新的复用可能 |

### 1.2 ImportService/ExportService → UiStateCenter 反向依赖

#### 问题描述

`ImportService.cpp` 和 `ExportService.cpp` 在 `Main/Src/Import/` 和 `Main/Src/Export/` 目录中，通过 `#include "../UI/Services/UiStateCenter.h"` 向上依赖 UI 模块。这意味着 Import/Export 模块知道了 UI 层的具体类型，违反了"高层模块依赖低层抽象"的原则。

#### 代码体现

```cpp
// Main/Src/Import/ImportService.cpp: 使用 ../ 向上引用
#include "../UI/Services/UiStateCenter.h"  // ← 反向依赖

ImportService::setStateCenter(UiStateCenter* stateCenter) { ... }
```

```cpp
// Main/Src/Export/ExportService.cpp
#include "../UI/Services/UiStateCenter.h"  // ← 反向依赖
```

整个 `Main/Src/Import/` 和 `Main/Src/Export/` 目录通过 `../UI/` 跨目录引用，没有任何模块边界约束。

#### 改造方案

**方案：使用回调/信号解耦，ImportService 不再持有任何 UI 类型的指针**

```cpp
// ★ 改造前:
class ImportService {
    UiStateCenter* m_stateCenter;        // ← 直接依赖 UI 具体类型
    // ...
};

// ★ 改造后: 通过回调告知上层，ImportService 不再知道 UI 类型
class ImportService {
    // 文档脏状态回调
    std::function<void(bool dirty)> m_dirtyStateCallback;
    // 状态栏消息回调
    std::function<void(const std::string& message)> m_statusCallback;
    // 进度回调
    std::function<void(float percent, const std::string& stage)> m_progressCallback;
};
```

在 `ApplicationCompositionRoot` 或 `WorkbenchWindow` 中组装时注入：

```cpp
// 组装时（在 CompositionRoot 中完成，ImportService 自己不需要知道 UiStateCenter）
importService->setDirtyStateCallback(
    [stateCenter](bool dirty) { stateCenter->setDocumentDirty(dirty); });
importService->setStatusCallback(
    [statusBar](const std::string& msg) { statusBar->showMessage(QString::fromStdString(msg)); });
```

#### 相比之前的提升与优势

| 维度 | 改造前 | 改造后 | 优势 |
|------|--------|--------|------|
| **依赖方向** | Import → UI（向上依赖） | 回调注入（依赖反转） | ✅ 符合 DIP 原则 |
| **可测试性** | 必须构造 UiStateCenter 才能测试 ImportService | 注入 lambda，可轻松 mock | ✅ 单元测试更简单 |

## 7. DLL ABI 注意事项

> 本文档涉及大量跨 DLL 的数据传递。以下是必须遵守的 ABI 规则。

### 7.1 编译器与 CRT 一致性

```
规则：所有 DLL + EXE 必须使用同一编译器和同一 CRT
- 编译器版本必须完全一致（如全部 MSVC 2022 17.x）
- CRT 链接方式必须一致（全部 /MD 或全部 /MDd）
- 禁止混用：/MD + /MT、Debug + Release
```

### 7.2 DLL 导出宏

每个 DLL 需要自己的导出宏，在头文件中正确标注：

```cpp
// FileIO/Include/FileIO/FileIOAPI.h
#ifdef FILEIO_EXPORTS
#define FILEIO_API __declspec(dllexport)
#else
#define FILEIO_API __declspec(dllimport)
#endif
```

所有跨 DLL 的类和函数必须标注：

```cpp
class FILEIO_API FileImporter { ... };   // 跨 DLL 边界的 PIMPL 类
struct FILEIO_API EntityInfo { ... };    // 跨 DLL 边界的 POD struct
struct FILEIO_API BinaryBlob { ... };    // 跨 DLL 边界的 POD struct
```

### 7.3 STL 容器跨 DLL 边界规则

```
规则：禁止 std::vector / std::string 出现在跨 DLL 的 public 接口中
- 容器仅在 DLL 内部使用（通过 PIMPL 隐藏）
- 跨 DLL 边界只传递 POD 类型（BinaryBlob、EntityInfo、LayerInfo）
- 如必须传递容器数据，使用 BinaryBlob 序列化/反序列化
```

PIMPL 方案彻底消除了 STL 容器跨 DLL 的风险：

```cpp
struct FILEIO_API BinaryBlob {
    // ✅ POD 类型，不含 std::vector / std::string
    uint8_t* data = nullptr;
    size_t   size = 0;
};

class FILEIO_API FileImporter {
    // ✅ public 方法只使用 POD 参数和返回值
    int  EntityCount() const;
    bool GetEntity(int index, EntityInfo* out) const;
    BinaryBlob ExportBlob() const;
};
```

⚠️ 如果未来引入新的跨 DLL 类型，仍需遵守"同一编译器 + 同一 CRT"的前提。

### 7.4 谁分配谁释放

```
规则：内存分配和释放必须在同一模块中

FileIO.dll 分配的内存：
  - FileImporter::ExportBlob() 返回 BinaryBlob
  - 通过 FileImporter::FreeBlob() 在 FileIO.dll 中释放
  - Engine2D/UI 层使用 BinaryBlob 后调用 FreeBlob()

Engine2D.dll 分配的内存：
  - GeometryConverter::toEntity() 返回 unique_ptr<SyEntity>
  - SyEntity 的析构在 Engine2D.dll 中完成
  - UI 层使用后析构它

禁止：FileIO 分配的内存由 Engine2D 释放（或反之）
```

### 7.5 接口与虚函数表

```cpp
// ✅ PIMPL 类跨 DLL 安全（前提：同一编译器）
class FILEIO_API FileImporter {
public:
    FileImporter();               // 构造在 FileIO.dll
    ~FileImporter();              // 析构在 FileIO.dll（delete pImpl）
    // ... 全部 POD 接口 ...
};

// ⚠️ 警告：不要在 DLL 之间传递 std::unique_ptr 作为函数参数
// 因为 unique_ptr 的 deleter 跨 DLL 边界可能调用不同的 delete
// 解决方案：传递裸指针 + 明确说明所有权
```

### 7.6 版本号兼容性

每个 DLL 有独立版本号（在 CMake 中设置），用于标识 ABI 兼容性：

```cmake
add_library(FileIO SHARED ...)
set_target_properties(FileIO PROPERTIES
    VERSION 1.2.0           # FileIO 自己的版本号
    SOVERSION 1)
```

### 7.7 跨 DLL 异常安全

```
规则：禁止跨 DLL 边界抛异常
- C++ 异常跨 DLL 可能因编译器/CRT 不一致而崩溃
- 所有跨 DLL 接口应返回错误码或错误结构体
- ParseData.success + errorMessage 模式正确
```

### 7.8 跨编译器方案（暂缓）

当前所有 DLL 使用同一编译器编译，暂不处理跨编译器场景。

未来如需支持不同编译器编译的 DLL 协同工作，可按以下思路实施：

1. **BinaryBlob 已是 ABI 中立**：当前 `BinaryBlob {uint8_t*, size_t}` 和 `EntityInfo`/`LayerInfo`（纯 POD struct）可跨不同编译器安全传递，无需修改
2. **C ABI 函数导出**：将 `FileImporter` 的核心方法以 `extern "C"` 形式导出：
   ```cpp
   extern "C" {
       FILEIO_API Fio::FileImporter* Fio_CreateImporter();
       FILEIO_API void               Fio_DestroyImporter(Fio::FileImporter*);
       FILEIO_API bool               Fio_Open(Fio::FileImporter*, const char* path);
       FILEIO_API Fio::BinaryBlob    Fio_ExportBlob(Fio::FileImporter*);
       FILEIO_API void               Fio_FreeBlob(Fio::BinaryBlob*);
   }
   ```
3. **PIMPL → C ABI 转换成本低**：已有 PIMPL 层，只需加一层 C 函数包装即可，无需改动内部逻辑

**优先级：暂缓**（等出现多编译器需求时再实施）
