# 架构决策文档：UI、算法、渲染解耦与客户化定制方案

> **目标**：在保持现有可运行框架稳定的前提下，逐步把 UI、算法、渲染、持久化的边界拆清，形成适合后续软件定制的架构。
>
> **核心原则**：
> 1. 算法内核稳定，不直接依赖 UI。
> 2. 渲染层只消费数据契约，不直接理解业务实体。
> 3. UI 负责编排和表达，不承载核心算法语义。
> 4. 客户化优先通过配置和插件实现，尽量不改核心代码。

---

## 1. 现状结论

当前框架不是“失控耦合”，但已经明显进入了**需要做边界收口**的阶段。

从现有代码看，已经具备一些好的方向，例如：

- `Engine/Common/Include/Engine/Scene/SceneRenderContract.h` 提供了场景数据契约
- `WorkbenchStateSnapshot` 已经把工作台状态从 UI 控件中抽离出来
- `SelectionService`、`SceneDocument2D` 已经开始承担适配器职责
- `RenderX` 与引擎本身没有直接互相侵入，这一点是好的

但同时也存在几个明显的耦合热点：

- `Main/Src/UI/Render/EntityToVertices.cpp` 直接依赖大量 `SyEntity` 具体类型
- `Main/Src/UI/Workbench/UiWorkbench.cpp` 仍然负责较多 UI 装配和状态恢复细节
- `Main/Src/UI/Services/UiServices.h` 暴露了太多具体服务类型
- `Main/Src/UI/Documents/SceneDocument2D.h` 仍然暴露底层 `SceneManager`

结论是：

> **建议做低耦合拆分重构，但必须是渐进式。不要推翻重写。**

## 2. 现状耦合评级

### 2.1 总体评级

| 领域 | 当前耦合度 | 说明 |
|------|------------|------|
| UI ↔ Engine 实体类型 | 高 | UI 直接包含 `SyLine`、`SyCircle` 等具体类型 |
| UI ↔ Engine 场景/编辑服务 | 高 | 工作台、文档、选择、编辑链路直接绑定 `SceneManager` / `SceneEditService` |
| UI ↔ 渲染转换 | 高 | `EntityToVertices` 直接承担实体识别和渲染数据转换 |
| Engine ↔ Render | 中 | 已有契约思路，但部分地方仍混入转换逻辑 |
| UI ↔ Qt | 中到高 | Qt 绑定不可避免，但不应让 Qt 负责业务语义 |
| 持久化 ↔ UI | 中 | 持久化服务已经被 UI 包装，但还未完全抽象到配置/仓储层 |

### 2.2 关键耦合点

#### A. UI 直接依赖引擎具体实体

典型位置：

- `Main/Src/UI/Render/EntityToVertices.cpp`
- `Main/Src/UI/Render/EntityToVertices.h`
- `Main/Src/UI/Workbench/UiWorkbench.cpp`
- 各类属性面板、工具、选择逻辑相关代码

问题：

- 新增或修改实体类型时，UI 代码要跟着改
- UI 无法独立于引擎实体类型演进
- 后续做客户化定制时，UI 层改动会非常频繁

#### B. 工作台承担了过多职责

典型位置：

- `Main/Src/UI/Workbench/UiWorkbench.cpp`
- `Main/Src/UI/Workbench/WorkbenchWindow.cpp`

问题：

- 既负责生命周期，又负责 UI 组装，还负责状态恢复
- 未来如果要替换 UI 布局或多个客户化工作台，会变得难以维护

#### C. UI 服务集合暴露过多具体类

典型位置：

- `Main/Src/UI/Services/UiServices.h`

问题：

- 上层过于了解底层实现
- 很多服务是"临时装配件"，但被做成了稳定依赖
- 不利于插件化和模块替换

#### D. 场景文档仍然暴露底层场景对象

典型位置：

- `Main/Src/UI/Documents/SceneDocument2D.h`

问题：

- `sceneManager()` 这类接口让 UI 继续向引擎内部穿透
- 适配层没有完全变成“外观接口”

#### E. 渲染转换层过于了解实体细节

典型位置：

- `Main/Src/UI/Render/EntityToVertices.cpp`

问题：

- 渲染层直接认识实体类型
- 将来若换渲染后端，或者改几何数据组织方式，影响面很大

## 3. 可定制 / 不可定制清单

这部分是后续做客户化最重要的边界定义。

### 3.1 适合客户定制的部分

这些部分应该尽量做到**配置化**或**插件化**，最好不需要改核心代码。

#### 3.1.1 可配置

- 界面布局
  - 菜单栏显示/隐藏
  - 工具栏位置
  - 停靠面板布局
  - 状态栏显示内容
  - 默认工作台
- 主题和外观
  - 深色/浅色主题
  - 图标包
  - 字体大小
  - 控件样式
- 快捷键
  - 命令映射
  - 用户自定义快捷键
- 视口辅助
  - 网格
  - 标尺
  - 捕捉提示
  - 坐标显示样式

#### 3.1.2 可插件扩展

- 自定义菜单和工具栏项
- 自定义属性面板
- 自定义工作台模块
- 自定义导入/导出适配器
- 自定义视口叠加层
- 自定义命令集

### 3.2 应保持稳定、不建议客户直接改的部分

这些属于框架核心，不建议开放成“客户随意改源码”的区域。

- 实体 ID 规则
- 选择语义
- 事务/撤销/重做语义
- 场景通知机制
- 几何缓存策略
- 渲染契约
- 持久化数据库 schema
- 日志、崩溃处理、许可系统

### 3.3 只允许有限扩展的部分

这些可以扩展，但应通过注册、适配器或接口实现，不建议让客户改核心逻辑。

- 算法参数面板
- 命令注册
- 选择服务包装
- 场景编辑入口
- 导入导出类型支持

## 4. 推荐架构方向

### 4.1 分层目标

建议将系统划分为四类角色：

1. **稳定内核**
   - Engine2D / Engine3D
   - 核心场景、实体、算法、撤销、持久化

2. **渲染桥接层**
   - 将场景数据转换为渲染数据
   - 只依赖契约，不认识业务细节

3. **UI 编排层**
   - 工作台、窗口、菜单、工具栏、面板
   - 负责装配和呈现，不承载业务语义

4. **客户定制层**
   - JSON 配置
   - 插件 DLL
   - 主题包
   - 定制工作台

### 4.2 推荐的边界原则

#### 原则 1：UI 不直接创建/理解具体实体

UI 应通过工厂或场景上下文操作实体，而不是直接 `new SyLine()` 或 `dynamic_cast<SyLine*>`。

#### 原则 2：渲染只看数据契约

渲染层应消费 `ISceneDataSource` / `ISceneGeometrySink` 这类接口，不直接依赖实体类型。

#### 原则 3：工作台只做生命周期和装配

工作台负责：

- 初始化
- attach / activate / deactivate / shutdown
- 组织菜单和面板

不负责：

- 实体创建细节
- 几何语义
- 算法参数结构

#### 原则 4：客户化优先配置，次选插件

优先顺序建议是：

1. JSON 配置
2. 主题包
3. 插件模块
4. 最后才是源码级改造

## 5. 推荐重构路线图

### 步骤 1：冻结边界，先不改行为

目标：先明确哪些接口是稳定边界。

要做的事：

- 固化工作台生命周期语义
- 固化场景数据契约
- 固化渲染输入输出契约
- 明确 UI 配置和插件入口

产出：

- 一版稳定的架构边界文档
- 一组最小可用接口清单

### 步骤 2：先切最痛的耦合点

目标：先处理最影响后续定制的地方。

优先改动：

- `EntityToVertices` — 已有增量路径（`IncrementalVertexSink`），旧全量路径 `DisplayCache`/`DisplayMeshBuilder` 已删除
- 属性面板中的实体类型依赖
- `UiServices` 对具体服务的暴露 — **仍未解除**（2026-08-27 复核纠正）：`IUiServices` 只有 3 个 getter；`UiServices.h` 的 20 个成员里只有 4 个是接口指针（`IInteractionDispatcher`/`IUndoRedoManager`/`ISelectionService`/`IRecentFileService`），其余 16 个仍是具体类型。此前"新增 14 个服务接口、成员变量改为接口指针"的说法不成立 —— 那 14 个头文件里 13 个零实现者、零引用、也从未进构建，已于 2026-08-27 物理删除，只留下真被实现的 `IRecentFileService`。要继续推进就得逐个"先实现、再换类型"，不要再只建接口头文件
- `SceneDocument2D` 对底层场景对象的直接暴露 — 已添加元数据覆盖，`editService()` 仍待进一步收窄
- `OperationBus` 2D 全局单例 — 已删除 `instance()`/`setActiveInstance()`，14 处调用点迁移为构造注入
- 左侧绘图面板对总线的依赖 — 已解除（2026-08-26）：`DrawToolBarWidget` 重写为纯展示层，只接受一批 `QAction`（`setToolActions()`），按钮用 `setDefaultAction()` 挂 `CommandActionHub` 托管的工具动作。它不再持有 `OperationBus`、不再自己用 `CommandCatalog::operationForToolName` 解析命令，也不再维护 `DrawToolEntry` 与 activeTool 状态；派发与勾选态都由中枢单点负责
- 14 个 UI/引擎层单例（`EntityIdGenerator`/`FontManager`/`FormatRegistry`/`ServiceLocator3D`/`EntityEditorFactory`/`AlgorithmTaskUiHost2D/3D`/`ReliefEngravingService3D`/`TextInputSettingsStore`/`UiInteractionGate`/`LanguageManager`/`ThemeManager`/`SystemThemeDetector`/`CommandPluginRegistry`）已消除，改为构造注入

### 步骤 3：把界面配置化

目标：客户能通过配置调整界面。

优先项：

- 菜单栏显隐
- 工具栏布局
- 停靠面板布局
- 状态栏展示
- 默认工作台
- 主题包

### 步骤 4：引入插件扩展点

目标：客户可以不改核心代码，添加 UI 组件。

优先项：

- 菜单/工具栏插件
- 属性面板插件
- 自定义工作台插件
- 自定义视口叠加层

### 步骤 5：进一步收口核心依赖

目标：把更多具体类型替换为抽象接口。

优先项：

- 场景上下文接口
- 实体工厂接口
- 对话框工厂接口
- 主题管理接口

## 6. 第一阶段落地任务列表

以下任务适合直接进入项目执行。

### 6.1 任务 1：定义稳定边界接口

**目标**：先把 UI / Engine / Render 三层的边界固定下来。

建议接口：

- `ISceneDataSource`
- `ISceneGeometrySink`
- `IEntityFactory`
- `ISceneContext`
- `ILayoutConfig`
- `IUiModule`
- `IMenuBuilder`
- `IToolbarBuilder`
- `IPropertyProvider`

### 6.2 任务 2：拆 `EntityToVertices`

**目标**：让渲染转换层不再直接认识大量具体实体类型。

策略：

- 先抽象几何读取接口
- 再把实体到顶点的转换逻辑挪到适配器里
- 让 UI 只看到统一数据结构

### 6.3 任务 3：收口 `UiServices`

**目标**：减少 UI 对具体服务的直接依赖。

策略：

- UI 层只保留必须的服务句柄
- 其余通过接口或上下文对象传递
- 尽量不要让 UI 直接知道引擎内部实现类

### 6.4 任务 4：让工作台只负责装配

**目标**：削减 `Workbench2D` / `Workbench3D` 的业务职责。

策略：

- 工作台只负责任务装配和生命周期
- 把实体创建、属性组织、菜单构建拆到独立组件

### 6.5 任务 5：落地布局配置

**目标**：先做到“能改 UI 布局而不改代码”。

策略：

- 用 JSON 描述菜单/工具栏/面板/状态栏布局
- 主窗口按配置构建界面
- 将默认布局和客户布局分离

### 6.6 任务 6：保留旧路径，逐步切换

**目标**：重构期间不影响现有功能。

策略：

- 新旧路径并存
- 通过开关或适配器切换
- 每次只迁移一个点，迁完立即验证

## 8. 项目执行模板

这一节把前面的路线图进一步展开成可执行的项目条目，方便直接排期和分工。

### 7.1 任务拆分

#### 任务 A：定义边界接口

**内容**：

- 补齐 `ISceneDataSource`、`ISceneGeometrySink`
- 定义 `IEntityFactory`、`ISceneContext`
- 定义 `ILayoutConfig`、`IUiModule`
- 定义 `IMenuBuilder`、`IToolbarBuilder`、`IPropertyProvider`

**拆分建议**：

1. 先确定接口边界和最小方法集
2. 再定义数据结构与返回值
3. 最后在现有代码中增加适配器实现

#### 任务 B：拆 `EntityToVertices`

**内容**：

- 把实体识别和几何提取逻辑从 UI 渲染转换层拆出去
- 让转换层只依赖几何契约

**拆分建议**：

1. 抽象几何查询接口
2. 新增适配器
3. 逐步替换直接 `SyEntity` 访问

#### 任务 C：收口 `UiServices`

**内容**：

- 减少 UI 对具体服务类型的直接依赖
- 让服务以接口或上下文形式传递

**拆分建议**：

1. 识别必须保留的服务
2. 将非核心服务改为接口或轻量句柄
3. 逐步清理 UI 对底层实现的直接引用

#### 任务 D：工作台装配去业务化

**内容**：

- 让工作台专注生命周期和界面装配
- 把菜单、工具栏、属性面板、命令注册拆出去

**拆分建议**：

1. 先分离 UI 装配和业务状态恢复
2. 再分离命令/工具栏构建
3. 最后收口工作台中的直连服务

#### 任务 E：布局配置化

**内容**：

- 用 JSON 或类似配置描述菜单、工具栏、面板、状态栏
- 支持不同客户不同布局

**拆分建议**：

1. 先做读取和解析
2. 再做最小布局恢复
3. 再扩展到工具栏和停靠面板

**当前落地状态**（2026-08-25 起：配置驱动为唯一路径，客户 ID 运行时化）：

1. **读取与解析** — `Main/Src/UI/ClientConfig/UiConfigLoader.cpp`：JSON 加载 + `extends` 继承合并 + 字段校验 → `UiConfigData`。
2. **最小布局恢复** — `UiConfigurationManager::shared()` 持有进程级唯一客户配置（`UiConfigData` + `UiPanelRegistry`）；`UiLayoutBuilder` 将数据驱动为 Qt 控件。
3. **全面配置化** — `WorkbenchLayoutManager` 用 `UiLayoutBuilder` + `UiPanelRegistry` 构建
   Dock / 工具栏 / 状态栏；`Workbench2D/3D::buildConfiguredContextMenu()` 构建右键菜单。

### 7.3 风险点

#### 风险 1：接口过早过多，导致设计膨胀

**表现**：接口太多、层级太深，最后维护成本反而变高。

**应对**：

- 先做最小接口集
- 先解决最痛的耦合点
- 不要一口气把所有功能都抽成接口

#### 风险 2：Qt 生命周期和插件生命周期冲突

**表现**：对象归属不清，出现悬空指针、重复释放、MOC 相关问题。

**应对**：

- 先在主程序内完成插件化验证
- 明确 QObject 所有权
- 尽量把插件边界控制在纯虚接口和工厂上

#### 风险 3：改造期间回归风险高

**表现**：迁移过程中 UI、选择、渲染、撤销任一条链路都可能出问题。

**应对**：

- 采用“新旧并存”策略
- 每次只迁移一个点
- 每次迁移后立即回归测试

#### 风险 4：渲染/几何契约设计不稳

**表现**：契约一旦设计太粗或太细，后面不好改。

**应对**：

- 优先围绕当前实体和现有渲染输出设计
- 保证接口足够稳定，但不要过度泛化

#### 风险 5：客户化需求不断扩张

**表现**：客户要求从“改布局”扩展到“改业务逻辑”。

**应对**：

- 事先明确可定制边界
- 把核心语义写进“不可定制”清单
- 插件只允许扩展点，不允许侵入核心语义

## 8. 当前代码中的可取之处

下面这些做法建议保留并继续扩展：

### 8.1 `SceneRenderContract` 思路是对的

这是目前最接近“真正解耦”的部分之一。它说明数据源和渲染 sink 是可以分开的。

### 8.2 `WorkbenchStateSnapshot` 的方向正确

工作台状态和 UI 控件分离，这是 UI 可恢复、可切换、可定制的基础。

### 8.3 `SelectionService` 是一个合理的过渡层

虽然还绑定 `SceneManager`，但它已经把选择能力从 UI 控件中抽离出来了，适合作为后续接口化的过渡点。

### 8.4 `SceneDocument2D` 适合作为适配器继续演进

它现在还不是完全抽象，但方向是对的。后续只要继续收口底层暴露，就可以成为稳定边界。

---

## 9. 需要警惕的做法

### 8.1 不要一次性大拆大建

如果把所有接口、插件、布局系统一次性都做完，风险会很高：

- 编译链复杂
- ABI 复杂
- Qt 生命周期复杂
- 回归成本高

### 8.2 不要把所有东西都做成插件

插件应该用于扩展，不应该替代核心框架。核心语义一旦过度插件化，框架会难以维护。

### 8.3 不要把 `Main` 当成架构层

`Main` 是应用壳，不适合承载长期演进的架构边界。真正的边界应该在 `EngineCommon`、`UICommon`、`Engine2D/3D`、`RenderX` 之间建立。

---

## 10. 最终建议

### 如果目标是“内部稳定开发”
可以先维持现状，但要尽快做边界收口。

### 如果目标是“后续给客户做软件定制”
必须做低耦合重构，而且要优先做：

1. UI 布局配置化
2. 渲染契约分离
3. 实体/场景接口化
4. 插件扩展点

### 推荐结论

> **保持现有核心功能不动，但从 UI 边界、渲染边界、工作台边界开始做渐进式重构。**
>
> 这样既不会破坏当前工程稳定性，又能逐步把系统推进到适合客户定制的形态。
