# 菜单功能完善计划

> **目标**：让 2D / 3D 的菜单成为“所有功能的入口集合”，并保证菜单分类清晰、图标统一、点击有日志、命令来源单一、后续便于客户化定制。
>
> **原则**：
> 1. 菜单不是少量功能入口，而是功能目录。
> 2. 菜单内容必须来源于统一命令目录，不允许各处硬编码分裂。
> 3. 菜单结构必须按业务语义归类，不混杂、不重复、不歧义。
> 4. 有图标的命令必须尽量在菜单中展示图标。
> 5. 菜单点击必须统一记录日志，便于调试和审计。

---

## 1. 现状问题

根据现有代码和命令目录的情况，当前菜单体系主要有以下问题：

### 1.1 菜单覆盖不完整

- 2D 命令目录 `CommandCatalog` 已经包含大量命令，但菜单中只覆盖了部分常用项。
- 某些命令已经在目录中定义，但菜单入口缺失。
- 有些命令只能通过工具栏触发，菜单中找不到。

### 1.2 菜单分类不够清晰

- 部分编辑类命令被硬编码在 `Edit` 菜单中，但目录层又已有统一定义。
- `File` / `View` / `Help` / `Tools` 的职责边界不够明确。
- 同类功能在不同位置重复出现，容易让用户困惑。

### 1.3 图标没有统一应用

- 命令目录里已有 `iconResource`，但菜单创建时未统一调用 `setIcon()`。
- 结果是：工具栏有图标，菜单没有图标，视觉和交互不一致。

### 1.4 菜单点击没有统一日志

- 当前菜单点击多为直接执行 `operationBus->run(...)`。
- 缺少统一的命令点击日志。
- 出现问题时不容易定位“用户点了什么、执行了什么、是否成功”。

### 1.5 新旧逻辑混用

- 菜单和工具栏命令来源有重合，但实现方式不完全一致。
- 这会导致后续定制时难以统一改造。

---

## 2. 总体目标

本次菜单完善分为四个目标：

### 2.1 让菜单成为功能全集

只要某个功能在系统中可用，就应尽量在菜单中找到入口。

### 2.2 让菜单分类逻辑清晰

菜单按语义分组，避免功能混淆、交叉、重复。

### 2.3 让菜单行为统一

菜单点击行为统一：

- 统一创建
- 统一绑定命令
- 统一加图标
- 统一打日志
- 统一执行方式

### 2.4 让菜单支持后续定制

菜单最终要支持：

- 按工作台切换显示
- 按配置增删
- 按命令目录自动生成
- 按客户需求扩展

## 3. 菜单设计原则

### 3.1 命令来源唯一

菜单命令必须以命令目录为准，避免：

- 菜单里写一份
- 工具栏里再写一份
- 实际命令注册又是另一份

建议原则：

> **`CommandCatalog` 是命令的唯一事实来源。**

### 3.2 菜单结构固定，内容动态

菜单顶层结构建议保持稳定，例如：

- `File`
- `Edit`
- `View`
- `Tools`
- `Help`
- `2D`
- `3D`

但每个顶层菜单内部的具体项，可按工作台、命令目录、配置进行动态生成。

### 3.3 菜单按语义归类

不要让一个菜单混入太多不相关功能。例如：

- 文件导入/导出放 `File`
- 变换、阵列、布尔、图层、分组放 `Edit`
- 视图导航、显示设置放 `View`
- 行业功能和工具型命令放 `Tools`
- 诊断、帮助、调试入口放 `Help`

### 3.4 图标和文字同时规范

- 如果命令有 `iconResource`，菜单应尽量显示图标。
- 如果无图标，则使用统一兜底策略，不允许风格混乱。

### 3.5 菜单点击必须记录日志

每次菜单触发都记录统一格式日志，建议至少包含：

- 菜单显示文本
- 命令 ID
- 工作台 ID
- 是否成功触发
- `checkable` / `checked` 状态变化

---

## 4. 菜单覆盖范围

### 4.1 2D 菜单覆盖范围

2D 菜单应尽量覆盖所有 2D 相关能力：

- 文件操作
- 导入导出
- 编辑操作
- 图层操作
- 视图操作
- 单位设置
- 2D 工具
- 2D 算法入口
- 调试/测试入口

### 4.2 3D 菜单覆盖范围

3D 菜单应覆盖：

- 3D 文件操作
- 3D 视图控制
- 3D 选择/编辑
- 3D 工具入口
- 3D 行业功能入口
- 调试/测试入口

### 4.3 共用原则

2D 和 3D 的菜单结构要尽量遵循同一套逻辑：

- 顶层分类一致
- 命名风格一致
- 图标策略一致
- 日志策略一致

区别只在于：

- 某些命令仅在 2D 或 3D 工作台可见
- 某些菜单项按工作台动态启用或隐藏

## 全局框架描述

这份菜单方案不是单纯“把菜单画出来”，而是把菜单变成一层可配置、可定制、可审计的框架能力。它的核心是把 **命令、菜单、工具栏、工作台、日志** 统一到一条链路上：

```text
CommandCatalog / CommandCatalog3D
        ↓
菜单树配置（JSON）
        ↓
UiLayoutBuilder / WorkbenchMenuManager
        ↓
QAction / QMenu / QToolBar
        ↓
OperationBus::run(OperationId)
        ↓
具体业务实现
```

### 框架由什么组成

- **命令目录层**
  - 负责定义“系统里有哪些功能”
  - 2D 由 `CommandCatalog` 提供
  - 3D 由 `CommandCatalog3D` 提供
  - 命令目录是唯一事实来源，不允许菜单自己另起一套命令名

- **菜单配置层**
  - 负责定义“这些功能在菜单里怎么展示”
  - 包括顶层菜单、子菜单、顺序、图标、工作台可见性
  - 同一个命令可以在菜单、工具栏、快捷键里重复出现，但来源必须统一

- **菜单构建层**
  - 负责把配置变成真正的 Qt 菜单和动作
  - 统一处理图标、日志、快捷键、启用状态
  - 统一调用 `OperationBus`

- **工作台控制层**
  - 负责决定 2D / 3D 当前应该显示哪些菜单
  - 负责切换工作台后重建菜单
  - 负责控制某些命令只在特定工作台出现

- **业务执行层**
  - 负责真正执行命令
  - 菜单只是入口，不直接写业务逻辑

### 2D / 3D 菜单逻辑是怎样的

#### 2D 菜单逻辑

2D 菜单以 `CommandCatalog` 为主，菜单结构按以下思路组织：

- `File`：文件新建、打开、保存、导入、导出
- `Edit`：撤销、剪切复制粘贴、变换、布尔、图层、数组
- `View`：缩放、平移、单位、网格、捕捉、图层管理
- `Tools`：行业功能、算法入口、调试入口
- `Help`：文档、快捷键、设置、关于

2D 菜单的原则是：

1. **菜单尽量覆盖所有 2D 可用命令**
2. **能归类的命令尽量归类，不要混放**
3. **图标、日志、快捷键都由统一结构驱动**
4. **新增功能先进入命令目录，再进入菜单配置**

#### 3D 菜单逻辑

3D 菜单以 `CommandCatalog3D` 为主，逻辑与 2D 保持一致，但具体内容按 3D 场景组织：

- `File`：3D 导入/导出
- `Edit`：3D 选择、变换、编辑、分组等
- `View`：相机、视角、旋转、平移、显示模式
- `Tools`：3D 算法、行业模块、扩展工具
- `Help`：帮助、设置、调试

3D 菜单的原则是：

1. **结构和 2D 保持同样的分类逻辑**
2. **命令来源仍然只看 `CommandCatalog3D`**
3. **同类功能不允许在 2D / 3D 中采用完全不同的菜单规则**
4. **工作台切换时，菜单按当前工作台重建**

### 菜单定制开发的实现路径

菜单定制不是“手工改几处 UI”，而是按下面顺序做：

1. 先把命令目录补齐
2. 再把菜单结构写成配置
3. 再由统一构建器生成菜单
4. 再由工作台控制菜单可见性
5. 最后再做客户级差异化配置

这条路径的好处是：

- 核心逻辑不被菜单污染
- 2D / 3D 的菜单规则一致
- 客户定制不会破坏主框架
- 日志和图标可以统一治理

## 开发步骤（建议严格按这个顺序做）

### 第 0 步：冻结规则

先不要继续随意加菜单，先确认：

- 菜单目录有哪些顶层分类
- 哪些命令必须进菜单
- 哪些命令只保留工具栏
- 哪些命令只对 2D / 3D 可见
- 日志格式统一成什么样

### 第 1 步：补齐命令目录

先把 `CommandCatalog` / `CommandCatalog3D` 的命令补完整。

要求：

- 命令 ID 统一
- 图标资源统一
- 可见工作台统一
- 菜单可用性统一

### 第 2 步：完成菜单 schema

把菜单从硬编码抽出来，写成 JSON 结构。

要求：

- 顶层菜单固定
- 子菜单按语义分组
- 支持图标、显隐、工作台范围
- 支持动作、子菜单、分隔符

### 第 3 步：完成统一 action 工厂

由统一工厂负责：

- 创建 `QAction`
- 设置文字
- 设置图标
- 设置快捷键
- 设置工作台属性
- 绑定 `OperationBus`
- 统一打日志

### 第 4 步：让 `WorkbenchMenuManager` 读取配置

将菜单创建逻辑从硬编码迁移到配置生成。

要求：

- 2D 读 2D 配置
- 3D 读 3D 配置
- 切换工作台时重新构建菜单
- 旧逻辑保留回退入口

### 第 5 步：补齐 2D 菜单

按 `File / Edit / View / Tools / Help` 逐项补齐。

要求：

- 缺失功能补菜单
- 已有功能统一图标和日志
- 分类不混乱

### 第 6 步：补齐 3D 菜单

按同样规则整理 `CommandCatalog3D`。

要求：

- 2D / 3D 菜单结构一致
- 仅功能内容不同
- 图标和日志行为一致

### 第 7 步：统一日志与验证

最后统一检查：

- 每个菜单点击都有日志
- 命令 ID 可追踪
- 工作台切换后菜单正确重建
- 配置缺失时有回退
- 新增客户配置不需要改核心代码

### 6.3 树草案使用规则

- 菜单树是“默认建议结构”，不是最终死结构。
- 客户定制时可以：
  - 隐藏某些节点
  - 调整节点顺序
  - 替换节点标题
  - 只保留部分顶层菜单
- `checkable` 菜单项应与状态中心同步，避免显示状态和业务状态分离。
- 但建议不要打乱基础语义分组，否则后续维护成本会升高。

## 7. 菜单实现规范

### 7.0 菜单与工具栏的统一映射原则

为了让“菜单是所有功能的集合”真正落地，建议采用以下映射原则：

- **菜单是主入口**：所有可执行功能都尽量在菜单中有入口
- **工具栏是快捷入口**：工具栏可作为高频命令的快速访问，但不作为唯一入口
- **同一命令多入口一致**：菜单、工具栏、快捷键都应指向同一命令 ID
- **以命令目录为准**：命令目录定义命令，菜单只负责组织和展示

### 7.1 统一 action 工厂

### 7.1 统一 action 工厂

建议引入统一的 action 工厂方法，例如：

- 创建菜单项
- 设置图标
- 绑定命令
- 绑定日志
- 绑定启用状态

这样可以避免各处重复写逻辑。

### 7.2 图标应用规则

建议规则：

- 命令目录中配置了 `iconResource`，菜单自动应用图标
- 图标不存在时，使用默认样式或不显示图标
- 图标资源路径统一管理

### 7.3 日志规则

菜单触发时统一记录日志，建议格式：

- `[Menu] <text> -> <cmdId>`
- 或加入工作台信息：`[Menu][2D] <text> -> <cmdId>`

如果命令执行失败，也要记录失败原因。

### 7.4 菜单构建来源

建议统一使用：

- 命令目录
- 工作台可见性规则
- 菜单分类规则
- 配置开关

而不是在 `WorkbenchMenuManager` 中硬编码大量菜单项。

### 12.3 多主题图标机制（本轮同步引入）

- **存储**：默认集 `Icons/` + 皮肤覆盖集 `Icons/<flavor>/`（`light` / `dark` / `highcontrast`）。
- **解析顺序**（`IconHelper::resolveIconResource`）：用户自定义目录 → `Icons/<flavor>/<相对路径>` → 默认集。
- **语义色令牌**：`ThemeManager::colorTokens()` 定义 `%bg%` `%accent%` 等 8 个令牌，`IconHelper::coloredSvgData` 渲染时按当前主题替换；`currentColor` 兼容旧图标。
- **刷新**：`ThemeManager::setTheme` → `IconHelper::refreshAllThemedIcons()`；渲染结果按「路径+令牌色+尺寸+DPR」缓存。
- 详细规范见 `Docs/01-当前架构/UI定制.md` 3.4。
