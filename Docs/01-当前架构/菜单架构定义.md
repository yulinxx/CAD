# 菜单架构定义

> **文档定位**：本文档是菜单体系的总纲，后续菜单设计、菜单实现、菜单定制与菜单迭代都以本文档为基准。
>
> **适用范围**：2D / 3D 主菜单、工具栏、快捷入口、工作台切换菜单、客户化菜单配置。
>
> **核心目标**：
> 1. 让菜单成为“所有功能的统一入口集合”。
> 2. 让 2D / 3D 菜单遵循同一套逻辑、同一套命令体系、同一套日志规范。
> 3. 让菜单支持配置化定制，而不是继续依赖大规模硬编码。
> 4. 让菜单与主框架的交互方式清晰、稳定、可扩展。

---

## 1. 菜单在系统中的定位

菜单不是业务实现层，也不是数据层，而是**应用级入口层**。

它的作用是把不同来源的能力整齐地组织起来，并把用户的操作稳定地转发到统一命令系统。

```text
用户点击菜单
    → 菜单项 / 子菜单 / 快捷键
    → CommandCatalog / CommandCatalog3D
    → 统一 action 工厂 / WorkbenchMenuManager / UiLayoutBuilder
    → OperationBus::run(OperationId)
    → 具体业务服务 / 场景 / 文档 / 渲染刷新
```

### 1.1 菜单不负责什么

菜单不直接负责：

- 几何算法实现
- 场景对象修改
- 渲染后端处理
- 实体生命周期管理
- 文档保存细节
- 业务状态持久化细节

这些事情必须由主框架和业务层完成，菜单只负责触发。

### 1.2 菜单负责什么

菜单负责：

- 提供全局入口
- 承载低频但重要的功能
- 组织功能分类
- 提供功能发现能力
- 与工具栏、快捷键共享同一套命令 ID
- 支持工作台切换和客户化定制
- 记录命令点击日志，便于排查和审计
- 管理 `checkable` / `checked` 状态的呈现与同步

## 2. 当前菜单体系的框架组成

当前菜单体系不是单一模块，而是由多个层协作完成。

### 2.1 命令目录层

命令目录定义“系统里有哪些功能”。

- 2D 使用 `UI/2D/Src/Operation/CommandCatalog.cpp`
- 3D 使用 `UI/3D` 对应的命令目录

命令目录是菜单体系的**唯一命令事实来源**。菜单可以重排、分组、隐藏，但命令定义本身不能分裂成多套。

命令目录中通常包含：

- `operationId`
- `menuId`
- `text`
- `shortcutId`
- `iconResource`
- `surfaces`
- `enable rule`
- `toolName`

### 2.2 菜单配置层

菜单配置层定义“这些功能怎么展示”。

它解决的是：

- 顶层菜单有哪些
- 菜单顺序如何
- 子菜单如何分组
- 图标如何显示
- 哪些工作台可见
- 哪些客户版本启用

当前代码已经开始引入 `UiConfigData / UiConfigLoader / UiLayoutBuilder / UiConfigurationManager`，用于把菜单从硬编码逐步转成配置驱动。

### 2.3 菜单构建层

菜单构建层负责把配置变成 Qt 控件。

当前主要实现点：

- `WorkbenchMenuManager`：主窗口菜单管理与工作台菜单刷新
- `UiLayoutBuilder`：通用菜单 / 工具栏 / Dock / 快捷键构建器
- `UiConfigurationManager`：客户配置加载与回退

### 2.4 工作台控制层

工作台决定当前应该显示哪一套菜单。

- 2D 工作台显示 2D 菜单逻辑
- 3D 工作台显示 3D 菜单逻辑
- 切换工作台时，菜单需要重建或重刷
- 部分菜单项会因为工作台不同而显示 / 隐藏 / 禁用

### 2.5 业务执行层

菜单最终触发的是业务执行层：

- `OperationBus`
- 场景服务
- 文件服务
- 编辑服务
- 工艺服务
- 视图服务

菜单不直接写业务逻辑，只把命令送到业务系统。

## 3. 菜单的设计原则

### 3.1 命令来源唯一

菜单命令必须以命令目录为准。

> **原则：CommandCatalog / CommandCatalog3D 是命令的唯一来源。**

这样可以避免：

- 菜单写一套命令名
- 工具栏写另一套命令名
- 快捷键再写第三套命令名

### 3.2 菜单结构固定，内容可变

菜单顶层结构应该尽量固定，例如：

- `File`
- `Edit`
- `View`
- `Tools`
- `Help`
- `2D`
- `3D`

但每个菜单内部的具体命令可以由：

- 命令目录
- 工作台
- 配置文件
- 客户版本

共同决定。

### 3.3 菜单按语义归类

菜单不能按“写代码方便”来分，而必须按业务语义来分。

例如：

- 文件导入/导出放 `File`
- 变换、阵列、布尔、图层、分组放 `Edit`
- 缩放、平移、单位、网格、捕捉放 `View`
- 激光 / 视觉 / 行业工具放 `Tools`
- 文档、设置、帮助、关于放 `Help`

### 3.4 图标、日志、快捷键必须统一

如果一个命令在命令目录中配置了图标，就应该尽量在菜单中显示图标。

菜单点击必须统一日志，建议至少记录：

- 菜单文本
- 命令 ID
- 工作台 ID
- 执行结果或是否触发成功

### 3.5 菜单与工具栏必须同源

菜单、工具栏、快捷键可以是不同入口，但必须使用同一套命令 ID 和同一套执行链。

> 菜单是主入口，工具栏是快捷入口，快捷键是高频入口，但三者不能互相独立维护。

## 4. 当前框架下的菜单实现方式

### 4.1 2D 命令目录

2D 菜单由 `CommandCatalog` 提供命令目录，当前目录里已经包含：

- 绘图命令
- 编辑命令
- 文件导入导出命令
- 图层相关命令
- 视图相关命令
- 工艺 / 激光 / 视觉相关命令
- 帮助 / 设置相关命令

### 4.2 3D 命令目录

3D 菜单由 `CommandCatalog3D` 提供命令目录。

3D 菜单逻辑与 2D 保持相同的结构原则，但内容按 3D 场景组织。

### 4.3 混合模式与过渡模式

当前工程处于“硬编码菜单 + 配置驱动菜单”的过渡状态。

因此菜单实现分成两类：

1. **旧路径**
   - `WorkbenchMenuManager` 中仍有部分硬编码逻辑
   - 用于兼容现有行为

2. **新路径**
   - `UiConfigLoader` + `UiLayoutBuilder`
   - 通过 JSON 菜单树生成菜单
   - 可用于客户化和后续统一化迁移

最终目标是让新路径成为主路径，旧路径只作为回退或兼容层保留。

## 5. 菜单与主框架如何交互

菜单和主框架的交互必须是单向且清晰的。

### 5.1 交互主链路

```text
QAction / 菜单项
    → commandId
    → CommandCatalog / CommandCatalog3D
    → OperationBus::run(OperationId)
    → 业务服务
    → 状态中心 / 文档 / 视口 / 日志反馈
```

### 5.2 工作台切换如何影响菜单

当工作台从 2D 切到 3D，或者从 3D 切到 2D：

- 菜单要按当前工作台重新构建
- 可见项要重新判定
- 一些菜单项要隐藏或切换
- 工具栏也应该同步重建或同步刷新

### 5.3 菜单状态由谁控制

菜单项的状态应主要来自：

- 当前文档状态
- 当前工作台状态
- 选择状态
- 权限状态
- 工具状态
- 布局配置

不要让菜单自己去推断业务状态。

## 6. 2D 菜单逻辑

2D 菜单的目标是：**覆盖 2D 场景下的全部功能入口**。

### 6.1 推荐分类

- `File`
- `Edit`
- `View`
- `Tools`
- `Help`

也可以在未来补充 `2D` 专属菜单，但前提是不要把本该归类为 `File/Edit/View` 的功能强行塞到专属菜单里。

### 6.2 2D 的菜单组织原则

2D 菜单主要按以下逻辑组织：

- 文件生命周期：新建、打开、保存、导入、导出、最近文件
- 编辑操作：撤销、重做、复制、粘贴、删除、分组、布尔、偏移、阵列
- 视图操作：缩放、平移、单位、网格、捕捉、图层管理
- 工具操作：激光、视觉、行业命令、算法命令、测试命令
- 帮助操作：文档、快捷键、设置、关于

### 6.3 2D 与工具栏的关系

2D 菜单和 2D 工具栏不能各做一套。

- 菜单负责完整入口
- 工具栏负责高频快捷入口
- 两者都必须引用同一个命令 ID

### 6.4 2D 的定制空间

2D 菜单后续可以定制：

- 菜单项显隐
- 顶层菜单显隐
- 菜单排序
- 菜单图标
- 菜单标题
- 工作台范围
- 客户行业专属功能

---

## 7. 3D 菜单逻辑

3D 菜单的目标是：**保持与 2D 相同的结构逻辑，但内容以 3D 命令为准**。

### 7.1 推荐分类

- `File`
- `Edit`
- `View`
- `Tools`
- `Help`

### 7.2 3D 的菜单组织原则

3D 菜单主要按以下逻辑组织：

- 文件生命周期：导入、导出、保存、打开、最近文件
- 编辑操作：选择、删除、变换、组装、编辑辅助
- 视图操作：相机、旋转、平移、重置、显示模式
- 工具操作：3D 算法、行业模块、扩展功能
- 帮助操作：文档、设置、关于、快捷键

### 7.3 3D 与 2D 的一致性要求

2D / 3D 之间必须保持：

- 顶层分类一致
- 菜单构建方式一致
- 图标策略一致
- 日志策略一致
- 命令执行链一致

差异只应体现在：

- 命令目录不同
- 工作台可见性不同
- 部分菜单项不同

### 7.4 3D 的定制空间

3D 菜单后续也要支持：

- 仅显示部分菜单项
- 隐藏行业模块
- 替换图标
- 定制子菜单结构
- 按客户版本启用 / 禁用功能

---

## 8. 菜单定制开发的实现路径

菜单定制不是直接在 `WorkbenchMenuManager` 里继续加硬编码，而是应该按以下路径实施：

### 8.1 第一步：统一命令目录

先把 2D / 3D 需要的命令统一整理出来。

要求：

- 命令 ID 统一
- 图标资源统一
- 工作台可见性统一
- 能否显示到菜单统一

### 8.2 第二步：统一菜单 schema

把菜单从代码抽离成 JSON 配置。

要求：

- 顶层菜单稳定
- 子菜单按业务语义组织
- 每个菜单项能绑定 `commandId`
- 支持 `visible`、`workbenches`、`icon`
- 支持 `action`、`separator`、`submenu`

### 8.3 第三步：统一 action 工厂

由统一工厂负责生成动作并接线。

要求：

- 设置文本
- 设置图标
- 设置快捷键
- 记录日志
- 绑定 `OperationBus`
- 标记工作台信息

### 8.4 第四步：由工作台控制显示范围

2D / 3D 由工作台决定当前应展示哪些菜单项。

要求：

- 2D 只显示 2D 菜单项
- 3D 只显示 3D 菜单项
- 共用项保持一致
- 切换工作台时重建菜单

### 8.5 第五步：支持客户配置

最终要支持按客户版本配置菜单。

要求：

- 不同客户可以有不同菜单树
- 不同客户可以有不同图标包
- 不同客户可以隐藏/启用不同命令
- 不同客户可以调整菜单顺序

## 10. 开发步骤

以下步骤建议作为菜单开发的标准流程。

### 第 0 步：明确范围

先确认本轮要做的是：

- 只做 2D
- 只做 3D
- 2D + 3D 一起做
- 只做菜单
- 菜单 + 工具栏一起做

### 第 1 步：盘点命令目录

先把命令目录盘清楚：

- 哪些命令已有
- 哪些命令缺失
- 哪些命令只在工具栏出现
- 哪些命令应补入菜单

### 第 2 步：整理最终菜单目录表

把命令 ID 映射到菜单位置。

要求：

- 2D 一张表
- 3D 一张表
- 顶层分类一致
- 冲突项先统一语义再落位

### 第 3 步：定义菜单配置 JSON

把最终菜单目录表转成配置文件。

要求：

- 结构清晰
- 支持嵌套子菜单
- 支持图标和可见性
- 支持工作台范围

### 第 4 步：接入统一构建器

让 `UiLayoutBuilder` 负责真正生成菜单项。

要求：

- 菜单、工具栏、快捷键同源
- 缺失命令自动禁用或告警
- 图标和日志统一处理

### 第 5 步：让菜单管理器读取配置

`WorkbenchMenuManager` 不再单独维护一套完全独立的菜单逻辑，而是以配置为主、兼容逻辑为辅。

要求：

- 新路径优先
- 旧路径可回退
- 2D / 3D 切换一致

### 第 6 步：补齐图标、日志和注释

每个关键菜单入口都应该具备：

- 图标
- 日志
- 注释
- 清晰命名

### 第 7 步：回归验证

最后确认：

- 菜单能正常显示
- 工作台切换后菜单正确重建
- 2D / 3D 规则一致
- 客户配置可正常覆盖
- 日志能准确记录菜单行为

---

## 11. 结论

菜单是整个应用功能组织的第一层入口，它必须做到：

- 命令来源统一
- 架构边界清晰
- 2D / 3D 逻辑一致
- 支持客户化配置
- 支持日志追踪
- 支持后续持续演进

> **后续所有菜单功能完善、菜单定制开发、工作台菜单切换、菜单图标和日志规范，都应以本文档为准。**
