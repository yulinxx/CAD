> 状态：**已修复（2026-08-25）**。本文保留原始问题分析，并在每节末尾追加实际落地的修复方式。

> 相关文档：`Docs/01-当前架构/命令与状态流.md`（6.3 命令 UI 状态桥接）、`Docs/01-当前架构/顶部工具栏架构定义.md`

## 问题 0（原分析遗漏，实际是最严重的根因）：6 个对齐按钮从未接入命令中枢

### 问题描述

`TopToolBar` 用一张手写的 `actionIdToMenuActionId` 映射表把 `ToolBarAction::actionId` 转成 `UI::MenuActionId`。这张表**漏了 6 个对齐命令**（`Edit_AlignLeft` / `Edit_AlignRight` / `Edit_AlignCenterH` / `Edit_AlignTop` / `Edit_AlignBottom` / `Edit_AlignCenterV`）。

### 根因分析

`ToolBarContext::Default` 注册的 actionId 是 `"Edit_AlignLeft"` 等帕斯卡下划线形式，`actionIdToMenuActionId` 查表失败返回 `MenuActionId(-1)`，`appendAction` 于是走到兜底分支：

```cpp
action = new QAction(this);
action->setEnabled(actionDef.enabled);   // ToolBarAction::enabled 默认 true
```

结果：**这 6 个按钮的 enabled 恒为 true**，与 `CommandActionHub` 完全脱钩。无论选中 0 个、1 个还是多个，无论是否锁定，对齐按钮始终可点。

而 `CommandCatalog.cpp` 里这 6 条命令的启用规则声明本身是正确的（`RequiresUnlockedMultiSelection`），规则内核 `Cmd::evaluateEnableRule` 也是正确的 —— 问题纯粹出在「actionId 解析」这一段接线上。

### 影响

用户可见行为：单选一个图元时点击对齐 → 命令被分发但语义无效；锁定图元后点击对齐 → 同样可点。

### 实际修复

让 `CommandCatalog` 成为 actionId 的唯一真值源，彻底删除第二张手写表：

1. `UI/2D/Src/Operation/CommandCatalog.cpp`：6 个 align 条目补上 `shortcutId`（`"edit.align_left"` 等，原为 `nullptr`）；同时删除 `menuIdForCommandId` 中 `precise[]` 表里重复的 6 条 align 映射，避免两处真值源漂移。
2. `Main/Src/UI/Workbench/UiWorkbench.cpp`：`ToolBarContext::Default` 的 actionId 全部从帕斯卡下划线改为 catalog 命令 id（`"Edit_AlignLeft"` → `"edit.align_left"`），与菜单栏 / JSON 配置统一到同一命名空间。
3. `UI/2D/Src/UI/TopToolBar/TopToolBar.cpp`：`appendAction` 改用 `CommandCatalog::menuIdForCommandId()` 解析；**`actionIdToMenuActionId` 整表删除（76 行）**。

风险点已核实：`shortcutId` 同时被用于查 `Main/resources/Shortcuts/default_shortcuts.json`，该 json 无 align 条目，且 `CommandActionHub::createEditAction` 不从 `shortcutId` 绑定快捷键，补 `shortcutId` 无副作用。

### 回归防护

`Main/Src/UI/Test/CommandUiWiringTests.cpp` 新增 5 个用例，其中：

- `DefaultToolBarContextIdsAllResolveToMenuActionId` —— `ToolBarContext::Default` 的每个 id 必须解析出非 0 `MenuActionId`
- `AlignCommandsRequireUnlockedMultiSelection` —— 6 个对齐命令必须携带 `RequiresUnlockedMultiSelection`
- `CatalogShortcutIdsResolveBackToOwnMenuId` —— 凡声明 `shortcutId` 的条目，反向解析必须回到自己的 `menuId`

`UI/Common/Test/CommandKernelTests.cpp` 新增 3 个用例补齐规则层空白：`RequiresMultiSelection`、`RequiresUnlockedMultiSelection` 此前**零覆盖**。

## 问题 1：TopToolBar::appendAction 中 toggle action 获取错误

### 问题描述

`TopToolBar::appendAction()` 在从 `CommandActionHub` 查找动作时，只调用了 `editAction()`，没有调用 `toggleEditAction()`。这导致可切换动作（toggle action，如 `Edit_Group`）无法从 Hub 中正确获取，最终退化为创建一个全新的 QAction，与 Hub 管理的动作失去同步。

### 根因分析

`CommandActionHub` 中编辑动作存储在 `m_editActions`，通过 `editAction()` 获取；切换动作存储在 `m_toggleEditActions`，通过 `toggleEditAction()` 获取。`Edit_Group` 在 `CommandCatalog.cpp` 中 `checkable = true`，因此被放入 `m_toggleEditActions`。

`installHubActions()` 的实现是正确的（`addEditAction()` / `addToggleAction()` 分别走两条路），但 `appendAction()` 只调用了 `editAction()`。

### 影响

1. 通过 `ToolBarContextManager` 动态添加 `Edit_Group` 等切换按钮时，按钮不是 Hub 管理的同一个 QAction 对象
2. 按钮的 enabled / checked / 文字图标切换（Group ↔ Ungroup）都不随 `refreshActionStates` 更新
3. 点击行为也可能不同（新建 action 没有连接到 `OperationRouting::dispatch`）

### 实际修复

`appendAction` 拆出私有方法 `resolveHubAction()`，以 `actionDef.checkable` 决定首选查找路径，两条路径互为兜底：

```cpp
QAction* action = actionDef.checkable ? m_commandActionHub->toggleEditAction(menuId)
                                     : m_commandActionHub->editAction(menuId);
if (!action)
{
    action = actionDef.checkable ? m_commandActionHub->editAction(menuId)
                                 : m_commandActionHub->toggleEditAction(menuId);
}
```

同时**删除了 2D 侧的 `installHubActions()`** —— 它是死代码（全仓无调用点），且固定列表无法承担 `ToolBarContext` 的动态切换需求。3D 侧的 `TopToolBar3D::installHubActions` 是不同签名的独立实现，不受影响。

兜底路径也做了分类：属于 catalog 的 id 若取不到 hub action 仍打 `SY_WARNF` 告警（真回归）；`Text_*` / `QR_*` / `Bitmap_*` / `Vector_*` / `Image_*` 共 20 个尚未实现的上下文占位项则**显式禁用 + tooltip 标注「not implemented yet」**，不再刷告警日志。

## 问题 2：上下文切换后新添加的 actions 是否需要立即刷新启用状态

### 问题描述

`ToolBarContextManager::setCurrentContext()` 切换上下文后，`TopToolBar` 会清空并重新添加 actions。新添加的 actions 从 Hub 获取时，其启用状态是否已经是最新的？

### 原分析结论

由于 Qt 信号按连接顺序传递，且 `setupViewportServices` 在 `createToolbars` 之前执行，刷新 Hub 状态的连接先建立、先执行，因此上下文切换时 Hub 状态已是最新。

### 潜在问题

1. 非选择变化触发的上下文切换（工具切换、模式切换）时 Hub 状态可能过时
2. 新上下文特有的非 Hub 动作，enabled 来自 `ToolBarAction` 静态配置，不随状态刷新

### 实际修复

没有采用「在 `setActions()` 末尾补一次防御性刷新」的方案 —— 那治的是症状。改为**消除顺序依赖本身**：

上下文切换不再单独监听 `selectionChanged`，而是移入 `Workbench2D::applySelectionContext(snapshot)`，由 `CommandActionHub::selectionContextChanged` 信号驱动。该信号在 `refreshActionStates()` 内部、`m_lastSnapshot` 已更新之后发出，因此「Hub 状态最新」不再依赖两个 connect 的建立先后，而是由数据流本身保证：

```
refreshCommandUiState()
  → captureSnapshot()
  → refreshActionStates(snapshot)      // Hub 内所有 action 的 enabled 已刷新
      → emit selectionContextChanged(snapshot)
          → applySelectionContext(snapshot)
              → 属性面板 / 状态栏 / 场景树右键 / 工具栏上下文切换
```

潜在问题 2（非 Hub 动作的静态 enabled）由问题 0 的修复处理：占位项现在显式禁用，不再假装可用。

## 问题 3：setupViewportServices 与 createToolbars 的调用顺序

### 问题描述

`setupViewportServices()` 在 `createToolbars()` 之前调用，前者连接了 `selectionChanged` 到 `m_commandHub->refreshActionStates()`，但此时 `m_commandHub` 尚未创建。

### 原分析结论

lambda 内有 `if (m_commandHub)` 空指针保护，不会崩溃；初始状态由 `rebuildAllActions()` 内的 `captureSnapshot()` 兜住。但「连接建立时目标对象不存在」这种模式容易在未来引入 bug。

### 实际修复

采纳了「把连接移到目标已存在之后」的思路，但落点更彻底：**新增 `Main/Src/UI/Workbench/UiStateBridge2D.h/.cpp`**，与 3D 的 `UiStateBridge3D` 对等，把所有触发源集中到一个 `install()` 里，并在 `attachToWindow()` **末尾**调用 —— 此时视口、工具栏、场景树、状态栏全部就绪，`install()` 内的首次 `refreshAll()` 可覆盖全部 UI。

`setupViewportServices` 中那 3 个 `selectionChanged` lambda 全部删除。

## 问题 4：CommandActionHub::captureSnapshot 中选择计数的获取逻辑

### 问题描述

`captureSnapshot()` 中不同 provider 使用了不同的选择数据源：选择计数与锁定判定走 `ISelectionService`，而分组切换走 `SceneManager::getSelectedEntities()`，可能导致快照内部状态不一致。同时 `GroupToggleState.enabled` 只判断了是否在锁定图层，没有判断是否有选中项。

### 实际修复

原分析的**方案 A（统一选择数据源）已在先前的重构中落地**：三个独立 provider 合并为单一 `selectionContextProvider`，一次 `visitSelectedIds` 遍历同时产出 `selectionCount` / `anyLockedLayer` / `anyLockedEntity` / `anyEditable` / `typeMask` / `groupOn`，`hasSelection` 由 `selectionCount > 0` 推导。数据源分裂已从根上消除。

本次额外修正了一处遗留的语义不一致：

```cpp
// 修复前：只看图层锁
result.groupEnabled = !result.anyLockedLayer;
// 修复后：与 RequiresUnlockedSelection 的双锁语义对齐
result.groupEnabled = !(result.anyLockedLayer || result.anyLockedEntity);
```

## 问题 5（本次新发现）：图元锁定状态变化不触发任何刷新

### 问题描述

在场景树中锁定当前选中的图元后，`Delete` / `Align` / `Mirror` 等 `RequiresUnlockedSelection` 系按钮**仍然可点**，属性面板的锁定态也停留在旧值。

### 根因分析

`Workbench2D::setSceneTreeLock()` 修改图元锁后只调 `scene->notifySceneChanged()`：

```cpp
entity->setLocked(locked);
if (changed) { scene->notifySceneChanged(); }
```

而 `notifySceneChanged` 在 2D 侧的唯一订阅者 `SceneTreeSceneObserver2D` **只按图元数量变化**判断是否重建树。锁定不改变数量 → 连树都不刷 → 更不会触发 `refreshActionStates` → 快照里的 `anyLockedEntity` 仍是旧值。

对比 3D：`UiStateBridge3D::install()` 订阅了 `SceneMonitor3D::sceneChanged`，任何场景变化都会刷 UI 状态。**2D 缺的正是这一路。**

### 实际修复

`UiStateBridge2D::install()` 集中挂载 5 路触发源，其中第 5 路即补上的缺口：

| 触发源 | 覆盖的状态变化 |
|---|---|
| `RenderViewport2D::selectionChanged` | 点选 / 框选 / 绘制后自动选中 / 撤销 |
| `QtLayerManagerBridge::sigLayerChanged` | 图层锁定与属性变更 |
| `OperationBus::undoStateChanged` | 撤销 / 重做栈变化 |
| `OperationBus::operationCompleted` | 任意操作完成（含剪贴板写入） |
| `SceneMonitor::sceneChanged` | **图元级 setLocked / setVisible 等不改数量、不经操作总线的变更** |

同时删除了原先硬编码的 `Edit_Copy` / `Edit_Cut` 剪贴板白名单 —— 新增写剪贴板的操作不必再回来改这里。

## 问题 6（本次新发现）：场景树右键菜单与视口右键菜单规则漂移

### 问题描述

同一个 Delete 命令在两处行为不同：视口右键菜单在选中项锁定时正确禁用，场景树右键菜单**仍可删除锁定图元**。

### 根因分析

`SceneTreePanel2D::showContextMenu` 自己遍历 selection model 算 `hasSelection`，构成第二个数据源，且完全没有考虑锁定：

```cpp
const bool hasSelection = !selectedIds().isEmpty();
action->setEnabled(hasSelection);   // 未判断 anyLocked
```

### 实际修复

面板不再做状态判定，只渲染。新增 `SceneTreePanel2D::setCommandState(bool hasSelection, bool anyLocked)`，由 `Workbench2D::applySelectionContext` 从命令中枢快照推入，与工具栏 / 视口右键菜单共用同一份事实。

启用规则对齐 `CommandEnable2D` 语义：

| 右键项 | 启用条件 | 对应规则 |
|---|---|---|
| Delete / Show / Hide | 有选中 **且** 未锁定 | `RequiresUnlockedSelection` |
| Lock / Unlock | 仅需有选中 | `RequiresSelection` |
| Select All / Clear | 恒可用 | `Always` |

**注意 Lock / Unlock 必须只要求 `hasSelection`** —— 若也要求未锁定，锁定后将永远无法解锁。

### 问题 7：菜单栏 QAction 完全不随选择联动

`Main/Src/UI/Workbench/WorkbenchMenuManager.cpp` 原先**全文 0 个 `setEnabled`**，菜单栏 QAction 是独立于 Hub 的第二套对象，只共享 `dispatchCommandSafely` 执行路径。后果：菜单栏的 Cut / Copy / Delete / Align 在无选中时可点，Paste 在剪贴板为空时可点，Undo / Redo 在无历史时可点。

一个容易看错的地方：菜单栏的真实构建路径不是 `WorkbenchMenuManager` 里那些 `buildFileMenu / refreshEditMenuForWorkbench`，而是配置驱动的 `rebuildMenusFromConfig()` → `UiLayoutBuilder::buildMenus(base.json)`；前者只在配置加载失败时作为回退执行。所以修复必须同时覆盖两条构建路径。共同点是两者都给 action 打了 `property("commandId")`，这就是抓手。

**实际修复**

不改菜单创建方式（改成复用 Hub 的 QAction 会牵动 JSON 的 label / shortcut / checkable / workbench 过滤与 dispatcher 接线），而是外挂一个按同一份快照工作的刷新器：

```text
property("commandId") → CommandCatalog::menuIdForCommandId()
  → findByMenuId() → entry->enableRule
  → Cmd::evaluateEnableRule(rule, snapshot) → Cmd::setActionEnabled()
```

- 新增 `WorkbenchMenuManager::refreshCommandStates(const CommandUiSnapshot&)`；扇出点挂在 `Workbench2D::applySelectionContext()`，与属性面板/状态栏/场景树同一批。
- 抽出私有 `forEachCommandAction(visitor)` 统一遍历 QMenuBar + legacy 菜单指针，checked 同步（`refreshConfiguredMenuState`）与 enabled 同步共用同一份递归，避免两处覆盖范围漂移。
- `UiLayoutBuilder::bindAction` 对未注册命令的构建期禁用，现在额外打 `property("commandUnavailable", true)`；刷新器跳过这类项，不会把未实现的功能重新点亮。
- 规则为 `Always` 的条目也跳过：写 `setEnabled(true)` 无意义，且会与 `setAllMenusEnabled(false)` 这类全局置灰互相打架。
- `rebuildAllMenus()` 结尾调 `m_workbench->refreshCommandUiState()`。菜单重建产出全新 QAction，`enabled` 默认 true，不补这一下问题会在每次工作台切换 / 语言切换 / 配置重载后复现。为此 `UiWorkbench` 基类新增 `virtual void refreshCommandUiState()`（默认空实现），框架层无需知道是 2D 还是 3D。

**仍未覆盖**

- 无（`bindShortcuts()` 的窗口级 Undo/Redo 快捷键动作已于同日接入，见问题 11）

- 3D 菜单栏本就没这个问题：`CommandActionHub3D::bindEditMenu()` 把 Hub 的 QAction 直接 `addAction` 进菜单，菜单与工具栏是同一实例。2D 需要外挂刷新器的根因是菜单构建走了配置化路径而绕过了中枢。

### 问题 8：配置化右键菜单完全绕过启用规则

这一条是复盘问题 7 时发现的，之前的文档（包括本文早期版本）错误地把"视口右键菜单"记为已联动 —— 那只对**内建回退路径**成立。

`base.json:379` 已定义 `contextMenus["canvas.2d"]`，因此 `Workbench2D::onViewportContextMenu` 的配置分支恒命中并直接 `return`，其后那句吃快照的 `m_commandHub->populateContextMenu(&menu, snapshot, ...)` 实际是死代码。配置分支里 `snapshot` 只有 `hasSelection` 一个 bool 传下去且仅用于图层动态段；静态条目交给 `UiLayoutBuilder::buildContextMenu`，唯一的 `setEnabled` 判据是构建期的"命令是否注册"。这些 QAction 每次弹出新建、弹完 `delete`，既不在 `m_editActions` 里，也不在菜单栏的 `forEachCommandAction` 遍历范围内。

后果：空选或选中锁定图元时，右键菜单的 Cut / Copy / Delete / Paste 仍是亮的可点态，与同名工具栏按钮的灰显直接矛盾。这是当时唯一"用户可见地绕过禁用规则"的入口。

**实际修复**

把"按快照应用启用态到一棵外部 QAction 树"从 `WorkbenchMenuManager` 里提为命令中枢的静态 API，避免在第三个调用点再抄一遍：

- `CommandActionHub::applySnapshotToAction(QAction*, snapshot)` —— 单个动作，含 `commandUnavailable` 与 `Always` 两个跳过条件。
- `CommandActionHub::applySnapshotToMenu(QMenu*, snapshot)` —— 递归整棵菜单树。
- `WorkbenchMenuManager::refreshCommandStates` 改为只负责"遍历到哪些 action"，规则求值全部委托给上面的静态函数。
- `onViewportContextMenu` 在 `configured->exec()` 之前调 `applySnapshotToMenu(configured, snapshot)`。

顺带把 `edit.group` 的缺口一并补掉：切换类命令的 on/off 与启用语义抽成 `resolveToggleUiState(menuId, snapshot, isOnMode, enabled)`，`refreshToggleActionStates`（中枢托管动作）与 `applySnapshotToAction`（外部动作）共用它，不再各写一套 menuId 分支。

### 问题 9：右侧色块可以绕过锁定改动被锁图元

`RightToolBar` 是 `QPushButton` 色块，没有 QAction 也就没有 `enableRule`，且只订阅 `QtLayerManagerBridge` 的图层数据信号，完全脱离快照总线。而 `sigLayerSelected` 的 handler 会调 `layerEditService->assignEntitiesToLayer(selectedIds, ...)` —— 语义等价于 `edit.move_to_layer`（规则 `RequiresUnlockedSelection`），却没有任何锁定判定。点色块即可把被锁图元移到别的图层。

**实际修复**

不是把整条工具栏置灰 —— 同一个色块承担两件事，只有一件受锁定约束：

- 「移动选中图元到该图层」按 `m_commandHub->currentSnapshot().anyLocked()` 前置 gate。
- 「设为当前图层」不受锁定影响，始终执行。

### 问题 10：场景树锁图标滞后一拍

`SceneTreePanel2D::setCommandState` 原先只是纯赋值，两个标志仅在右键弹出时被读。树行的锁图标由 `SceneTreeBuilder2D` 在树重建时绘制，而图元级 `setLocked` 不改变图元数量，`onSceneTreeSceneChanged` 的计数守卫会把它挡掉 —— 结果是通过场景树右键锁定图元后，锁图标要等到下一次增删才出现。

**实际修复**

`setCommandState` 改为返回"锁定态是否翻转"，`applySelectionContext` 在翻转时 `m_sceneTreeRefreshTimer->start()`，复用已有的 150ms 去抖。只在真的翻转时排重建，避免每次选择变化都做 O(N) 重建。代价是在锁定/未锁定图元之间来回切选择时会多做几次重建，可接受。

### 问题 11：窗口级 Undo/Redo 快捷键不随撤销栈联动

`bindShortcuts()` 为 Ctrl+Z / Ctrl+Y 另建了两个 QAction 挂到 `m_window`（存在成员容器 `m_editShortcuts`）。它们不进任何菜单，`forEachCommandAction` 的菜单树遍历触达不到，`enabled` 恒为 true。无历史时按快捷键会 dispatch 到操作层空转 —— 无数据副作用，但属于"规则没生效"。

**实际修复**

两处小改，不引入新机制：

- `bindShortcuts()` 里给两个动作调 `setCmdId(action, "edit.undo" / "edit.redo")`，与菜单项使用同一个文件内 helper，从而携带 `property("commandId")`。
- `forEachCommandAction()` 在菜单树遍历之后追加一段遍历 `m_editShortcuts`，交给同一个 visitor。规则求值仍然是 `CommandActionHub::applySnapshotToAction`，无第二套判定。
- `bindShortcuts()` 结尾同样调 `m_workbench->refreshCommandUiState()`（与 `rebuildAllMenus()` 一致）：新建 QAction 的 `enabled` 默认 true，必须立即按当前快照校正。

`edit.undo` / `edit.redo` 的目录规则是 `RequiresUndo` / `RequiresRedo`，因此这两个快捷键现在与菜单栏、顶部工具栏的 Undo/Redo 按钮完全同步。

### 问题 12：切换工作台后菜单管理器仍指向上一个工作台

`WorkbenchWindow::triggerWorkbench` 换了 `m_workbench`，但 `WorkbenchMenuManager::m_workbench` 只在 bootstrap 注入过一次。该指针的三个消费者因此全部停留在旧工作台：`MenuDispatcher` 的派发目标（3D 下点菜单会执行 2D 操作）、`commandAvailable` 的 `isCommandRegistered()`（3D 独有项被判未注册）、`filterMenusForWorkbench` 的 `workbenchKind`。

`rebuildAllMenus(wbId)` 的 `wbId` 来自状态中心、一直正确，所以 2D 独有项不会视觉上漏进 3D —— 这个缺陷表现为"3D 项缺失 + 点了不生效"，而不是"2D 界面残留"，因此长期未被肉眼发现。

**实际修复**

切换序列里加步骤 6b（工厂解析出 `target`、赋给 `m_workbench` 之后立刻）：`m_menuManager->setWorkbench(m_workbench)`。

### 问题 13：3D 配置化菜单栏完全没有启用态刷新

2D 侧补齐 `refreshCommandStates` 后，3D 侧仍是空白：3D 由中枢直接建的菜单（`bindEditMenu` 等）与工具栏共用同一批 QAction，一次 `refreshFromSnapshot()` 就够；但走 `UiLayoutBuilder` 的那份配置化菜单栏同样绕过中枢，空选时 Delete / 布尔运算仍是亮态。

**实际修复**

与 2D 完全对称，仍共用 `Cmd::evaluateEnableRule`：

- `CommandActionHub3D::applySnapshotToAction/applySnapshotToMenu`（静态），链路是 `property("commandId")` → `CommandCatalog3D::operationForCommandId()` → `findByOperation()` → `enableRule`。
- 新增信号 `CommandActionHub3D::commandUiSnapshotRefreshed`，在 `refreshFromSnapshot()` 结尾 emit，`build3DWorkbenchUi` 订阅后转调 `WorkbenchMenuManager::refreshCommandStates3D(snapshot)`，复用同一个 `forEachCommandAction()`。
- 配套：`m_workbenchWindow` 上移到 `UiWorkbench` protected，`Workbench3D::attachToWindow` 赋值，`Workbench3D::refreshCommandUiState()` 转发给 `MainWindow3D`（否则 `rebuildAllMenus()` 结尾那次回调对 3D 是空实现）。

两侧应用器结构相同、识别依据相同，隔离完全依赖"各自目录解析不到对侧 id"。这条契约由 `CommandUiWiringTests.cpp` 的 `Switch_*` 用例锁定。

### 问题 14：切换时活着的对象里的累积与遗留

工作台不销毁、只 deactivate/reattach，因此残留来自"活对象里的状态"而非"没删的控件"：

- `Workbench2D` 每次 attach `new SceneMonitor(this)`，`deactivate()` 不释放 —— N 次往返 N 个监视器，一次场景变更触发 N 次刷新。现在 `deactivate()` 里 `deleteLater()` 并置空。
- `ToolBarContextManager` 的上下文跨切换保留（例如 `TextEditing`），回到 2D 时工具栏还是文字编辑态。现在 `deactivate()` 复位 `ToolBarContext::Default`。
- `Workbench3D::deactivate()` 解绑 renderWidget 前未判空 `sceneEditService`，补空指针保护。
