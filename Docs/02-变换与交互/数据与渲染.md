# 数据与渲染

## 1. 目标

本文件把“绘图交互”和“渲染联动”整理成一条顺序清楚的实施路径，重点回答三个问题：

- 先做什么
- 后做什么
- 每一步检查什么

当前阶段不先追求高级渲染优化，也不先扩展工艺、路径、硬件。当前目标只有一个：**让绘图结果稳定进入数据流，并稳定传到渲染层显示出来。**

---

## 2. 当前判断

现在渲染底座已经能用，核心渲染管线也已经稳定，但绘图交互和渲染联动还需要继续补顺。

当前更适合的策略不是“先把所有渲染做完，再做绘图交互”，而是：

```text
先把绘图交互打通
→ 再让数据流进入渲染链
→ 再补齐动态更新
→ 再补大量图元优化
```

这样不会把事情做反，也不会把时间提前花在不必要的渲染细节上。

---

## 3. 总流程

绘图交互和渲染联动的总流程建议按下面理解：

```
工具按钮
→ OperationBus
→ 绘图 / 编辑命令
→ 文档 / 场景数据变化
→ selection / preview 同步
→ SceneDocument2D
→ RenderViewport2D::updateSceneRender()
→ RenderWidget::submitSceneFromDataSource()
→ SceneManager::gatherGeometry(sink)
→ SceneGeometrySinkAdapter → C API
→ Renderx (SanYiRender.dll)
→ renderFrame() → GPU 绘制
→ 视口显示
```

这条链路应该尽量保持单线条、少分叉、少绕路。

#### 先做什么
- 确认左侧绘图按钮可以触发正确命令
- 确认顶部操作按钮可以触发正确命令
- 确认按钮触发后进入 `OperationBus`
- 确认命令来源和命令 ID 能正确记录

#### 要完成的内容
- 选择
- 直线
- 多段线
- 圆
- 圆弧
- 多边形
- 移动
- 旋转
- 删除
- 复制
- 镜像

#### 这一步检查什么
- 编译检查：按钮绑定代码能编译通过
- 测试检查：按钮触发后对应命令能进入测试链
- 日志检查：能看到按钮触发、命令进入、来源标识
- grep 检查：确认按钮入口没有旧路径、没有空工具条逻辑残留

## 5. 交互与渲染联动的核心原则

### 5.1 文档负责真相
文档 / 场景数据是真相源，不能由视口反向决定。

### 5.2 render data 负责转译
render data 负责把事实数据转成可绘制数据，不保存业务真相。

### 5.3 后端负责绘制
后端只负责把 render data 画出来，不负责修改文档。

### 5.4 视口负责显示
视口只负责承载输入和显示结果，不负责业务调度。

---

## 6. 动态更新策略

### 6.1 轻量更新
适用于：
- selection 切换
- preview 小范围变化
- 单个操作反馈

特点：
- 刷新范围小
- 响应快
- 不重建全量数据

### 6.2 增量更新
适用于：
- 单个图元修改
- 少量图元变化
- 局部重算

特点：
- 只更新变化部分
- 保留已有缓存
- 避免全量重绘

### 6.3 全量更新
适用于：
- 文档大范围变化
- 场景切换
- 首次加载
- 缓存失效严重时

特点：
- 成本高
- 但最稳
- 只在必要时使用

---

## 7. 大量图元时的处理策略

### 7.1 批次化
把相近的绘制对象组织成批次，减少重复提交。

### 7.2 缓存化
把不常变的数据缓存起来，减少重复编译。

### 7.3 视口裁剪
只绘制视口内可见内容，减少无效渲染。

### 7.4 局部失效
图元变化时只标记相关区域失效，不重置全部。

### 7.5 选择性重绘
selection / preview 等高频变化内容单独处理，不拖慢主图元绘制。

---

## 8. 当前必须避免的情况

- 绘图结果直接绕过文档进渲染层
- 视口自己维护数据真相
- 每次变更都做全量重绘
- 预览和提交共用一份最终状态
- 大量图元时还采用同一套无差别刷新
- 工艺、路径、硬件提前混入当前主链

---

## 9. 检查方式

### 编译检查
确认绘图交互、数据更新、渲染联动相关代码能正常编译。

### 测试检查
确认以下链路都能跑通：
- 按钮触发
- 绘图模式
- 预览
- 提交
- 取消
- selection 刷新
- render data 更新
- 大量图元更新

### 日志检查
确认关键流程能看见：
- 命令进入
- 状态变化
- render data 更新
- 渲染提交
- 局部更新
- 全量更新

### grep 检查
搜索旧图元、旧桥接、旧刷新入口、旧渲染路径，确认没有回流。

---

## 10. 最终结论

绘图交互和渲染联动应该按"先交互、后联动、再优化"的顺序推进。

最稳妥的路线是：

1. 先把绘图主链打通
2. 再把数据流接进渲染链
3. 再补动态更新
4. 最后补大量图元性能处理

这样最符合当前阶段，也最符合现有代码状态。
