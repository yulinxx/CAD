# 绘图交互

## 1. 目标

本文件只讨论当前软件里最紧急的一件事：把绘图交互先做顺、做稳、做可用。

当前阶段先不推进工艺、路径、仿真、任务、硬件，也不扩展更大的业务体系。当前优先级只有一个：**绘图先能正常工作**。

---

## 2. 当前问题

当前软件最核心的问题不是业务能力，而是基础绘图交互还没有完全顺起来，导致用户无法顺畅完成最基本的绘图操作。

现阶段需要重点解决的内容包括：

- 绘图工具是否能正常触发
- 绘图模式是否能正确进入
- 视口是否能正确显示预览
- selection 是否能正确同步
- 提交后是否能正确刷新
- 顶部工具栏和左侧工具栏职责是否清楚

---

## 3. 当前主线

绘图交互的主线应当保持清晰一致：

```text
工具按钮
→ OperationBus / CommandDispatcher
→ 绘图 / 编辑命令
→ 文档 / 场景状态变化
→ selection / preview 同步
→ ViewWidgetAdapter 刷新
→ 视口显示
```

这条链路必须稳定，不允许再出现多个分叉入口或临时绕行路径。

## 3.1 2D 绘图 与 `SyEntity` 的完整关系图

下面这张图是当前最推荐的理解方式：`2D 绘图` 负责“怎么画、怎么交互”，`SyEntity` 负责“画出来的东西是什么”。

```text
用户操作
  ↓
2D 绘图界面 / 工具栏 / 快捷键
  ↓
OperationBus / CommandDispatcher
  ↓
具体绘图命令（Line / Circle / Arc / Polyline / Polygon / Bezier / NURBS / SmartLine）
  ↓
临时交互状态（采点、预览、回退、取消、确认）
  ↓
实体生成 / 更新
  ↓
SyEntity（图元数据模型）
  ├─ SyLine
  ├─ SyCircle
  ├─ SyArc
  ├─ SyPolygon
  ├─ SyBezier2
  ├─ SyBezier
  ├─ SyNurbs
  └─ SySmartLine
  ↓
SceneDocument / Document2D
  ↓
selection / undo-redo / 快照管理
  ↓
渲染层读取图元
  ↓
视口显示结果
```

### 3.1.1 这条链路里每一层分别做什么

| 层级 | 职责 | 是否应该保存临时交互状态 |
|---|---|---|
| `2D 绘图界面` | 接收点击、拖拽、快捷键、工具切换 | 否 |
| `CommandDispatcher` | 分发命令、切换当前绘图工具 | 否 |
| `绘图命令` | 采集输入、组织预览、决定提交或取消 | 是 |
| `SyEntity` | 保存最终图元几何与必要属性 | 否 |
| `Document / Scene` | 管理图元生命周期、事务、选中状态、快照 | 否 |
| `Undo/Redo` | 恢复已提交状态 | 否 |
| `Render` | 按图元数据绘制 | 否 |

### 3.1.2 现在和未来的关系判断

- **现在**：有些入口已经接上 `SyEntity`，有些还在收口中
- **以后**：绘图功能越完整，和 `SyEntity` 的关联会越强
- **最终**：绘图命令几乎都会以某种形式落到 `SyEntity`，然后再由文档和渲染层接管

### 3.1.3 一个最直观的例子

以画线为例，完整路径一般是：

```text
点击“直线”
→ 命令开始采点
→ 鼠标第一次点击记录起点
→ 鼠标第二次点击记录终点
→ 生成 `SyLine`
→ 写入文档
→ 渲染层读取 `SyLine`
→ 视口显示线段
```

这说明 `2D 绘图` 不是和 `SyEntity` 平行的两套系统，而是**上层交互**与**下层图元模型**的关系。

### 3.1.4 图元 ID 的分配：持久 ID 与临时 ID

每个 `SyEntity` 在构造时会通过 `EntityIdGenerator` 获得一个唯一 ID。早期实现里，**任何**图元构造都会从全局生成器拿一个“持久 ID”，导致绘制过程中的预览/中间图元大量消耗 ID，用户连续画两个图形时，两个图形的 ID 会相差很多。

现在把 ID 分成两类，彻底解决预览导致的 ID 浪费：

| 类型 | 取值范围 | 何时分配 | 说明 |
|---|---|---|---|
| 持久 ID | 正数（1, 2, 3, …） | 图元**真正进入场景**时 | 保证连续紧凑，只给落地的图元 |
| 临时 ID | 负数（-1, -2, …） | 绘制/预览过程中的中间图元 | 永不与持久 ID 冲突，不占用持久计数 |

**工作机制：**

1. `EntityIdGenerator` 维护两个原子计数器：`m_nextId`（持久，从 1 递增）与 `m_transientNextId`（临时，从 -1 递减）。
   - `getNextId()`：**感知当前线程的临时作用域**——作用域内返回临时 ID，作用域外返回持久 ID。
   - `getNextPersistentId()`：始终返回持久 ID。
   - `getNextTransientId()`：始终返回临时 ID。
   - `isTransient(id)`：`id < 0` 即为临时 ID。
2. 工具激活期间（`ToolManager::setActiveTool`）自动进入“临时作用域”，绘制/预览过程中构造的所有中间图元（如 SmartLine 的段、预览曲线、`clone()` 等）都只拿临时 ID，不再消耗持久计数。
3. 图元进入场景时统一“转正”：`SceneManager::insertEntityPreserveId` / `insertEntitiesPreserveId` / `addEntity` 在插入前，若发现 `isTransient(id)`，则调用 `getNextPersistentId()` 换成连续的正 ID。

**必须使用持久 ID 的导入/归属路径**（显式调用 `getNextPersistentId()`，避免在临时作用域内拿到负数 ID）：

- `SceneManager::addEntity(const SyEntity*)` / `addEntities(...)`（克隆后入库，不走 insertEntityPreserveId）
- `SceneEditService::addEntities()`（导入图元分配新 ID）
- `PyBindCore::SceneGateway`（Python 侧创建图元）
- `SyGroup` 构造（群组直接按 ID 存入 `GroupManager::m_groups`，不走场景插入转换）

**为什么要这样做：**

- 连续绘制多个图形时，落地图元的持久 ID 保持连续（1、2、3…），调试、持久化、跨 DLL 传 ID 更直观。
- 预览/中间图元数量巨大也不会影响持久 ID 计数。
- 负 ID 与正 ID 天然隔离，永远不会冲突，也无需回填“被预览占掉的 ID”。

## 4. 界面职责划分

### 4.1 左侧工具栏
左侧工具栏只放“选择 / 绘图工具”，属于“创建或进入绘图状态”的入口。

建议内容：
- 选择
- 直线
- 多段线
- 圆
- 圆弧
- 多边形
- NURBS 曲线
- 二阶贝塞尔曲线
- 三阶贝塞尔曲线
- SmartLine

### 4.2 顶部工具栏
顶部工具栏只放“图元操作工具”，属于“处理已有图形”的入口，不包含绘图工具。

建议内容：
- 移动
- 旋转
- 删除
- 复制
- 镜像
- 编辑
- 其他针对已存在图元的操作

### 4.3 视口
视口只负责：
- 接收输入
- 显示预览
- 显示结果
- 触发重绘

视口不应继续承担业务调度中心的职责。

### 4.4 绘图工具与快捷键的统一约定
为了让交互更顺，绘图工具需要统一以下键鼠约定：
- `Ctrl + 滚轮`：调整绘图参数（如多边形边数、NURBS 权重等）
- `双击 / 空格 / Enter`：确定当前绘图
- `Backspace / Delete`：回退当前绘图的最后一步临时输入，不参与 `Undo / Redo`
- `右键 / Esc`：取消当前正在绘制的图元
- `右键 / Esc` 且当前还没有开始绘制：取消当前绘图工具并切换回选择工具

### 4.5 键鼠约定表

| 按键 / 操作 | 适用对象 | 语义 | 是否影响 Undo/Redo |
|---|---|---|---|
| `Ctrl + 滚轮` | NURBS / Polygon 等带参数工具 | 调整当前绘图参数 | 否 |
| `Backspace` | 所有绘图命令 | 删除当前命令的最后一步临时输入 | 否 |
| `Delete` | 所有绘图命令 | 删除当前命令的最后一步临时输入（与 Backspace 等价） | 否 |
| `Enter` | 所有绘图命令 | 确认当前绘制 | 是（确认后提交才进入 Undo/Redo） |
| `空格` | 所有绘图命令 | 确认当前绘制 | 是（确认后提交才进入 Undo/Redo） |
| `双击` | 折线 / 多点输入类绘图命令 | 结束当前绘制并提交 | 是（提交后才进入 Undo/Redo） |
| `右键` | 所有绘图命令 | 取消当前图元或结束当前工具 | 否 |
| `Esc` | 所有绘图命令 | 取消当前图元；若尚未开始输入则退出工具并回到选择 | 否 |

### 4.6 不允许的混淆
- `Backspace` 不能被当成 `Undo`
- `Esc` 不能被当成 `Redo`
- `双击` 不能替代 `Backspace`
- `Enter` 和 `空格` 都只能做“确认”，不能做“回退”
- 已提交图元的撤销只能走 `Undo/Redo`，不能走 `Backspace`

该约定优先于局部工具实现，所有绘图命令都应该遵守。

## 5. 绘图交互必须满足的能力

### 5.1 选择
- 能进入选择模式
- 能正确高亮已选对象
- 能正确切换到其他工具

### 5.2 直线 / 多段线
- 能进入绘制状态
- 能正确采集点位
- 能显示预览
- 能提交成正式图形
- 能取消并回滚

### 5.3 圆 / 圆弧 / 多边形
- 能正确进入对应工具模式
- 能显示实时预览
- 能正确提交结果
- 能正确取消并回滚

### 5.4 NURBS 曲线 / 贝塞尔曲线 / SmartLine
- 能正确进入对应工具模式
- 能按点位采集控制点 / 端点 / 权重 / 参数
- 能显示实时预览
- 能提交成正式图形
- 能取消并回滚
- 能在选择、变换、undo/redo 中保持语义一致
- 绘制过程中支持回退（Backspace / 撤销最后一个点），删除最近采集的一点后继续绘制

### 5.5 绘制过程中的回退能力
- 多段线绘制时，支持回退删除最近一个顶点
- 圆弧绘制时，支持回退删除最近一个阶段输入点
- NURBS / 贝塞尔 / SmartLine 绘制时，支持回退删除最近一个控制点或采样点
- 回退只作用于当前命令的临时输入，不应删除文档中已提交的正式图元
- 回退后预览必须立即刷新，状态栏必须同步更新
- 回退行为必须与 Esc 取消区分：Backspace 是删最后一步，Esc 是取消整个命令
- Backspace 只影响当前命令的临时输入栈，不参与 Undo / Redo 命令栈

### 5.6 命令与图元的类设计原则
- 每种图元应有独立命令类，不要把不同图元塞进同一个大类里统一分支处理
- 每种图元应有独立图元类或明确的图元语义模型
- 命令类只负责输入、预览、提交、撤销，不负责渲染细节
- 渲染层只负责显示图元，不负责命令状态机
- 文档层只负责保存图元事实，不负责临时预览状态
- 低耦合、高聚合，避免一个类同时处理多个图元的全部分支
- 能支持 `Ctrl + 滚轮` 调整图元参数（例如 NURBS 权重、控制参数等）

### 5.5 通用绘图确认与取消
- 双击 / 空格 / Enter 可确认当前绘图
- 右键 / Esc 可取消当前正在绘制的图元
- 当当前工具处于“已激活但尚未开始绘制”的状态时，右键 / Esc 应退出该工具并回到选择工具

### 5.5 编辑操作
- 移动、旋转、删除、复制、镜像等操作能正确触发
- 操作命令和按钮名称一致
- 操作结果能正确刷新到视口

## 6. 推荐实现顺序

### 第一步：先让按钮能真正触发命令
确认工具栏按钮和 `OperationBus` / `CommandDispatcher` 的对应关系是通的。

### 第二步：再让命令进入正确的绘图模式
确认命令进入后，绘图工具状态不会乱跳。

### 第三步：再让视口能显示预览
确认鼠标输入和预览链路正常。

### 第四步：再让提交 / 取消稳定
确认提交后能刷新，取消后能回滚。

### 第五步：再整理交互体验
把重复入口、空工具条、职责混乱的问题清掉。

## 7. 关键依赖

绘图交互涉及的核心组件应保持分工清楚：

- `WorkbenchWindow`：负责工具栏和窗口级入口
- `OperationBus`：负责统一命令调度
- `IInteractionDispatcher`：负责 UI 命令生命周期和工具切换
- `ViewWidgetAdapter`：负责 selection 同步和刷新
- `SceneEditServiceAdapter`：负责预览、提交、取消
- `Viewport2D`：负责视口事件和显示
- `MouseInteractionAdapter`：负责鼠标输入转化
- `TransformDialogAdapter`：负责对话框输入转化

---

## 8. 当前必须避免的情况

- 左侧和顶部工具栏都放同类功能
- 空工具条继续存在
- 绘图按钮只是摆设，没有实际命令入口
- 视口自己兼任业务调度
- 选择、预览、提交、取消各走各的
- 工艺、路径、硬件提前介入当前主线
- 新图形类型只接了按钮，没有接入预览、提交、undo/redo、渲染刷新

## 11. 左侧工具栏交互总表

下面是当前左侧工具栏每个按钮应该走的流程、当前风险点，以及你接下来按文档应该怎么做。

### 11.1 Select

#### 期望流程
```text
点击 Select
→ Dispatcher.execute("2d.select")
→ SelectCommand.activate()
→ 鼠标点击/框选
→ selection 更新
→ 视口刷新
```

#### 当前风险点
- 命令系统和旧 hit test 还可能并存
- 框选与精确点选边界不一定一致
- selection 刷新可能不统一
- `Esc` / 右键 的退出行为可能仍与绘图工具冲突

#### 接下来怎么做
- 确认 SelectCommand 是唯一主入口
- 清掉 Viewport2D 里对选择的旧分支
- 确认点选与框选都走统一 selection 更新
- 确认选中后一定触发视口刷新
- 确认绘图取消后回到选择工具的行为统一

### 16.0 RenderViewport2D 绘图工具无法工作修复

**问题**：在 2D 模式下，使用左侧工具栏的 Arc、Circle、Line 等绘图工具无法绘制图元。

**根因分析**：经过完整的流程梳理，定位到以下问题：

1. **BUG#1（致命）**：交互式工具命令在通过 `OperationBus` 路由后，**无条件立即调用 `submit()`**。`submit()` 清空活动命令 ID，导致 `hasActiveCommand()` 返回 `false`，`RenderViewport2D` 不再转发鼠标事件给绘图命令处理器。

### 17.0 根因修复：OperationBus 双重注册覆盖 + RenderWidget 鼠标事件拦截

```text
  → OperationBus::run(Tool_Line)
  → begin("2d.draw_line")                          ← 设置活动命令 ID
  → ToolSwitchOperation::execute()                  ← ❌ 被覆盖！不是 CommandHandlerAdapter！
  → ctx.viewWidget->setActiveTool("LineTool")       ← 在 MainWindow 的 ViewWidget 上切换工具
  → DrawLineCommand::activate() 永远不会被调用     ← ❌ 命令处理器从未激活
  → 鼠标点击视口时，forwardMouseDown() 找不到 handler
```

**根因 B：`RenderWidget` (QOpenGLWidget) 拦截鼠标事件**

`RenderWidget` 是 `QOpenGLWidget`（原生窗口），鼠标事件直接发送给 `RenderWidget`，**不会冒泡到父控件 `RenderViewport2D`**。因此 `RenderViewport2D::mousePressEvent()` 永远不会被调用，所有鼠标事件在源头被截断。

**修复**：

| 文件 | 修改内容 |
|------|----------|
| `UI/Common/Include/UI/Command/OperationRegistryBase.h` | `registerOperation()` 改用 `try_emplace()` 替代 `operator[]`，防止后注册的 `ToolSwitchOperation` 覆盖先注册的 `CommandHandlerAdapter` |
| `UI/2D/Src/Operation/OperationRegistry.cpp` | 重复注册时改为跳过（`return`）并记录 info 日志，而非覆盖并 warning |
| `Main/Src/UI/RenderViewport2D.h` | 添加 `eventFilter()` 重写声明 |
| `Main/Src/UI/RenderViewport2D.cpp` | `initRenderWidget()` 中 `m_renderWidget->installEventFilter(this)`；实现 `eventFilter()` 将 RenderWidget 上的鼠标/滚轮/键盘/右键菜单事件转发到 RenderViewport2D 对应处理方法 |

**修复后的完整链路**：

```text
用户点击 Line 按钮
  → OperationBus::run(Tool_Line)
  → begin("2d.draw_line")                          ← 设置活动命令 ID
  → CommandHandlerAdapter::execute()               ← ✅ 不再被覆盖
  → DrawLineCommand::activate(services)            ← ✅ 命令处理器激活
  → [不立即 submit()，保持 hasActiveCommand()=true]
  → 用户鼠标点击 RenderWidget
  → eventFilter() 转发到 RenderViewport2D::mousePressEvent()  ← ✅ 事件过滤器
  → hasActiveCommand() == true
  → IInteractionDispatcher::forwardMouseDown()
  → currentHandler() → DrawLineCommand::onMouseDown(x, y)    ← ✅ 处理器接收事件
  → 第1击：记录起点
  → 第2击：记录终点，m_document->createLine()
  → SceneManager::addEntity() → notifySceneChanged() → 视口刷新
  → isComplete() == true → submit() → m_activeCommandId 清空
```

## 18. DXF 导入与渲染链路修复（2026-07-17）

### 18.0 问题概述

经过深入追踪两条完整链路（绘制→渲染 和 DXF导入→渲染），发现了以下问题：

| 优先级 | 问题 | 影响 |
|--------|------|------|
| P0 | DXF 导入颜色丢失 | 所有导入图元渲染为黑色 |
| P0 | DXF 导入绕过 SceneEditService | 无法撤销，无图层分配 |
| P1 | 预览颜色硬编码为蓝色 | 绘图工具预览颜色不正确 |
| P2 | 导入嵌套 batch 调用 | 结构不清晰 |
| P2 | 导入图元双重 clone | 内存开销大 |

### 18.1 修复详情

#### 18.1.1 P0-1: DXF 颜色丢失

**根因**：`DxfConverter::applyEntityStyle()` 将 DXF 颜色索引存入 `m_entityColorMap`，但从未设置到图元上。`SyEntity::getColor()` 返回 `pLayer->getColor()`，导入图元 `pLayer` 为 `nullptr`，渲染为黑色。

**修复**：
- `FileIOError.h`：`ParseResult` 添加 `entityColorMap` 字段
- `DxfParser.cpp`：`parse()` 中填充 `result.entityColorMap`
- `SyEntity.h`：添加 `m_overrideColor` (std::optional) + `setOverrideColor()`/`clearOverrideColor()`
- `SyEntity.cpp`：`getColor()` 优先返回 `m_overrideColor`
- `ApplicationCompositionRoot.cpp`：导入后应用 `entityColorMap` 到图元

#### 18.1.2 P0-2: DXF 导入无 Undo

**根因**：导入 lambda 直接调用 `scene->addEntities(rawPtrs)` 绕过 `SceneEditService`。

**修复**：
- 改用 `SceneEditService::addEntities(std::move(imported), "Import")`，支持 Undo/Redo
- 同时修复了双重 clone 问题（原代码 clone 两次）

#### 18.1.3 P1-1: 预览颜色硬编码

**根因**：`RenderWidget::applyOverlayUpdate()` 中预览线始终使用 `0xFF3333FF`（蓝色），忽略 `overlayUpdate.drawingColor`。

**修复**：当 `hasDrawingColor` 为 true 时，将 `drawingColor` 转换为 RGBA 并传递给 `renderSetPreviewLines`。

#### 18.1.4 P2-1: 嵌套 batch 调用

**根因**：导入 lambda 中 `scene->beginBatchUpdate()`/`endBatchUpdate()` 与 `addEntities` 内部 batch 嵌套。

**修复**：移除外层手动 batch 调用（`SceneEditService::addEntities` + `SceneNotifier` 已正确管理 batch）。

#### 18.1.5 P2-2: 导入图元 ID 为 0 问题

**根因**：DxfConverter 创建的图元 ID 均为 0，`insertEntitiesPreserveId` 检测到重复 ID 后跳过，导致只有第一个图元被添加。

**修复**：`SceneEditService::addEntities()` 中为 ID=0 或重复 ID 的图元自动分配新 ID。

### 19.5 绘图流程中的冗余环节与优化建议

从“工具栏点击 → 画出图元 → 刷新视图”这条主路径来看，当前链路可以正常工作，但确实偏长，主要原因不是功能不成立，而是中间层较多、职责切分较细。若只看高频的绘图场景，以下几个环节属于可简化或可进一步优化的部分。

#### 冗余或可收敛的环节

- **步骤 3-5：`OperationBus` 中间层**
  - 问题：工具激活本质上只是一次简单的状态切换，目前并没有撤销/重做语义。
  - 现状：`LambdaOperation` 只是包了一层 lambda，却仍然要经过 `OperationBus::runImpl()` 和 `OperationRegistry::get()` 两层分发。
  - 建议：如果后续不需要把“切换工具”纳入统一操作体系，可以让工具栏直接持有 `ToolManager*` 或等价的轻量控制入口，直接切换当前工具，跳过 `OperationBus`。

- **步骤 13-14：`SceneEditService` 封装**
  - 问题：`SceneEditService` 会先检查 `UndoRedoManager`，再创建 `AddEntitiesCommand`，最后交给 `SceneManager`。
  - 现状：`addEntityFromPointer(..., "Draw")` 这类调用已经带有明确的绘图语义，但是否真的需要完整撤销链路，取决于产品定义。
  - 建议：如果绘图操作明确需要撤销/重做，保留这层封装是合理的；如果只是简单的数据落场，可以考虑直接调用 `SceneManager` 或抽出更轻的“直接提交”路径。

- **步骤 15-16：双重通知链**
  - 问题：`SceneNotifier::notifySceneChanged()` → `RenderViewport2D::onSceneChanged()` → `scheduleSceneUpdate()` 看起来多了一层调度。
  - 现状：这层结构有利于统一事件通知，也方便批量添加时延迟刷新。
  - 建议：这部分不建议简单删除，更适合保留为“场景变更通知层”，只是在实现上避免无意义的重复触发。

#### 性能瓶颈

- **步骤 17：`submitSceneFromDataSource()` 全量提交**
  - 问题：每次图元创建都会走一次全量 gather，再把整份场景提交给渲染器。
  - 现状：文档里也已经标注了 TODO——当 `RenderWidget` 支持 `updateEntity()` / `addEntity()` 时，可以逐个做增量更新。
  - 建议：尽量尽快补上增量更新接口，避免每次都重新提交整棵场景树；这是当前最明显的性能优化点。

#### 必要且建议保留的环节

- **步骤 6：`findActiveViewport2D()`**
  - 虽然多了一层查找，但它支持多视口场景，属于合理抽象。
- **步骤 9-10：事件分发**
  - 视口把鼠标事件转发给当前工具，是工具系统成立的基础，必要。
- **步骤 12：`emitEntity`**
  - 工具与场景解耦的接口，必要。
- **步骤 15：`SceneNotifier`**
  - 观察者模式，支持多视图同步，必要。

#### 小结

如果目标是“先把系统跑起来”，现在这条链路是可接受的；如果目标是“让绘图更轻、更快、更容易维护”，优先级最高的优化顺序建议是：

1. 先收敛工具激活链路，减少 `OperationBus` 的转发层。
2. 再评估 `SceneEditService` 是否需要对所有绘图动作都强制走撤销命令。
3. 最后补齐 `RenderWidget` 的增量更新能力，把全量提交改成增量提交。

### 19.6 增量渲染实现（2026-07-28）

#### 19.6.1 设计目标

用增量渲染替代全场景提交，当图元创建/修改/删除时，只提交变化的图元到渲染引擎，避免每次都 gather 整个场景。

#### 19.6.2 渲染引擎图元管理 API

底层渲染引擎提供三个持久化图元管理函数（基于唯一 ID）：

```cpp
// 新增图元（首次提交）
renderAddEntity(RenderDevice* dev, EntityId id,
    const VertexP3C3* vertices, uint32_t vertexCount,
    PrimitiveType type, uint16_t materialIdx);

// 修改已有图元（更新顶点数据）
renderModifyEntity(RenderDevice* dev, EntityId id,
    const VertexP3C3* vertices, uint32_t vertexCount,
    uint16_t materialIdx);

// 删除图元
renderRemoveEntity(RenderDevice* dev, EntityId id);
```

#### 19.6.3 RenderWidget 增量接口封装

`RenderWidget` 对上提供简洁的增量接口，隐藏渲染引擎细节：

```cpp
void addRenderEntity(uint64_t entityId,
    const render::VertexP3C3* vertices, uint32_t vertexCount,
    render::PrimitiveType type, uint16_t materialIdx = 0);

void modifyRenderEntity(uint64_t entityId,
    const render::VertexP3C3* vertices, uint32_t vertexCount,
    uint16_t materialIdx = 0);

void removeRenderEntity(uint64_t entityId);
```

#### 19.6.4 RenderViewport2D 增量提交流程

```text
SceneNotifier::notifySceneChanged()
  ↓
RenderViewport2D::onSceneChanged(changedIds, deletedIds)
  ↓
标记 m_pendingDirtyIds / m_pendingDeletedIds
  ↓
scheduleSceneUpdate() → updateSceneRender()
  ↓
[RefreshLevel::LightUpdate 路径]
  ├─ 处理删除的图元 → removeRenderEntity(id)
  ├─ 处理脏图元：
  │    ├─ 已渲染过 → entityToVertices() → modifyRenderEntity(id, vertices)
  │    └─ 首次渲染 → entityToVertices() → addRenderEntity(id, vertices, type)
  ├─ 提交网格背景 → submitDefaultSceneEnv()
  └─ 请求重绘 → update()
```

#### 19.6.5 图元 → 顶点转换

`entityToVertices()` 函数将各种引擎图元类型转换为渲染用的 `VertexP3C3` 顶点数组和 `PrimitiveType`：

| 图元类型 | 转换方式 | 图元类型 |
|---------|---------|---------|
| `SyLine` | 直接取两点 | `LINE` |
| `SyCircle` | 按分段数 tessellation | `LINE_STRIP` |
| `SyArc` | 按角度范围 tessellation | `LINE_STRIP` |
| `SyEllipse` | 按分段数 tessellation | `LINE_STRIP` |
| `SyBezier2` | 递归细分 + 直线段 | `LINE_STRIP` |
| `SyBezier` | 三次贝塞尔采样 | `LINE_STRIP` |
| `SyNurbs` | NURBS 采样 | `LINE_STRIP` |
| `SySmartLine` | 直线 + 箭头 | `LINES` |
| `SyPolygon` | 顶点直接转换 | `LINE_LOOP` |
| `SyPoint` | 单点 | `POINTS` |
| `SyImage` | 四角顶点 | `TRIANGLE_FAN` |
| `SyText` | 跳过（暂不支持） | - |

#### 19.6.6 状态跟踪

- `m_renderedEntityIds` (unordered_set<uint64_t>)：记录已提交到渲染系统的图元 ID，用于区分"新增"vs"修改"
- `m_pendingDirtyIds`：待处理的脏图元 ID（新增或修改）
- `m_pendingDeletedIds`：待处理的删除图元 ID

#### 19.6.7 全量 vs 增量路径选择

`RefreshLevel` 枚举控制刷新粒度：

| Level | 行为 | 使用场景 |

## 20. 图层链路修复（2026-08-14）

### 20.0 问题概述

两个环节的图层语义此前未接上：

| 优先级 | 问题 | 影响 |
|--------|------|------|
| P0 | `addEntityFromPointer` 不分配当前图层 | 绘制的图元无 `pLayer`，渲染颜色不正确 |
| P0 | DXF 导入不还原源文件图层 | 导入图元全部落到当前图层，图层结构丢失 |

### 20.1 修复详情

#### 20.1.1 绘制 → 当前图层

**修复**：`addEntityFromPointer` 在场景插入后调用 `m_layerManager->assignEntityToCurrentLayer(added)`，与 `addEntity` / `addEntities` 保持一致的图层语义，并补充日志。

**调用方**：`Workbench2D` 连接 `entitySubmitRequested` → `addEntityFromPointer(e, "Draw")`；`ToolManager` 回退路径同源。

**修复**（数据链路：解析 → IR → 转换 → 导入服务 → LayerManager）：

- `FileIO/DxfParser.cpp`：`parseToIR` 末尾按图层名匹配 `converter.getEntityLayerMap()`，填充 `EntityInfo.layerSourceId`

- `ImportResult`：新增 `importedLayers`（源图层表）与 `entityLayerMap`（图元归属映射）字段
- `DxfImportReader`：提取图层表 + 图元图层映射填入 `ImportResult`
- `ImportService`：注入 `LayerManager`；`phaseBuildDocument` 增加 `parseResult` 参数（同步/异步路径均传递）；新增 `restoreImportedLayers`——按名创建/复用图层（复制颜色/可见/锁定），再 `applyEntityLayerMap` 归属图元
- `LayerManager`：新增 `findLayerByName`（未找到返回 -1，用于按名去重）
- `ApplicationCompositionRoot`：`setupImportExportServices` 中 `m_importService->setLayerManager(m_layerManager.get())`

**还原语义**：
- 仅 DXF IR 路径还原图层；legacy 回退路径无图层表，保留原行为并加日志说明
- `preserveLayers=false` 时跳过还原（图元保持在当前图层）

## 21. 交互链路修复（2026-08-14）

### 21.0 问题概述

对 §4.4/§4.5 键鼠约定做逐条核对时，发现两条与文档不符：

| 优先级 | 问题 | 影响 |
|--------|------|------|
| P1 | 右键事件在 `ViewportInputRouter::dispatchMousePressToInput` 中被过滤（仅 `LeftButton` 分发给活动工具） | 右键“取消当前图元 / 退出工具”永远不生效，与 §4.4/§4.5 文档不符 |
| P2 | `BaseTool::onKeyPress` 的回退键只认 `Backspace`/`Ctrl+Z`，不含 `Delete` | §4.5 表中已约定“删除当前命令的最后一步临时输入”，`Delete` 键应等价支持 |

### 21.1 修复详情

#### 21.1.1 右键分发接线

**根因**：`dispatchMousePressToInput` 顶部直接 `if (event->button() != Qt::LeftButton || m_panModeEnabled) return false;`，右键在到达 `BaseTool::onMousePress` 之前就被丢弃；`handleContextMenu` 仅取消交互分发器，不处理工具。

**修复**：`ViewportInputRouter::dispatchMousePressToInput` 对 `RightButton` 单独走 `dispatchRightButtonPressToInput`：

- 交互分发器有活跃命令 → 作为取消该命令处理
- 活动工具 `onMousePress` 返回 true（绘制态右键取消当前图元）→ 消费事件
- 空闲态且活动工具非 `SelectTool` → `cancelCurrentTool()` + 走 `OperationBus::Tool_Select` 切回选择工具，与 §4.4「右键 / Esc 且当前还没有开始绘制：取消当前绘图工具并切换回选择工具」一致
- 空闲态 `SelectTool` → 不消费，保留给右键菜单/后续处理

#### 21.1.2 Delete 键回退

**根因**：`BaseTool::onKeyPress` 的 `stepBackKey` 仅含 `Backspace` 与 `Ctrl+Z`。

**修复**：`stepBackKey` 增加 `Qt::Key_Delete`，使 `Delete` 与 `Backspace` 等价回退最后一步临时输入（仅绘制态生效，空闲态由上层 `handleDeleteKeyPress` 删除选中图元，行为不变）。

## 22. DXF 图层颜色不显示修复（2026-08-16）

### 22.0 问题概述

导入 DXF 后，图层已解析出名称与颜色（图层表可见），但场景中图元不显示对应颜色。

### 22.1 根因

DXF/SVG 解析器给图层分配的 `IrLayerInfo.sourceId` 从 **0** 开始，而 `EntityInfo.layerSourceId` 的「0 = 无图层」哨兵语义在 `FioEntityConverter::convertAll` 中被过滤（`if (layerSourceId != 0)`）。因此首个图层（DXF 中即默认图层 "0"，绝大多数图元都位于其上）的所有图元被从 `entityLayerMap` 剔除 → `restoreImportedLayers` 虽创建了带颜色的图层，但图元未被重新归属，停留在当前图层（默认黑色），故场景无颜色。

legacy 路径 `FileImporter` 已使用 1-based（`size() + 1`），仅 IR 路径存在 0/1 冲突。

### 22.2 修复

| 文件 | 修改内容 |
|------|----------|
| `FileIO/FileIO/Src/Parsers/DxfParser.cpp` | `parseToIR` 中 `IrLayerInfo.sourceId` 改为 `s_layers.size() + 1`（1-based，0 保留为「无图层」哨兵） |
| `FileIO/FileIO/Src/Parsers/SvgParser.cpp` | `getOrCreateLayer` 中 `sourceId` 改为 `m_outLayers.size() + 1`（同样 1-based） |

这样图层表 `sourceId` 与图元 `layerSourceId` 均 ≥ 1，`convertAll` 的 `!= 0` 过滤不再误伤首个图层图元，`restoreImportedLayers` 可正确把图元归属到带颜色的源图层。

### 22.3 验证

- 新增回归测试 `ImportExportRegressionTest.IrPipeline_RealDxf_FirstLayerSourceIdIsOneBased`：构造含 `TABLES/LAYER "0"` 的最小 DXF，断言 `sourceId != 0` 且 `convertAll` 产出的 `entityLayerMap` 包含该图层图元（sourceId 与图层表一致）
- `MainTests.exe`：全量 713 通过（1 跳过：`SimpleRenderer3DTest.Render` 无 GUI 上下文，既有行为）

## 23. 图层累积治理：去重 / 上限 / 多选删除 / 性能（2026-08-16）

### 23.0 需求背景

反复导入不同 DXF 后，右侧图层列表不断累积图层。要求：
1. 若两个图层的颜色相同，应共用一个图层（导入时按色去重）；
2. 软件应限定图层数量上限，避免超大量图层导致界面/性能异常；
3. 图层管理对话框支持多选删除等列表操作；
4. 大量图层下列表重建与右侧色块重建需做性能优化。

### 23.1 修复

| 文件 | 修改内容 |
|------|----------|
| `Engine/2D/Include/Engine2D/Interaction/LayerManager.h` | 新增 `kMaxLayerCount = 256` 上限常量与 `maxLayerCount()`；新增 `getLayerEntityCounts()`（单趟 O(N) 统计各图层图元数） |
