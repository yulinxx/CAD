# 菜单工具栏交互文档

## 1. 当前架构

当前菜单和工具栏都围绕统一命令目录展开：

- 2D 使用 `CommandCatalog`
- 3D 使用 `CommandCatalog3D`
- 2D 的菜单、左侧绘图栏、导入入口都从同一份 UI 元数据视图构建
- UI 构建层通过 `WorkbenchMenuManager`、`WorkbenchLayoutManager`、`UiLayoutBuilder` 等组件组装动作
  （2026-08-25 起 2D / 3D 共用同一条配置驱动路径，`MenuManager3D` 硬编码路径已移除）
- 动作最终统一进入 `OperationBus`

---

## 2. 命令分发主链路

触发期（点击后执行什么）：

```text
QAction::triggered
→ 菜单/工具栏回调
→ CommandCatalog::operationForCommandId()
→ OperationBus::run(OperationId, params, source)
→ OperationRegistry::get(OperationId)
→ IOperation::execute(ctx, request)
```

构建期（按钮绑定的是哪个 QAction、启用态由谁管）：

```text
配置里的 actionId / commandId（小写点分，如 edit.align_left）
→ CommandCatalog::menuIdForCommandId()
→ CommandActionHub::editAction() / toggleEditAction() / toolAction()
→ 复用中枢托管的同一个 QAction（启用态由 CommandUiSnapshot 统一驱动）
```

两条链路都以 `CommandCatalog` 为唯一解析方。菜单和工具栏的差异只在展示层，执行路径与启用态来源都应一致。

`menuIdForCommandId()` 解析落空返回 `MenuActionId(0)`，此时顶部工具栏会退化为 `createUnmanagedAction()` 新建的非托管 QAction —— 启用态从此不再联动，属于必须避免的接线错误。


---

## 3. 当前菜单分工

### 3.1 2D

2D 菜单当前以 `WorkbenchMenuManager` 为主，负责 `File / Edit / View / Draw / Algorithm / Laser / Vision / Help` 的组装。

2D 的左侧绘图栏、菜单导入入口、以及右侧联动状态，都应尽量从同一份元数据视图派生，避免多处维护。

顶部工具栏这一项已落地（2026-08-25）：`TopToolBar` 原先手写的 `actionId → MenuActionId` 映射表已删除，改为调用 `CommandCatalog::menuIdForCommandId()`。此前该表遗漏了 6 个对齐命令，导致对齐按钮全程可点。

菜单栏同期接入启用态联动，但机制不同：菜单项由配置驱动（`UiLayoutBuilder`）创建，是独立于命令中枢的 QAction，无法复用 Hub 实例，因此由 `WorkbenchMenuManager::refreshCommandStates(snapshot)` 外挂刷新 —— 按 `property("commandId")` 反查目录条目的 `enableRule`，规则与工具栏同源。「同一份元数据视图」在规则层面已收口，QAction 实例层面仍是两套。



### 3.2 3D

3D 菜单与 2D 共用 `WorkbenchMenuManager` + 客户 JSON + `CommandCatalog3D`，
顶层结构与 2D 一致，内容差异由 JSON 的 `workbenches: ["3D"]` 过滤决定。
`Workbench3D::managesOwnMenus()` 恒为 `false`，`MenuManager3D` 及其 5 个 Menu 子类的
硬编码构建路径已于 2026-08-25 移除。

3D 画布右键菜单同样配置化，来自 `contextMenus` 中 `id = "canvas.3d"` 的定义
（`Workbench3D::buildConfiguredContextMenu`）。

### 3.3 UI 构建层

`UiLayoutBuilder` 负责把配置化布局构建成菜单、工具栏、Dock、状态栏与右键菜单；
`IUiCommandDispatcher` 只作为构建层抽象存在。

#### 3.3.1 命令绑定是构建期一次性决定（重要）

`UiLayoutBuilder::bindAction` 在**构建那一刻**就按 `dispatcher->isCommandRegistered(commandId)`
二选一：

- 已注册 → 连 `QAction::triggered` 到 `dispatcher->dispatch(commandId)`；
- 未注册 → `setEnabled(false)` + `setProperty("commandUnavailable", true)` + tooltip + 一条
  `[UiLayoutBuilder] Unknown command id` 警告，**并且不连信号**。

`commandUnavailable` 表示"构建期的静态结论"，与"当前选择/剪贴板/撤销栈不满足"是两回事，
快照刷新（`WorkbenchMenuManager::refreshCommandStates`）会主动跳过带该标记的项。
因此这个决定**没有任何后续流程会纠正**，必须保证绑定时分发器已经能给出正确答案。

由此得到两条硬约束：

1. **工具栏不得使用空分发器。** `WorkbenchLayoutManager` 里的 `NullDispatcher`
   （`isCommandRegistered` 恒 false）只能用于 Dock 构建 —— Dock 没有命令动作。
   历史上工具栏误用了它，结果是全部按钮永久变灰 + 启动刷屏 `Unknown command id`。
2. **工具栏必须与菜单共用同一个分发器实例，且在工作台注入之后再构建。**
   主窗口构造期（`initializeToolBarSkeleton`）还没有工作台，命令目录无从查询，
   所以 `WorkbenchLayoutManager::buildToolBars()` 在未注入分发器时只打一条 debug 日志并推迟；
   `WorkbenchWindow::setWorkbench()` 拿到工作台后先
   `setCommandDispatcher(m_menuManager->commandDispatcher())` 再调 `buildToolBars()`。
   分发器由 `WorkbenchMenuManager` 持有（`commandDispatcher()` 按需创建并同步当前工作台），
   绝不能用栈上临时对象 —— QAction 的触发回调会长期持有该指针。

回归测试：`Main/Src/UI/Test/ClientConfigTests.cpp`
- `ClientConfigLayoutBuilderTest.ToolBarActionsBindThroughDispatcher`
- `ClientConfigLayoutBuilderTest.ToolBarBuiltWithBlindDispatcherDisablesEveryAction`
- `WorkbenchLayoutManagerTest.ToolBarBuildDeferredUntilDispatcherInjected`
- `WorkbenchMenuManagerTest.CommandDispatcherIsSharedAndStable`

## 4. 当前需要保持一致的点

- 菜单和工具栏都应尽量走同一命令目录
- 顶层菜单必须保持稳定语义：`File / Edit / View / Draw / Algorithm / Laser / Vision / Help`
- `Theme` 归入 `Help`，不要单独散落在 `Tools`
- 菜单点击和工具栏点击都应记录统一日志
- 命令字符串命名应保持小写下划线风格（`edit.align_left`、`edit.mirror_horizontal`）。UI 配置里的 `actionId` 必须直接用这个 id，不能写成 `Edit_AlignLeft` —— 否则 `menuIdForCommandId()` 解析不到，按钮会退化成非托管 QAction 且启用态失效
- 菜单、右键菜单、顶部工具栏的启用态必须来自同一份 `CommandUiSnapshot`，任何 UI 组件都不应自行判断"有没有选中/是否锁定"

- 2D / 3D 切换时要尽量清理旧 UI 残留，避免面板、菜单与工具栏混淆
- 导入入口在 2D / 3D 下都应呈现“支持格式汇总”逻辑，而不是按扩展名碎片化

---

## 5. 当前收口方向

1. 继续减少硬编码菜单项。
2. 继续让菜单和工具栏共享命令目录。
3. 继续把 UI 构建层和业务执行层分开。
4. 继续让 2D/3D 菜单各自只处理自己的工作台。
