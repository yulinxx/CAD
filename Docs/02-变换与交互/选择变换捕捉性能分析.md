# 2D 大量图元下的选择/变换/删除/捕捉性能分析与优化

> 范围：点选、框选(Window)、交叉选择(Crossing)、取消选择、移动、旋转、缩放、镜像、删除、撤销重做，以及鼠标移动 + 图元捕捉 + 场景刷新。
> 代码基线：`Engine/2D` + `UI/2D`。文中路径均为相对仓库根目录。结论均附代码定位（文件:行号）。

## 0. 结论速览（TL;DR）

整体架构已经做了大量正确的批处理与去冗余：RTree 空间索引（点选/框选/捕捉）、矩阵合并一次性施加、批量撤销命令、场景几何哈希去重、Qt `update()` 帧内合并、曲面细分 LRU 缓存。**方向是对的，多数链路已达标。**

但存在 **一处与"批量"原则直接矛盾的实时热路径**，是万级图元拖动的首要卡顿源：

- `UI/2D/Src/UI/DrawTools/SelectTool.cpp:439-467` 的变换回调里，**每个图元**在 `ent->transform(mat)` 之后都调用了 `updateEntityBoundsNoNotify(ent)`（逐图元空间索引 remove+insert + 树重平衡），并且在每次 `mousemove` 都会执行。
- 同一份代码仓库里，落库路径 `Engine/2D/Src/Edit/SceneEditService.cpp:704-709` 已经注释明说「逐个 updateEntityBoundsNoNotify 就是万级万次重平衡，要用 updateEntityBoundsBulk」，可拖动路径却没走这条批量接口。
- 但要注意：`updateEntityBoundsBulk` **并不是「一次性重建」**（见 §2.4 第 1 条）。它的收益是「把逐图元索引开销从**每帧一次**降到**每次拖动一次**」的**频次下降**，而不是复杂度消除。

次要热点：捕捉主路径已走 RTree，交点捕捉 O(k²) 是次热点（工程内 `SnapBenchmarkTests.cpp` 注释已承认）。其余为细粒度浪费。

> 勘误（2026-09）：原稿称「多边形/曲线先物化全部候选点再过滤」已过时——现行 `SnapEngine` 已用 `pushInRadius` 就地过滤；原稿称「空索引退化为全量」亦不成立。详见 §2.2 与 §2.7。

## 2. 各链路流程与瓶颈（含优化建议）

### 2.1 点选拾取（单击）

**流程：**
```
鼠标按下 → SelectTool::onMousePress
  → SceneManager::queryByPoint(p, tol)
      1) p 扩张成容差包围盒
      2) m_spatialIndex.queryIntersects(queryBox, candidates)   // RTree O(logN+k)
      3) Geo2DParallel::pickFromCandidates(candidates, p, ...)  // 几何命中
  → selectEntities(...)
  → SelectionManager::selectRange → syncEntityFlags            // O(旧+新)
  → notifySelectionChanged                                    // 一次（batch 内延迟）
  → SelectTool::setDrawSelectionOutline → SelectionOutlineBuilder::buildFromEntities  // O(选中×顶点)
  → 渲染层 setSelectionOutlines → requestRepaint
```

**性能评估：** 候选查询正确用 RTree。剩余成本：
1. `syncEntityFlags` 每次选中变化对旧集+新集各遍历一遍设 `m_bSelected`（`SelectionManager.cpp:30-45`）。对万级选择可接受，但可改为「只处理 old△new 的差集」。
2. 描边 `buildFromEntities` 全量重新离散（`SelectTool.cpp:196-214`）。每次选择变化、每次缩放都会重建。
3. `hitTest` 里每次构造 `unordered_set<EntityId>`（`SelectionGizmo.cpp:325`）用于成员判定，重复分配。

**优化：**
- 描边按「实体 ID + 视口比例量化」缓存：同一批实体、同一缩放档位不重离散（当前 `buildFromEntity` 是纯函数，天然可缓存）。
- 选中成员判定改用「选择集自带的位图/hash set + 版本号」，避免每次临时建 set。
- `syncEntityFlags` 走差集。

### 2.2 框选 / 交叉选择

**流程：**
```
鼠标拖拽 → SelectTool 维护选择矩形 → 鼠标释放
  → SceneManager::queryByBox(box, containedOnly)
      1) m_spatialIndex.queryIntersects(box, candidates)    // RTree
      2) containedOnly ? box.contains(entityBBox) : 直接命中  // Crossing/Window 差异
  → selectEntities(newSelection)  → notifySelectionChanged → 描边/UI 刷新
```

**性能评估：** RTree + AABB 过滤正确。`queryByBox`/`queryByPoint` **没有全量回退分支**：索引为空时返回空结果，不会退化成 O(N) 遍历（全量回退只存在于捕捉路径，见 §2.7）。框选过程若「拖动中实时刷新选区高亮/统计」，要保证只走 AABB 快路径，不做逐图元几何求交。

**优化：**
- 拖动过程中仅做「候选计数 + 包围盒着色」的预览，几何命中延迟到释放（现状基本如此，保持）。
- 对「全选 / 反选」这类会瞬间构建超大选择集的操作，套一层 `beginBatchUpdate/endBatchUpdate`，确保通知只发一次、描边只建一次。

### 2.3 取消选择

**流程：**
```
SelectTool/Clear → SceneManager::selectEntities({}) 或 clearSelection
  → SelectionManager::selectRange 清空 → syncEntityFlags（遍历旧集置 false）
  → notifySelectionChanged → SelectTool 清空描边 → setSelectionOutlines({}) → repaint
```

**性能评估：** 主体没问题；`syncEntityFlags` 遍历旧集是 O(旧选择数)。对取消选择，「逐个置 false」可换成「批量按选择集整体清标志」。收益有限，属微优化。

### 2.4 移动 / 旋转 / 缩放（交互拖动）★ 关键

**流程（当前实现）：**
```
SelectionGizmo::onMousePress
  → hitTest（RTree 候选 + 命中手柄/几何）
  → m_interactionBeginFn → InteractiveEditSession::begin → beginInteractive  // 记 before 快照

每次 mousemove：
  SelectionGizmo::onMouseMove
  → computeTransform（一次 3x3 矩阵）
  → applyTransform → m_transformFn(mat)
      = SelectTool::setTransformRequest 的 lambda（SelectTool.cpp:439-467）：
        for id in selection:
           ent->transform(mat)                          // ① 每图元一次矩阵乘法，标记 dirty
           m_sceneManager->updateEntityBoundsNoNotify(ent) // ② 每图元空间索引 remove+insert+重平衡 ★瓶颈
        m_sceneManager->notifySceneChanged()            // ③ 触发场景重渲染
  → repaintHandles()（只重绘手柄/包围盒，不重建描边）   // ④ 已优化点

渲染帧（Qt update 合并后）：
  → renderFrame → RenderSceneBuilder 检测 dirty 图元
  → 逐 dirty 图元重新细分 + 重新上传几何 + 重建 draw list   // ⑤ 每帧重离散 ★潜在瓶颈

鼠标释放：
  onMouseRelease → m_interactionCommitFn → commitInteractive
  → after 快照 → notifyGeometryChanged 一次 → 单条 undo
  → repaint()（完整重绘，重建描边虚线）
```

**瓶颈与优化（按收益排序）：**

1. **② 每图元空间索引 update 的执行频次应从「每帧」降到「每次拖动一次」。** `updateEntityBoundsNoNotify` 内部是 `m_spatialIndex.update(entity)`（`SceneManager.cpp:228-240`），每次 remove+insert 并触发一次树重平衡，这个 O(N·logN + N 次重平衡) 在每次 mousemove 都发生。方向是：拖动中只 `ent->transform(mat)`，把「已变换的图元」收集进脏集合，`notifySceneChanged()` 仍每帧一次维持视觉；到 `commitInteractive` 时再统一收尾。这是与 `SceneEditService::transformEntities` 思路对齐的最小改动，收益最大。但有两个必须澄清的点：

   - **批量接口不消除重平衡，只是把开销挪到一次。** `EntitySpatialIndex::updateBulk`（`Engine/2D/Src/Core/EntitySpatialIndex.cpp:257-303`）的实现是「先收集旧包围盒 → 逐个 remove → 逐个 insert」，仍是 **N 次 remove + N 次 insert**，与逐图元 `update()` 的树操作次数相同，**不存在「一次性重建」**。仓库内 `SceneEditService.cpp:707-709` 所称的「先收集再一次性重建」并不成立（`EntityTransform.cpp:478-481` 的注释反而描述得更准确）。因此收益来自**频次下降**（每帧 N 次 → 每次拖动 N 次），不是复杂度消除。
   - **拖动期索引必须保持新鲜——但只在「需要新 AABB 的时点」新鲜即可。** 拖动中每一次 `mousemove` 都会「先吸附、再分发」：`ViewportInputRouter::dispatchToActiveTool → applySnap`（`Main/Src/UI/Render/ViewportInputRouter.cpp:655-682`）→ GridSnapManager → `SnapEngine::getCandidateEntities`（`Engine/2D/Src/Interaction/SnapEngine.cpp:266-277`），最终查的就是空间索引。但过期索引**不会**造成错误吸附：`SnapEngine::processEntitySnapPoints` 用图元「活」AABB 做半径预过滤（`SnapEngine.cpp:287-305`），过期条目最多成为假候选，其捕捉点会被半径过滤掉。真正必须新鲜的是**拾取/框选**（否则会漏掉被拖图元）。

   **已实现（2026-09）**：新增 `SceneManager::markEntityGeometryChanged()`（只登记变更进变更流，图元进「待修索引」集合）；`queryByPoint`/`queryByBox`（拾取/框选）与 `updateEntityBoundsBulk`（交互收尾）在查询/收尾前统一补齐；捕捉改走 `queryByBoxForSnap()`，刻意**不补齐**——因为它是每帧都跑的路径。拖动期因此零索引开销，且异常结束的交互也会被下一次拾取补齐（无需改动手势语义）。图元离场/被替换时会从待修集合摘除指针。

2. **⑤ 每帧重新细分 + 上传几何。** `ent->transform` 置 dirty → 下一帧对每个图元重新细分。平移/旋转不改变曲率与弧长，**细分顶点拓扑不变**，理想情况下只需对顶点做一次矩阵变换即可（甚至整批在 GPU 侧用一个 instance/uniform 矩阵完成），不用重新离散、不用重传缓冲。建议：拖动期间走「变换预览」快路径——场景几何不动，仅用单个矩阵在渲染层做整体变换（或对已缓存顶点做 SIMD 变换）；释放时才真正落地几何与细分缓存。注意：**缩放**会改变屏幕弦高误差，只有缩放拖动需要触发重离散。

3. **`recordChange` 不能延后。** `updateEntityBoundsNoNotify` 里还有 `recordChange(id, GeometryChanged)`（增量变更集），它是渲染增量刷新的**唯一驱动**（`SceneRefreshCoordinator::onSceneChanged → readChanges`），延后它拖动就不再重绘。已实现的方案保留了每帧逐图元 `recordChange`，只把**索引**延后（开销在 RTree 的 remove+insert，不在变更登记——后者是 O(1) 摊还，超过 65536 条才压实）。

4. 拖动中 `m_startBBox = computeSelectionBBox()`（`SelectionGizmo.cpp:527`）每帧遍历选择集重算包围盒（O(N)）。N 大时可缓存/增量更新（平移直接平移 bbox，旋转/缩放才重算）。

### 2.5 删除

**流程：**
```
deleteEntities(ids) → rejectIfLocked（批量） → 构造单个 DeleteEntitiesCommand
  构造：只记录 m_ids，不克隆
  execute：m_removed = extractEntitiesById(m_ids)  // 直接把原件所有权移入命令，内部 beginBatchUpdate/endBatchUpdate
  notifySelectionChanged / notifySceneChanged 一次
undo：insertEntitiesPreserveId（把保管的原件批量回插）
redo：再按 m_ids extractEntitiesById 取回
```

**结论（2026-09 已修复，原为「深拷贝」首要卡顿源）：**
- **原问题**：构造期对每个待删图元 `clonePreserveId()` 做整图元深拷贝，随后 `execute` 又把场景里的原件 `extract` 掉销毁——等价于「先完整复制一遍、再销毁原件」，万级/十万级图元时 N 次 `clone()` + 双份峰值内存，正是「Scene 面板大选区删除很慢」的直接原因（15.4 万图元场景实测卡顿）。
- **修复**：改为与 `AddEntitiesCommand` 相同的**零克隆所有权转移**——图元在「场景 ↔ 命令」之间移动，全程不 clone。构造只记 `m_ids`；`execute` 用 `extractEntitiesById` 把原件直接移过来由撤销栈保管；`undo` 归还、`redo` 再取回。删除从「一次全量深拷贝 + 一次销毁」降到「一次所有权搬移」。
- **保持项**：`extractEntitiesById` 内部仍走 `removeRange` 单趟压缩（O(N)，非逐个 `remove` 的 O(N·M) 尾部搬移），且把空间索引移除、群组/选择集解绑、变更登记打包进同一次 `beginBatchUpdate`，不要回退。
- **副作用说明**：`m_ids` 现在直接存构造期传入的 id 清单（不再像旧实现那样从快照里过滤一遍）；`extractEntitiesById` 内部本就跳过不存在的 id，语义不受影响。`execute` 加的 `!m_removed.empty()` 守卫避免重复 execute 时用空 extract 结果覆盖 undo 依赖的已保管对象。

### 2.6 撤销 / 重做

**流程：** 批量变换 → 单条 `EntitySnapshotsCommand`（before/after 快照）；同类同 ID 集可 `canMergeWith → mergeWith` 合并；redo 栈在无法合并时才 push。
**性能评估：** 粒度与合并策略正确。注意点：`pushExecutedSnapshotCommand` 保存 before+after 两份深拷贝，万级图元连续拖动每次 commit 都产生两份大快照，撤销栈默认 50 条上限（`UndoRedoManager.h:187`，Main 未覆写）也会占大量内存。可评估用「增量快照（只存变换矩阵 + 引用）」压缩。

### 2.7 鼠标移动 + 捕捉 + 场景刷新

**流程：**
```
鼠标移动 → 输入路由器（InputRouter）
  → GridSnapManager::snap → SnapEngine::findSnap
      1) getCandidateEntities：有 m_spatialQueryFn 则 RTree rangeQuery，否则 getAllEntities() 全量 O(N)
      2) processEntitySnapPoints：bbox 最近距离平方预过滤 → 端点/中点/象限点等
      3) 网格/极轴/起点吸附
      4) Snap_Intersection：Geo2DParallel::intersectionPointsAllPairs（O(k²)）
  → BaseTool::onMouseMove：只追加正交约束 → onPointerMoved → updatePreview
  → RenderOverlayUpdate → ViewRenderCoordinator::applyOverlayUpdate → requestRepaint
  → scheduleRepaint → QWidget::update()（Qt 同轮合并）
```

**性能评估与优化：**

1. **捕捉候选必须强制走空间索引。** `getCandidateEntities` 现在「有回调走 RTree、无回调回退全量 O(N)」（`SnapEngine.cpp:266-277`）。应移除全量回退，改为「未注入空间回调即不返回图元候选」+ 启动期断言，避免任何生产路径退回 O(N)。（注意：测试及无场景路径目前可能依赖该回退，收敛时需同步处理。）

2. **「多边形/曲线先物化全部候选点再过滤」已修复，此条已过时。** 现行 `SnapEngine` 已引入 `pushInRadius` 做「边生成边过滤」（`SnapEngine.cpp:22-43`），`extractLinePoints` / `extractPolygonPoints`（`SnapEngine.cpp:491-528` / `603-652`）全部走它，不再物化全量候选。仍停留在旧描述的是 `SnapBenchmarkTests.cpp` 的 B 段注释（属注释过时，应修注释而非改代码）。剩余可做的只有 `extractCurvePoints`（`SnapEngine.cpp:688-743`）不带半径过滤，但它只产出端点/中点/节点，规模是 O(控制点数)，与「物化全部顶点」不是一回事。

3. **交点捕捉 O(k²) + 极轴候选缺半径过滤。** 交点（`SnapEngine.cpp:141-179`，`intersectionPointsAllPairs` 见 803 行）现状**已用「查询半径减半 + 包围盒预过滤」收窄候选**，剩余空间是再按「距离 + 图元类型 + 长度」剪枝。另有一处真实缺陷：极轴候选（`SnapEngine.cpp:230-241`）只设 `distSq` 而**不判 `distSq <= radiusSq`**（起点/网格/交点候选都判了），可能让半径外的极轴点成为「最佳候选」，把鼠标吸附到捕捉半径之外——这既是性能问题也是正确性问题。

4. **`EntityTessellateUtil` 无缓存**（`EntityTessellateUtil.cpp` 固定 0.001 离散），若捕捉预览路径会离散化，应复用 `Tessellator` 的 LRU（或加 entityID+参数缓存）。

5. 鼠标移动链路本身已符合「覆盖层更新 + Qt update 合并」，保持；注意 `updatePreview` 别触发 `RenderSceneBuilder::rebuild()`（全量装配）——现状两者分离，保持。

## 3. 你尚未想到的优化点

1. **拖动中的 GPU 侧整体变换（instance/uniform 矩阵预览）。** 平移/旋转拖动时，被拖图元的细分顶点拓扑不变，可以在渲染层用一个矩阵整体变换缓存顶点，CPU 完全不碰几何，释放时一次落地。这是比「优化循环」更彻底的一步，能把万级拖动从「每帧重离散」降到「每帧一个矩阵 + 一帧绘制」。(工程已具备 `EngineParallel/Geo2DParallel`，可评估并行施加矩阵。)

2. **平移/旋转不必重算细分，缩放才需要。** 细分缓存目前以 `entity->isDirty()` 失效，任何 transform 都会置脏。可细分失效策略：平移/旋转只失效包围盒；缩放才失效细分缓存。配合第 1 点，收益显著。

3. **并行变换。** `applyMatrixToIds` 逐图元串行 `transform(mat)`。万级图元时，纯几何矩阵乘法（尤其 NURBS/样条控制点重拟合）可 `EngineParallel` 并行化；对内存带宽敏感，需测是否受限于 cache miss。

4. **选择集用位图 + 版本号而非临时 `unordered_set`。** 现在 `hitTest`/成员判定每次都建临时 set（`SelectionGizmo.cpp:325`），高频（hover）场景反复分配。改为选择集自维护的哈希表/位图并随选择变更递增版本号。

5. **通知的「观察者差异化 + 节流」。** `notifySelectionChanged`/`notifySceneChanged` 会同步打给所有观察者（属性面板、状态栏、工具栏、渲染描边）。拖动/高频选择时应把「重计算型观察者（多选属性面板 MultiEntity2DPropertyProvider、状态栏统计）」节流（debounce），只让「渲染型观察者」即时响应。

6. **快照内存：copy-on-write / 矩阵引用代替全量 clone。** 万级图元每次 commit 的 before/after 深拷贝内存压力大，撤销栈会被吃满。可用 COW 或有向变换链压缩。

7. **脏区/差异渲染。** 场景已有 `recordChange` + 几何仓持久化 + 哈希去重，但被拖图元每帧仍走「重离散 + 重传」。可加「变换层」(transform overlay) 让拖动只重绘被拖对象，静态背景不重绘（进一步降低帧成本）。

8. **避免每帧 `computeSelectionBBox()` 全量遍历。** 平移拖动 bbox 直接平移；旋转/缩放才算；或对「包围盒」维护增量合并。

9. **对象池 / 复用 `thread_local` 缓冲。** 捕捉候选、覆盖层 `RenderOverlayUpdate`、描边顶点容器等在 mousemove 热路径反复分配，统一走 preallocated/thread_local。

10. **量化视口缩放档位做描边缓存键。** 描边离散按 pixelToWorld 且每帧重算虚线；把缩放的连续量量化成档位 + 按「实体集指纹」缓存 outline path，避免 hover/缩放时反复 `buildFromEntities`。

## 4. 分优先级落地清单

### P0（立即，改动小、收益大）
- [x] **拖动变换：把逐图元索引更新从「每帧」降到「每次拖动一次」**（已完成，2026-09）——`SelectTool.cpp` 变换回调里的 `updateEntityBoundsNoNotify(ent)` 改为 `markEntityGeometryChanged(ent)`（只记变更、不动索引）；`SceneEditService::commitInteractive` 收尾时 `updateEntityBoundsBulk` 一次补齐。降低的是**执行频次**：`updateBulk` 内部仍是 N 次 remove + N 次 insert，不减少树操作总量。
- [x] **拖动期索引的补齐时点**（已完成，2026-09）——拖动中每次 `mousemove` 都会走 `ViewportInputRouter::dispatchToActiveTool → applySnap → SnapEngine → 空间索引`。但过期索引不会造成错误吸附（`SnapEngine::processEntitySnapPoints` 用活 AABB 半径预过滤）；必须新鲜的是拾取/框选。实现：`queryByPoint`/`queryByBox` 与 `updateEntityBoundsBulk` 前统一补齐「待修索引」，捕捉改走 `queryByBoxForSnap()`（刻意不补齐）。异常结束的交互由下一次拾取兜底，无需改动手势语义。
- [ ] **捕捉强制空间索引**——移除 `SnapEngine::getCandidateEntities` 的全量回退，未注入回调即返回空（注意测试/无场景路径当前依赖该回退，需同步收敛）。
