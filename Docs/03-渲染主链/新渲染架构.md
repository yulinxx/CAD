# 新渲染架构设计

> 目标：渲染 DLL **只管「怎么画」**，应用层 **定义「画什么」**。  
> 原则：跨 DLL 零 STL 暴露、多窗口共享 GPU 资源、动态逐帧提交、视图不变性显式表达、深度有序。

---

## 0. 设计意图与要达到的目的

### 0.1 当前架构的核心矛盾

| 矛盾 | 当前表现 | 后果 |
|------|----------|------|
| 语义泄漏 | `RenderWorld` 存 `EntityId`/`PrimitiveType`/`MaterialIndex`/bbox/四叉树 | DLL 绑死 CAD 业务语义，无法复用 |
| 全量提交 | 每帧 `renderBeginScene` → `renderSubmitGeometry` ×N → `renderFrame` | 图元规模上去后 CPU 提交瓶颈明显 |
| 跨 DLL STL | `std::vector<VertexP3C3>`、`std::string` 穿过 C API | 不同编译器/STL 版本 ABI 崩溃风险 |
| 视图不变性缺失 | 缩放时所有图元等比缩放，无「屏幕空间固定」机制 | 标注、十字准星、Logo 等无法固定大小 |
| 深度混乱 | 2D 用 zOrder 字段、3D 用深度缓冲，二者割裂 | 面/线/点/位图叠加顺序不可控 |
| 多窗口单体 | `RenderDevice` 聚合全部状态 | 多窗口 = 多进程或串行，GPU 资源不共享 |

### 0.2 本设计要达到的目的

1. **彻底解耦**：DLL 只接收「字节流 + 绘制命令描述符」，不解析任何业务概念。
2. **动态逐帧渲染**：GPU 资源分「持久（跨帧）」与「瞬态（每帧）」两类；只有变更的图元重传顶点，静态图元只重排绘制命令。
3. **视图不变性显式化**：每个 `DrawCommand` 标注自己是 **世界空间** 还是 **屏幕空间**，屏幕空间图元在缩放/平移时保持像素级位置/大小不变。
4. **统一深度排序**：用全局 `sortKey`（含层、深度、半透明标志）对全部图元类型（点/线/面/位图）做确定性排序。
5. **多窗口共享**：进程级 `RenderRuntime`（共享 GL context / 管线 / 字体 / buffer 池）+ 每窗口 `RenderSession`（私有相机/视口/瞬态资源）。
6. **ABI 安全**：跨 DLL 边界只传递 POD 结构体 + 原始指针/句柄 + 长度计数，绝不暴露 `std::`。

**三层职责边界**

| 层 | 只见什么 | 不见什么 |
|----|----------|----------|
| Application | `SyEntity`、`Layer`、`SelectionSet`、`BusinessId` | RHI、GPU buffer、shader |

| Runtime | 字节流、RHI 抽象、POD 描述符 | 任何应用概念 |

## 2. 图元类型映射

所有图元最终归一化为 `DrawCommand`。四类图元的映射关系：

| 应用图元 | 离散化产物 | 拓扑 (Topology) | 空间 | 典型 sortKey 层 |
|----------|------------|-----------------|------|-----------------|
| **点 (Point)** | 单顶点 + 点大小 | `Points` | 世界（或屏幕固定大小） | 中层 |
| **线 (Line/Polyline/Arc/Circle/Ellipse)** | 折线/环顶点序列 | `LineStrip` / `LineLoop` | 世界 | 中层 |
| **面 (Surface/Polygon/Fill)** | 三角网（索引缓冲） | `Triangles` | 世界 | 底层（被线/点覆盖） |
| **位图 (Bitmap/Image)** | 2 个三角形 quad + 纹理 | `Triangles` (instanced) | 世界或屏幕 | 可配置（通常底层或顶层） |
| **文本 (Text)** | 字形 SDF quad 实例 | `Triangles` (instanced) | 屏幕（或世界） | 顶层 |
| **Overlay (十字准星/预览)** | 线/点顶点 | `Lines` / `Points` | **屏幕空间** | 最顶层 |

> 注：文本、Overlay 由应用层在 `RenderSceneBuilder` 中离散化为 DrawCommand，DLL 不区分「文本」与「普通三角面」。

## 3. 视图不变性（View Invariance）

### 3.1 两种渲染空间

每个 `DrawCommand` 携带 `RenderSpace` 标志：

```c
typedef enum RenderSpace : uint8_t {
    RS_WorldSpace = 0,   // 受相机变换影响（缩放/平移/旋转）
    RS_ScreenSpace = 1,  // 完全不受相机缩放影响，仅随视口尺寸重新定位
} RenderSpace;
```

### 3.2 屏幕空间图元的处理流程

```
应用层 RenderSceneBuilder:
  - 对「固定大小标注」：将其世界坐标通过当前相机矩阵投影到 NDC，
    再换算为像素坐标，生成 RS_ScreenSpace 的 DrawCommand。
  - 对「固定位置 HUD」：直接给出像素坐标（viewport-relative）。

Session 提交时:
  - RS_WorldSpace:  vertexShader 用 uViewMatrix * pos
  - RS_ScreenSpace: vertexShader 用 uViewportMatrix * posPixel
                    且 posPixel 已经在 CPU 端算好（或传 NDC 让 GPU 不做缩放）

结果:
  - 缩放时：世界空间图元变大/变小；屏幕空间图元像素大小恒定。
  - 平移时：世界空间图元跟随；屏幕空间图元若绑定锚点(如右下角)则随视口动，否则不动。
```

### 3.3 常见不变性需求对照表

| 需求 | 设置 |
|------|------|
| 缩放时线宽不变（屏宽恒定） | `lineWidthSpace = RS_ScreenSpace`（shader 用像素宽） |
| 缩放时点大小不变 | 点用 `RS_ScreenSpace` 或 shader 内反除 scale |
| 标注文字大小恒定 | 文本 DrawCommand 设 `RS_ScreenSpace` |
| 十字准星居中固定 | 锚点 = viewport 中心像素，随 resize 重算 |
| 水印固定右下角 | 锚点 = viewport 右下角像素 |
| 网格背景随缩放变密 | `RS_WorldSpace` + 动态 LOD（应用层按 scale 决定网格步长） |

## 4. 深度排序（Depth Sorting）

### 4.1 统一排序键 sortKey（64-bit）

```
| 63..56 | 55..48 | 47..32 | 31..0 |
|  Layer |  Transp|  Depth |  Seq  |
|  (8bit)|  (8bit)| (16bit)|(16bit)|

Layer   : 应用层定义的绘制层（0=背景网格, 1=面, 2=线, 3=点, 4=overlay, 5=text）
Transp  : 半透明标志（0=不透明, 1=半透明 → 半透明必须后画做混合）
Depth   : 世界 Z 或 2D 伪深度（同一层内前后顺序，16-bit 量化）
Seq     : 同 key 内的稳定序号（保证确定性，避免闪烁）
```

### 4.2 排序规则

1. 先按 `Layer` 升序。
2. 同层内：不透明图元按 `Depth` 升序（远→近，Painter 算法）；半透明图元聚到该层末尾按 `Depth` 降序（近→远，正确混合）。
3. 同 key 内按 `Seq` 稳定排序（radix sort 天然稳定）。

> **GPU 深度缓冲只在 3D 模式启用**；2D 模式完全依赖 `sortKey` 的 Painter 排序，避免深度冲突导致线被面吞掉。

### 4.3 合批（Batching）

排序后，连续相同 `(pipelineIndex, materialIndex, topology, vertexBufferHandle)` 的 `DrawCommand` 合并为一次间接绘制（`DrawIndirect` / MDI），减少 API 调用。合批不破坏 sortKey 顺序。

## 5. 动态逐帧渲染（核心性能机制）

### 5.1 GPU 资源两类生命周期

| 类别 | 生命周期 | 示例 | 更新策略 |
|------|----------|------|----------|
| **持久 (Persistent)** | 跨帧，直到 Entity 删除/几何变更 | 静态图元顶点缓冲、纹理、网格 | 仅在 `EntityId` 几何变更时 `uploadBuffer` |
| **瞬态 (Transient)** | 单帧，下帧回收 | Overlay 顶点、预览线、每帧文本四边形 | 每帧从 ring-buffer 分配，帧末归还 |

### 5.2 持久缓冲管理（应用层拥有，Runtime 托管）

```
应用层 RenderSceneBuilder:
  - 为每个 EntityId 在 Runtime 申请持久 BufferHandle（首次出现时）
  - 几何变更时：runtimeUploadBuffer(handle, offset, size, data)
  - EntityId 删除时：runtimeDestroyBuffer(handle)

Session 每帧：
  - 不重新上传静态图元顶点
  - 仅重新生成 DrawCommand[]（sortKey 可能因为相机/选择态变化）
  - 提交 DrawCommand[] → Runtime 绑定已有 BufferHandle
```

### 5.3 瞬态 Ring-Buffer（Runtime 提供）

```
Runtime 内部维护 N 帧轮换的 vertex/index 池（如 3 帧，避免 CPU 写时 GPU 还在读）：
  TransientAlloc(size) → 返回 {BufferHandle, offset}
  帧末 sessionPresent() 后标记该帧瞬态区可回收

应用层 Overlay/预览：
  auto alloc = runtimeAllocTransient(vertSize);
  memcpy(alloc.cpuPtr, verts, vertSize);
  DrawCommand.vertexBufferHandle = alloc.handle;
  DrawCommand.vertexOffset = alloc.offset;
```

### 5.4 每帧流程（动态提交）

```
[应用层, 仅变更时触发]
  onEntityGeometryChanged(id):
      rebuild DrawCommand for id (离散化) → 写入持久 buffer
  onCameraChanged():
      仅重算屏幕空间 DrawCommand 的像素坐标 + 所有 sortKey（不重传顶点）

[Session, 每帧]
  sessionBeginFrame(session):
      收集 DrawCommand[]（应用层 push，或 Session 持有引用）
  sessionSubmitDrawCommands(session, DrawPacket):
      1. 若启用裁剪：GPU/CPU 可见性查询，过滤不可见图元
      2. Radix sort by sortKey
      3. 合批：连续同状态 → 间接绘制命令
      4. 绑定持久 buffer + 瞬态 buffer
      5. 通过 CommandEncoder → RenderGraph 执行 Pass
  sessionPresent(session):
      呈现，回收本帧瞬态区
```

> **关键收益**：平移/缩放时，90% 的图元顶点**完全不重传**，只重排 `DrawCommand` 数组（纯 CPU 排序，零 GPU 上传）。

## 6. 多窗口渲染

### 6.1 Runtime 共享，Session 私有

```
Runtime (进程唯一):
  - 创建共享 GL context（wglShareLists / GLX / Vulkan device / Metal device）
  - 所有 Shader/Pipeline/Texture/Buffer 跨 Session 可见
  - 字体 Atlas、全局 Buffer 池共享

Session A (Viewport A 窗口):
  - 私有：viewMatrix, viewport, DrawCommand[], 瞬态 ring-buffer 偏移
  - 引用同一 Runtime 的持久 BufferHandle（场景共享时）

Session B (Viewport B 窗口):
  - 不同相机、不同视口
  - 可引用同一批持久 BufferHandle（同一文档多视图）
  - 也可独立（不同文档）
```

### 6.2 多窗口同步场景数据

```
同一 Document 多视图：
  RenderSceneBuilder 生成一份持久 BufferHandle 集
  Session A / B 各自持有 DrawCommand[]（可能不同可见性/相机）
  → 顶点只存在一份（Runtime 托管），两个窗口共享

不同 Document：
  各自独立 RenderSceneBuilder + 独立持久 buffer
  → 仍共享 Runtime 的 shader/pipeline/font
```

### 6.3 资源冲突规避

| 冲突点 | 方案 |
|--------|------|
| GL context 并发 | 单线程渲染或每个 Session 在各自 context 但共享对象；命令提交串行化 |
| 瞬态 buffer 跨窗口 | 每个 Session 独立 ring-buffer 分区 |
| 字体 Atlas | Runtime 全局唯一，只读共享 |
| Pipeline 缓存 | Runtime 全局唯一，按 hash 查表 |

## 7. 跨 DLL ABI 规范（零 STL 暴露）

### 7.1 边界规则

| 规则 | 说明 |
|------|------|
| 只传 POD | 所有跨 DLL 结构体用 `#pragma pack` 对齐，仅含基础类型/句柄/指针 |
| 不传 `std::` | 禁止 `std::vector`/`std::string`/`std::map` 出现在 `render.h` 导出的签名 |
| 数组用「指针 + 长度」 | `const DrawCommand* cmds, uint32_t count` |
| 字符串用 `const char*` + 长度 或 调用前拷贝 | Runtime 内部转 `std::string` |
| 句柄为不透明 64-bit | `BufferHandle = uint64_t`，应用层不得解引用 |
| 内存所有权单向 | 调用方分配/释放调用方侧；Runtime 分配的通过 Runtime API 释放 |
| 结构体版本化 | `struct Header { uint32_t magic; uint32_t version; uint32_t size; }` 前缀 |

### 7.2 导出头文件最小集

```c
// render.h（DLL 唯一公开头）
#pragma once
#include <cstdint>

#ifdef RENDERX_EXPORTS
#  define RENDER_API __declspec(dllexport)
#else
#  define RENDER_API __declspec(dllimport)
#endif

typedef uint64_t RuntimeHandle;
typedef uint64_t SessionHandle;
typedef uint64_t BufferHandle;
typedef uint64_t PipelineHandle;
typedef uint64_t TextureHandle;

// ---- 所有结构体均为 POD，#pragma pack(8) ----

struct RuntimeDesc { /* backend, windowHandle, w, h, shaderDir... */ };
struct SessionDesc { /* runtime, windowHandle, w, h, clearColor[4] */ };
struct DrawCommand { /* 见 §8 */ };
struct DrawPacket  { /* cmds, count, viewMatrix[16], viewport[4], frameId */ };
struct VisibilityResult { /* indices, count, maxCount */ };
struct BufferDesc  { /* size, usageFlags, memoryFlags */ };
struct PipelineDesc{ /* vs/fs shader ids, blend, depth, topology */ };
struct TextureDesc { /* w, h, format, dataPtr, dataSize */ };

// ---- Runtime ----
RENDER_API RuntimeHandle runtimeCreate(const RuntimeDesc*);
RENDER_API void          runtimeDestroy(RuntimeHandle);
RENDER_API BufferHandle   runtimeCreateBuffer(RuntimeHandle, const BufferDesc*);
RENDER_API void           runtimeDestroyBuffer(RuntimeHandle, BufferHandle);
RENDER_API void           runtimeUploadBuffer(RuntimeHandle, BufferHandle, uint64_t off, uint64_t size, const void* data);
RENDER_API PipelineHandle runtimeCreatePipeline(RuntimeHandle, const PipelineDesc*);
RENDER_API TextureHandle  runtimeCreateTexture(RuntimeHandle, const TextureDesc*);
RENDER_API TransientAlloc runtimeAllocTransient(RuntimeHandle, uint64_t size); // {handle, offset, cpuPtr}

// ---- Session ----
RENDER_API SessionHandle sessionCreate(const SessionDesc*);
RENDER_API void          sessionDestroy(SessionHandle);
RENDER_API void          sessionResize(SessionHandle, uint32_t w, uint32_t h);
RENDER_API void          sessionSubmitDrawCommands(SessionHandle, const DrawPacket*);
RENDER_API void          sessionQueryVisibility(SessionHandle, const float viewMatrix[16], VisibilityResult*);
RENDER_API void          sessionPresent(SessionHandle);
RENDER_API void          sessionGetStats(SessionHandle, Stats*);
```

> 应用层可用薄封装（`.cpp` 内 `#include <vector>`）把 `std::vector<DrawCommand>` 转成 `DrawPacket`，但 **`.h` 不向 DLL 暴露 STL**。

## 8. DrawCommand 完整定义（POD, 64 bytes）

```c
#pragma pack(push, 8)
typedef enum PrimitiveTopology : uint8_t {
    PT_Points = 0,
    PT_Lines = 1,
    PT_LineStrip = 2,
    PT_LineStripAdj = 3,
    PT_Triangles = 4,
    PT_TriangleStrip = 5,
    PT_TriangleFan = 6,
} PrimitiveTopology;

typedef enum RenderSpace : uint8_t {
    RS_WorldSpace = 0,
    RS_ScreenSpace = 1,
} RenderSpace;

typedef enum VertexFormat : uint8_t {
    VF_P3C3 = 0,     // pos(3f) + color(3f)
    VF_P3C4 = 1,     // pos(3f) + color(4f)
    VF_P3N3C4 = 2,   // pos(3f) + normal(3f) + color(4f)  (3D)
    VF_P2UV = 3,     // pos(2f) + uv(2f)  (bitmap/text)
} VertexFormat;

struct DrawCommand {
    // ---- 顶点/索引缓冲（Runtime 托管的不透明句柄）----
    uint64_t vertexBufferHandle;   // 持久或瞬态
    uint32_t vertexOffset;         // 顶点起始（顶点数）
    uint32_t vertexCount;
    VertexFormat vertexFormat;     // 决定 stride
    uint8_t  _pad0;

    uint64_t indexBufferHandle;    // 0 = 无索引
    uint32_t indexOffset;
    uint32_t indexCount;
    uint8_t  indexType;            // 0=uint16, 1=uint32
    uint8_t  _pad1;

    // ---- 绘制状态 ----
    PrimitiveTopology topology;
    RenderSpace       space;        // 世界空间 or 屏幕空间
    uint16_t pipelineIndex;         // PSM 管线索引
    uint16_t materialIndex;         // 材质索引（Runtime 材质表）

    // ---- 实例化 ----
    uint32_t instanceCount;
    uint32_t firstInstance;

    // ---- 排序/语义 ----
    uint64_t sortKey;               // 见 §4.1
    uint64_t userData;              // 业务 ID 回传（拣选/命中测试），DLL 不解析

    // ---- 视口无关参数（屏幕空间用）----
    float    lineWidth;            // >0 时覆盖材质线宽（像素或世界由 space 决定）
    float    pointSize;
};
#pragma pack(pop)
// sizeof(DrawCommand) == 64 (验证: 8*8 = 64)
```

### 8.1 DrawPacket

```c
#pragma pack(push, 8)
struct DrawPacket {
    const DrawCommand* commands;   // 调用方分配的数组（不转移所有权）
    uint32_t           commandCount;
    uint32_t           _pad;
    float              viewMatrix[16];   // column-major
    float              viewport[4];       // x, y, w, h (像素)
    uint64_t           frameId;
    uint32_t           enableCulling;    // 0/1
    uint32_t           _pad2;
};
#pragma pack(pop)
```

## 9. 完整流程示例（缩放时的动态渲染）

```
用户滚轮缩放:
  1. Viewport A 更新 Camera2D → 新 viewMatrix
  2. RenderSceneBuilder::onCameraChanged():
       - 世界空间图元：DrawCommand 不变（顶点已持久上传）
       - 屏幕空间图元：重算像素坐标 → 更新对应 DrawCommand（仅命令，不传顶点）
       - 重算全部 sortKey（若深度/层受相机影响，例如 3D）
  3. sessionSubmitDrawCommands(sessionA, packet):
       - 可见性裁剪（GPU/CPU）→ 过滤视野外
       - Radix sort by sortKey
       - 合批
       - 绑定持久 buffer（零上传）
       - 瞬态 ring-buffer 写入本帧 overlay/preview
       - CommandEncoder + RenderGraph 执行
  4. sessionPresent(sessionA) → 回收瞬态

结果：缩放过程中 CPU 只做「排序 + 命令重组」，GPU 顶点带宽占用 ≈ 0（静态图元）。
```

## 11. 风险与对策

| 风险 | 对策 |
|------|------|
| 排序不稳定导致闪烁 | `sortKey` 含 `Seq` 稳定位；radix sort 稳定 |
| 瞬态 buffer 与 GPU 读冲突 | 3 帧 ring-buffer，present 后延迟回收 |
| 多 GL context 共享对象失败 | 创建时显式 `wglShareLists`/等价；失败回退单 context 串行 |
| 屏幕空间坐标精度 | 像素坐标用 float，NDC 变换在 shader 内做，避免 double→float 抖动 |
| 大坐标浮点精度 | 世界空间顶点仍采用 camera-relative（应用层减 center 再加回），与旧方案一致 |
| ABI 破坏 | 每个结构体带 `magic+version+size`，DLL 启动校验 |
| 回归 | P0-P5 每阶段跑现有测试；旧 `LegacyDevice` 双轨并行对比像素 |

## 12. 结论

本设计满足全部要求：

- ✅ **动态逐帧**：持久/瞬态资源分离，静态图元零重传
- ✅ **四类图元**：点/线/面/位图统一为 `DrawCommand`
- ✅ **视图不变性**：`RenderSpace` 标志显式区分世界/屏幕空间
- ✅ **深度排序**：64-bit `sortKey` 统一层/透明/深度/序号
- ✅ **多窗口**：Runtime 共享 + Session 私有
- ✅ **跨 DLL 零 STL**：全 POD + 句柄 + 指针/长度，ABI 版本化

DLL 最终只见「字节流 + DrawCommand 描述符」，应用层独占语义。

### 13.3 DrawCommand 与 sortKey

- `RTDrawCommand` 为 **80 字节** POD（`static_assert(sizeof==80)`），字段：
  `vertexBufferHandle / indexBufferHandle / vertexOffset / vertexCount / indexOffset / indexCount /
   sortKey / userData / textureHandle / topology(RTPrimitiveTopology) / space(RenderSpace) /
   vertexFormat(uint8_t) / indexType / pipelineIndex / materialIndex / instanceCount /
   firstInstance / lineWidth / pointSize`。
- `sortKey` 布局与 §4.1 一致：`Layer(8) | Transp(8) | Depth(16) | Seq(16)`，
  由 `uint64_t rtMakeSortKey(uint8_t layer, uint8_t transparent, uint16_t depth, uint16_t seq)` 构造。
- 覆盖层固定使用 `layer=200`（高于实体默认层 0），`transparent=1`，确保绘制在实体之上。

### 13.4 瞬态缓冲（单帧 ring-buffer）

- `runtimeFrameBegin(rt)`：映射瞬态顶点缓冲（写映射）。
- `runtimeAllocTransient(rt, size, &RTTransientAlloc)` → `{handle, offset, size, cpuPtr}`；
  句柄即专用瞬态 BufferHandle；超出容量时回绕到 0（`frameBegin` 后从零重新累积）。
- `runtimeFrameEnd(rt)`：解映射。
- 单帧内由应用层"分配→memcpy→构造 DrawCommand"；跨帧不保留。默认容量
  `RuntimeDesc::transientBufferSize`（默认 64MB）。

## 14. 跨平台 Shader 方案（Phase 4，已落地）

本节补上原文档缺失的一块：shader 如何在三个后端之间跨平台，且不引入第三方库依赖。

### 14.1 目标形态

- **零运行期文件 IO**：shader 在构建期编入 DLL。
- **零第三方库依赖**：只使用构建期可执行程序（Vulkan SDK 的 `glslangValidator`、
  Xcode 的 `xcrun metal`），不链接任何 shader 编译库。
- **DLL 不做跨语言转译**：库只按「名字 + 目标语言」查表；转译发生在构建期。

### 14.2 落地结构

```
src/shader/*.vert|frag|comp          GLSL 源（OpenGL 后端直接用）
src/shader/*.metal                   MSL 源（手写，Metal 后端）
        ↓  CMake/EmbedShaders.cmake  （cmake -P 脚本模式，构建期代码生成）
<build>/generated/shaderBlobs.cpp    unsigned char[] + { 名字, 语言, 指针, 字节数 } 表
        ↓
src/shader/shaderLibrary.{h,cpp}     find(name, language, &blob) / glslSource(name)
        ↓
后端 createPipeline                   拿到的字符串既可是源码本身，也可是库中文件名
```

- 语言按扩展名推断：`.vert/.frag/.comp` → GLSL，`.metal` → MSL，`.spv` → SPIR-V，
  `.metallib` → MetalLib。文本类语言额外补一个 NUL 字节，使数据可直接当 `const char*` 用，
  `sizeBytes` 仍是不含 NUL 的实际长度。
- shader 文件是 `add_custom_command` 的 `DEPENDS`：改 shader 即重新生成、重新编译。
- 同名多语言变体并存（`scene.vert` / `scene.vert.spv` / `scene.metallib`），后端通过
  `Capabilities::acceptedShaderLanguage` 声明自己接受哪一种。
- 新增 shader 只需把文件加进 `Renderx/CMakeLists.txt` 的 `RENDERX_SHADER_SOURCES`，
  不改任何 C++ 代码。
- 生成物与对应的 `shaderLibrary.cpp` 收在 OBJECT 库 `RenderxShaders` 中，由 `RenderX`
  与两个测试目标共同链接（`add_custom_command` 的 OUTPUT 只能被同目录目标消费，
  测试在子目录 `Test/`，故必须抽成目标而非直接列源文件）。

### 14.3 后续后端接入点

- **Vulkan（Phase 8）**：在 `RENDERX_SHADER_SOURCES` 之前插一个 `glslangValidator -V`
  的 `add_custom_command`，产出 `.spv` 后再交给 `EmbedShaders.cmake`；找不到
  `glslangValidator` 时不生成 `.spv`，Vulkan 后端在 `isBackendAvailable` 中返回 false。
- **Metal（Phase 7）**：手写 `.metal`，用 `xcrun -sdk macosx metal / metallib` 编成
  `.metallib` 后嵌入；非 Apple 平台跳过这一步。

### 14.4 被替换掉的旧方案与其三个实际故障

`src/shader/shaders.{h,cpp}`（18 个 `extern const char*` + `shader::initialize(shaderDir)`
运行期 `std::ifstream` 读取）已删除，原因：

1. 目录由 `renderCreateDevice` 用 `std::filesystem` 从可执行文件路径推导，macOS `.app`
   bundle 下推导失败 → 视口全黑（见 `Docs/Mac渲染.md` §4）。
2. shader 文件不是构建依赖，改了不重新拷贝，调试时跑的是旧 shader。
3. 文本加载无法承载 Vulkan/Metal 需要的 SPIR-V 与 metallib——这是原方案在架构上就走不到
   多后端的根因。

另外，真正在用的 11 个 shader 此前是 `rendererRuntime.cpp` 里的 11 段裸字符串字面量，
而 `src/shader/` 下的 18 个文件只服务于 legacy 路径（经 `rhiGl.cpp` 一段约 125 行的
`strcmp` 名字映射链，legacy 删除后已成死代码）。Phase 4 把前者提取为独立文件，
删除后者中已无用的 8 个（`scene_2d.*` / `overlay.*` / `overlay_screen.*` / `bitmap.*`）。

### 14.5 精度处理的归属变化

legacy 2D 路径靠 `scene_2d.vert` 里的 `uCameraCenter` uniform 做相机相对渲染。
当前 RT 世界空间 shader（`world_p3c3.vert` / `world_p3c4.vert`）只有一个 `uniform mat4 uView`，
大坐标的相机相对偏移**完全在 CPU 侧离散化阶段以 double 精度减去**——与 §1、§13.5
「离散化归应用层 `RenderSceneBuilder`」一致。Phase 10 迁移 2D 时须确保这一步不被漏掉，
否则大坐标场景会重现虚线/图元消失。

## 15. 渲染空间：三档语义（新增 WorldPinned）

标记类图元有三种截然不同的期望行为，必须在 ABI 层区分，不能靠业务层每帧重算顶点。

- **World**（已有）：跟随平移，跟随缩放。常规图元。
- **Screen**（已有）：不跟随平移，不跟随缩放。顶点即像素坐标。屏幕角标、HUD、标尺。
- **WorldPinned**（本节新增）：**跟随平移，不跟随缩放**。锚在场景某个世界坐标上，
  但屏幕上的尺寸恒定。定尺寸箭头、符号、标注框、引线端点属于这一档。

### 15.1 为什么不用「CPU 每帧重算」

RT 路径每帧重传全部顶点，理论上业务层可以在每次缩放后按当前比例反算几何尺寸。
不采用的原因：

1. 「屏幕尺寸恒定」是渲染语义，放进业务层会让每个调用点各写一遍缩放反算，
   与 §1「离散化只做几何离散，不掺渲染策略」冲突。
2. 缩放过程中需要全量重建标记几何，而这类图元通常数量多、单个很小，
   重建开销与视觉收益不成比例。
3. 三个后端要表现一致，这个换算必须只有一处实现——放在顶点着色器里。

### 15.2 实现方式

顶点布局新增 `P3O2C4`：`anchor(vec3 世界坐标) + offset(vec2 像素) + color(vec4)`。

顶点着色器：

```glsl
vec4 clip = uView * vec4(anchor, 1.0);
// 像素偏移换算到裁剪空间：乘 clip.w 抵消透视除法，
// 因此偏移量不受缩放影响，恒等于 offset 个像素
clip.xy += offset * (2.0 / uViewportSize) * clip.w;
gl_Position = clip;
```

`uViewportSize` 由 Session 每帧写入 pushConstant（与 `uView` 同一个块），
不需要业务层参与。

### 15.3 需要改动的清单（增量，ABI 尺寸不变）

- `renderx.h`：`RenderSpace` 增加 `WorldPinned = 2`；`VertexFormat` 增加 `P3O2C4`，
  `rxVertexStride` 相应返回 36 字节。两者都是 `uint8_t` 字段的取值扩展，
  `DrawCommand` / `PipelineDesc` 的 `static_assert` 尺寸不变。
- `DefaultPipeline`：增加 `WorldPinnedLine` / `WorldPinnedTri`（点仍走 ScreenPoint 系列）。
- shader：新增 `world_pinned_p3o2c4.vert`，片段复用 `world_p3c4.frag`。
- Phase 6：Runtime 注册上述默认管线。
- Phase 10：`RenderSceneBuilder` 对标记类图元产出「锚点 + 像素偏移」而非绝对坐标。

### 15.4 与拾取的关系

拾取仍在应用层（§13 的职责划分不变）。WorldPinned 图元的命中判定必须用
「锚点投影到屏幕后再加像素偏移」的同一套公式，否则视觉与拾取会错位。
这是应用层唯一需要复制这段换算的地方，需在实现时与 shader 注释相互引用。

### 15.5 落地修正（Phase 6）

`uViewportSize` 在实现时统一改名为 `uViewport`：它与屏幕空间 shader 里
早已存在的同名 uniform 是同一个量，两个名字会让共享的 pushConstant 块

## 16. RT 层落地：Runtime / Surface / Session 切到 renderx.h（Phase 6，已落地）

本节记录 RT 层重写的最终形态。旧的 `runtime_session.h` + `RenderTypes.h`
公共 API 与 `rendererRuntime` / `rendererSession` / `pipelineStateManager` /
`transientBufferPool` 实现已删除，`renderx.h` 的 32 个 `rx*` 导出是唯一对外接口。

### 16.1 三层所有权

```
Runtime  ── 1 个 GPU 设备 + 全部共享资源（管线缓存、shader、纹理、瞬态环）
   ├── Surface ×N  ── 一个窗口的原生表面 + 交换链
   └── Session ×N  ── 一个视口的相机与提交（1 Session 绑 1 Surface）
```

每帧：

```
rxSessionBeginFrame  → ISurface::acquireNextImage（GL 在此 makeCurrent）
                     → IGpuDevice::beginFrame 取命令记录器
                     → 瞬态环切段（见 16.4）
                     → beginRenderPass（clear 在此一次性给定）
rxSessionSubmit      → 瞬态刷写 → 按 sortKey 稳定排序 → 逐条绑定并绘制
rxSessionEndFrame    → endRenderPass → submitFrame → ISurface::present
```

「提交」与「呈现」分离是多窗口共享资源的前提（§6）：N 个 Session 可各自
录制并提交后再统一呈现，设备不与任何一个窗口绑死。

### 16.2 统一的 PushConstants 块

所有 RT shader 共用一个 std140 块，Session 每帧写一次：

```glsl
layout(std140) uniform PushConstants
{
    mat4  uView;      // 0..63    世界→裁剪，列主序；Screen 空间忽略
    vec2  uViewport;  // 64..71   视口像素尺寸
    float uPointSize; // 72..75   写入 gl_PointSize
    float uSdfScale;  // 76..79   SDF 字形边缘锐度
};                    // 共 80 字节，在 kMaxPushConstantBytes = 128 之内
```

C++ 侧对应 `Render::RT::detail::PushConstants`，有 `static_assert(sizeof == 80)`。

**声明只有一处**：`src/shader/rx_push_constants.glsl`。各 shader 在 `#version`
之后用一行 `#include` 引入，由 `CMake/EmbedShaders.cmake` 在构建期展开
（单文件、双引号、同目录，深度上限 8 层兼作循环包含保护）。

为什么必须只有一处：std140 布局不匹配**不产生任何编译错误**，只会算出错误
的偏移，表现为「矩阵读到一半变成视口尺寸」这类无从下手的画面错乱。
在 9 个文件里各抄一份，迟早会漂移。

GL 后端把该块落地为绑定在 0 号 UBO binding point 的 uniform buffer
（`GlDevice::kPushConstantBinding` / `kPushConstantBlockName`），
Vulkan 映射为 push constant，Metal 映射为 `setVertexBytes`。

### 16.3 管线缓存键：把「不能在录制期改的状态」都放进键里

`PipelineKey = (顶点格式, 渲染空间, 拓扑, 深度测试/写入/比较, 混合, 线宽, shader 名)`。

- **线宽**是管线固定状态：Vulkan 与 Metal 都不允许在命令录制期修改，
  因此不同线宽必须是不同管线。实现按 0.5 量化并按 `Capabilities::maxLineWidth`
  钳制——macOS 的 GL 与 Metal 上该值是 1.0，**Windows 上若上下文是前向兼容的
  也会被修正成 1.0**（见 §22.1），于是所有线宽塌缩成一条管线，
  这正是期望行为：真正需要粗线的调用方必须自己三角化。

- **点大小**相反，它走 pushConstant，可以逐笔命令变化。
- 旧实现 `resolvePipeline` 每帧每笔命令都往管线表追加一个重复句柄，
  且销毁时与 `PipelineStateManager` 的缓存重复释放同一批句柄（双重释放）。
  现在按键缓存，每组状态只建一次、只销毁一次。

**点图元有独立的顶点着色器**：点尺寸是像素量，只能写 `gl_PointSize`，
不能用顶点几何表达（否则缩放时点会跟着变大）。因此
`world_point_p3c3.vert` / `world_point_p3c4.vert` / `screen_point_p3c3.vert` /
`screen_point_p3c4.vert` 四条，片段侧 `point_p3c3.frag` / `point_p3c4.frag`
负责把方形 point sprite 裁成圆形。GL 后端在设备创建时统一开启
`GL_PROGRAM_POINT_SIZE`——桌面核心 profile 下不开这个开关，shader 里写的
`gl_PointSize` 会被静默忽略而改用 `glPointSize()` 的全局值。

### 16.4 瞬态环形缓冲

- 双段轮转（frames-in-flight = 2）+ CPU 影子内存，帧末统一上传。
  不依赖持久映射，因此 Null 后端与不支持 `GL_MAP_PERSISTENT_BIT` 的驱动
  行为一致。
- 容量不足时为该次分配单独开一个缓冲、帧末释放，**不做回绕覆盖**。
  回绕覆盖已提交命令引用的数据，表现是「画面随机少一部分」，极难定位。
- **切段按 Runtime 计数，不按 Session**：环由整个 Runtime 共享，
  若每个 Session 开帧都切一次，第二个窗口开帧就会把第一个窗口本帧数据
  所在段翻掉。实现用 `Runtime::sessionsInFrame` 计数，0→1 时才切段。
- `TransientAlloc::offset` 是 `uint32`，故单段容量上限 2GB，
  `rxRuntimeCreate` 超限时钳制并告警。

### 16.5 句柄校验

- 资源句柄（Buffer / Texture）走世代式 `SlotMap`，销毁后旧句柄立即失效，
  且不会命中被复用的槽位。
- `RuntimeHandle` / `SessionHandle` 本质是指针，C API 层维护一份进程内
  活跃对象登记表，解引用前先确认指针在表中。旧实现在 C API 里裸
  `reinterpret_cast`，传一个已销毁的句柄就直接崩在解引用处。
  登记表带互斥量，但那只保证表本身不被撕裂——资源创建/销毁仍要求串行。
- `SurfaceHandle` 用「是否在本 Runtime 的表面列表里」校验，
  因此来自其他 Runtime 的表面句柄会被拦下。

### 16.6 ABI 修正

- 移除 `PipelineHandle`：`rxPipelineCreate` 返回 `uint16_t` 索引。
  `DrawCommand::pipelineIndex` 是 `uint16`，绘制路径每帧要用它查表数万次，
  索引可直接下标寻址；再定义一个 64 位句柄类型只会让两种表示并存。
- 明确 `DrawCommand::vertexOffset` / `indexOffset` 是**字节**偏移，
  与 `TransientAlloc::offset` 同一坐标系，可原样填入。

### 16.7 本轮明确的缺口

- **文本**：字形图集（旧 `textAtlas`）依赖已删除的 `rhiDevice.h`，未一并移植。
  `rxFontLoad` 明确返回 `ErrorUnsupportedBackend` 并记录错误，
  **不静默成功**——静默成功会让调用方以为文本可用，最终表现为
  「文字不显示但没有任何错误」。随 2D 链路改造一并接入。
- **P3N3 / 3D**：`mesh_3d.*` 仍用 `uModelMatrix` / `uViewMatrix` / `uProjMatrix`
  独立 uniform，未并入 PushConstants 块。`defaultShadersFor` 对 P3N3
  明确返回空并报错，不提供「建得出来但画不对」的半实现路径。
  → **已在 §27 收口（ABI 5.0）**，本条为当时状态记录。
- **宿主**：`UI/` 与 `Main/` 自 legacy 删除起即无法构建，
  这是「legacy 全删」的既定代价，随 2D/3D 改造阶段修复。

### 16.8 测试覆盖

## 17. 增量大批量图元渲染（Phase 7，已落地）

### 17.1 为什么瞬态环不够

§5 的动态逐帧渲染解决的是「每帧都变」的数据：预览线、橡皮筋、覆盖层。
它的语义就是每帧全量重传，对这些内容是对的。

CAD 的真实负载恰好相反 —— **绝大多数图元帧间完全不变**。
10 万条线段里改动一条，瞬态环仍要把 10 万条重新搬一遍。

更关键的是，光解决「重传顶点」没有意义。在 10 万条的量级上有两笔同一数量级的开销：

- 顶点上传：10 万 × 每条数十字节
- 命令重建：调用方每帧填 10 万个 `DrawCommand`（80 字节）并交给 DLL 排序

只优化其中一个，另一个立刻变成瓶颈。因此本轮同时引入两块基础设施：

- `GeometryStore`（`src/rt/rxIncremental.{h,cpp}`）：顶点常驻显存，编辑只重写变化的块
- `DrawList`（同文件）：`DrawCommand` 由 DLL 持有，调用方只 upsert 变化的槽位

两者配合还带来第三个收益：同类图元的块通常在仓内**相邻**分配，于是
「状态相同 + 顶点区间连续」成为常态，`DrawList` 能把它们合并成极少数 draw call。

### 17.2 GeometryStore：结构与三条不显然的决定

一个 GPU 缓冲 + 一份等大的 CPU 影子 + 块表（`SlotMap`）+ 空闲表 + 脏区表。

**CPU 影子不是可省的冗余**。三个理由：
部分写（只改块内几个字节）之后要能把整个脏区间一次提交，必须有完整字节视图；
扩容时要把旧内容搬到新缓冲，从 GPU 回读远比从内存拷贝慢；
Null 后端与不支持持久映射的驱动上行为需一致。
代价是 1 倍显存大小的内存占用，对 CAD 场景（几十 MB）可接受。

**翻倍扩容而非线性**。线性增长在建大场景时会退化成 O(n²) 次搬迁。
扩容后整段标脏（新缓冲内容未定义），由下一次 `flush()` 从影子重传。

**扩容时原地改写公共句柄槽位**，而不是 erase + insert。
`SlotMap` 是世代式的，重新插入会让世代自增，已发出的所有
`GeometryBlock::buffer` 集体失效。原地改写后句柄数值保持稳定，
调用方不必逐块刷新。`rxGeometryAlloc` 仍返回 `ErrorGeometryStoreGrown`
（**正数，不是失败**）告知底层缓冲已被替换，供调用方按需用
`rxGeometryStoreGetBuffer` 重新取一次。

**分配用 first-fit 而非 best-fit**。空闲表按 offset 升序且保证无相邻空洞
（释放时与前后合并），first-fit 的定位性比 best-fit 好 —— 同类图元倾向
落在相邻位置，这正是 §17.4 合批能生效的前提。

**释放不标脏**。已释放的字节不会被任何 draw 引用（对应的 `DrawCommand`
应同时从 `DrawList` 移除）。为「保险」重传一遍已释放区域是纯粹的浪费。

**粒度向上对齐到 16 字节**。顶点属性最坏对齐是 `vec4`，块起始偏移
不满足对齐要求会在部分驱动上静默画错。

### 17.3 脏区合并：刻意的过度传输

`rxGeometryWrite` 只登记脏区间，不上传。`flush()` 时按 offset 排序，
相邻区间合并 —— 间隙小于 `kDirtyMergeGap`（4KB）也合并。

多传几 KB 远比多一次 `writeBuffer`（含驱动侧同步）便宜。
于是「改 1 万个小块」不会变成 1 万次 GPU 传输。
`FrameStats::geometryUploadBytes` 报的是合并后的实际传输量，
因此这个数字**大于**写入的字节数是正常的，测试锁住了这一行为。

### 17.4 DrawList：剔除、按需排序、合批

每帧 `resolve()` 依次做三件事：

1. **剔除**：条目自带 AABB 与视口矩形求交。AABB 存在 DLL 侧，调用方
   不必每帧再传一遍 —— 那份传输本身就是 O(n)。
2. **排序**：只在 upsert 引入新槽位或 `sortKey` 变化后重排，**不是每帧**。
   仅改顶点范围/颜色不触发排序，这是「每帧只 upsert 变化条目」
   能真正省下 CPU 的关键。稳定排序保证同 `sortKey` 维持槽位顺序。
3. **合批**：相邻条目状态相同且顶点区间连续时合成一次 draw。

**合批的安全边界**（写进代码注释与测试，因为搞错会静默画错）：

- 只有**列表型拓扑**（Points / Lines / Triangles）可合并。
  Strip / Loop 合并会把两条独立折线连起来，多画一段 ——
  这种错误在密集图形里几乎看不出来。
- 必须 `instanceCount == 1`：实例化绘制的语义不可拼接。
- 非索引绘制要求顶点字节连续：`b.vertexOffset == a.vertexOffset + a.vertexCount * stride`。
- 索引绘制额外要求 `vertexOffset` **完全相同**：索引值是相对
  `vertexBuffer` 起点的绝对值，`vertexOffset` 不同会让索引解释错位。
- 合并后的条目 `userData` 置 0：归属已不明确，保留第一个会让调用方
  误以为能靠它反查实体。

槽号上限 `1 << 24`。条目用稠密数组按 slot 直接下标（每帧热路径上
胜过哈希表），因此槽号必须紧凑分配 —— 直接拿实体的 64 位 ID 当槽号
会撑爆内存，这种情况明确报错而不是静默 resize。

### 17.5 Session 侧的接入

`Session::submit(DrawPacket)` 与 `Session::submitDrawList(DrawList*)`
共用同一份 `recordCommands()`：绑定冗余消除（管线 / 顶点缓冲+偏移 /
纹理绑定组 / pushConstants memcmp）只有一份实现。
分成两份必然随时间走偏，而「少消除一次绑定」不会报错，只是变慢 ——
这类退化没人会注意到。

`flushGeometryStores()` 放在 `Runtime` 而非 `Session` 上：
几何仓由整个 Runtime 共享，多窗口时只应上传一次；
若每个 Session 各自 flush，第二个窗口会重传同一批字节。

`FrameStats` 由 40 字节扩到 **56 字节**，新增
`culledCommandCount` / `mergedDrawCount` / `geometryUploadBytes`。
ABI 次版本号 0 → 1。

### 17.6 rxSessionReadPixels

取代已删除的 `renderReadPixels`。契约刻意收紧：

- 必须在 `EndFrame` **之前**调用。之后后备缓冲已交给呈现，内容不再保证
  有效；这里明确报错而不是「尽力读一次」—— 读到上一帧或空白画面更难排查。
- 输出恒为 **RGBA8、左上原点、逐行紧凑**（`rowPitch = width * 4`）。
  GL 原生是左下原点、交换链可能是 BGRA，翻转与通道交换都在 DLL 内完成，
  否则调用方要为每个后端各写一份解释代码。
- 实现上先 `endRenderPass` + `waitIdle` 再读，读完**必须重开 RenderPass**
  （`LoadOp::Load`，不能 Clear 掉已画内容）：否则 `EndFrame` 的
  `endRenderPass` 变成未配对调用，整帧被后端判废。

## 18. 宿主接入：2D 视口切到单一渲染路径（Phase 8，已落地）

Phase 6/7 把 DLL 侧改完了，但宿主（`UI/` + `Main/`）仍停在旧头文件上。
本阶段把 2D 视口整条链路接到 `renderx.h`，**删除双路径**。

### 18.1 帧的所有者从 DLL 回到视口

旧结构里 legacy `renderFrame` 拥有帧生命周期，RT 路径靠
`renderSetRTWorldDraw` 注入回调寄生在其中，两条路径各自维护一份
选择框/虚线/位图/屏幕文字状态——`RenderWidget.cpp` 2509 行里约 1400 行是这种双写。

现在 `RenderWidget` 自己拥有一套 Runtime / Surface / Session，一帧三次提交：

```
rxSessionBeginFrame
  ├─ rxSessionSubmit(场景环境)          瞬态环：工作台/网格/标尺线，layer=10
  ├─ rxSessionSubmitDrawList(场景实体)   常驻几何仓 + 保留式绘制列表，layer=100
  └─ rxSessionSubmit(覆盖层)            瞬态环：选择框/手柄/流水虚线，layer=200
rxSessionEndFrame
```

提交顺序即绘制顺序，同一次提交内部再按 `sortKey` 排。
重写后 `RenderWidget.{h,cpp}` 合计约 640 行。

### 18.2 谁走瞬态环，谁走几何仓

- **实体**走几何仓 + 绘制列表：帧间基本不变，10 万条改一条不该重传 10 万条。
- **场景环境**走瞬态环，但 CPU 侧几何按 `markSceneEnvDirty()` 缓存：
  网格线生成是 CPU 侧主要开销，顶点写入环则每帧必做（环在 BeginFrame 复位）。
- **覆盖层**走瞬态环：随鼠标每帧变化，塞进几何仓只会退化成每帧 alloc/free。

### 18.3 QOpenGLWidget 的接入方式

Surface 用 `NativeWindowKind::ForeignGlContext`，不传任何窗口句柄：
上下文由 Qt 创建与管理，GL 后端在 `acquireNextImage` 时记录**当前绑定的帧缓冲**
（QOpenGLWidget 画到自己的 FBO，不是 0 号），`present()` 只做 `glFlush`，
交换缓冲仍归 Qt。因此 `rxSessionBeginFrame` 必须在 `paintGL` 内调用。

### 18.4 修掉的一处静默错误：3x3 → mat4 转换丢平移

`Ut::Matrix` 是列主序（`data[col * 3 + row]`），shader 是
`gl_Position = uView * vec4(aPos, 1.0)`，uView 同为列主序。
旧 `mat3fToMat4` 做了一次隐式转置，把平移量 `(m02, m12)` 写进了 mat4 的**第 2 行**，
平移完全丢失。这类错误不会有任何报错，只表现为「画面不跟随平移」。
正确映射是把 3x3 的三列放进 mat4 的第 0、1、3 列，z 直通。

### 18.5 视图导出：读回收进控件内部

`rxSessionReadPixels` 必须在 `EndFrame` **之前**调用，因此不能由外部
「先渲染再抓取」。新增 `RenderWidget::captureFrameRGBA()`，整个
begin / submit / readPixels / end 序列在控件内完成。

由此 `RenderWidget::renderDevice()` 被删除——它是宿主唯一一处直接握着
渲染设备句柄的地方（`ViewCaptureService.cpp` 曾用它直接调
`renderSetView2D` / `renderReadPixels`）。DLL 保证输出 RGBA8、**左上原点**、
逐行紧凑，因此宿主侧原先的 `img.mirrored(false, true)` 一并删除。

### 18.6 场景构建器归位

- `RenderSceneBuilder`（`UI/2D/Include/Render/` + `Src/UI/ViewWidget/`）
  直接实现 `Eg::ISceneGeometrySink`，圆/弧/椭圆的离散化用 `Render::tess::*`，
  顶点写入几何仓、命令 upsert 进绘制列表。槽位与几何块是**每段一个**
  （一个实体可能产出多段），槽号紧凑分配（DrawList 上限 `1 << 24`）。
- `SceneGeometrySinkAdapter` 整个删除：它的全部职责就是喂
  `renderSubmitGeometry`，而新 ABI 明确拒收解析曲线。
- `Main/Src/UI/Render/RenderSceneBuilder.{h,cpp}` 删除（无调用方的旧副本）。

### 18.7 覆盖层与协调器

- `OverlaySceneBuilder::build(state, session, out)`：改吃 `SessionHandle`，
  顶点走 `rxSessionAllocTransient`，`pipelineIndex` 留 0
  （`Runtime::resolvePipeline` 默认就开 SrcAlpha/OneMinusSrcAlpha 混合）。
  `vertexOffset` 直接填 `TransientAlloc::offset`——同为**字节**偏移，不除 stride。
  捕捉指示器的顶点是逐段点对，拓扑从 `LineStrip` 改回 `Lines`。
- `ViewRenderCoordinator::applyFrameUpdate` 删除：它每帧全量重建场景命令，
  正是增量渲染要消除的模式。场景几何现在只经 `RenderSceneBuilder`。

### 18.8 本轮暂缺的能力

位图（`setBitmapImage`）与世界/屏幕文字依赖纹理与字形图集路径，
`rxFontLoad` 目前返回 `ErrorUnsupportedBackend`。位图接口保留声明并
**告警一次**——静默 no-op 会表现为「图片不显示但没有任何报错」。
标尺刻度数字同理暂缺，网格与标尺**线**已保留。

> 已由 §19 部分解决：字形图集完成移植，标尺刻度数字与屏幕文字恢复；
> 位图与世界文字（SyText 实体）仍缺，见 §19.8 / §19.9。

`ViewCaptureService` 的「任意分辨率离屏重渲染」退化为按后备缓冲结果缩放：
真正的实现需要渲染到纹理的 Surface，DLL 侧尚未提供。

### 18.9 `RuntimeDesc::glGetProcAddress`（已补齐）

RHI 层的 `DeviceDesc` 一直有该字段，且文档明确写着「Qt 宿主应传
`QOpenGLContext::getProcAddress` 的包装」，但公共 `RuntimeDesc` 没有透出，
落到了平台默认实现（macOS `dlsym` 可用；Windows + Qt 的 ANGLE/EGL 路径
与 Qt 自己的符号解析可能不是同一套，症状是「函数指针非空但行为不对」，
无任何报错，只表现为画面局部异常）。本轮补齐：

- `RuntimeDesc` 末尾新增 `void* glGetProcAddress`（签名 `void* (*)(const char*)`），
  结构体 48 → 56 字节，`static_assert` 同步；ABI **3.1 → 3.2**（只加尾部字段，
  旧宿主传 `nullptr` 语义不变，故只抬 minor）。
- `rxRuntime.cpp` 转发给 `DeviceDesc::glGetProcAddress`，为空时后端继续走平台默认。
- 宿主侧 `RenderWidget.cpp` 匿名命名空间提供 `qtGlGetProcAddress`，
  转发 `QOpenGLContext::currentContext()->getProcAddress()`，在 `createRenderer()` 里填入。

至此 §18 列出的跨平台缺口全部关闭。

## 19. 字形图集移植（文字能力恢复）

### 19.1 职责切分：度量在 DLL，排版在宿主

`rxFontLoad` 恒返回 `ErrorUnsupportedBackend` 的状态结束。移植没有照搬旧
实现，而是把边界挪了位置：

- **DLL 出**：`rxFontCreate` / `rxFontDestroy` / `rxFontMetrics` /
  `rxFontGlyph`（按需光栅化，返回图集 UV + bearing + advance）/
  `rxFontFlushAtlas`（脏行上传）/ `rxFontAtlas`（取 `TextureHandle`）
- **宿主出**：UTF-8 解码、字距推进、hAlign/vAlign、世界坐标→像素换算，
  自己拼 P2T2C4 四边形（`UI/2D/Src/UI/ViewWidget/TextQuadBuilder.cpp`）

被删除的 `core/textAtlas` + `core/screenTextRenderer` 是反向的：宿主递字符串，
DLL 内部两遍扫描做对齐、逐字符拼四边形、自己 `bindPipeline` + `draw`。代价有两条：
文本永远是独立的一批 draw call，无法与其他图元一起参与 `sortKey` 排序与批次
合并；「对齐规则」这种纯业务约定被编进了渲染 DLL——而 `renderx.h` 的职责边界里
明写着「不做文本布局排版」。

### 19.2 ABI 4.0

`rxFontLoad(runtime, data, size, pixelHeight)` 换成句柄式
`rxFontCreate(runtime, FontDesc*, FontHandle*)`，签名不兼容，故抬 major。
代价为零：旧接口从未成功返回过，无可用调用方。

新增公共类型：`FontHandle`、`FontDesc`（32 字节）、`FontMetrics`（16 字节）、
`GlyphInfo`（36 字节）。`GlyphInfo` 的坐标约定是「以基线上的笔位置为原点、
x 向右、y 向下为正」，与 `RenderSpace::Screen` 一致，因此 `bearingY` 通常为负。

### 19.3 一个 FontHandle = 一份字体 + 一个像素高度 + 一张 R8 图集

图集存的是位图而非矢量，换字号必须重新光栅化，所以多字号 = 多个句柄，
宿主侧 `TextQuadBuilder` 按字号维护批次。图集挂在 Runtime 而非 Session：
纹理多窗口共享一份即可（旧 Runtime 与窗口一对一绑定，两个窗口就是两份
2048×2048 图集）。

图集懒填充，不预烘任何字符——CAD 图纸的字符集无法预知，预烘 ASCII 既浪费
又不够用。

### 19.4 顺带修掉的四个旧缺陷

- 图集用 RGBA8 存 8 位覆盖率，把同一个值复制到四个通道。2048² 占 16MB，
  其中 12MB 是副本。现为 `Format::R8Unorm`。
- 每次 `renderText` 都无条件上传整张图集、并销毁重建顶点缓冲。
  现在按脏**行**增量上传（整行像素在 CPU 影子里连续，可直接交给 `writeTexture`，
  不必为任意矩形多一次重排拷贝）。
- 字形缓存是 `vector` + 线性扫描，中日韩场景下 O(n) 退化。现为哈希表。
- `loadFont` 忽略 `dataSize` 且不留字体副本，而 `stbtt_fontinfo` 持有原始
  数据指针——调用方一释放就是悬垂指针。现在 DLL 内部拷贝一份。

### 19.5 「SDF」路径从未存在过

旧 `text_sdf.frag` 对图集做
`smoothstep(0.5 - 0.5/uSdfScale, 0.5 + 0.5/uSdfScale, dist)`，把它当距离场解释；
但 `rasterizeGlyph` 用的是 `stbtt_MakeCodepointBitmap`，产出的是 8 位**覆盖率**。
把覆盖率喂给 smoothstep 等于硬阈值化，反而把抗锯齿边缘削掉了。

因此不是「补齐 SDF」，而是删掉这条名不副实的路径：`text_sdf.*`、
`text_screen.*` 四个 shader 与 `PushConstants::uSdfScale` 一并移除
（该字段位置改为显式占位 `pad0`，保持 std140 块尺寸 80 字节不变）。

### 19.6 ScreenGlyph 管线：为什么必须显式指定

`DefaultPipeline` 新增 `ScreenGlyph = 15`。它与 `ScreenTextured` 同为
P2T2C4 + Screen + Triangles，只有片元不同：

- `ScreenTextured` 采样 RGBA 位图，`texture(uTex, vUV) * vColor`
- `ScreenGlyph` 采样 R8 覆盖率，`vec4(vColor.rgb, vColor.a * coverage)`

GL 采样单通道纹理时 g/b 为 0、a 为 1，所以字形若走 `ScreenTextured` 会被画成
纯红色。二者无法由（格式, 空间, 拓扑）区分，因此调用方**必须**显式填
`DrawCommand::pipelineIndex`，不能留 0 让 Runtime 自行解析。

内部 `PipelineKey` 相应新增 `fragmentShaderName` 维度——不进键的话两者会命中
同一条缓存管线，先建的那条赢，另一条静默画错。

### 19.7 宿主侧接线

- 字体字节来源：`UI/Common/Resources/Fonts/default_screen_font.ttf`，
  经 `ui_common.qrc` 编入资源，`RenderWidget::createRenderer` 用 `QFile` 读出后
  注入。DLL 不做文件 IO，而「用哪个字体」是应用层决策（将来换 CJK 字体改的是
  这里）。`Renderx/src/res/` 下那份保留为 DLL 单测的夹具。
- 字体不可用只影响文字，几何照常绘制，因此注入失败**不算**渲染器创建失败，
  只告警一次。
- 标尺刻度数字已恢复：`buildSceneEnvText` 消费 `envGeo.rulerTexts` 与
  `envGeo.texts`，与几何层合成同一个 `DrawPacket` 提交（分两次提交会让 sortKey
  失去意义——提交顺序压过排序键）。文字的 `transparent` 位置 1，恒排在同层
  不透明几何之后。
- 同字号的所有字形合成一笔 DrawCommand。按项各出一笔会让 40 个刻度数字变成
  40 次绘制调用。

### 19.8 仍缺的一块：世界文字（SyText 实体）

> **已由 §26 补齐**（2026-08-27）。下文保留当时的判断，因为「为什么不能塞进
> 几何仓」这个结论仍然成立，只是结论指向的方案换成了距离场 + 独立账本。

`RenderSceneBuilder::emitText` / `emitTextEx` 当时是「告警一次并跳过」。原因不是
字形能力缺失，而是通路形态不匹配：场景实体走常驻几何仓（P3C3，帧间不变），
而世界锚定 + 像素字号的文字每次视图缩放都要重新排版，属于瞬态数据。把它塞进
几何仓会让「常驻」这个前提失效。要补的是第四条提交：从场景数据源里单独收集
文本项，每帧经 `TextQuadBuilder` 排版后走瞬态环。

（§26 的实际做法比这更进一步：距离场让「缩放时必须重新排版」这个前提本身消失，
于是排版结果可以按实体缓存，只有内容/位置变化才重排。）

### 19.9 暂缺的其他能力

> 位图部分已由 §25 补齐，`emitImagePlaceholder` 现在是明确的空实现 + 分工注释。

`ViewCaptureService` 的「任意分辨率离屏重渲染」仍退化为按后备缓冲结果缩放：
真正的实现需要渲染到纹理的 Surface，DLL 侧尚未提供。

## 20. 覆盖层双通道契约与流水虚线相位（修正 §18 的两处回归）

§18 把覆盖层状态的所有权收进 `ViewRenderCoordinator` 时引入了两处回归，
表现是「选中图形后既没有橙色选择框，也没有流水虚线」。

### 20.1 装饰图元有两条并行通道，`applyOverlayUpdate` 不能整体 clear

覆盖层内容有两条互不经过对方的写入通道：

- **增量通道**：`RenderOverlayUpdate` + `applyOverlayUpdate`，由绘制工具按
  `hasXxx` 标志只填自己关心的组（选择框、手柄、旋转手柄、吸附指示……）。
- **直写通道**：`setSelectionOutlines` 直接写 `OverlayState`，因为轮廓顶点是
  按当前视图比例离散化后的结果，不适合塞进 POD 的 update 结构。

回归的成因是 `applyOverlayUpdate` 被写成「先 `m_overlay.clear()` 再按标志填充」。
`SelectionGizmo` 一次重绘会**连续**调用四个回调（框 → 轮廓 → 手柄 → 旋转手柄），
于是第三个回调把前两个的成果抹掉；`repaintHandles` 更是每次悬停移动都清一遍。

契约（现已落地）：`applyOverlayUpdate` **只清 update 实际携带的组**。
`clearAll` 是唯一的整体重置入口。选中轮廓在 `applyOverlayUpdate` 里刻意
**没有 else 分支**——它的主通道是直写，清除由 `clearSelectionDecoration` 负责。

### 20.2 相位必须由视口控件驱动，且节距要做像素→世界换算

虚线样式（`dashLengthPx` / `gapLengthPx` / `speedPxPerSec`）全部以**像素**为基准，
而轮廓顶点在世界空间。`OverlaySceneBuilder` 的离散化必须把三者都乘上
`pixelToWorld`，否则在图元世界尺度小于一个 dash 时整条轮廓退化成实线。

相位（`selectionDashOffsetPx`）由 `RenderWidget` 推进，理由是只有控件知道
何时该 `update()`，也只有它持有视图矩阵做换算。要点：

- 定时器**按需启停**：`needsSelectionDashAnimation()` 为假时停掉，
  否则没有选中对象也会每 16ms 无谓重绘整个视口。
- 用**实测 dt**（`QElapsedTimer::restart()`）而不是每 tick 固定步长：
  定时器在负载下会被拉长，固定步长会让虚线速度随帧率变化。
- 相位对 `dash + gap` 取模，避免长时间运行后浮点尾数被吃掉、动画先卡后停。
- `pixelToWorldScale()` 由控件独占实现，`ToolContext::pixelToWorld` 只做转发：
  工具的命中容差与虚线节距必须用同一个比例。

### 20.3 瞬态环的公共句柄必须自己摘除

`Runtime::destroy()` 末尾会遍历 `buffers` 表逐个 `destroyBuffer`。凡是把自己的
RHI 句柄登记进这张表的组件，都必须在自己的 shutdown 里先 `buffers.erase`，
否则同一个缓冲被销毁两次——日志里的
`Renderx [gl] destroyBuffer: 句柄已失效（重复销毁？）` 就是它。

`GeometryStore` 一直是对的，`TransientRing` 漏了：环本体的公共句柄
（`Runtime::initialize` 里 `setPublicHandle`）与溢出缓冲的句柄
（`allocate` 里 `buffers.insert`）都没摘。现已收敛到
`TransientRing::releaseOverflowBuffers()` + `shutdown()` 两处。

### 20.4 选择框是线框，`selectionBoxColor` 是边框色

`OverlayState` 曾有一个 `selectionBoxFill`，并把调用方传来的颜色赋给它、同时把
边框硬编码成黑色。但所有调用方传的都是**描边色**：gizmo 的回调签名是
`(bbox, bool dashed)`，语义就是「画一个（虚线）框」；`ViewportSelector` 传的是
`QColor(204, 102, 0, 200)`。`SelectTool` 的 `kSelectionBoxColor` alpha 是 220/255，
于是选中一条线段会得到一个近不透明的橙色实心块，把线段本身完全盖住。

现在选择框只描边。需要半透明填充的场景另有独立分组：`selectionHighlightQuads`
（文字选区高亮，N 个四边形，跨行选区每行一块，见 20.4.1）。

#### 20.4.1 文字选区高亮：一条通道装 N 块四边形

这里曾经是两条并列的持久通道：`filledSelectionBox`（轴对齐矩形）与
`filledSelectionQuad`（随文字整体变换的四边形）。两个缺陷叠在一起：

1. 业务层只写生效的那条，另一条留着上一帧的残影 —— 带变换的文字块里取消选区，
   quad 通道的高亮永远不消失；
2. 每条只能装**一块**，跨行选区只能退化成一个并集大矩形，会把首末两行未选中的
   部分一起涂色。

合并为 `std::vector<Render::Vec2f> selectionHighlightQuads`（每 4 顶点一块）：
矩形是四边形的特例，跨行选区就是每行一块，**空列表即清除**，不需要 has 标志。
`OverlaySceneBuilder` 把所有块的填充批成一条 Triangles 命令、边框批成一条 Lines
命令，跨行选区不会按行数放大命令条数。

### 20.5 直写入口的「退化 bbox = 清除本组」约定

`setSelectionBox` / `setSelectionRect` 等直写入口原先都是 `if (!bbox.isValid()) return;`，
于是「清除」这个意图根本无法表达。`ToolInitializer::onRectPreview` 在拖拽结束时
正是靠传空矩形收尾的，结果框选的橡皮筋矩形永远留在屏幕上。

这条之前没暴露，是因为 §20.1 那个无条件 `clear()` 顺手把它擦了——一个 bug 掩盖
另一个 bug。现在这些入口统一：退化输入即清除对应的 `hasXxx`（列表型分组则清空列表）。

### 20.6 装饰点走 `WorldPinned`，尺寸单位是物理像素

控制点手柄、旋转标记、捕捉指示器、实体编辑控制点，都是**屏幕定尺寸装饰**：
锚点在世界里，大小按屏幕像素固定，不随视图缩放变化。

原先它们和普通图元一样走 `RenderSpace::World` / `P3C4`：业务层用
`pixelToWorld() * 6.0` 把像素反算成世界尺寸，覆盖层再补一句
`std::max(size, 12.0f)`。那个下限是 **12 世界单位**，于是钳位恒生效——手柄实际是
固定世界尺寸的，缩放视图时跟着一起放大缩小。

这类反算本就不该出现在业务层（§15.1）：它是渲染语义，只能有一处实现，即顶点
着色器。现在这四类装饰统一改走 `RenderSpace::WorldPinned` + `VertexFormat::P3O2C4`
（anchor `vec3` + offsetPx `vec2` + color `vec4`），像素偏移在
`world_pinned_p3o2c4.vert` 里换算：

```glsl
clip.xy += aOffsetPx * (2.0 / uViewport) * clip.w;
```

配套约定：

- 所有 `...SizePx` / `...OffsetsPx` 字段的单位是**物理像素**（`uViewport` 取
  `backingSize()` = 逻辑尺寸 × dpr）。字段名带 `Px` 后缀是硬要求——重命名
  `pointMarkerSize` → `pointMarkerSizePx` 时立刻暴露出 `BaseEditor.cpp` 一处
  按世界单位理解的旧调用。
- 覆盖层不再做任何尺寸钳位。
- 「在角点外 28 像素处」这类相对位置用 `pointMarkerOffsetsPx` 表达，锚点保持在
  包围盒角点上，偏移一路以像素形式送到顶点着色器。
- §15.4 的一致性要求（可见形状与命中区必须同一套公式）由
  `SelectionGizmo::computeRotationHandles` 改成从
  `computeRotationHandleAnchors` 派生来满足。原先 `computeRotationHandles`
  在重绘时把 `p2w * 28` 烘进世界坐标，而 gizmo 只在选择集变化时重绘一次
  （`SelectTool.cpp` 里唯一的 `m_gizmo->repaint()`），`hitTest` 却用实时 `p2w`
  重算——任何缩放之后画出来的点和它的命中区就分开了。

## 21. GL 资源释放的责任分层（工作台切换崩溃）

2D→3D 切换时应用崩溃，日志停在 `Step A: releasing GL resources` 与
`Runtime 已销毁` 之后、`Step B` 之前。三层各有一处职责错位。

### 21.1 「上下文必须当前」由控件自己保证，不外推给调用方

`RenderWidget::releaseGLResources` 会一路调到 Runtime 内的
`glDeleteBuffers` / `glDeleteProgram` / `glDeleteFramebuffers`，因此必须有当前
GL 上下文。它有两类调用方，前提不同：

- `initializeGL` → `createRenderer`：上下文已当前，且**不能** `doneCurrent`（后面还要建资源）
- 工作台切换、析构：上下文不当前，必须 `makeCurrent`

此前这个前提被外推给调用方，而 `RenderViewport2D::releaseGLResources` 那条路径
没做 `makeCurrent`（它的注释声称「内部会判断可见性」，与实现不符）。于是整个 GL
删除在无当前上下文下执行，紧接着 Qt 又要用同一上下文重建 FBO。

现在由 `releaseGLResources` 自己按「进来时是否已当前」决定要不要收尾：

```cpp
QOpenGLContext* ctx = context();
const bool needMakeCurrent = ctx != nullptr && QOpenGLContext::currentContext() != ctx;
```

它同时负责停掉本控件的动画定时器（流水虚线相位，见 §20.2）：**谁拥有重绘来源，
谁负责关掉它**。外部刷新来源（`SceneRefreshCoordinator`）由持有它的视口停。

析构函数因此简化为无条件调用一次。原先它用 `rxValid(m_runtime)` 做守卫，
而工作台切换已提前释放过一次、句柄已置 Invalid，整个兜底块反被跳过。

### 21.2 不要用 `setParent(nullptr)` 规避绘制事件

视口层曾在释放后做 `layout()->removeWidget()` + `setParent(nullptr)`，目的是
阻止 `hide()` 期间的绘制访问失效句柄。这既没必要也有害：

- 没必要：释放后 `m_session` 无效，`renderFrame` 在入口直接返回，绘制事件是空操作
- 有害：`RenderWidget` 被摘成孤立顶层，视口析构时不再级联删除它（每次切换泄漏
  一个 `RenderWidget`），且这个孤立控件仍会继续收到定时器与绘制事件

### 21.3 框架层不认识具体视口类型

`WorkbenchLayoutManager::clearLayoutContent` 原先 `qobject_cast` 出
`RenderViewport2D` / `Viewport3D` 各调一次 `releaseGLResources`，而
`UiWorkbench::releaseCentralWidgetGLResources` 这个虚接口一直存在、三份实现却
全是死代码（零调用点）。现在改为把「即将被替换的工作台」传进
`clearLayoutContent`，由它委托——`triggerWorkbench` 第 6 步才把 `m_workbench`
指向新工作台，所以清理时它仍是旧的。布局管理器随之不再 include 任何视口头文件。

释放顺序本身不变，仍是 §21 开头日志里的
`releaseGLResources()` → `setCentralWidget(nullptr)` → `hide()` → `deleteLater()`。

注意排查手法：`SY_*` 走异步 spdlog，崩溃时会丢队列中的行，「停在某一行」有几行
误差，不能只靠日志定位，要用代码把窗口夹出来或取真实 backtrace。

### 21.4 缓存的 widget 指针一律用 QPointer

修完 §21.1–21.3 之后 Step A–E 全部走通，崩溃点前移到
`Workbench3D::build3DWorkbenchUi` 的**第一句** `window.setSkeletonDocksVisible(false)`。
原因不在 3D：`clearLayoutContent` 同步 `delete` 了所有 Dock，而
`PanelState::leftDock` / `rightDock` 是裸指针，`delete` 后依然指向已释放对象，
`setVisible` 一调用就崩。此前这条从未暴露，是因为 Step A 的 GL 崩溃更早发生。

`PanelState` 的全部 widget 指针改为 `QPointer`：这些对象的所有权在
`QMainWindow` 的父子关系里，而工作台切换会成批销毁它们，缓存方无法可靠地
逐个置空（原代码只手工清了 `sceneTreeDock` / `propertiesDock` 两个，漏了另外两个）。
同文件的 `m_statusBarSlots` / `m_busyProgressBar` 本来就用 `QPointer`，此处只是补齐。

### 21.5 橡皮筋走 selectionRect，选中集包围盒走 selectionBox

§20.4 把 `selectionBox` 改成纯线框后，框选拖拽过程中的半透明遮罩消失了：
`ViewportSelector`（鼠标分发链最低优先级的框选实现）一直在用 `setSelectionBox`
画橡皮筋，靠的正是被删掉的那个 fill。

这是一个通道被两种意图复用：
- `selectionBox`：选中集的包围盒，**只描边**（填充会盖住图元，§20.4）
- `selectionRect`：框选/交选拖拽中的橡皮筋，**半透明填充 + 描边**

现在 `ViewportSelector` 改走 `RenderWidget::setSelectionRect`。这个转发入口传
空指针时只清本组，而 `setSelectionBox(nullptr, ...)` 走的是
`clearSelectionDecoration()`（全清）——橡皮筋收尾不该顺手擦掉刚选中图元的
轮廓与手柄。

> 后续修正（2026-08-30）：`ViewportSelector` 的整套框选实现后来被删除——
> 它挂在鼠标分发链的兜底分支上，而 `dispatchToActiveTool` 丢弃工具返回值、
> 无条件返回 true，兜底分支永远走不到；且路由从未调用 `updateBoxSelect` /
> `endBoxSelect`，即便可达也画不出橡皮筋。现在 `selectionRect` 通道的唯一
> 生产者是 `SelectTool`（经 `ToolInitializer.cpp` 的橡皮筋回调），
> `ViewportSelector` 只保留 `selectionBBox()`。本节关于两个通道语义的
> 区分仍然成立。

### 21.6 状态栏的所有权：注释曾描述了一个不存在的契约

`unmountStatusBar` 原来写着「不在这里 delete —— StatusBarBase 的生命周期由
创建它的 Workbench 负责，Workbench2D/Workbench3D 在析构时会清理」。核对实现：
`~Workbench2D() = default`，`~Workbench3D()` 只调 `shutdown() → deactivate()`，
两者都没碰状态栏。这个契约不存在。

真实的所有权是 Qt 父子关系：`new StatusBar(&window)` 先挂在 WorkbenchWindow 上，
`mountStatusBar` 里的 `QStatusBar::addWidget` 又把它 reparent 到 `QStatusBar`；
而 `QStatusBar` 跨工作台切换一直存在（`clearStatusBarSlots` 只删配置驱动的槽位
控件），所以卸载后对象仍然活着，下次 attach 由 `if (!m_statusBar3D)` 复用同一
实例。**它不会悬空**——之前担心的「第二次进 3D 拿到悬空指针」经核对不成立。

做了两件事：把注释改成描述真实的回收者；把 `m_statusBar2D` / `m_statusBar3D`
改成 `QPointer`，这样万一将来它被别处销毁，那条复用判断会自动走到重建分支，
而不是拿着悬空指针去 mount。

`WorkbenchWindow::m_activeStatusBar` 保持裸指针：`StatusBarBase` 在该头文件里
只有前向声明，而 `QPointer` 需要完整类型；且这个指针只由 mount/unmount 一对
函数写，作用域自洽。跨切换存活的复用指针在工作台侧，已经是 `QPointer`。

### 21.7 lambda 捕获的所有者要比 sender 活得久；QShortcut 要有归属

沿着 §21.4 的同类缺陷做了一次定向审计（不是普适性 QPointer 普扫），另外找到
三处真实可达的问题，都在「谁拥有这个回调 / 这个 QShortcut」上：

**1. `UiLayoutBuilder` 的 lambda 捕获 `this`。** 它建出来的 `QAction` 挂在
menubar 子树上、`QShortcut` 挂在窗口上，而 builder 本身是
`WorkbenchMenuManager::m_menuLayoutBuilder`（`unique_ptr`），每次
`rebuildMenusFromConfig` 都被整体替换。两处 `connect` 都是 3 参形式（无 context
对象），生命周期只绑 sender，于是切一次工作台之后触发这些 action 就解引用已析构
的 builder。改为捕获 `m_dispatcher`——它由 MenuManager 持有且只创建一次，
这也正是那里注释早就写明的意图（「必须保证指针在菜单存在期间有效」），
只是实现捕获错了对象。

**2. builder 建的 `QShortcut` 没有归属。** 它 parent 到窗口，但每次 rebuild 都会
按当前工作台的命令目录重新过滤一遍，上一批必须先消失。此前无人回收，后果两种：
两个工作台都有的键（Ctrl+Z…）累积同键 `QShortcut`，Qt 判 ambiguous 后两个都不
触发（表现为「切一次工作台快捷键就失效」）；只有 2D 有的键（Ctrl+N / Ctrl+F…）
在 3D 下仍由上一批响应。现在由 builder 自己拥有并在析构/`clearBuiltLayout` 里销毁。

**3. 2D 的 5 个全局 `QShortcut` 没走 `window.registerShortcut`。**
`clearAllShortcuts` 只回收登记过的，所以切到 3D 后 2D 的 Delete 仍然活着——
一边在 3D 界面里删 2D 场景的图元，一边和 3D 注册的 Delete 同键冲突。
3D 侧（`setup3DDeleteShortcuts`）一直是正确做法，2D 补齐即可。

**4. `FileDropHandler` 的屏幕→世界回调按值捕获 `RenderViewport2D*`。**
handler 由 `WorkbenchWindow` 持有、跨切换永生，且装的是 application 级事件过滤器，
所以切到 3D 后往窗口拖一张图片同样会走进来。`Workbench2D::deactivate` 已经清了
ImportService 的三个回调，唯独漏了这个，现在补上。

一条可复用的判据：**回调里捕获的对象必须比 sender 活得久，否则要么换捕获对象，
要么给 connect 传 context 对象。**「parent 到窗口」不等于「有人会在正确时机删它」。

## 22. 上下文能力与上传时机（每帧 GL 报错与"要动一下鼠标才刷新"）

两个症状看着无关，根因都在「宿主给的 GL 上下文到底是什么状态」上。

### 22.1 前向兼容上下文里没有宽线，而 caps 查询会撒谎

现象：每帧一条
`GL_INVALID_VALUE ... Operation is not valid from a preview context`
（"preview context" 是 NVIDIA 对前向兼容上下文的说法），画面看着却正常。

根因链：

```text
Main/Src/main.cpp 请求 GL 4.6 Core，但未设 QSurfaceFormat::DeprecatedFunctions
  → Qt 于是给上下文加上 FORWARD_COMPATIBLE 位
  → 前向兼容上下文里宽线已被移除，glLineWidth 只接受精确 1.0
  → 但 GL_ALIASED_LINE_WIDTH_RANGE 仍谎报 [1, 10]
  → 原有"按 caps 夹取"的两级防御全部失效
```

数据链（谁在发这个 1.5）：

```text
SceneEnvironmentSettings.borderWidthPx = 1.5
  → TableLayer 的 border.lineWidth
  → RenderWidget: topology = Lines + lineWidth = 1.5
  → 帧中途建管线
  → GlCommandList::applyPipelineState 的 f.LineWidth(1.5f) → GL_INVALID_VALUE
```

修法：`GlDevice` 在创建设备时查 `GL_CONTEXT_FLAGS` 的
`GL_CONTEXT_FLAG_FORWARD_COMPATIBLE_BIT`，命中就把 `caps.maxLineWidth` 修正为 1.0
并打一条 info。之后所有走 caps 夹取的代码自动只发 1.0。

三点要记住：

1. **画面没有任何变化。** 那句 `glLineWidth(1.5)` 一直在失败，线宽本来就一直是 1px。
   这次修的是"每帧刷一条错误日志"，不是修显示。
2. **不要让宿主去掉前向兼容位来换宽线。** macOS 的 Core 4.1 无论如何只有 1px，
   真需要宽线的正解是在 Renderx 里做四边形扩展描线（与 §16.3 的结论一致：
   调用方自己三角化）。
3. **能力查询不可盲信。** 驱动报的 range 是"这个 GL 实现支持的范围"，
   不代表"当前这个上下文允许"。要用 `GL_CONTEXT_FLAGS` 拿事实，而不是猜宿主怎么配的。

顺带：KHR_debug 回调把 `GL_DEBUG_TYPE_OTHER`（驱动闲聊，如
"driver allocated storage for renderbuffer"）降级到 debug。**日志里的 warning 必须条条值得看**，
否则真正的问题会被驱动噪声冲掉。

### 22.2 帧外上传必须自己 makeCurrent

现象："改完场景要动一下鼠标才刷新。"

`RenderWidget::submitSceneFromDataSource` 与 `addRenderEntity` 由
`SceneRefreshCoordinator` 在**定时器回调**里调用 —— 不在 `paintGL` 内，因此没有当前
GL 上下文；而它们会一路走到 `rxGeometryAlloc` / `rxGeometryWrite` / `rxGeometryFlush`，
发出 `glGenBuffers` / `glBufferData` / `glBufferSubData`。

无当前上下文时这些调用在 Windows 上通常**直接返回：既不报错也不上传**。数据要等下一次
帧内 flush 才偶然补上，于是表现为"得动一下鼠标（触发重绘）才看到改动"。

现在这两个入口按需 `makeCurrent` / `doneCurrent`，并且**已在帧内时不重复切换**
（判据与 §21.1 相同：`QOpenGLContext::currentContext() != context()`）。

推广的约定：**任何会发 GL 调用的入口，都要自己确认上下文当前性，不把这个前提外推给调用方。**
§21.1 是释放路径的同一条结论，这里是上传路径。

## 23. 管线失效的两条静默通道（`program == 0` 与失效绑定的复用）

`GlCommandList` 里有两处「出错了但画面不报错」的路径，都在
`Renderx/src/rhi/gl/glCommandList.cpp`。共同点是：GL 侧要么什么都不做、要么只在
错误队列里留一个码，而调用方拿到的返回值一切正常，于是问题以「显示不对」而不是
「报错」的形式暴露出来 —— 这类症状的排查成本比崩溃高得多。

### 23.1 `bindPipeline` 失败时必须清空当前绑定

`bindPipeline` 拿不到管线记录（句柄无效或已失效）时除了报错，**还要把
`m_pipelineHandle` 置空**：

```cpp
GlPipelineRecord* record = m_device->pipelineRecord(pipeline);
if (!record)
{
    m_device->log().error("[gl] bindPipeline: invalid pipeline handle");
    m_pipelineHandle = PipelineHandle{};   // 这一句是必需的
    return;
}
```

不清的后果：`m_pipelineHandle` 还指着**上一条**成功绑定的管线，而 `boundPipeline()`
是每次重新解析句柄的（见 §16.5 与该函数的注释），于是它照样返回一个有效记录。
后续 `draw` 就用旧 program、旧 VAO、旧顶点布局把这批数据画出去，画面上表现为
「图元错位或用错着色器」，日志里除了那一条 `invalid pipeline handle` 之外没有任何
线索 —— 而那条日志很容易被当成「这一条命令没画」，实际是「这一条命令用错管线画了」。

清空之后，紧随的 `draw` 会被 `prepareDraw` 的 `boundPipeline()` 判空拦下并报
`必须先 bindPipeline`，错误就落在真正出问题的那次绘制上。

### 23.2 `prepareDraw` / `dispatchCompute` 拦住 `program == 0`

管线链接失败时 `createGraphicsPipeline` 返回的是无效句柄，正常路径上拿不到记录。
但还有一种情况会拿到**空壳记录**：槽位被复用、或句柄已失效却仍解析出一条
`program == 0` 的记录。此时：

- 图形侧：用 program 0 发 `glDrawArrays` / `glDrawElements`，核心 profile 下只会得到
  一个 `GL_INVALID_OPERATION`，几何体静默消失，而调用方以为自己画出去了；
- 计算侧：`glDispatchCompute` 同理，派发出去什么也不会发生。

因此两处都补了显式拦截：

```cpp
// prepareDraw：在 flushVertexBindings / flushPushConstants 之前
if (boundPipeline()->program == 0)
{
    m_device->log().error("[gl] %s: bound pipeline has no linked program (program=0), draw skipped", what);
    return false;
}

// dispatchCompute：在计算管线判定之后
if (boundPipeline()->program == 0)
{
    m_device->log().error(
        "[gl] dispatchCompute: bound pipeline has no linked program (program=0), dispatch skipped");
    return;
}
```

放在 flush 之前是刻意的：既然这次绘制注定不成立，就不该再把顶点绑定与
push constant 下发出去 —— 那些状态会留在上下文里影响下一次绘制的判断。

配套约定：拦下之后**跳过这条命令并留日志**，不做任何「找一条能用的管线兜底」的
补救。用错管线画出来的画面比不画更难排查，静默兜底等于把一次可定位的失败换成
一个查不出来的显示问题。KHR_debug 回调（§22.1）只能告诉你哪一次 GL 调用非法，
它无法告诉你「这次调用本来就不该发出」，所以这层拦截不能指望驱动日志代替。

## 24. 2D/3D 刷新调度接口统一（2026-08-27，阶段 2）

### 24.1 统一前的事实：两侧连"刷新级别"这个词都不共享

2D 侧有一套成熟调度 `SceneRefreshCoordinator`（`Main/Src/UI/Render/`）：
五级刷新级别、脏/删除 ID 集合、16ms `QTimer` 合帧、增量与全量两条提交路径，
增量转不出顶点（文本）时自动回退全量。

3D 侧此前**一个都没有**：

- `RenderWidget3D::markSceneDirty()` 的函数体就是一句 `update()`；
- 视口内部另有十几处交互代码直接裸调 `update()`；
- `paintGL` 每帧新建 `SceneGeometryCollector`，从场景全量重收集顶点，
  逐实体 `allocate` 整个 VBO、逐实体一次 `glDrawArrays`；
- 没有节流、没有脏 ID、没有增量提交，也不走 Renderx（自持 GL 3.3 Core 与 shader）；
- `isRenderLoopRunning()` 只是 `m_renderLoopEnabled && m_ready` 的布尔回显，
  并没有任何在跑的循环 —— 空闲时是 0 fps 的纯事件驱动。

后果是工作台层没法用同一套语义描述刷新意图：对 2D 说"轻量重绘"，对 3D 只能说"重画"。

### 24.2 公共契约：`UI/Render/ISceneRefreshScheduler.h`

只定义**调度语义**，不出现 GL / Renderx / DrawList / 顶点格式：

- `UI::SceneRefreshLevel`：`None < Repaint < LightUpdate < Selection < FullRefresh`，
  严格单调升级不可降级；一轮内多次请求取最高级，派发时取走并复位 `None`。
- `requestRepaint / requestLightRefresh / requestFullRefresh`：按"我改了什么"选，
  不按"我猜要多重"选。
- `markEntityDirty / markEntityDeleted`：可选的精度补充。给了就能走增量；
  不给（或实现尚未支持）由实现退到更高级别，语义上不会画错。
- `pendingLevel()`：待办级别，供测试与日志断言，不改状态。
- `flushPendingRefresh()`：跳过节流同步派发（文档加载完、截图导出前需要）。
- `stop()`：切场景或析构前调用，之后的请求一律忽略。

### 24.3 两侧实现现状

- 2D：`SceneRefreshCoordinator` 实现该契约，私有 `RefreshLevel` 改为
  `using RefreshLevel = UI::SceneRefreshLevel`，**行为完全不变**。
  新增的 `flushPendingRefresh` 会先停掉节流定时器再派发，避免待办已清空还空跑一次。
- 3D：新增 `UI3D::SceneRefreshCoordinator3D`（`UI/3D/Src/Render/`），
  由 `RenderWidget3D` 用 `unique_ptr` 持有（前置声明，避免把 `unordered_set`
  塞进导出类布局）。`markSceneDirty()` 收口为 `requestLightRefresh()`。

阶段 2 的 3D 实现刻意**只记账、不分流**：任何级别都落到一次整帧重绘，
帧时序与改造前的裸 `update()` 完全一致。理由是 3D 目前没有常驻顶点仓，
`paintGL` 每帧都重收集，"增量"和"全量"在实现上没有区别 —— 先接口后实现，
不引入半成品分支。

### 24.4 后续分期（2026-08-27 复核后调整了顺序）

**原计划的阶段 3（3D 接 16ms 节流）已判定为无收益，与阶段 4 对调。**

理由：`QWidget::update()` 本身就是合帧的 —— 一帧内调多少次，Qt 也只投递一次
`paintEvent`。3D 的 `SceneRefreshCoordinator3D::dispatch()` 除了 `update()`
不做任何事（见 `UI/3D/Src/Render/SceneRefreshCoordinator3D.cpp:43`），
真正的开销全在 `paintGL` 里（每帧新建 `SceneGeometryCollector` 全量重收集）。
在这之上再叠一层 16ms QTimer，**不会减少一次 paintGL，只会给每个交互加最多
16ms 延迟** —— 纯亏。

2D 的 16ms 节流有收益，是因为 `SceneRefreshCoordinator::updateSceneRender()`
在请求重绘之前要做 CPU 侧的几何重建与 `rxSessionSubmitDrawList`，
合帧省掉的是这部分重复计算，而不是 paint 本身。

调整后的顺序：

- 阶段 3（原阶段 4）：3D 接常驻顶点仓与增量提交，`FullRefresh` 退为兜底。
  只有这一步做完，`dispatch()` 里才会出现「值得合帧」的 CPU 工作。
- 阶段 4（原阶段 3）：在阶段 3 的基础上再加节流，让 `markEntityDirty` 参与判定。
  届时才需要单独验证交互手感（orbit / pan / gizmo 拖拽）。
- 未收口的一块：2D 侧仍有第二套脏位 `RenderWidget::m_sceneEnvDirty`（网格/标尺几何），
  以及不经脏标记的覆盖层链（`ViewRenderCoordinator` 每帧全量重传）。
  这两条都不在本契约管辖范围内，属于后续是否并入的待议项。

## 25. 位图渲染：世界空间贴图（2026-08-27）

### 25.1 缺口与选型

`RenderWidget::setBitmapImage` 此前是个只打一次告警的空壳，图片实体（`Eg::SyImage`）
在 2D 视口里完全不显示。历史实现走的是屏幕空间贴图（`bitmap.*` shader，
随 legacy 路径一并删除），那条路要求宿主每帧把图片的世界坐标换算成像素，
平移/缩放都得重算顶点，旋转与斜切根本表达不了。

选定的方案是**世界空间贴图 + CPU 侧四点变换**：

- 新增顶点格式 `VertexFormat::P3T2C4`（36 字节：位置 float3 + UV float2 + RGBA float4）；
- 新增默认管线 `DefaultPipeline::WorldTextured`（`Count` 由 16 → 17），
  顶点着色器 `world_tex_p3t2c4.vert`（与屏幕变体唯一的差别是乘 `uView`），
  片段着色器复用 `screen_tex_p2t2c4.frag`（它与空间无关）；
- 宿主把 `SyImage` 的四个角点（`topLeft/topRight/bottomLeft/bottomRight`）
  直接落成顶点。这四点已经承载了平移、缩放、旋转、斜切乃至一般四边形，
  因此**DLL 不需要 per-draw 模型矩阵**，旋转能力是零成本得到的。

`TextureDesc` 刻意没有扩字段：位图沿用 RGBA8Unorm + `defaultSampler`
（GL_LINEAR / CLAMP），与字形一致。sRGB / mipmap / 最近邻是独立议题，
需要时再加，不预留空洞。

### 25.2 `defaultShadersFor` 的静默画错通道（顺手关掉）

改动前 `P2T2C4` 是**无条件**返回屏幕变体的：`(P2T2C4, World)` 能成功建出一条
管线，跑的却是屏幕空间顶点着色器 —— 不报错、不返回失败，只是画在错误的位置。
现在两个纹理格式都按空间校验，不匹配直接返回空、拒绝建管线：

- `(P2T2C4, 非 Screen)` → `{}`
- `(P3T2C4, 非 World)` → `{}`

`WorldTextured` 与 `ScreenTextured` 因此靠**顶点格式**区分，不靠空间。

### 25.3 宿主侧：`Render::BitmapQuadBuilder`

与 `TextQuadBuilder` 完全对称的一层：DLL 只出资源（纹理 / 图集），
"放在图纸哪里、怎么变换"留在应用层。差别只在资源寿命的键 ——
字形按**字号**缓存，位图按**实体 id** 缓存。

- `Include/Render/BitmapQuadBuilder.h` + `Src/UI/ViewWidget/BitmapQuadBuilder.cpp`
- 像素格式转换在宿主：`Gray8` / `RGB24` / `RGBA32` → RGBA8。
  理由同 §19 的排版归属 —— 来源格式是业务事实，DLL 不该为此长出格式枚举。
- UV 方向：纹理第 0 行是图像顶行，采样时 `v=0` 即顶行，所以
  `topLeft ↔ (0,0)`、`bottomLeft ↔ (0,1)`。世界 y 向上而 v 向下，方向相反不是笔误。
- 显式指定 `pipelineIndex`，与字形同一纪律（§19.4）。
- 一张图一笔 `DrawCommand`：各自绑定不同纹理，无法合批。

### 25.4 上传时机：GL 上下文的时机约束（§21.1 的又一例）

`setBitmapImage` 的调用方是 `SceneRefreshCoordinator::reconcileBitmaps`，
它跑在 `paintGL` **之外**，那里没有当前 GL 上下文。因此三个宿主接口
（`setBitmapImage` / `removeBitmapImage` / `clearBitmaps`）只做 CPU 侧登记：

- 新增/更新 → 转好 RGBA8 存在 `Entry::rgba`，置 `pixelsDirty`；
- 移除 / 尺寸变化 → 句柄进 `m_pendingDestroy`，**不当场 destroy**；
- 真正的 `rxTextureCreate` / `rxTextureUpdate` / `rxTextureDestroy`
  全部发生在 `flush()`，即帧内、上下文已当前。

上传成功后立刻 `clear() + shrink_to_fit()` 释放 CPU 副本，否则每张图在内存里留两份。
纹理创建失败时置 `pixelsDirty = false` 并只告警一次，避免每帧重试 + 日志刷爆。

### 25.5 帧内提交顺序：从三路变四路

```
rxSessionBeginFrame
  ├─ rxSessionSubmit(场景环境)          网格/工作台/标尺线   layer 10
  ├─ rxSessionSubmit(位图)              世界空间贴图         layer 20  ← 新增
  ├─ rxSessionSubmitDrawList(场景实体)   常驻几何仓
  └─ rxSessionSubmit(覆盖层)            选择框/手柄/虚线
rxSessionEndFrame
```

位图必须排在实体**之前**：提交顺序压过 `sortKey`（§16），图片是底图，
矢量图元要盖在它上面。`sortKey` 的 `transparent` 位取 1 —— 位图可能带 alpha。

两张位图在世界空间重叠时谁在上，取决于账本顺序；业务侧目前没有定义图片间的
叠放语义，所以这里不假造一个。

### 25.6 验证

- DLL 侧 4 例（`RenderxGLTests`）：默认管线全部可用、`WorldTextured` 与
  `ScreenTextured` 不是同一条、两个纹理格式各自拒绝错空间、P3T2C4 步长 == 36。
- 宿主侧构建器与 `TextQuadBuilder` / `RenderSceneBuilder` 一样没有单测 ——
  三者都需要活的 GL Runtime，当前测试工程里没有这样的夹具。
- 人工确认（2026-08-27）：拖入图片后原位显示、跟随平移缩放、旋转后贴图跟着倾斜，
  三项均正常。

## 26. 世界空间文字：真距离场（2026-08-27）

### 26.1 缺口与选型

§19 恢复的是**屏幕定尺寸**文字（标尺刻度值、HUD）：字高是像素、图集是覆盖率
位图、顶点直接就是像素坐标。图纸里的 `SyText` 一直没画出来 ——
`RenderSceneBuilder::emitTextEx` 告警一次然后跳过，且 `EntityToVertices`
一见文本就返回 false，把整帧升级成全量刷新。

三个候选：

1. **屏幕空间近似**：每帧按当前缩放算出像素字高，复用 `TextQuadBuilder`。
   缩放一次就要换一个字号 → 换一个 FontHandle → 重新光栅化整套字形。
   连续缩放时等于每帧重建图集。
2. **世界空间覆盖率图集**：字形四边形用世界坐标，图集仍是覆盖率位图。
   放大是插值糊、缩小是采样噪点 —— 覆盖率位图只在「1 纹素 ≈ 1 像素」时正确。
3. **世界空间真距离场**（采纳）：图集存有符号距离场，抗锯齿窗口取
   `fwidth(d)`，即距离场在屏幕上的每像素梯度。一张图集通吃所有缩放级别。

选 3 的前提是**距离场必须真的生成出来**，不能在采样阶段假装：被删除的旧
`text_sdf.frag` 就是对覆盖率位图做 `smoothstep`，那是硬阈值化，反而削掉了
本来有的抗锯齿边缘。vendored 的 `stb_truetype` 自带 `stbtt_GetGlyphSDF`，
所以这条路不引入新依赖。

### 26.2 DLL 侧：`FontDesc::sdfPadding`

```cpp
struct FontDesc {
    const void* data; uint64_t dataBytes;
    float pixelHeight;      // SDF 模式下只是距离场的采样精度
    uint32_t atlasWidth, atlasHeight;
    uint32_t sdfPadding;    // 0 = 覆盖率位图；>0 = SDF 留白（像素）
};
static_assert(sizeof(FontDesc) == 32, "FontDesc ABI size changed");
```

新字段占用结构体原有的尾部填充，`sizeof` 不变。`rxFontGlyph` 按此分流：
`sdfPadding != 0` 走 `stbtt_GetGlyphSDF`（字形四周外扩 padding，
`xoff/yoff` 已含该外扩，`advance` 取自 hmetrics 因而不受影响），否则走
`stbtt_MakeGlyphBitmap`。这三条语义由 `FontSdfModeOutsetsGlyphByPadding`
锁定，不是靠读文档相信。

新管线 `DefaultPipeline::WorldGlyphSdf`（第 18 条，`Count = 18`）：
顶点复用 `world_tex_p3t2c4.vert`，片元是新的 `world_glyph_sdf_p3t2c4.frag`：

```glsl
float d = texture(uTex, vUV).r - 0.5;
float w = max(fwidth(d), 1e-5);
float alpha = smoothstep(-w, w, d);
```

它与 `WorldTextured` 的（格式, 空间, 拓扑）三元组完全相同，因此**必须**显式
填 `DrawCommand::pipelineIndex`，与 `ScreenGlyph` 同一纪律（§19）。让 Runtime
自行解析会命中 `WorldTextured`，把 R8 距离场当 RGBA 采样，结果是纯红色的字。

### 26.3 宿主侧：`Render::WorldTextQuadBuilder`

- 账本按**实体 id** 保留（`Entry{ item, verts, layoutDirty }`），与
  `BitmapQuadBuilder` 同一形状。文字属于场景，场景是它的真源；每帧重排一遍
  等于把增量刷新的收益在文本上还回去。
- 只需要**一个** FontHandle：距离场尺度无关，`kSdfPixelHeight = 64` 只是采样
  精度。世界字高由顶点缩放实现：`scale = dHeight / metrics.pixelHeight`，
  即让字体的 `ascent - descent` 对应 `SyText::dHeight`。
- 排版在**字形像素空间**里算完（y 向下、基点为原点），最后统一
  「缩放 → 翻 y → 旋转 → 平移」。对齐算在缩放之前，旋转才不会把对齐偏移
  当成第二个平移量。`vAlign` 直接对 `Eg::SyTextVAlign` 的四个值 switch
  （含 `Baseline`），不再有第二套编号。
- **不做整像素对齐**。屏幕文字要 `std::round(penX)`，因为覆盖率位图落在半
  像素上会被插值糊一圈；世界文字取整既没有「像素」可对齐，还会让文字在缩放
  时相对图元跳动。
- UTF-8 解码抽到 `Render/TextLayoutUtf8.h`，屏幕/世界两个构建器共用一份。
  两份实现里迟早有一份会漏改（非法序列、截断序列这些分支都不是自明的）。

### 26.4 文本自己一路：删掉全量刷新回退

以前的链路是：脏实体是文本 → `entityToVertices` 返回 false →
`m_pendingFullRefreshFallback = true` → 遍历结束后 `applyFullRefresh`。
代价是改一个字把 10 万条几何全重传了一遍，且表现为「偶发卡顿」。

现在与位图完全对称：

- `SceneRefreshCoordinator` 的增量循环里 `EType::TEXT` 与 `EType::IMAGE`
  一样直接跳过；
- 新增 `reconcileTexts(sm, fullReconcile)`，以「场景中所有可见 SyText」为
  期望集合，做增删改；
- `RenderWidget::setWorldText / removeWorldText / clearWorldTexts` 只做 CPU
  记账并配对 `update()`（§20.1 的双通道纪律），字形图集的创建与上传推迟到
  帧内的 `flush()`（§21.1 的上下文时机约束）。

`entityToVertices` 的 `sawText` 标志与 `m_pendingFullRefreshFallback` 一并删除。
残留的 `!entityToVertices(...)` 分支改为「告警并跳过该实体」：文本与位图都已
各有通道，走到那里只意味着新增图元类型时漏配了离散化分支，静默升级成全量刷新
只会把这个 bug 藏起来。

`RenderSceneBuilder::emitText / emitTextEx / emitImagePlaceholder` 由「告警一次
并跳过」改为**明确的空实现 + 注释说明分工**：它们不是缺口，是职责边界 ——
字形图集与纹理都是跨帧资源，塞进按段重建的几何仓拿不到收益。

### 26.5 帧内提交顺序：从四路变五路

```
rxSessionBeginFrame
  ├─ rxSessionSubmit(场景环境)          网格/工作台/标尺线   layer 10
  ├─ rxSessionSubmit(位图)              世界空间贴图         layer 20
  ├─ rxSessionSubmitDrawList(场景实体)   常驻几何仓           layer 100
  ├─ rxSessionSubmit(世界文字)          SDF 字形四边形       layer 100  ← 新增
  └─ rxSessionSubmit(覆盖层)            选择框/手柄/虚线     layer 200
rxSessionEndFrame
```

世界文字与场景几何**同层**，靠提交顺序排在其后：标注被几何盖住就失去了意义。
`sortKey` 的 `transparent` 位取 1 —— 距离场的边缘就是 alpha 混合。

### 26.6 验证

- DLL 侧 6 例（`RenderxGLTests`）：默认管线全部可用（含 `WorldGlyphSdf`）、
  `WorldGlyphSdf` 与 `WorldTextured` 不是同一条、SDF 模式的字形几何
  （`width + 2*padding`、`bearing - padding`、`advance` 不变）。
- 宿主侧构建器同 §25.6，没有单测：需要活的 GL Runtime，当前无此夹具。
- 人工确认（2026-08-29）：图纸文字原位显示、放大后边缘仍锐利（距离场相对覆盖率
  位图的收益点）、编辑单个文本时其它几何不再重传，三项均正常。

## 27. 3D 收口（一）：DLL 侧（2026-08-30，ABI 5.0）

### 27.1 目标与边界

把 `RenderWidget3D.cpp` / `GizmoRendererGL.cpp` 里的裸 GL 调用迁进 Renderx，
且**2D 逻辑保持不变**。本节只覆盖 DLL 侧——公共 ABI、内建管线、光照参数块、
着色器。宿主接入是下一节。

刻意留在外面的一项：`captureOffscreen` / render-to-texture。它需要一套新的
离屏目标 API（也正好能填 `ViewCaptureService` 的长期空洞），单独一轮做。

### 27.2 三处架构分歧与结论

**(1) 光照算在哪里** → DLL 内建。

2D 完全没有光照：颜色在宿主算好写进顶点，Renderx 只做 `uView * pos` 然后输出
顶点色。3D 不能照搬，因为**高光是视角相关的**：把 Blinn-Phong 的结果烘进顶点色，
相机每动一次就要重传全部顶点（十万面网格每帧数 MB），否则就只能放弃高光。
另一条路——宿主写 GLSL 传进来——等于把跨平台目标（Vulkan / Metal 各需不同着色器
语言）交还给宿主，与整个重构的方向相反。

**(2) 迁移范围** → 除截图外全迁。

**(3) ABI 版本** → 抬到 5.0。三处结构体尺寸变化：`PipelineDesc` 增 `fillMode`
与 `depthBiasConstant`/`depthBiasSlope`（24 → 32 字节）、`MaterialDesc` 增 3D 材质
三色与高光指数、`DefaultPipeline` 追加四项使 `Count` 变化。
Renderx 是与唯一消费方同批构建的子模块，不存在旧 DLL 配新头的场景，
因此按需抬 major 而不引入兼容层（MAJOR 4 也是这么来的：字体 API 破坏性变更）。
深度偏移是在同一次未发布的 5.0 里补的，不另起 6.0——5.0 还没有任何外部消费方。

### 27.3 四条内建管线与「状态提示」

新增 `Mesh3D`（18）、`Mesh3DWire`（19）、`Highlight3D`（20）、`Gizmo3D`（21），
`Count = 22`。

它们打破了一个此前隐含的前提：`Runtime::resolvePipeline` 把「深度关、实心填充」
写死成常量——2D 的遮挡关系由排序键而非深度缓冲决定，所以一直不需要深度。
3D 需要四种不同组合：

- `Mesh3D`：深度测试开 + 深度写入开。三角面之间的遮挡无法用排序键表达
  （互相穿插的面片没有正确的全局顺序）。
- `Mesh3DWire`：同上，`fillMode = Wireframe`。
- `Highlight3D`：深度测试开、`LessEqual`、**不写深度**。高亮线贴在面上，
  `Less` 会被面片自己遮掉；而写深度会让后画的网格被高亮线挡住。
- `Gizmo3D`：同高亮的深度状态，但实心填充 + **深度偏移 1/1**。手柄常与网格
  表面共面，`LessEqual` 也压不住 z-fighting；不写深度使手柄互不遮挡，前后
  关系由提交顺序决定，因此不透明与半透明手柄共用这一条。

与其在 `resolvePipeline` 上继续平铺参数，把这组状态提成 `PipelineStateHint`：
由顶点格式给出默认值（`defaultStateFor`：只有 P3N3 开深度），内建管线表按需覆盖。
好处是宿主若漏填 `pipelineIndex`、走到逐命令的 `resolvePipeline` 兜底，
P3N3 也会拿到正确的深度状态，而不是静默画成一团没有遮挡的面片。

`fillMode` 与深度偏移都必须进管线：Vulkan 的 `VK_POLYGON_MODE_LINE`、
`VkPipelineRasterizationStateCreateInfo::depthBias*` 与 Metal 的
`MTLTriangleFillModeLines`、`setDepthBias:slopeScale:clamp:` 都写在管线对象里，
录制期不可改。因此线框与偏移不能是 `DrawCommand` 上的开关。两者同时进了管线
缓存键，否则 `Mesh3D` 与 `Mesh3DWire`（以及 `Gizmo3D` 与 `Highlight3D`）
会命中同一条管线——先建的赢，另一条静默画错（与 §26 的
`WorldGlyphSdf` vs `WorldTextured` 是同一类碰撞）。

深度偏移一路贯到 RHI：`RasterState::depthBiasConstant/Slope` → GL 后端
`glEnable(GL_POLYGON_OFFSET_FILL)` + `glPolygonOffset(slope, constant)`
（注意 GL 的参数顺序是 factor=斜率、units=常量，与字段顺序相反）。
`GL_POLYGON_OFFSET_FILL` 是**全局开关**，零偏移的管线必须显式 `Disable`，
否则偏移会漏到下一条管线上。`glPolygonOffset` 是新加进 `GLFuncs` 的函数指针。

### 27.4 两个 uniform 块的分工

| | 块 | 位置 | 频率 | 尺寸 |
|--|----|------|------|------|
| 视图 + 材质 | `PushConstants` | 0 号 UBO | per-draw | 128 字节 |
| 光照 | `FrameUniforms` | 1 号 UBO | per-pass | 160 字节 |

`PushConstants` 从 80 字节扩到 128（正好等于 `kMaxPushConstantBytes`），
80..127 是 3D 材质段（`uMatDiffuse` / `uMatAmbient` / `uMatSpecular` /
`uMatShininess`）。材质必须放这里——它随 `DrawCommand::materialIndex` 逐命令变化。

光照不能放这里：160 字节塞不进 128 的预算，而且 `PushConstants` 在每次换管线/
换材质时都会重推，把逐帧不变的常量挂上去是纯浪费。

std140 的对齐纪律不容妥协：`vec3`/`vec4` 需 16 字节对齐，字段顺序不能随意调整。
C++ 侧用 `static_assert(sizeof == 128)` 加两条 `offsetof` 锁定；
`Lighting3DDesc` 的 13 个字段偏移由 `RxRuntime.Lighting3DDescMatchesStd140Layout`
逐条锁定——**`sizeof` 相等不代表布局相等**，字段调换后总大小可能不变，
而 shader 仍按旧偏移取值，表现为「高光颜色被当成光照方向」这类无从下手的错乱。

一个刻意的选择：**2D shader 也声明完整的 128 字节块**。让 2D 只声明前 80 字节
在 GL 上合法（不同程序可对同一 UBO 声明不同长度的块，只要偏移一致），
但那等于把「同一块有两种长度」引入构建期，日后插字段时两种声明会悄悄错位。
`rx_push_constants.glsl` 仍是唯一声明处。

`viewPos` 由宿主提供而非从视图矩阵反解：`DrawPacket::viewMatrix` 是
`proj * view` 的合并矩阵，透视投影下无法稳定恢复眼点。

### 27.5 绑定组按管线记账

`FrameUniforms` 落在 `(set = 0, binding = 1)`——binding 0 被 pushConstant 占用
（GL 后端把它放在 0 号 UBO binding point，用户块从 1 开始）。

只有 P3N3 管线声明这个块。因此 Runtime 维护一份与 `pipelines` 平行的
`pipelineNeedsLighting`，`Session::recordCommands` 据此决定是否
`bindBindGroup`。不这么记账的替代方案是每次换管线都无条件绑一次，
但 2D 管线没声明 binding 1，GL 后端会为此 warn 一条——一帧上百条，
日志直接失去价值。

光照 UBO 与绑定组挂在 Runtime（GPU 资源按设备共享一份）且**懒创建**：
纯 2D 的进程不为此付出任何 GPU 内存。上传时机在 `Session::beginFrame` 内、
`beginRenderPass` **之前**（Vulkan 不允许在 RenderPass 内做缓冲拷贝），
每帧无条件重传而不是脏标记跳过——UBO 由整个 Runtime 共享，多窗口下每个
Session 的光照不同，按脏标记跳过会让第二个窗口沿用第一个窗口的光照
（与 §16 瞬态环「按 Runtime 而非 Session 切段」是同一类多窗口陷阱）。

### 27.6 顺带删除的死文件

- `mesh_3d_instanced.vert`：把 `aModelMatrix` 声明为逐实例顶点属性，
  但 RHI 没有 divisor API，实例全部塌缩到原点；`DefaultPipeline` 里也从来没有
  对应项。建不出来也用不上。
- `highlight_3d.vert` / `.frag`：`Highlight3D` 与 `Gizmo3D` 都复用 `world_p3c4.*` ——
  3D 高亮与手柄的颜色都是宿主给的常量色，不需要光照，没有独立着色器的理由。

## 28. 3D 收口（二）：宿主侧（2026-08-30）

§27 把能力补进了 DLL，本节是宿主侧的落地：`RenderWidget3D.cpp` 与
`GizmoRendererGL.cpp` 里的裸 GL 调用全部迁走，3D 视口与 2D 视口走同一条链路。
迁完之后这两个文件里没有任何 `gl*` 调用，也不再包含
`QOpenGLFunctions / QOpenGLShaderProgram / QOpenGLBuffer / QOpenGLFramebufferObject`。

### 28.1 分层与 2D 同构

- `UI3D::Mesh3DBuilder`（新增）—— 对标 2D 的 `Render::RenderSceneBuilder`：
  实现 `Eg::ISceneGeometrySink`，把网格顶点写进 **GeometryStore**（常驻显存）
  与**保留式 DrawList**（DLL 持有槽位）。取代的旧做法是
  `renderEntities` 每帧 `gatherGeometry` 全场景 + 逐实体 `QOpenGLBuffer::allocate`
  重传顶点 —— 十万面的模型在那条路径上每帧要重传数 MB，相机不动时也照传。
- `GizmoRenderer3D`（由 `GizmoRendererGL` 改名）—— 对标 2D 的
  `BitmapQuadBuilder`：顶点逐帧走**瞬态环**，命令追加给视口统一提交。
  类名里的 `GL` 去掉是因为文件里已经没有任何后端痕迹。
- `Render::host::rxLogBridge` / `qtGlGetProcAddress` 提到
  `UI/Common/Include/Render/RenderxHostBridge.h`，2D/3D 共用一份。
  它们此前在 2D 视口里是文件内静态函数，3D 若照抄就会出现第二份并各自漂移。

### 28.2 常驻 vs 瞬态的划线

划线依据只有一条：**内容是否逐帧变**。

- 常驻（GeometryStore + DrawList）：网格实体顶点。只在
  `markSceneDirty()` 置起 `m_meshDirty` 后重传一次；纯漫游一帧顶点都不传。
- 瞬态（`rxSessionAllocTransient`）：地面网格、世界坐标轴、选中高亮、变换手柄。
  前两者内容其实不变，但瞬态环在 `BeginFrame` 复位，跨帧不能复用，
  因此 CPU 侧顶点缓存在 `m_gridVerts / m_axisVerts`，每帧只做一次 memcpy。

线框切换不动顶点：只把 `DrawCommand::pipelineIndex` 在 `Mesh3D` 与
`Mesh3DWire` 之间翻转（`Mesh3DBuilder::setWireframe`），P3N3 几何共享。
材质同理 —— `setEntityMaterial` 首次 `rxMaterialAdd`、之后 `rxMaterialUpdate`，
材质号不变就不用重写命令。

### 28.3 帧内五路提交

`paintGL` 的顺序是固定的，同 sortKey 时提交顺序决定叠放，因此必须分段 flush：

1. 地面网格 + 世界坐标轴（`kGridLayer = 10`）；
2. 网格实体：`rxSessionSubmitDrawList` 一行；
3. 选中高亮：填充（`Mesh3D` + 高亮材质）+ 线框（`Highlight3D`）；
4. 变换手柄（`kGizmoLayer = 200`）；
5. `EndFrame` 之后才是 QPainter 叠加层。

第 5 步的两处（角落轴指示器、框选橡皮筋）是本轮**没有**迁走的部分：
轴指示器要画文字，得先接 Renderx 的字形图集。它们必须在 `EndFrame` 之后，
QPainter 会重设 GL 状态，夹在命令记录中间会互相干扰。

### 28.4 三处必须区别对待的细节

- **Surface 要开深度**：`SurfaceDesc::enableDepth = 1` 是 3D 与 2D 唯一的
  Surface 差异。3D 的遮挡靠深度缓冲，2D 靠排序键；少了它，`Mesh3D` 的
  深度测试无处可写，模型会按提交顺序互穿。
- **光照每帧下发**：光照 UBO 是 Runtime 共享的（一个设备一份），
  多窗口下每个 Session 都必须在自己的 `BeginFrame` **之前**重传
  `Lighting3DDesc`，否则第二个窗口会继承第一个窗口的光照。
- **参考线管线要「测深不写深」**：地面网格与坐标轴用自建的 P3C3 Lines 管线
  （`depthTest = 1 / depthWrite = 0`）。要测深，否则地面浮在模型前面；
  不能写深，否则细线的插值深度会把贴着它的模型表面戳出条纹。

### 28.5 顺手修掉的一个光照缺陷

旧代码取相机眼点写的是 `QVector3D(view(3,0), view(3,1), view(3,2))`。
`QMatrix4x4::operator()` 是 `(row, col)`，这读的是视图矩阵的**最后一行**，
在 `lookAt` 矩阵里恒等于 `(0, 0, 0)` —— 也就是说镜面高光一直按「相机在原点」
在算。现在直接给 `m_camera.eye*()`，高光位置因此会变（是修正而非回归）。

### 28.6 两处刻意保留的空实现

- **`captureOffscreen` / `captureIsometricOffscreen`**：视口里已无自建 FBO，
  而 Renderx 还没有 render-to-texture 目标 API，无法按任意分辨率离屏出图。
  用视口后备缓冲凑会把请求分辨率悄悄降到窗口大小 —— 这种"看着能用、结果
  不可控"的降级比明确失败更难排查，因此恒返回空 `QImage` 并记错误日志。
  调用方 `ViewCaptureService` 本来就要处理空图像（旧实现 FBO 失败时也是空）。
- **3D DrawList 的剔除**：`rxDrawListUpsert` 的 aabb 是 **2D** 契约
  `(minX, minY, maxX, maxY)`，拿它裁 3D 在斜视角下会误裁可见实体，
  因此 `enableCulling = 0`、`aabb = nullptr`。六平面视锥剔除属于单独一轮。
  合批也一并关掉：相邻实体各有自己的 `materialIndex`，合批会把材质抹成一个。

### 28.7 拖拽预览的重影：按帧对账而不是成对开关

拖拽中选中实体由瞬态顶点逐帧提交（增量矩阵作用到顶点上），此时常驻列表里
那份原位几何必须让位，否则原位与预览位同时可见。

做法是每帧调一次 `syncPreviewVisibility()`：先把上一帧隐藏的全放回，再按
`isTransforming()` 重新隐藏。不采用「按下时隐藏、松开时恢复」是因为退出拖拽
有三条路径（松开、Esc、切换变换模式），任何一条漏掉恢复，实体就永久消失，
而且只在特定操作序列下复现。
