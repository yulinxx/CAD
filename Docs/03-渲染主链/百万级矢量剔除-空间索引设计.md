# 百万级矢量剔除：DrawList 空间索引设计

> 定位：对《新渲染架构》§17.4「DrawList：剔除、按需排序、合批」的升级。
> 把每帧剔除从 **O(n) 线性遍历** 升级为 **空间索引驱动的 O(可见) 查询**。
>
> 本轮范围：只做 **CPU 空间索引（2D 主战场）**。
> Metal / Vulkan 后端、GPU-driven（compute cull + indirect draw）、矢量抽稀 / LOD
> 均不在本轮，属后续演进。

---

## 0. 背景与问题

### 0.1 现状

`DrawList` 的每帧入口是 `resolveImpl`（`Renderx/src/rt/rxIncremental.cpp`）：

```cpp
for (uint32_t slot : m_order)   // 对全部存活条目线性遍历
{
    if (cull2D && entry.boundsKind == BoundsAabb2)
    {
        // 逐条做 AABB 与 viewBounds 的矩形求交
    }
    ...
}
```

- 排序只在 `m_orderDirty` 时重排（改动才 O(n log n)），这块是对的。
- 但**剔除对 `m_order` 全量线性遍历，每帧 O(n)**，这是从「10 万」跨到「100 万」的硬墙。

`Entry` 的组成（`rxIncremental.h`）：`DrawCommand`（80 字节）+ `bounds[6]` + 标记，
约 112 字节/条。100 万条 ≈ 每帧扫 112MB，即使只做一次矩形判交，也是毫秒级到十毫秒级
的开销，且随图元数线性增长。

### 0.2 根因

**没有空间加速结构**。视口只覆盖世界的一小片，却要遍历全部图元。剔除本身的计算量
（一次矩形求交）极小，真正贵的是「遍历 + 触碰 112 字节的 Entry」这件事。

---

## 1. 设计目标与非目标

### 1.1 目标

1. **把剔除降到 O(可见) + 查询开销**：只遍历视口覆盖区域内的候选条目，不再全量线性扫。
2. **增量维护**：空间索引只在 `upsert` / `remove` 时更新，帧间不变——继承 `DrawList`
   现有「只在图元变化时调用」的纪律，不引入每帧重建索引的开销。
3. **跨后端统一**：纯 CPU 实现，不依赖 compute / indirect draw，macOS OpenGL 4.1 可用。
4. **接口零改动**：公共 ABI（`DrawCommand` / `DrawListDesc` / 全部 `rxDrawList*` /
   `rxSessionSubmitDrawList*`）不变，对调用方完全透明。

### 1.2 非目标

- 不做 Metal / Vulkan 后端。
- 不做 GPU-driven（compute cull + indirect draw，`culling.comp` 仍保持未接入）。
- 不做矢量抽稀 / LOD：折线简化是几何语义，属应用层（RenderX 职责边界已明确不做离散化）。
- 不改 `DrawCommand` / `DrawListDesc` / 任何 `static_assert` 锁定的 ABI 尺寸。

---

## 2. 方案选型

| 方案 | 结论 | 理由 |
|------|------|------|
| 均匀单层网格 | ❌ | 单层 cellSize 无法同时容纳「墙」（大尺度）与「螺钉」（小尺度），要么大图元铺满几十格，要么小图元全挤一格。 |
| BVH | ❌ | 增量维护（图元移动/AABB 变化需上溯更新 + 树平衡）复杂；CAD 编辑是高频增量操作，与「帧间不变、只改变化槽位」的契约不契合。 |
| 八叉树（3D） | 暂缓 | 3D 量级小，本轮不做，预留接口后续接。 |
| **分层哈希网格（2D）** | ✅ | 2 的幂次多层 cellSize 天然覆盖大小尺度差异；哈希网格 O(1) 插入/删除，天然契合增量 upsert/remove。 |
| GPU-driven | 后续 | 千万级/复杂 3D 的终局形态，依赖 compute，macOS GL 4.1 不可用。本轮明确不做。 |

**结论：分层均匀哈希网格（hierarchical hashed uniform grid），2D。**

## 3. 数据结构设计

全部为 `DrawList` 私有实现，不暴露到 ABI。

### 3.1 层级

```cpp
// 层 l 的格子边长 = baseCellSize << l（2 的幂次）
// 共 kGridLevels 层（默认 12），覆盖从 baseCellSize 到 baseCellSize << 11 的单图元尺度
struct GridLayer
{
    std::unordered_map<uint64_t, Cell> cells;  // key = 编码后的 (cx, cy)
    float cellSize;
};

struct Cell
{
    std::vector<uint32_t> slots;  // 该格内的 slot 号，无序
};
```

- `baseCellSize` 默认 256 世界单位，`kGridLevels` 默认 12（最大单图元约 52 万世界单位）。
  世界坐标在离散化阶段已做相机相对 double 减法，量级有限，12 层足够；参数为内部常量。
- 哈希键 `(cx, cy)` 用 `int32`（世界坐标可为负），编码进 `uint64`，避免稠密二维数组的
  内存浪费（世界坐标范围大且稀疏）。

### 3.2 Entry 扩展

```cpp
struct Entry
{
    DrawCommand command{};
    float bounds[6]{};
    uint8_t boundsKind = BoundsNone;
    uint8_t alive = 0;
    // 以下为空间索引新增，不影响 ABI
    uint16_t gridLevel = kInvalidLevel;  // 当前所在层；kInvalidLevel 表示未入索引
    uint32_t frameStamp = 0;             // 帧内去重标记
};
```

**不额外存储「所在格」**：`remove` / 移动时从 `bounds` + `gridLevel` 重算格子，
与 `upsert` 共用同一份「算格」函数，逻辑单一，避免两份状态漂移。

### 3.3 选层规则

图元插入「cellSize >= max(AABB宽, AABB高) 的**最细**层」。

由此保证：**每个图元的 AABB 至多覆盖 2×2 = 4 个格**（宽高都 ≤ cellSize，最坏跨两个格边界）。
这是后续增量维护与去重的前提，极大简化边界处理。

## 4. 增量维护

索引维护只在 `upsert` / `remove` / `clear` 发生时进行，帧间不触碰。

### 4.1 upsert

```cpp
RxResult DrawList::upsertImpl(slot, command, bounds, boundsKind)
{
    // 1. 若该槽位已入索引：先按旧 bounds + 旧 gridLevel 摘除
    //    （只在 bounds 变化或 boundsKind 变化时才摘；仅改颜色/顶点范围不碰索引，
    //     与「sortKey 变了才重排」同一思路）
    // 2. 写 command / bounds / boundsKind（现状逻辑）
    // 3. 若 bounds 非空：按选层规则算 gridLevel，算覆盖的 cellKeys（≤4），
    //    把 slot 追加进对应 Cell
    // 4. bounds 为空（覆盖层）：不入索引，gridLevel = kInvalidLevel
}
```

### 4.2 remove / clear

```cpp
// remove：先按 Entry 里的 bounds + gridLevel 摘除索引，再 m_entries[slot] = Entry{}（现状清零）
// clear ：直接重建整张网格（比逐条摘除快），再 std::fill 清零 m_entries
```

摘除与插入都只遍历 ≤4 个格，O(1)~O(4)。

> **补遗（2026-09）：「永可见」列表的摘除曾是 O(N)**
>
> 无包围盒 / 3D 条目不进网格，另存于无序列表 `m_nonIndexed`（2D 视口下照常画、不裁）。
> 它的摘除虽也是 swap-and-pop，但定位 slot 位置一度靠**线性扫描**；全量重建
> `endRebuild` 会对每个 stale piece 调一次 `rxDrawListRemove`，N 次删除相互叠加成
> O(N²)——实测 16.7 万 PLT 图元导入后删除 9.3 万，Debug 下重建耗时 13.2s。
>
> 修复：`Entry` 增加 `nonIndexedPos`（slot 在 `m_nonIndexed` 中的下标），摘除直接
> O(1) swap-and-pop 并修正补位条目的位置；upsert 在网格与「永可见」列表之间迁移时
> 位置成对维护。回归见 `RxRuntimeTests` 的
> `DrawListNonIndexed*` 两个用例。
>
> **补遗 2（2026-09）：几何仓空闲表的 vector 中段插入同样是 O(N²)**
>
> DrawList 的 O(N²) 修掉之后，删除 15.9 万块的全量重建在 Debug 下仍耗时 27.6s
> （单位成本与修复前几乎不变），说明还有第二个同族热点：`GeometryStore` 的空闲表
> `m_free` 是「按 offset 有序、相邻自动合并」的 `std::vector<Range>`，`rxGeometryFree`
> 经 `insertFreeRange` 在 vector 中段插入是 O(N) memmove；15.9 万块按
> unordered_map 哈希乱序释放，前半程相邻命中率极低、空闲表线性膨胀，整体 O(N²)。
>
> 修复：`m_free` 改为 `std::map<uint32_t offset, uint32_t size>`——lower_bound 定位、
> 与前后邻合并、first-fit 摘除全部 O(log N)，first-fit 的偏移局部性语义不变。
> 回归见 `GeometryBulkFreeStaysCoalescedAndReallocatable`（2 万块交错释放后
> 必须合并成单一空洞，再分配严格落回偏移 0 起）。
>
> 两次教训一致：**「释放 N 个资源」路径里，凡是有序容器的中段插入都要按 O(N²)
> 审查**；删除/撤销这类批量操作与导入走的是完全不同的数据结构路径。

## 5. 查询与 resolve 流程

### 5.1 2D resolve（主路径）

```
resolve(viewBounds):
  if (!culling || viewBounds == null):
      // 无剔除：走现状全量路径（遍历 m_order 直接合批，不做判交）
  else:
      stamp += 1                       // 帧内去重标记递增
      visible.clear()
      for layer in 0..kGridLevels-1:
          计算 viewBounds 覆盖的 (cx, cy) 范围
          for 每个相交的 cell:
              for slot in cell.slots:
                  if entry.frameStamp != stamp:
                      entry.frameStamp = stamp
                      visible.push_back(slot)
      // 网格是粗筛选：cell 内条目仍要精确判交（与现状同一份 boundsOutside 公式）
      for slot in visible:
          if AABB 与 viewBounds 相交: 保留，否则剔除计数 +1
      k = visible.size()

      if k > 退化阈值:                    // zoom out 全图可见时回退
          走现状全量路径（遍历 m_order 精确判交 + 合批，不排序）
      else:
          对 visible 按 sortKey 排序     // O(k log k)
          合批（沿用现有 canMerge，规则不变）
```

### 5.2 3D resolveFrustum

**本轮保持现状 O(n) 线性**（`resolveFrustum` 不改）。理由：

1. 3D 场景量级小（几万~几十万面），O(n) 可接受；
2. 3D 视锥剔除是「六平面 vs AABB」，网格会退化成 3D 网格/八叉树，复杂度高；
3. 百万矢量是 2D 主战场，本轮聚焦 2D，3D 网格预留接口后续接。

---

## 6. 退化与回退

**问题**：zoom out 到全图时可见集 k ≈ n，此时「收集 + 排序」反而比现状更贵。

**对策**：设退化阈值，默认 `k > n / 2`（或某个常数下限，如 65536）时回退到现状全量路径。

- 全量路径遍历 `m_order`（已是全局有序），只做精确判交 + 合批，**不排序**。
- 因此 zoom out 不会比现状更差，日常 pan/zoom 得到 O(k log k) 的收益。

平移场景下 `m_order` 不 dirty（sortKey 未变），排序只对可见集做，k 通常几万，
O(k log k) 是亚毫秒级，可接受。

---

## 7. 复杂度分析

| 场景 | 现状 | 改造后 |
|------|------|--------|
| 局部缩放（k=1 万，n=100 万） | O(n) = 100 万次判交 | O(k log k) ≈ 1 万×14 |
| 平移 | O(n) = 100 万次判交 | O(k log k)，k 为可见量 |
| zoom out 全图（k≈n） | O(n) 判交 + 合批，不排序 | 回退现状，无退化 |
| upsert / remove | O(1) | O(1)~O(4) 维护索引 |

核心收益：把「每帧触碰 n 个 Entry」变成「每帧触碰 k 个可见 Entry + 少量格遍历」。
排序仍是 O(k log k)，但 k ≪ n，且真正的墙（全量遍历）被拆掉。

## 8. 正确性边界

这些是「搞错会静默画错」的地方，需进代码注释与测试：

1. **跨格去重**：图元 AABB 最多覆盖 4 个格，查询时会被多个格重复收集。
   用 `frameStamp` 去重，保证每个 slot 只进一次可见集。
2. **网格是粗筛选，精确判交不能省**：cell 相交 ≠ 条目 AABB 相交，
   收集后仍要逐条跑与现状完全相同的 `boundsOutside` 判交。
3. **sortKey 有序是合批前提**：`canMerge` 不检查 sortKey，靠排序保证同状态相邻。
   空间索引只改变「哪些条目进入合批」，不改变排序与合批规则本身。
4. **无 AABB 条目**：`boundsKind == BoundsNone`（覆盖层）不入索引，也不被剔除，
   走现状「不参与剔除」路径，语义不变。
5. **`frameStamp` 回绕**：`uint32` 回绕概率极低；即便回绕，只要一帧内不重复标记即正确
   （每次 `clear` 后重建索引，stamp 从当前值继续即可）。

**黄金标准校验**：新增测试断言「空间索引路径产出的可见集」与「线性扫描逐条判交产出的
可见集」**完全一致**（同一份判交公式），用随机 AABB + 随机 viewBounds 批量比对。
这是防止漏剔/误剔的核心护栏。

## 9. 接口与 ABI 影响

- **公共 ABI 零改动**：`DrawCommand` / `DrawListDesc` / `rxDrawListUpsert*` /
  `rxDrawListRemove` / `rxDrawListClear` / `rxSessionSubmitDrawList*` 全部不变。
- 空间索引是 `DrawList` 私有成员，对外不可见。
- `DrawListStats`（24 字节，`static_assert` 锁定）**本轮不动**。若后续要观测
  「查询格数 / 候选条目数」，优先走 `log.debug`，需要落 ABI 时再按次版本递增处理。

1. **数据结构 + 选层/算格**：`GridLayer` / `Cell` / `Entry` 扩展 + 哈希键编码 + 选层规则。

## 12. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 网格参数（baseCellSize / 层数）不匹配场景尺度，格子过稀或过密 | 2 的幂次 12 层 + 选层规则覆盖大范围；参数集中为内部常量，实测调优 |
| 大量图元聚在单格（热区），退化回 O(cell 内条目) | 分层 + 选层把大图元分散到粗层；极端热区是数据本身问题，后续可用格内细分 |
| 索引维护 bug 导致漏摘/重复 | 黄金标准比对测试 + 复用现有回归；摘除/插入共用同一「算格」函数 |
| 3D 未索引，3D 大场景仍 O(n) | 本轮明确不做；预留 3D 网格/八叉树接口，量级上来了再接 |

## 13. 实测结果（2026-09-13）

测试用例：`RxIncrementalFixture.DrawListMillionPrimitiveCullingBaseline`
（`Renderx/Test/RxRuntimeTests.cpp`）。100 万条 2D 线段散布在 10000×10000 世界范围，
视口 1000×1000（约占 1% 面积，期望可见约 1 万条）。每个视图预热 3 帧后取 10 帧平均。

### 13.1 两种分配顺序的对照

基准刻意做了 A/B 对照，因为「顶点在几何仓里怎么摆」直接决定合批能否生效：

- **scatter**：槽位按随机顺序分配，顶点区间与可见集无关；
- **clustered**：槽位按空间格（与空间索引的 `kGridBaseCellSize = 256` 对齐）排序分配，
  使视口覆盖的格对应**连续槽位段**，进而让排序后的可见条目顶点区间也连续。

### 13.2 数据

Release（`/O2`）：

| 场景 | 视图 | 每帧 | 可见 | drawCalls |
|------|------|------|------|-----------|
| scatter | local | 0.82 ms | 9,982 | 9,978 |
| scatter | pan | 0.93 ms | 10,219 | 10,216 |
| scatter | full | 34.07 ms | 1,000,000 | 1 |
| clustered | local | **0.15 ms** | 9,982 | **430** |
| clustered | pan | 0.34 ms | 10,219 | 2,369 |
| clustered | full | 30.20 ms | 1,000,000 | 1 |

Debug（未优化，仅供对比量级）：

| 场景 | local | pan | full |
|------|-------|-----|------|
| scatter | 13.95 ms | 15.67 ms | 158.74 ms |
| clustered | 2.96 ms | 7.34 ms | 99.76 ms |

建场景（100 万次 upsert，Release）：scatter 71.6 ms，clustered 131.9 ms（后者含一次排序）。

### 13.3 三条结论

**1. 空间索引剔除生效。** 局部视图剔掉 99% 条目、只留约 1 万条，
Release 单帧 0.15~0.82 ms，达到设计目标。

**2. 合批是性能的决定因素，且它依赖调用方的顶点布局。**
`drawCalls` 从 9,978 降到 430，耗时从 0.82 ms 降到 0.15 ms（5.4 倍）。
但要注意这里的**隐式耦合**：clustered 之所以生效，是因为槽位按「与空间索引
相同的格粒度（256）」聚集。若用更大的聚类格（如 1000），同一索引格内会混入
来自不同聚类格的条目，槽位在格内重新变得稀疏，合批立刻失效（实测仅从
9,978 降到 9,374，几乎无效）。

也就是说：**合批要求调用方按空间索引的格粒度组织顶点**——这是当前架构里
一处未显式表达的约束，也是后续要解决的接口问题（见 §14）。

**3. zoom out 全图是唯一明显的遗留瓶颈：约 25 ~ 34 ms/帧（波动约 30%）。**
该路径走退化回退的线性遍历：对 100 万条逐条判交 + 合批。

> **最终定性（见 §14.8）：这是一个「可接受、且不应用此前的内存优化手段解决」的
> 边缘场景。** 正确的解法是 LOD（多级细节，应用层配合），不是继续在 RenderX
> 的线性遍历上做文章。此前据此做的两次内存优化均已证伪并回退（§14.1、§14.5）。

## 14. 后续优化方向

### 14.1 已排除：热冷数据分离（实测无效，已回退）

曾假设全图 30ms 受内存带宽限制（`Entry` 每条 112 字节），据此实现了一版
「剔除热数据」（40 字节/条的紧凑数组 + 预计算合批标志）。

**实测结论：该优化零收益，已回退。** 依据是回退后的重复测量：

| 状态 | clustered full |
|------|----------------|
| 优化前（首次测量） | 30.20 ms |
| 优化后 | 25.69 / 25.54 ms |
| **回退后** | **25.77 ms** |

回退后仍落在「优化后」的区间里，说明那 12~15% 完全来自测量噪声。

由此得到一条硬结论：**全图路径的瓶颈不是内存带宽**——40MB / 25ms ≈ 1.6GB/s，
远低于单线程带宽上限。基于错误假设做重构是这轮的主要教训：**应先做逐段计时
定位真瓶颈，再动手**。

### 14.2 基准本身的噪声问题（需先解决）

full 视图的重复测量在 25.5 ~ 34 ms 之间波动（约 30%），单次 10 帧平均不足以
支撑「改善 15%」这类量级的结论。在继续优化全图路径之前，必须先让测量可信：
提高帧数或重复轮次取最小值，或在 `resolve` 内部做逐段计时（判交 / 排序 / 合批
分别计时）。

### 14.3 可信测量下的成本分解（2026-09-13 补充）

在修掉测量方法后（每变体**独立进程**运行 + 多轮取最小值 + 规模降到 20 万），
终于拿到可复现的数据。跑法：

```
RenderxGLTests --gtest_filter=*ZoomOutBreakdownCullMerge*
RenderxGLTests --gtest_filter=*ZoomOutBreakdownNoCull*
RenderxGLTests --gtest_filter=*ZoomOutBreakdownNoMerge*
RenderxGLTests --gtest_filter=*ZoomOutBreakdownNeither*
```

20 万条全部可见（走退化回退的线性路径），Release：

| 变体 | 每帧 | drawCalls | 含义 |
|------|------|-----------|------|
| cull+merge | 4.80 ms | 1 | 现状 |
| no-cull | 1.34 ms | 1 | 去掉判交 |
| no-merge | 14.62 ms | 200,000 | 去掉合批 |
| neither | 11.19 ms | 200,000 | 纯遍历 + 输出 |

两条独立路径算出的判交成本高度一致：

- `cull+merge − no-cull` = 4.80 − 1.34 = **3.46 ms**
- `no-merge − neither` = 14.62 − 11.19 = **3.43 ms**

**结论（可信）**：

1. **判交占现状的 72%**（3.46 / 4.80），约 17ns/条。这才是 zoom out 的热点，
   不是内存带宽（旧假设）。
2. **合批的价值约 3 倍**（14.62 → 4.80）。
3. 交叉验证：20 万条 4.80ms 折算到 100 万条约 24ms，与独立测量到的
   25.7ms 吻合，说明这套测量方法可信。

### 14.5 已排除：针对判交的紧凑布局（实测无效，已回退）

§14.3 指出判交占 72%，据此把包围盒复制成独立的紧凑数组（32 字节/条，按 slot
索引），让判交不再触碰 `Entry` 的第二个 cache line。

**实测结论：无效，判交反而更慢，已回退。** 同批内的相对量：

| 状态 | 判交成本（cull+merge − no-cull） |
|------|--------------------------------|
| 原始 | 3.46 ms |
| 紧凑 bounds 版 | 4.71 ms |
| 回退后 | 4.13 ms |

**判断失误在哪**：`Entry` 的 112 字节里，`command`（cache line 0）与 `bounds`
（line 1）**都是热数据**——合批要 command、判交要 bounds，两条都必须读。
把 bounds 分离出去只是**多读了一个数组**，净访存不降反升。

由此得到一条可复用的边界：

> 在「成对访问」的场景里，分离热数据不会减少访存。
> 唯一有效的方向是让**单条数据压进一个 cache line**（≤64 字节）。

而单条压缩要动 `DrawCommand`（80 字节，公共 ABI 不可改），或改变合批机制
（见 §14.6-2）——两者都不是小改动。

### 14.6 测量方法要点（后续做性能改动必须遵守）

| 做法 | 原因 |
|------|------|
| 每个变体**独立进程**跑 | 同进程连跑会让累积分配改变内存状态，实测同一场景差异达 2.4 倍 |
| 多轮取**最小值**而非均值 | 环境噪声只会让某轮变慢；均值曾把噪声当成 15% 收益（§14.1） |
| 规模取 20 万量级 | 够体现 O(n)，又不让内存压力主导 |
| 用**两条独立路径**交叉验证同一量 | §14.3 中判交的两个测法差 0.03ms，可信度由此建立 |
| **只比较同批内的相对量** | 机器状态会漂移：同一 `no-cull` 基线在三批测量中为 1.34 → 1.57 → 1.88ms（+40%），跨批次比绝对值会得出错误结论 |

### 14.7 结论：本轮性能优化到此为止

**渲染链路的核心性能已经达标**（局部缩放 0.15~0.82 ms、平移 0.32~0.93 ms，
均为 Release 实测）。唯一「看起来慢」的场景是 zoom out 全图（25~34 ms），但：

1. 它是**边缘场景**——CAD 用户不会长时间停留在「100 万条图元全部可见」的状态，
   那意味着每条只剩亚像素，看不清任何东西。
2. 它是**视觉冗余**的——全图时渲染的是大量用户根本看不见的信息。
3. 这个场景的正确解法是 **LOD**（多级细节：缩到远处时用抽稀后的简化几何），
   而 LOD 的几何抽稀属于**应用层**（RenderX 职责边界明确不做几何离散化）。

因此在 RenderX 层面，zoom out 全图 25ms 应标记为**已知、可接受**，不作为继续
优化的目标。

### 14.8 后续方向（仅当确实需要时）

1. **LOD 多级细节**（真正解决 zoom out 的正确路径）。需要应用层配合做几何抽稀，
   RenderX 侧提供「按缩放级别选哪一级几何」的机制。属跨层设计，非 RenderX 单方
   面能完成。
2. **3D 视锥剔除的空间索引**（3D 场景量级上来后再做）。
3. **合批的显式契约**（§13.3 结论 2 的隐式耦合）。是否值得做取决于是否有真实
   场景因「调用方不知道 256 格粒度」而出现性能问题——目前没有这样的证据，
   暂缓。
