# 厂商接入现状

> 这份文档记录每个适配器的完成度、参数清单与**未实测项**。各厂商适配器头文件的「未实测的部分」都指向这里。
> **上机验证后请直接改这份文档**：把未实测项打勾或改成实测结论，附上卡型、SDK 版本、日期。
> 最后更新：2026-08-25

## 0. 总览

| `bjjcz_ezcad` | 金橙子 BJJCZ | Galvo + Laser | `MarkEzd.dll` | Windows | 完成 | 未测 |

## 1. `bjjcz_ezcad` —— 金橙子 / EzCad 振镜卡

- 显示名：金橙子 / EzCad 振镜卡 (MarkEzd)；型号在 `open()` 后填为 `LMC series`
- 接口：`IGalvoCard` + `ILaserSource`（**无 IO**，红光/吹气需另配 IO 模块）
- 编程模型：立即执行型，卡上无缓冲队列，进度由适配器自行维护
- 参数：`sdk_path`、`ezcad_dir`(必填)、`correction_file`、`field_size_mm`(默认 110，必填)、`rated_power_watt`(默认 30)、`test_mode`(高级)

未实测：

- [ ] `lmc1_Initial` 对 `ezcad_dir` 的路径形式要求（是否必须含尾部分隔符、是否接受相对路径）
- [ ] 校正文件版本兼容性（`.cor` / `.ecf`）
- [ ] `testFire` 由 LaserOn + Dwell + LaserOff 组合实现，**适配器刻意不阻塞**，需上层配 `QTimer::singleShot` 收光——需确认真机上收光时序是否可靠
- [ ] 功率百分比到 SDK 数值的映射（是否线性、是否受激光器类型影响）

## 2. `scanlab_rtc5` —— SCANLAB RTC5 / RTC6

- 显示名：SCANLAB RTC5 / RTC6 振镜卡；型号运行期填为 `RTC card #N`
- 接口：`IGalvoCard` + `ILaserSource` + `IIoModule`（EXTENSION 口）
- 编程模型：列表缓冲型。`set_start_list` → 写指令 → `set_end_of_list` → `execute_list`，进度靠查 list 位置
- 必需符号：`init_rtc5_dll`、`free_rtc5_dll`、`set_start_list`、`set_end_of_list`、`execute_list`、`get_status`、`jump_abs`、`mark_abs`；另有约 25 个可选符号，缺失则收窄能力
- 参数：`sdk_path`、`card_no`(默认 1)、`correction_file`(必填)、`field_size_mm`(默认 100)、`bits_per_mm`(高级，0 表示按 `65536/field` 推算)、`laser_mode`(CO2/YAG1/YAG2/YAG3/MOPA/IPG，默认 MOPA)、`rated_power_watt`、`safe_output_levels`(高级)

未实测（这张卡的坑最多）：

- [ ] **坐标单位是 bits 不是 mm**（16 位有符号）。`bits_per_mm` 的实际标定值需用已知尺寸的方块实测校准
- [ ] `init_rtc5_dll` 返回值的位域含义（当前只判非零失败）
- [ ] 延时单位换算：扫描延时按 10 µs、激光延时按 ½ µs——需实测确认，写错会表现为拐角过烧或缺角
- [ ] `arc_abs` 是否存在；不存在时走弦高 0.01 mm 离散，最大 4096 段
- [ ] RTC6 的符号命名是否与 RTC5 一致（当前只按 `RTC5DLL` 搜索，RTC6 需用户把 DLL 放到 `sdk_path`）
- [ ] EXTENSION 口无输出回读，`readDigitalOutputs` 返回的是影子值，需确认现场是否接受

## 3. `leadshine_ltdmc` —— 雷赛运动控制卡

- 适用：DMC1000/2000/3000/5000 系列 PCI/PCIe，以及 SMC/ECI 系列以太网控制器（同一套 LTDMC.dll）
- 接口：`IMotionCard` + `IIoModule`（默认 16 DI / 16 DO）
- 编程模型：连续插补 list，**必须边跑边续填**；填过量会导致几何被静默截断
- 参数：`sdk_path`、`card_no`、`axis_count`(必填)、`pulse_per_mm`(必填)、`max_velocity`、`acc_time`、`s_curve_time`(高级)、`laser_enable_bit`(默认 -1 = 不用)、`di_count`、`do_count`、`safe_output_levels`(高级)

已在代码中特殊处理的坑：

- `dmc_board_init` **返回卡数量**，`<= 0` 才是错误，不走通用的 `dmcResult` 判定
- 激光由普通 DO 驱动（`laser_enable_bit`）；`pausePlan` 强制关光，`resumePlan` 恢复原状态
- 输出逐位写，不整端口写——整端口写会连带释放别人置起的夹具

未实测：

- [ ] 续填水位（一次填多少条、剩多少条开始续）在真机高速下是否够
- [ ] `dmc_conti_*` 系列在多轴联动下的实际缓冲深度
- [ ] `pulse_per_mm` 与卡内部单位换算的精度损失
- [ ] 回零信号极性与 `dmc_home_move` 参数组合

## 4. `zmotion_zmc` —— 正运动 ZMC 控制器

- 接口：`IMotionCard` + `IIoModule`（默认 8 DI / 8 DO）
- 连接：`connection` = `eth`（默认，配 `ip_address`）或 `pci`（配 `card_no`）
- 参数：`sdk_path`、`connection`(必填)、`ip_address`(默认 192.168.0.11)、`card_no`、`axis_count`(必填)、`pulse_per_mm`(必填)、`atype`(高级)、`max_velocity`、`acceleration`、`sramp`(高级)、`laser_enable_io`、`io_output_base`(默认 8)、`di_count`/`do_count`/`ai_count`/`ao_count`、`safe_output_levels`(高级)

设计取舍：

- **刻意不使用控制器内置的 ZBasic 解释器**：那样工艺逻辑会分裂成「PC 一半、控制器一半」，两边版本不同步就是现场事故；本适配器只把控制器当执行器。
- 激光同步用 `MOVE_OP`（进缓冲、与运动同步）而不是 `SetOp`（立即执行、与运动不同步）。
- `io_output_base`：ZMC 的 IN/OUT 共用编号空间，输出起始号由接线决定，因此做成参数而非硬编码。
- `ZAux_OpenEth` 需要可写 `char*`，IP 先拷进本地缓冲再传。
- SDK 用 `float`，double → float 的精度损失已评估为可接受（1 µm 级）。

未实测：

- [ ] 以太网连接的断线重连行为与超时时长
- [ ] `atype` 取值与实际驱动器类型的对应关系
- [ ] 每轴缓冲深度查询在多轴插补时的语义
- [ ] `io_output_base` 在不同型号上的默认值

## 5. `aerotech_a3200` —— Aerotech A3200

- 接口：`IMotionCard` + `IIoModule`
- 参数：`sdk_path`、`axis_count`(必填)、`max_velocity`(单位 units/s)、`laser_output_bit`、`io_axis_index`、`di_count`/`do_count`/`ai_count`/`ao_count`、`safe_output_levels`(高级)

必须知道的三件事：

1. **返回 BOOL，非零 = 成功**，与国产卡完全相反。全部收敛在 `Impl::check()` 里，失败时用 `getLastErrorString` 取详情。
2. **PSO 未实现**。激光走普通 DO（`laser_output_bit`），`open()` 时会 `WARN`。PSO（位置同步输出）是这台控制器的招牌能力，高速打标场景需要时再补。
3. `setAxisConfig` 会 `WARN`：`pulse_per_unit` 之类的标定在控制器的 `.prma` 参数文件里，软件侧改不动。

其他：工作任务固定用 Task 1；队列水位靠 `STATUSITEM_QueueLineCount` / `QueueCapacity`；**刻意不声明 `CapArcInterp`**（先用离散化保证正确性）。

未实测：

- [ ] `A3200Connect` 在 A3200 未启动时的返回与超时
- [ ] Task 1 是否与客户现场既有程序冲突
- [ ] 队列水位阈值在高速下是否够
- [ ] `io_axis_index` 与实机 IO 板卡编号的对应

## 6. `ruida_rdc` —— 睿达一体控制器

- 接口：`IMotionCard` + `ILaserSource`；`sdkVersion` 标为 `protocol (no vendor SDK)`
- 传输：`transport` = `file`（默认，可用）/ `udp` / `serial`（均返回 `NotImplemented`）
- 参数：`transport`(必填)、`output_path`(file 模式下必填)、`travel_x`/`travel_y`(必填)、`invert_y`(默认开)、`scramble`(高级，默认开)、`magic`(高级，默认 0x88)、`rated_power_watt`

为什么先做文件输出：

1. 产物可以直接在 RDWorks 里离线校验，不需要机器；
2. UDP / 串口会把 Qt6::Network / QSerialPort 拉进部署包，需先定部署策略；
3. U 盘拷文件到机器是这类设备真实存在的主流工作流。

协议要点：坐标为 5 字节 / 7 位编码的 µm 整数；`pushCoordUm` 对负值与溢出**直接拒绝**而不是截断；已用操作码 `0x88/0xA8/0xC6/0xC9/0xE7/0xD7`；`copyCommandStream()` 供测试取字节流比对。

`emergencyStop()` 会先把本地状态置 `Aborted` 并发事件，然后返回 `NotImplemented`——file 模式确实没有实时通道，但静默返回 `Ok` 会让上层以为机器已经停了。

未实测：

- [ ] `ruidaScramble(b, magic)` 的加扰算法（`scramble` / `magic` 两个参数就是为了现场试出正确组合）
- [ ] 各操作码的参数字节序与个数
- [ ] 生成的文件能否被 RDWorks / 机器面板正确识别
- [ ] `invert_y` 的正确取值（不同机型原点位置不同）

## 7. `simulated_composite` —— 模拟设备

- 接口：四个全实现（`IMotionCard` + `IGalvoCard` + `ILaserSource` + `IIoModule`），另外实现 `ISimulationClock`
- 参数：`axis_count`、`field_size_mm`、`rated_power_watt`、`laser_type`(Fiber/CO2/UV/Green/Picosecond)、`safe_output_levels`(高级)、`correction_file`(高级)
- 规格：4 轴、16 DI / 16 DO / 4 AI / 2 AO

它是**契约的参考实现**，`HardwareTests` 全部用例跑在它上面。由 `tick(elapsedMs)` 确定性推进：不起线程、不用 `QTimer`、不用随机数，因此用例可重复。宿主只拿得到 `IDevice*`，通过 `hwQuery<ISimulationClock>()->advance(dt)` 推进时间——真机上这个查询返回 `nullptr`，宿主自然跳过，不需要判断「是不是模拟器」。


支持故障注入（激光故障、轴报警、联锁断开、温度），用于在无硬件条件下验证上层的报警与安全链路。

**模拟设备比真机更严或更松都是 bug。** 例如「未回零禁止绝对定位、但允许相对定位」这条，就是先在真机适配器里成立、再回头修正模拟设备而对齐的。
