# 数据到硬件全链路

> 本文回答一个问题：**一份画在屏幕上的图，是怎么变成机器上的动作的？**
>
> 适用范围：全链路 —— 文档模型 → 工艺 → 加工几何 → 设备指令 → 厂商适配器 → 真机。
> 配套阅读：[CAM层与IR边界.md](CAM层与IR边界.md)（为什么这样分层）、[硬件抽象层架构.md](硬件抽象层架构.md)（设备侧契约）。
> 建立日期：2026-10-22

---

## 1. 数据从哪里来（文档模型）

### 1.1 图元是唯一真源

| 概念 | 位置 | 备注 |
|---|---|---|
| 图元 | `Eg::SyEntity`（Engine/Common） | 由 `Eg::SceneManager` 唯一持有 |
| 图层 | `Eg::SyLayer`（Engine/Common） | 只存归属与显示属性 |
| 工艺 | `Eg::ProcessDefinition`（Engine/Common，v2 新增） | 加工参数的载体 |

`SceneManager` 持有 `std::vector<std::unique_ptr<SyEntity>>`，外部只拿裸指针观察。
跨模块传递用 `EntityId` 而不是指针。

### 1.2 图元类型与加工类别

加工链路**只认加工类别，不认图元类型**。分类由 `Eg::Cam::GeometryExtractor::kindOf()` 给出，
是一张纯函数表（完整表见 [CAM层与IR边界.md §4](CAM层与IR边界.md)）。

**为什么要有这张表**：旧的加工链路直接用 `Eg::Geo2DPath::decompose`，
而那是**拾取用**几何 —— 位图返回四个角点、二维码返回包围盒、色块返回三角剖分的每一条边。
用它做加工的实际后果：

| 图元 | 旧行为（拾取几何） | 正确行为 |
|---|---|---|
| 图片 | 烧一个矩形框 | 光栅雕刻（未实现 → 显式报不支持） |
| 二维码 | 烧一个矩形框 | 按模块烧方块 |
| 色块 | 照着三角网烧（视觉上是一团乱麻） | 边界环 + 填充扫描 |
| 文字 | **静默消失**（界面显示加工成功，工件上什么都没有） | 字形轮廓 |
| 条码 | **静默消失** | 条码模块几何 |

「静默消失」是其中最危险的一种：操作者以为烧了，工件上什么都没有。

### 1.3 单位与坐标系

| 项 | 约定 | 落点 |
|---|---|---|
| 长度单位 | **恒为 mm**，全仓库只有这一种长度语义 | 导入时 `Fio::scaleParseResult` 归一 |
| 角度 | 弧度（Cam / Engine2D） | |
| 时间 | 微秒（HAL） | |
| 速度 | mm/s | |
| 用户空间 | X 右、Y 上、左下角为原点 | 渲染、编辑、拾取 |
| 机器空间 | 由台面尺寸 + 原点角点决定 | `Eg::MachineFrame` |

文档 v2 起显式声明 `DocumentMetadata.units`（恒为 mm），为将来支持英制留好位置 ——
现在它是「用户以为自己用什么单位」的记录，而不是换算开关。

## 2. 工艺：参数的唯一载体

### 2.1 为什么工艺是一等对象

把工艺参数挂在图层上，在三个真实场景里立刻失效：

1. **同层不同参数**：一个图层里既有「要切透的外框」又有「只标刻的标识」，
   只能拆成两个图层来迁就数据结构 —— 图层本来是为了组织，不是为了迁就存储；
2. **同一批图元加工两次**：粗切 + 精修，参数不同但目标相同；
3. **多工序**：先雕刻后切割，顺序本身是工艺知识，图层没有「顺序」以外的表达能力。

所以 v2 起工艺成为独立对象，图层只保留一个**默认绑定**（`LayerData.default_process_id`）作为快捷方式。

### 2.2 参数类型只有一份

v1 时代仓库里有四套互不相通的工艺参数：

| 旧参数 | 位置 | 问题 | v2 处置 |
|---|---|---|---|
| `HardwareProfile` | Engine2D，按图层绑定 | `HardwareProfileManager` 全仓库无实例化点；`hardwareProfileId` 不写入 `.sy` | **删除** |
| `Eg::ProcessParams` | SQLite 预设 | 与图层/图元无绑定 | **合并** |
| `Eg::MaterialInfo` | 材料推荐值 | 与下面一份重复 | **合并** |
| `MaterialDatabase::MaterialInfo` | Hardware 模块 | 材料库是设备知识，位置错 | 迁出，作为**推荐值选择器** |
| `LayerProcessParams` | Main/Src/Hardware | 第四份 | **改为 `Eg::ProcessParams` 的类型别名** |

v2 的唯一参数类型：`Eg::ProcessParams`（`Engine/Common/Include/Engine/Process/ProcessParams.h`）。

它放在 Engine/Common 是因为 **FileIO 只依赖 EngineCommon，Engine2D 也依赖 EngineCommon** ——
放这里，三方（持久化 / 几何 / 界面）都能用，且不产生任何新的模块依赖。

参数范围与校验规则由 `Eg::ProcessSchema` 的一张表统一描述（字段名 / 类型 / 单位 / 范围 / 默认值），
界面按表生成控件、新增参数只需加一行 —— 与 HAL 里设备参数的 `ParamSchema` 同一思路。

### 2.3 保守的默认值

`ProcessParams` 的默认值刻意保守：**50% 功率 / 100 mm/s / 1 遍**。

理由：接到一台陌生机器上，「功率不足打不深」是可返工的，而「满功率烧穿台面」不是。

其中一条硬规则：**速度为 0 不是「慢慢走」，而是「原地持续出光」** —— 在真机上是烧穿孔洞的最快方式。
所以 `speedMmPerSec <= 0` 是**非法值**，而不是被钳制到某个最小值。

## 3. 加工几何（`Eg::Cam`）

### 3.1 为什么需要这一层

直接编译成指令会漏掉一整类工艺知识，因为这些东西在「段」这一层才能表达：

| 工艺知识 | 为什么指令流里表达不了 |
|---|---|
| 填充 | 区域 → 扫描线，需要知道「这是个面」而不是「一串线」 |
| 割缝补偿 | 需要知道轮廓的**绕向**（外环外扩 / 孔洞内缩），逐条指令上已经看不出来了 |
| 内孔先于外轮廓 | 需要「轮廓之间的包含关系」，指令流里没有这个信息 |
| 排序与空移优化 | 需要能自由重排的一组段 |
| 预览与统计 | 需要「有哪些段、多长、属于哪个图元」 |

### 3.2 圆弧的行进方向

这是加工几何与几何算法**唯一的语义差异**，值得单独说：

- `Eg::PathSegment`（几何算法用）的约定是「`dStartAngle → dEndAngle` 恒为 CCW 参数化」。
  那是几何算法需要的 —— 它们只关心「这段弧占哪些点」。
- 加工链路多要一件事：**往哪边走**。

用户可以逆时针画弧（`dEndAngle < dStartAngle`）。按几何约定理解，
本该 90° 的小弧会变成 270° 的大弧。真机走错边不是「差一点」，是**烧掉一整块料**。

v1 的编译代码写着「Geo2DPath 约定分解出的圆弧一律为 CCW 扫掠，因此这里恒传 true」——
那是错的。

现在 `Eg::Cam::PathSegment` 自带 `counterClockwise` 字段，
提取器用 `Geo2DPrimitives::arcSweepAngle` 的**带符号**结果判定方向，编译器照传，
镜像时按 `MachineFrame::isReflected()` 取反。

### 3.3 圆弧为什么拆成两段半圆

整圆在 `Cam` 层被拆成两段 180° 圆弧。原因：不少运动控制卡不接受「起止点重合的单条圆弧」
（它无法判断该走 0° 还是 360°），有的会走成整圆、有的直接报错。拆开在所有卡上都合法，
代价只是多一条指令。

## 4. 设备指令（`Hw::MotionPlan`）

### 4.1 为什么要有 IR

没有 IR 时的耦合形态：

```
Engraving 刀路 → 直接调用 LaserController::loadToolpath(点数组)
```

这条路径隐含了「设备就是一个逐点走位的东西」的假设。可是：

- **振镜卡**（金橙子 / SCANLAB RTC5）的原生模型是「跳转 + 标刻 + 延时」指令流，
  出光与运动在硬件层同步，不存在「一个点一个功率」的概念；
- **运动控制卡**（雷赛 / 正运动）的原生模型是「插补段 + IO 联动」；
- **Ruida 控制器**接收的是它自己的私有二进制指令包。

IR 的职责边界：

```
几何/工艺层 → 生成 MotionPlan（与厂商无关，纯数据）
设备适配器  → 把 MotionPlan 翻译成自己 SDK 的调用序列
```

于是：新增一种硬件 = 新写一个翻译器，**几何层零改动**；
新增一种工艺 = 生成新的 IR 指令，**所有已支持硬件自动受益**。

### 4.2 指令集

| Opcode | 语义 |
|---|---|
| `RapidTo` | 快速定位（不出光） |
| `LineTo` | 直线插补，`laserOn` 决定是否出光 |
| `ArcTo` | 圆弧插补，`counterClockwise` 决定绕向 |
| `Dwell` | 原地停留（激光器起停延时补偿） |
| `LaserOn` / `LaserOff` | 出光使能 |
| `SetLaserParams` | 功率/频率/脉宽/波形 |
| `SetFeedRate` / `SetRapidRate` | 进给/空移速度 |
| `SetDigitalOut` | IO 输出（吹气、送料、指示灯） |
| `WaitDigitalIn` | 等待输入点（超时则失败） |
| `WaitMotionDone` | 等待前序运动排空 |
| `BeginLayer` / `EndLayer` | 图层分段 |
| `BeginPass` / `EndPass` | 遍次分段 |
| `BeginComment` / `EndComment` | 注释块 |

指令集刻意保持**小而完备**：每新增一个 opcode，所有适配器都要实现或显式拒绝。

## 5. 坐标换算：只发生一次

### 5.1 机器坐标系

`Eg::MachineFrame`（Engine2D/Machine）描述「用户空间 → 机器空间」的映射：

| 原点角点 | 变换 |
|---|---|
| 左下（默认） | 恒等 |
| 右下 | X 镜像 |
| 左上 | Y 镜像 |
| 右上 | X/Y 双镜像（等价绕台面中心旋转 180°） |

台面尺寸来自 `MachineFrameConfig::tableW / tableH`。

### 5.2 换算点只有一个

**换算发生在编译器发射指令的那一刻**（`MotionPlanCompiler` 里的 `FrameTransform`）。
适配器与作业服务都不再换算。

之前的状态是「UI2D 的旧链路在 `HardwareLaserService` 里换算、新 HAL 链路完全不换算」——
两套坐标语义并存，同一份文档走不同路径会烧到不同位置。

### 5.3 镜像会反转绕向

X 镜像把逆时针变成顺时针。只改端点不改绕向，圆弧会走反边。
编译器在发射 `ArcTo` 时按 `frame.isReflected()` 取反 `counterClockwise`。

> ⚠️ 这条路径**目前尚无单测覆盖**，真机联调前必须补（见 §7）。

### 5.4 机器档案不在文档里

`MachineProfile`（`Main/Src/Hardware/MachineProfile.h`）是**磁盘上的可写文件**，
描述「眼前这台机器接了什么卡、卡在几号槽、IP 是多少、急停接在哪一路输入」。
每台机器都不同，装机现场才知道 —— 若塞进 qrc，就得每装一台机器重新编译一次可执行文件。

文档 v2 起只在 `ProjectSettings.machine_profile_ref` 里记一个**引用**（用于追溯「这份图是为哪台机器出的」），
**不参与坐标换算** —— 换算的依据是本机装配时的机器档案，不是文档里的这个字符串。

## 6. 失败必须显式

### 6.1 三类失败与处理

| 失败 | 表现 | 处理 |
|---|---|---|
| 工艺参数非法 | 功率越界、速度 ≤ 0、遍数 < 1 | **拒绝编译**，报出具体哪一项 |
| 没有可加工内容 | 空场景、选集为空、全部图层被禁用 | **拒绝编译**，报「一共 N 个、跳过 M 个」 |
| 存在无法加工的图元 | 位图（光栅未实现）、条码（模块几何未实现） | **默认拒绝整份作业**，列出类型与数量 |

第三条对应 `ToolpathJobSpec::failOnUnmachinableEntity`（默认 `true`）。
默认拒绝是故意的：跳过意味着「用户以为烧了、其实没烧」——
在激光加工里这等于废件。宁可拒绝开工并说清楚是哪一类图元。

界面后续可以提供「忽略这些图元继续」的显式开关（那时才置 `false`），
前提是它把被跳过的清单完整展示给操作者。

### 6.2 为什么「空计划」必须当失败

如果空计划被当成成功返回，上层会照常点亮「开始加工」，
操作者按下去什么都不发生，且没有任何错误提示 —— **最难排查的一类现场问题**。

### 6.3 安全联锁

设备开始之前，安全裁决先跑（`DeviceHost` 的安全门 / 急停 / 温度等）。
裁决不通过 → 拒绝开工；加工中裁决转坏 → 自动暂停。

门控发生在**编译之前**：设备没起来时不应该白白编译一遍十万条指令。

## 7. 当前缺口（按优先级）

| # | 缺口 | 影响 | 位置 |
|---|---|---|---|
| 1 | **镜像后绕向反转无单测** | 反射机台上圆弧可能走反边 → 烧废 | `MotionPlanCompiler` |
| 2 | **光栅雕刻未实现** | 图片不能加工 | `Cam` 层 `Raster` 类别 |
| 3 | **填充 / 扫描线阶段未实现** | 色块填充图层不能按面积加工 | `Cam` 层 `Fillable` 类别 |
| 4 | **割缝补偿未实现** | 切割没有割缝补偿，尺寸偏大 | `Cam` 层 Transform 阶段 |
| 5 | **排序优化未接入** | 空移路径不是最短，加工慢 | `Cam` 层 Order 阶段（`PathOptimizerV2` 已存在但未进链路） |
| 6 | **pass 展开仍在编译器里** | 每遍不能独立优化 | 见 [CAM层与IR边界.md §5.2](CAM层与IR边界.md) |
| 7 | **单点打点用零长度移动表达** | 部分卡不接受零长度移动 | `MotionPlanCompiler::emitEntity` |
| 8 | **真机实测全部为空** | 六个适配器都只做过编译与模拟验证 | 见 [厂商接入现状.md](厂商接入现状.md) |

## 8. 排查手册

现场出问题时，按这条链**从上游往下游**查，每一步都有对应的可观测点：

| 现象 | 先查什么 | 怎么查 |
|---|---|---|
| 屏幕上有的东西没被烧 | 提取阶段 | `GeometryExtractor::kindOf()` 返回什么？`Unsupported` 会被编译拒绝（除非显式跳过） |
| 烧出来的是矩形框不是图 | 提取阶段 | 说明走到了旧的 `Geo2DPath` 路径 —— 那是拾取几何，不该出现在加工链路里 |
| 位置整体偏移 / 镜像 | 换算阶段 | `MachineFrame` 的原点角点与台面尺寸；换算**只**在编译器发生一次 |
| 圆弧走反边 | 方向阶段 | `Cam::PathSegment::counterClockwise` + 镜像取反 |
| 尺寸偏大 / 偏小 | 补偿阶段 | 割缝补偿尚未实现（§7 #4） |
| 加工特别慢 | 排序阶段 | 路径优化未接入（§7 #5） |
| 按了开始没反应 | 编译阶段 | `ToolpathCompileResult::error` 有内容吗？空计划被当成成功是历史 bug，已修 |
| 走了一半停了 | 安全层 | `DeviceHost` 的安全裁决事件 |
