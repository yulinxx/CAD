# 硬件抽象层架构（Hardware HAL）

> 适用范围：`Hardware` 子模块（`Hardware/Hardware/`）中 `Include/Hardware/Device/` 与 `Src/Device/` 下的全部代码。
> 本文档描述**设计意图与约束**；具体函数签名以头文件注释为准，两者冲突时以代码为准并回来修文档。
> 建立日期：2026-08-25

---

## 1. 为什么需要这一层

产品形态是「同一套图形算法 + 每个客户不同的机器」。图形与工艺算法稳定，**UI 与硬件接口是变化最剧烈的两块**。

在引入本层之前，硬件相关代码的状态是：

- `LaserController` 用定时器伪造运行状态，没有任何真实设备通道；
- `SafetyManager` 只有一个固定 10 项的 `SafetyEvent` 枚举，没有「点位」概念，客户机器上多一个气压开关就得改枚举；
- 零厂商实现：没有运动控制卡抽象、没有振镜卡抽象、没有 IO 读写接口。

结论：新客户接一张新卡，等于改一遍上层。本层的目标就是把这件事变成「加一个适配器文件 + 改一份配置」。

**硬性设计目标（按优先级）**

1. **上层不认识任何厂商**。UI、命令层、工艺层只依赖 `Hw::` 接口与设备 ID 字符串。
2. **跨 DLL 安全**。仓库全局开了 `CMAKE_CXX_VISIBILITY_PRESET hidden`，跨模块 `dynamic_cast` 不可靠，接口设计必须绕开它。
3. **跨平台可编译**。非 Windows 平台不允许因为「厂商只给了 Windows DLL」而编不过。
4. **失败必须可见**。宁可报错，不要静默降级——静默降级在激光加工里等于废件或事故。

## 2. 分层

```
    ┌──────────────────────────────────────────────────────────┐
    │ 应用层   Main / UI / 命令中枢 / SafetyManager（未改动）   │
    └───────────────────────┬──────────────────────────────────┘
                            │ 只依赖 Hw:: 接口 + 设备 ID 字符串
    ┌───────────────────────┴──────────────────────────────────┐
    │ 语义层                                                    │
    │   MotionPlan / MotionPlanBuilder   几何 → 设备无关字节码   │
    │   IoPointMap                       物理通道 → 命名点位     │
    │   SafetyMonitor                    点位 → 安全裁决         │
    │   DeviceRegistry                   设备 ID → 工厂          │
    └───────────────────────┬──────────────────────────────────┘
                            │ IDevice::queryInterface(InterfaceId)
    ┌───────────────────────┴──────────────────────────────────┐
    │ 契约层   IDevice / IMotionCard / IGalvoCard /             │
    │          ILaserSource / IIoModule   （纯虚 + POD ABI）    │
    └───────────────────────┬──────────────────────────────────┘
    ┌───────────────────────┴──────────────────────────────────┐
    │ 适配层   DeviceBase + 各厂商适配器 + SimulatedDevice      │
    │          DynamicLibrary（运行期加载厂商 SDK）              │
    └──────────────────────────────────────────────────────────┘
```

一句话概括每层的职责边界：

- **契约层**只描述「一台机器能做什么」，不描述「怎么做」。
- **适配层**把契约翻译成某个厂商 SDK 的调用序列，是唯一允许出现厂商符号的地方。
- **语义层**做的是「让上层用业务语言说话」：说 `in.door_closed` 而不是 `DI 7`，说 `MotionPlan` 而不是 `dmc_line_unit`。
- **应用层**从此不再随卡型变化。

## 3. 契约层：五个接口与一次 `queryInterface`

| 接口 | 抽象的东西 | 典型实现者 |
|---|---|---|
| `IDevice` | 一台设备的生命周期与自描述 | 所有适配器 |
| `IMotionCard` | 多轴运动：回零、点动、插补、轨迹执行 | 雷赛 / 正运动 / Aerotech / Ruida |
| `IGalvoCard` | 振镜扫描：视场、校正、延时、跳转/打标 | 金橙子 / SCANLAB |
| `ILaserSource` | 激光器：使能、功率/频率/脉宽、故障、测试出光 | 金橙子 / SCANLAB / Ruida |
| `IIoModule` | 物理 IO：DI/DO/AI/AO 读写 | 雷赛 / 正运动 / Aerotech / SCANLAB |
| `ISimulationClock` | 由宿主推进内部时间 | **仅模拟/虚拟设备** |

最后一个接口值得单独说明：`tick()` 刻意**没有**放进 `IDevice`。真机的时间由硬件自己走，宿主无权推进；若放进 `IDevice`，每个真机适配器都要实现一个空函数，还在契约上暗示了相反的事实。宿主也不该「按 deviceId 判断是不是模拟器再向下转型」——那样每加一种虚拟设备（回放、数字孪生）都要改宿主。于是仍然沿用同一套办法：能力用 `queryInterface` 问出来，真机上拿到 `nullptr` 自然跳过。


一台机器常常同时是好几样东西（振镜卡自己带激光同步口和扩展 IO），所以设备 `kind` 多为 `DeviceKind::Composite`，能力通过 `queryInterface` 逐个问：

```cpp
if (auto* motion = Hw::hwQuery<Hw::IMotionCard>(device)) { /* 有运动能力 */ }
if (auto* io     = Hw::hwQuery<Hw::IIoModule>(device))   { /* 有 IO 能力 */ }
```

### 3.1 为什么是 `queryInterface(InterfaceId) -> void*` 而不是 `dynamic_cast`

根 `CMakeLists.txt` 全局设置了：

```cmake
set(CMAKE_CXX_VISIBILITY_PRESET hidden)
set(CMAKE_VISIBILITY_INLINES_HIDDEN ON)
```

隐藏可见性意味着 typeinfo 不跨 DLL 共享，跨模块 `dynamic_cast` 会**静默返回 nullptr**——不是编译错误，不是崩溃，是「这台设备好像没有运动能力」。这种 bug 在现场无法定位。

因此改成显式的整数 ID 查询，适配器内部用 `static_cast` 明确指定基类：

```cpp
void* Foo::queryInterface(InterfaceId id)
{
    switch (id)
    {
    case InterfaceId::MotionCard: return static_cast<IMotionCard*>(this);
    case InterfaceId::IoModule:   return static_cast<IIoModule*>(this);
    default: return DeviceBase::queryInterface(id);
    }
}
```

`static_cast` 而不是直接 `return this`：多重继承下不同基类的子对象地址不同，`return this` 会给出错位的 vtable 指针，调用时崩在一个和原因毫无关系的位置。

### 3.2 ABI 规则（跨 DLL 传参）

接口签名中**只允许 POD**：

- 不出现 `std::string` / `std::vector` / `QString` / `QList`——它们的内存布局与分配器随编译选项变化，`_ITERATOR_DEBUG_LEVEL` 不一致就是内存破坏；
- 变长数据统一用「指针 + 数量」，例如 `MotionPlanView{ const MotionCommand*, size_t }`；
- 字符串用定长 `char[]`（`kIdLen` / `kMessageLen`），配 `hwCopyText()` 做截断安全的拷贝；
- 多轴数据用定长 `AxisVector`（`double v[kMaxAxes] + count`），按值传递零分配；
- 实现类中的 STL 成员一律藏进 `struct Impl`（pimpl），既避免 MSVC C4251，也让头文件不泄漏实现细节。

**对象生命周期**：设备由 `DeviceRegistry::create()` 在 DLL 内 new，必须由 `IDevice::destroy()` 在 DLL 内 delete。`IDevice` 的析构不对外开放（受保护），从语法上堵住「跨模块 delete」这条路——调用方拿到的 `operator delete` 可能来自另一个 CRT 堆。

**头文件必须能被 Qt 侧直接包含**。宿主是 Qt 应用，而 Qt 把 `emit`、`signals`、`slots` 定义成了宏。因此 HAL 的公开头文件里不允许出现这些标识符——`MotionPlanBuilder` 的追加指令方法叫 `emitCommand` 而不是 `emit`，就是这个原因（写成 `emit` 时，Qt 侧一包含就会被预处理器展开成 `void (...)` 而报语法错误，而且报错位置在 HAL 头文件里，与真正的原因隔了好几层）。


### 3.3 导出宏

沿用仓库既有做法：手写 `HARDWARE_API`（`HARDWARE_EXPORTS` 定义时 `dllexport`，否则 `dllimport`，非 Windows 展开为 `__attribute__((visibility("default")))`）。全仓库没有用 `generate_export_header`，本层不破例。

需要导出的东西有三类，容易漏第三类：

1. 接口类与具体类（`class HARDWARE_API ...`）；
2. 自由函数（`hwErrorName` / `deviceKindName` / `planStateName` / `motionPlanToText` / `registerBuiltinDevices` …）；
3. **纯数据的常量与 constexpr 不需要导出，但依赖它们的内联函数需要**——若把安全上限之类的常量写进 .cpp，另一个 DLL 里就看不见，各自取默认值，安全约束形同虚设。`Hw::kMaxTestFireMs` 因此定义在 `ILaserSource.h` 里。

## 4. 跨平台策略：厂商 SDK 一律运行期加载

**CMake 里不出现任何厂商 `.lib`。** 一旦 `target_link_libraries(... LTDMC.lib)`，Linux/macOS 立刻编不过，而且 Windows 上没插卡的开发机也起不来。

统一走 `DynamicLibrary`（`QLibrary` 的薄封装）：

```cpp
m_sdk.setWindowsOnly(true);                 // 非 Windows 直接 PlatformUnsupported
m_sdk.setSearchNames("LTDMC", sdkPathParam); // 先按名字找，再用用户给的路径兜底
if (!m_sdk.load()) { return hwFail(HwError::SdkNotFound, ...); }
m_pmoveUnit = m_sdk.resolve<PmoveUnitFn>("dmc_pmove_unit");
```

由此得到三条现场很值钱的性质：

1. **缺 DLL 是一条明确错误**（`SdkNotFound`），不是「程序双击没反应」；
2. **DLL 版本不匹配也是明确错误**（`SdkSymbolMissing`），并且报出缺的是哪个符号；
3. **能力按实际解析到的符号收窄**。例如 `arc_abs` 没解析到，就不上报 `CapArcInterp`，上层于是不会把圆弧交给它，而是收到离散化后的直线。绝不能出现「声明支持、第一次用就失败」。

`__stdcall` 差异同样收在适配器内部：

```cpp
#ifdef _WIN32
#  define HW_RTC_CALL __stdcall
#else
#  define HW_RTC_CALL
#endif
```

## 5. MotionPlan：几何与设备之间的唯一接触面

上层不调用「画一条线」，而是**编译出一段与设备无关的字节码**再整段下发。

```cpp
Hw::MotionPlanBuilder b;
b.setPlanId("job-001");
b.beginLayer(0);
b.setLaserParams(power, freqHz, pulseUs);
b.rapidTo(x0, y0);          // 空移，永不出光
b.lineTo(x1, y1, true);     // 出光直线
b.arcTo(x2, y2, cx, cy, true);
b.endLayer();
device->loadPlan(b.view());  // view() = { const MotionCommand*, count, header }
device->startPlan();
```

`MotionCommand` 是定长 POD，`MotionOp` 覆盖五类操作：

- 运动：`RapidTo` / `LineTo` / `ArcTo` / `Dwell`
- 激光：`LaserOn` / `LaserOff` / `SetLaserParams`
- 速度：`SetFeedRate` / `SetRapidRate`
- IO 与同步：`SetDigitalOut` / `WaitDigitalIn` / `WaitMotionDone`
- 结构标记：`BeginLayer` / `EndLayer` / `BeginPass` / `EndPass` / `Comment`

这样设计的收益：

- **同一份轨迹能喂给任何设备**。振镜卡把 `RapidTo` 翻成 `jump_abs`，运动卡翻成快移，Ruida 翻成协议字节流。
- **能力差异由适配器兜**。不支持圆弧的卡按弦高容差离散成直线（默认 0.01 mm），上层不需要知道。
- **可离线验证**。`motionPlanToText()` 把整段 IR 打成文本，出问题时不必接机器就能比对。
- **进度可上报且语义统一**。`PlanProgress{ state, commandIndex/Count, currentPass, currentLayer, fraction, error }` 由运动卡与振镜卡共用，所以 `PlanState` 定义在 `MotionPlan.h` 而不是 `IMotionCard.h`——否则 `IGalvoCard` 得反向包含运动卡头文件，两个平级抽象凭空多一条假依赖。

**未实现的操作码必须报错，不许跳过。** 静默跳过的表现是「工件上少了一块，软件一切正常」，这是最难查的一类现场问题。适配器返回 `NotImplemented` 时同时带上操作码名与指令下标。

## 6. IO 与安全：四层，`SafetyManager` 不动

```
IIoModule      readDigitalInputs(...)          物理层：DI 7 是高还是低
    ↓
IoPointMap     definePoint{ name, channel,     语义层：极性归一 + 去抖
               activeLow, debounceMs }         → in.door_closed 是否 active
    ↓
SafetyMonitor  addCondition{ point,            策略层：条件 → 裁决
               triggerOnActive, severity,      SafetyVerdict{ canStartProcessing,
               actions, violateWhenInvalid }   violations, worstSeverity }
    ↓
SafetyManager（应用层，本轮未改动）              对接 UI / 命令中枢 / 事件
```

分四层而不是两层的理由：**客户差异全部落在配置里**。同一个「门开」在 A 客户是常开触点接 DI 3、B 客户是常闭接 DI 11，差异被 `IoPointDef{ channel, activeLow, debounceMs }` 吸收，`SafetyMonitor` 的条件表和上层代码一个字都不用改。

三条 fail-safe 约定：

1. `violateWhenInvalid = true` 默认值：点位读不到（未映射、通道越界、模块掉线）**按违规处理**。读不到门开关不等于门是关的。
2. 初始裁决是 `Blocked`：`evaluate()` 没跑过之前不允许开工，而不是「先放行、发现问题再拦」。
3. 急停类点位 `debounceMs = 0`：去抖是为了滤掉机械抖动，安全信号不接受任何延迟。
4. 急停链路上不做前置状态检查、不申请锁——`emergencyStop()` 在 `Fault` 态也必须能执行。

## 7. 设备注册与自描述参数

`DeviceRegistry` 是一张「字符串 ID → 工厂函数」的表：

```cpp
Hw::registerBuiltinDevices();                                  // 幂等
Hw::IDevice* dev = Hw::DeviceRegistry::instance().create("leadshine_ltdmc");
```

上层配置里存的是 `"leadshine_ltdmc"` 这样的字符串，因此**换卡是改配置，不是改代码，更不需要重新编译**。ID 重复注册会被拒绝并告警；用未知 ID 创建时，日志会把当前可用 ID 全列出来，避免现场对着「创建失败」猜拼写。

每台设备用 `ParamSchema` 自述它的 `open()` 参数（名称、类型、单位、范围、默认值、是否必填、是否属于「高级」）。于是**参数面板可以完全通用**：UI 遍历 `paramSchemaCount()/paramSchemaAt()` 生成控件，新增厂商不需要新增 UI 代码。这也是「UI 与硬件解耦」在本层的落点。

`advanced = true` 的参数（如 `bits_per_mm`、`safe_output_levels`、`s_curve_time`）在界面上折叠收起：这些改错了会直接撞机或错烧，不该和「IP 地址」平铺在一起。

## 8. 装配与启动（Main 侧）

HAL 只提供零件，**谁来装配**是应用的事。装配代码在 `Main/Src/Hardware/`：

- `MachineProfile` / `MachineProfileLoader`：一台具体机器的档案（设备 ID、`open()` 参数、IO 点位、安全条件、tick 周期）。
- `DeviceHost`：把零件组装成一台可用的机器，并且是 POD 世界与 Qt 世界的边界。

### 8.1 机器档案为什么是磁盘文件

客户 UI 配置（`:/configs/<clientId>.json`）编进了可执行文件，描述的是「这个客户的产品长什么样」。而「这台机器的卡在几号槽、IP 是多少、急停接哪一路」**每台机器都不同，装机现场才知道**——塞进 qrc 等于每装一台机器重新编译一次。

因此档案是可写文件，查找顺序：

1. 环境变量 `SANYI_MACHINE_PROFILE`（现场调试 / 多机切换，与 `UiClientContext` 的 `SANYI_CLIENT_ID` 同一套思路）；
2. `<configDir>/machine.json`；
3. 都没有 → 内置的模拟设备档案。

第 3 条是刻意的：开发机、演示机、刚装好还没配的机器都必须能正常启动进入模拟模式，而不是弹「找不到硬件配置」然后退出。但**必须 WARN 说清当前跑的是模拟设备**——静默地把模拟当真机用，是这种兜底最危险的失败方式，所以 `DeviceHost::isSimulated()` 也如实暴露给界面。

档案本身写错（JSON 语法错、缺 `deviceId`）与「这台机器没配硬件」是两件事：前者日志级别是 ERROR 并把原因原样交给上层展示，然后才回退。

### 8.2 DeviceHost 做的四件事

1. **装配**：`registerBuiltinDevices()` → 按 ID `create()` → `open(ParamSet)` → `IoPointMap::attachModule(hwQuery<IIoModule>)` → 逐条 `definePoint` → `SafetyMonitor::attach(pointMap, actuator)` → 逐条 `addCondition`。任何一步失败都回滚（`destroy()` 已创建的设备），不留半装配状态。
2. **周期驱动**：一个 `QTimer`（默认 20ms）→ 推进 `ISimulationClock`（真机为 nullptr，跳过）→ `IoPointMap::poll(now)` → `SafetyMonitor::evaluate(now)`。顺序不能颠倒，`evaluate` 读的是上一次 `poll` 的结果。裁决**只在变化时**发信号，否则 20ms 一次会把界面和日志刷爆。
3. **安全动作落地**：实现 `ISafetyActuator`，把「切断出光/停运动/暂停/急停」映射到具体设备的具体接口。急停顺序刻意是**先关光再停机械**——反过来的话，机械已停但激光还亮着的那几毫秒足够烧穿工件。
4. **线程边界**：HAL 用纯虚 sink 回调上报事件，且约定回调可能发生在适配器工作线程。`DeviceHost` 的 sink 只做一件事——用 `QueuedConnection` 把 POD 事件投递到主线程，再转成 Qt 信号。

### 8.3 启动时机与失败策略

`AppBootstrapper::initialize()` 里、UI 起来**之前**装配硬件：安全联锁必须在用户能点「开始加工」之前就在评估，而不是等界面加载完才开始判断。

但装配失败**不阻止应用启动**——没有机器同样要能画图、改工艺参数。失败只是让 `canStartProcessing()` 保持 false（fail-safe），并把原因写进日志与提示文案。同理，`BUILD_HARDWARE=OFF` 的构建里 `DeviceHost::start()` 明确失败并说明原因，而不是提供一个「假装成功」的空实现：那样上层会以为设备已就绪，第一条加工命令才炸，且报错与真实原因（构建时关掉了硬件模块）毫无关系。

退出路径上硬件**最先停**：`AppBootstrapper::shutdown()` 与组合根析构都会调 `DeviceHost::stop()`（幂等），关光、停运动、输出置安全态之后其他服务才销毁。「窗口已经关了但激光还在出光」是绝不能出现的状态。

## 9. 日志约定


统一走仓库的 `Log` 模块（`SY_INFOF` / `SY_WARNF` / `SY_ERRORF` / `SY_DEBUGF`），前缀固定为 `[Hw::<deviceId>]` 或 `[Hw::<Vendor>]`，便于按设备过滤。

分级标准按「现场排障时想先看到什么」定：

- `ERROR`：动作失败、超限被拒、急停、SDK 加载失败——凡是返回 `HwResult::failed()` 的路径都要留下一条。
- `WARN`：能力降级（圆弧要离散、PSO 不可用、红光需外接 IO）、可疑参数。这类信息在 `open()` 时一次性说清，不要等到运行中才暴露。
- `INFO`：生命周期节点（open/close、计划加载、回零完成、测试出光）。
- `DEBUG`：逐指令下发细节。

`HwResult` 自带定长 `message`，返回错误时把「哪个厂商函数、返回什么码、什么参数」写进去；只返回一个枚举，现场等于没有信息。

## 10. 测试


`Hardware/Hardware/Test/`，由 `BUILD_HARDWARE_TESTS`（`BUILD_HARDWARE` 打开时默认 ON）挂进构建，产物 `HardwareTests.exe`。

**全部用例跑在 `SimulatedDevice` 上，不需要任何真实硬件**——HAL 的回归价值正在于「改了某个适配器，不要破坏共同契约」。

- `DeviceHalTests.cpp`：`MotionPlanBuilder` 指令顺序与边界、`ParamSet` 取值与回退、注册表去重与 `listByKind`、`HwResult` 消息截断。
- `IoSafetyTests.cpp`：`IoPointMap` 极性只翻转一次、去抖时序、通道越界返回 invalid 而不是静默 0；`SafetyMonitor` 初始拦停、失效点位违规、软件急停保持到显式清除、严重度取最坏且动作取并集。
- `SimulatedDeviceTests.cpp`：设备状态机（重复 open 拒绝、close 幂等、未 open 报 `NotOpen`）、未回零禁绝对定位/允许相对定位、计划执行与暂停/中止/恢复、联锁与急停对出光的拦截、参数越界拒绝而非钳制、振镜视场与延时。
- `MaterialDatabaseTests.cpp` / `SafetyManagerTests.cpp`：本轮之前就存在的用例，随本层一起纳入构建。

当前状态：**98 / 98 通过**。

装配层的测试在 `Main/Src/UI/Test/HardwareAssemblyTests.cpp`（`MainTests` 目标，18 个用例全绿），断言的是「装配契约」而不是设备行为：档案缺失/写错时的兜底与告警、数值参数转字符串、越界 tick 周期纠正、未启动时 `canStartProcessing()` 必须为 false、重复 `start` 被拒、`stop()` 幂等、`autoOpen=false` 不算就绪、配了 IO 点位却用无 IO 能力的设备要在启动阶段失败。

> `MainTests` 与应用目标必须用同一套 `ENABLE_HARDWARE` 宏，否则 `DeviceHost.cpp` 在两个目标里编出来的是不同实现（一个真装配、一个空壳），测试就测不到真实行为。


> 新增 `.cpp` 文件后需重新 `cmake -S . -B build`——`Test/CMakeLists.txt` 用的是 `file(GLOB_RECURSE ... CONFIGURE_DEPENDS)`，增量构建不一定会自动重扫。

## 12. 已知待办

1. **加工链路尚未接通**：设备已经在启动时装配好、IO 与安全在周期评估，但「把 `MotionPlan` 交给设备执行」的命令路径还没接（`loadPlan` / `startPlan` 目前只有测试在调）。
2. **`ILaserService` 需要收口**：`UI/2D/` 里那个 20 方法的大接口仍在，`connectToLaser(port, baudRate)` 把传输细节泄漏到了 UI 层，还反向依赖 `Eg::MachineFrameConfig`；且它当前是**死代码**（`ServiceFactory::createLaserService` 没有任何调用点）。它应当被本层的 `ILaserSource` + `IIoModule` 取代。因与正在进行的 UI 改动冲突，留到后续轮次。
3. **界面还没有硬件状态出口**：`DeviceHost` 已经发出 `safetyVerdictChanged` / `deviceStateChanged` / `deviceEventReceived`，但状态栏、IO 监视面板、参数面板都还没有接收方。参数面板可以直接遍历 `paramSchemaAt()` 生成，不需要为每个厂商写代码。
4. **Ruida 仅支持文件输出**：UDP / 串口通道返回 `NotImplemented`（会引入 Qt6::Network / QSerialPort 依赖，需先确认部署包策略）。
5. **真机实测全部为空**：六个适配器均只做过编译与模拟验证。上机结论请逐项记录到 `厂商接入现状.md`。
