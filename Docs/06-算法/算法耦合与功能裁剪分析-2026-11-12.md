## 0. 结论摘要

**先纠正一个口径**：本仓库里"算法"不是一个可独立装拆的单元，而是三层不同的东西混用同一个词。裁剪难度完全取决于删的是哪一层：

| 层 | 例子 | 删掉意味着 |
|---|---|---|
| 命令/入口 | 菜单项 `edit.boolean_xor` | 只是少一个入口，算法还在，改动 5~9 个文件 |
| 任务/处理器 | `AlgorithmTaskId::Boolean2D` + handler | 入口点了会"没反应"（有日志无提示），改动 6~10 个文件 |
| 算法实现 | `Eg::EntityBoolean` + `Geo2DBoolean` | 引擎 DLL 导出面变化，所有消费者必须同版本重建 |

按"**能不能单独删掉**"这个可执行标准（编译通过 + 无残留入口 + 其它算法不回归），逐项结论：

| 算法 | 能否单独删除 | 一句话原因（证据见 §8） |
|---|---|---|
| 螺旋填充 | **能，最干净** | 独立函数 `insetSpiralPaths`（979 行）+ 独立对话框页；只与同心环共用参数 POD，不动内核 |
| 排样 Nesting | **已经能** | `BUILD_NESTING` + 40 处 `ENABLE_NESTING` + 源文件排除，是仓库里唯一跑通的裁剪样板 |
| 雕刻 Engraving | 能（模块级） | `BUILD_ENGRAVING` 12 处；但 Engraving 反向依赖 Engine3D，不能单独删 Engine3D |
| 色块填充 | 近似能 | 独占一层实现；但 `FillGeometryUpdater` 在图元移动时会回调它（§5.1） |
| 线填充 | 否 | 与另外三个样式共用 `FillTaskHandler`/`FillDialog`/`FillParameters`，且内缩依赖 `Geo2DOffset` |
| 同心环填充 | 否 | 与螺旋共用 `ContourFillParameters` POD 与 `computeRings` 前段 |
| 偏移/内缩 | 否 | 线填充在 `EntityFill` 内部调用 `Geo2DOffset::offsetContours` 做 kerf/margin 内缩 |
| 布尔运算 | 否 | `Geo2DBoolean` 是偏移与线填充的公共内核；能删的是命令，不是算法 |
| 阵列 | 能（近似自包含） | `ArrayAlgorithm` 只依赖 `PathOptimizer`，不碰几何内核 |
| 文字转曲线 | 否 | 不是独立功能，而是渲染 / CAM / 离散化三处共用的底层设施 |
| 导入导出几何 | 否（不建议） | FileIO 私有实现，删了就没有图纸存取 |

其余要点：

1. **真正把算法绑在一起的不是目录，而是三个共享内核**：`Geo2DBoolean`（280 行）→ `Geo2DOffset`（2334 行）→ `EntityDiscretizer`。所有填充/偏移/布尔/排样准备层都落在这一条栈上。
2. **算法之间几乎不互相 include**：`grep 'include "Engine2D/Algorithm/'` 在 7 个算法实现文件里只找到 1 条算法→算法边——`FillGeometryUpdater.cpp:7 → EntityColorFiller.h`。这说明"算法层"本身是松的，紧的是它们共同依赖的几何内核。
3. **Engine2D 是单一 DLL + `file(GLOB_RECURSE)` 收录**（`Engine/2D/CMakeLists.txt:33-38`、`:62`），所以"删一个算法"在构建粒度上等于"改一个源码集合、重编整个 Engine2D 及其全部消费者"，不存在"少链一个算法库"这种选项。
4. **导出基线把算法符号钉死了**：`Tools/Abi/baseline/Engine2D.txt` 1329 行，其中 `EntityContourFiller::computeSpiralPaths` 在 905 行、`writeSpiralPathsToScene` 在 907 行、`Geo2DOffset::insetSpiralPaths` 在 319 行。物理删除 = 必须同步改基线 + 所有消费者一起重建。
5. **UI 侧删一个算法约 9 个文件、25~30 处**，其中至少 4 处"删了不报错但语义变了"（§6.2）。
6. **CAM 对填充结果有硬形状假设**：`AprFillRegion` 必须是三角汤，CAM 靠"共享边抵消"反推边界环（`Engine/2D/Src/Cam/GeometryExtractor.cpp:262-306`、`:711`）。换填充策略若改变落盘图元类型，刀路直接拿不到轮廓。
7. **注册码门禁不要进算法层**：Engine 目前对 `License`/`UiFeatureGate` 零依赖（`grep -rn 'UiFeatureGate|License' Engine` 无命中），且算法层的裁剪已是 ABI 级操作。落点建议见 §11。

## 1. 分析口径与可复现命令

判定"可单独删除"必须同时满足三条，缺一不算：

- **编译通过**：删掉源码后全量构建成功（含 Main、测试）。
- **无残留入口**：菜单、快捷键、右键、工具栏、命令目录、参数面板、翻译、图标都不再暴露它。
- **不回归他人**：其它算法功能与数值结果不变。

复现命令（只读）：

```bash
# 算法间 include 关系
grep -rn 'include "Engine2D/Algorithm/' Engine/2D/Src/Algorithm/*.cpp Engine/2D/Src/Algorithm/*/*.cpp

# UI → 引擎的全部算法调用点
grep -rn 'EntityFiller::\|EntityColorFiller::\|EntityContourFiller::\|EntityOffset::\|EntityBoolean::' \
     UI/2D/Src UI/Common/Src Main/Src | grep -v Test

# 导出面
grep -n 'EntityContourFiller\|insetSpiralPaths\|insetRingLayers' Tools/Abi/baseline/Engine2D.txt

# 样式枚举与 UI 散落点
grep -rn 'SpiralFill' Engine UI Main --include=*.cpp --include=*.h | grep -v Test
```

从"点菜单"到"结果回写"，一条命令要穿过 8 层。填充一族每一层的真实落点与数量：

| 层 | 文件 | 真实调用点 | 该算法在此层的条目数 |
|---|---|---|---|
| 1 菜单 | `Main/Src/UI/ClientConfig/configs/base.json` | `216`（算法菜单项）、`217` `algo.fill` | 1 |
| 2 命令目录 | `UI/2D/Src/Operation/CommandCatalog.cpp` | `1064` `algo.fill → OperationId::Algo_Fill` | 1 |
| 3 操作枚举 | `UI/Common/Include/UI/Command/OperationId.h` | `Algo_Fill` / `Algo_FillColor` | 2（`Algo_FillColor` 无入口，见 §6.3） |
| 4 操作注册 | `Main/Src/Composition/AlgorithmOperationRegistry.cpp` | `registerAlgoOp(OperationId::Algo_*…)` | 1（Fill2D） |
| 5 任务映射 | `UI/2D/Src/Operation/AlgorithmOperationMapping.cpp` | `Algo_Fill → AlgorithmTaskId::Fill2D` | 2（Fill2D / FillColor2D） |
| 6 任务注册 | `UI/2D/Src/Algorithm/AlgorithmTaskRegistration2D.cpp` | `registerHandler(Fill2D, …)`，`1376-1387` | 2 |
| 7 处理器 | 同上 | `FillTaskHandler::doCompute`，按 `FillStyle` 四分支 `343-370` | 1 个类 / 4 分支 |
| 8 引擎 | `Engine/2D/Src/Algorithm/*` | `EntityFiller::computeFill` / `EntityColorFiller::computeRegions` / `EntityContourFiller::computeRings` / `computeSpiralPaths` | 4 个静态入口 |
| 9 回写 | `AlgorithmTaskRegistration2D.cpp` | `doApply` 写场景 + 撤销包装 | 1 |

**关键事实**：UI 对引擎算法的**全部**调用面只有 6 个静态调用点，且集中在同一个文件：

```
AlgorithmTaskRegistration2D.cpp:343  Eg::EntityFiller::computeFill
AlgorithmTaskRegistration2D.cpp:348  Eg::EntityColorFiller::computeRegions
AlgorithmTaskRegistration2D.cpp:353  Eg::EntityContourFiller::computeRings
AlgorithmTaskRegistration2D.cpp:368  Eg::EntityContourFiller::computeSpiralPaths
AlgorithmTaskRegistration2D.cpp:774  Eg::EntityOffset::computeOffsetEntities
AlgorithmTaskRegistration2D.cpp:980  Eg::EntityBoolean::computeBooleanEntities
```

这意味着"UI 层做门禁、算法层无感"在结构上是成立的：所有算法调用已经被收进一个 handler 文件，只要收口这一层的注册，就不必碰算法。

对照：排样有独立处理器（`NestingTaskHandler`），雕刻走 3D 侧，都不在这 6 个点里。

## 4. 编译期耦合

### 4.1 单 DLL + GLOB，没有算法级构建单元

`Engine/2D/CMakeLists.txt:33-38` 用 `file(GLOB_RECURSE Src/*.cpp)` 收全部源文件，`:62` 一次性 `apr_add_shared_library(Engine2D …)`。所以：

- 不存在 `Engine2DFill` / `Engine2DBoolean` 这样的子库；
- 也没有 `BUILD_FILL` / `BUILD_BOOLEAN` 开关（`Config.cmake` 的 `BUILD_*` 清单里只有 `BUILD_NESTING / BUILD_ENGRAVING / BUILD_RASTER / BUILD_VISION / BUILD_UI3D / BUILD_CAM / BUILD_HARDWARE / BUILD_GEOMODELCORE / BUILD_RENDERX / BUILD_NETWORK / BUILD_CRASHHANDLER`）；
- 任何"删一个算法"都是改源码集合 + 重编 Engine2D + 全部消费者。

### 4.2 公开头把内核带给了消费者

`Engine/2D/Include/Engine2D/Algorithm/EntityContourFiller.h:6-7` 直接 include：

```cpp
#include "Engine2D/Geometry/Geo2DOffset.h"
#include "Engine2D/Geometry/NarrowStripCenterline.h"
```

`Engine/2D/Include/Engine2D/Algorithm/Boolean/EntityBoolean.h:4` 直接 include `EntityDiscretizer.h`。

后果：**只要 UI 代码 include 了 `EntityContourFiller.h`，就同时拿到了偏移内核的完整声明**。这是"看起来只依赖一个算法、实际依赖整套内缩"的典型编译期耦合。

### 4.3 共享参数 POD：螺旋与同心环共用一个结构体

`Engine/2D/Include/Engine2D/Algorithm/Fill/ContourFillParameters.h` 是"同心环填充与螺旋填充共用参数"（文件头注释第 4-5 行）。其中至少 4 个字段是螺旋专属语义：

| 字段 | 行 | 说明 |
|---|---|---|
| `bStartFromSourceContour` | `64` | 注释明写"仅螺旋生效" |
| `bOuterToInner` | `66` | 螺旋方向 |
| `bKeepOuterBoundary` | `68` | 螺旋外轮廓圈 |
| `dLinkTolerance` | `73` | 螺旋桥接容差 |

同时 `bMergeToSpiral`（`69-71`）已被标为 `[[deprecated]]`，注释写"螺旋样式已由 SpiralFill 独立实现，本字段不参与计算"，但**仍保留**——因为它参与 `memcpy` 布局（`:42-44` 同类注释）。

这就是"目录分开了、结构体没分开"的实证：删除螺旋后，这 4 个字段会变成死字段，但不能随手删，因为结构体被按字节拷贝、且被导出面引用。仓库已有的处理范式是"标 deprecated 保留占位"（`structSize`、`dMinWidth`、`bMergeToSpiral` 三处），可以沿用。

另外，`FillStyle` 枚举存在**两份定义**：`Fill/FillParameters.h` 的 `Eg::FillStyle`（算法层）与 `Fill/FillUIParams.h` 的 `::FillStyle`（UI 边界层），靠 `static_assert` 做数值同步。这是**受控重复**，不是缺陷；但删除样式时要两处一起改，漏一处 `static_assert` 会替你把编译卡住。

### 4.4 ABI 基线锁定了算法导出

`Tools/Abi/baseline/Engine2D.txt`（1329 行）里与本次分析直接相关的符号：

| 基线行 | 符号 |
|---|---|
| `319` | `Geo2DOffset::insetSpiralPaths(...)` |
| `318` | `Geo2DOffset::insetRingLayers(...)` |
| `902` | `EntityContourFiller::computeRings(...)` |
| `905` | `EntityContourFiller::computeSpiralPaths(...)` |
| `907` | `EntityContourFiller::writeSpiralPathsToScene(...)` |

物理删除 = 基线删行 = 所有消费者必须同版本重建。这既是"删得掉"的证据（删除动作是显式的、可审计的），也是"别指望热插拔"的证据。

## 5. 运行期耦合

### 5.1 `FillGeometryUpdater`：唯一"算法→算法"的隐式回调

`Engine/2D/Src/Algorithm/FillGeometryUpdater.cpp:7` include `EntityColorFiller.h`，并在图元移动/编辑后重算色块填充。它被 UI 侧安装（`AlgorithmTaskRegistration2D.cpp` 内初始化），因此：

- 删色块填充，必须同时改 `FillGeometryUpdater`（否则任何图元移动都会调用一个不存在的算法）；
- 删除线/同心环/螺旋，**不**影响这条回调——这反证色块填充是四样式里最"独立"的一个。

### 5.2 单例与静态状态

本次范围内**没有**发现算法层持有全局可变单例。`SceneManager` / `LayerManager` 通过构造函数传入（如 `EntityContourFiller(SceneManager*)`），属于显式依赖而非隐式全局。这是有利事实。

风险在于**参数对象的"只有一个"假设**：`FillTaskHandler` 一个实例承担四种样式，`m_taskParams` 里同时挂着 `lineParams / colorParams / contourParams / spiralParams`。删掉某样式后，这些成员是否还有人读，靠人工检查，编译器不会报。

### 5.3 跨模块回写

结果回写统一走 `SceneEditService`（`setEditService`，见 ABI 基线 `903` 行），撤销由 `doApply` 包装。算法本身只返回几何数据，不直接改场景——这一点是干净的，删除算法不会留下"半个场景"。

## 6. UI 与配置耦合

### 6.1 一个算法在 UI 里散落多少处

以"完整删掉一个算法命令"计，固定要碰的地方：

| # | 位置 | 性质 |
|---|---|---|
| 1 | `base.json` 菜单项 | 入口 |
| 2 | `CommandCatalog.cpp` 别名表 | 命令→操作映射 |
| 3 | `OperationId.h` 枚举 | 操作 id（共享枚举，删值会移动后续值） |
| 4 | `AlgorithmOperationRegistry.cpp` | 操作注册 |
| 5 | `AlgorithmOperationMapping.cpp` | 操作→任务映射 |
| 6 | `AlgorithmTaskId.h` 枚举 | 任务 id（注释写明"与 Python 任务表对齐"） |
| 7 | `AlgorithmTaskRegistration2D.cpp` | 处理器注册 + 分支代码 |
| 8 | `UI/Common/Resources/ui_common.qrc` | 图标（`algo_fill.svg` 在 `:59`） |
| 9 |  translations（标签按文本 key，不按命令 id） | 文案 |

### 6.2 四处"删了不报错、语义却变了"的隐式点

1. **`CommandCatalog.cpp:485-487` 注释**：`menuIdForCommandId` 找不到返回 0，
   ```cpp
   // 四个布尔操作共用一个 OperationId 的分支如果漏掉本映射，
   // dispatch 会丢掉 booleanOp，全部退化成 union。
   ```
   删映射不报错，运行时四个布尔全变并集。
2. **`AlgorithmOperationMapping.cpp` 返回 `None`**：`AlgorithmApplicationService` 只 `WARN` + 返回失败信息，用户侧看到的是"点了没反应"。
3. **`AlgorithmTaskRegistration2D.cpp:1371` 注释**：漏注册一个处理器"就是一个「点了没反应」的菜单"。
4. **`base.json` 的 `feature` 字段只在菜单构建时生效**（见 §11），工具栏路径会把它丢掉。

### 6.3 现有重复入口：`algo.offset` 与 `edit.offset`

`CommandCatalog.cpp:985` 有 `edit.offset → Algo_Offset`，`:1069` 又有 `algo.offset → Algo_Offset`；`base.json:98` 和 `:220` 各有一条菜单项。同一个操作两个入口，删除时必须两处都清理，否则会留下"幽灵菜单"。

同理，`Algo_FillColor`（`OperationId.h`）有映射（`AlgorithmOperationMapping.cpp:17-19`）、有处理器注册，但 `CommandCatalog` 无条目、`base.json` 无入口（`grep -c '"algo.fill_color"'` 为 0）。这是现成的**低风险删除样板**：删掉它不会改变任何用户可见行为。

## 7. CAM 侧耦合

### 7.1 形状假设：`AprFillRegion` 必须保持三角汤

`Engine/2D/Src/Cam/GeometryExtractor.cpp`：

- `:33` include `AprFillRegion.h`
- `:711` `extractFillRegion(...)`
- `:715` 调 `extractFillRegionRings(verts, rings)`
- `:262-306` 用"量化点 + 边计数"，把三角汤里出现两次的共享边抵消，剩下的边串成边界环。

结论：**CAM 不认识"填充策略"，只认识"三角化区域"这一种落盘形态**。如果未来引入一种不三角化、只输出线段/多段线的新填充，CAM 不需要改；但只要新策略仍写 `AprFillRegion`，就必须保持三角汤语义（否则孔洞识别、共边规划、引线全部失准）。

反例（有利面）：线填充输出的是 `AprLine`（`EntityFiller` 写 hatch 线），CAM 走通用实体提取，**不依赖三角汤**。所以"换线填充策略"对 CAM 影响最小。

### 7.2 割缝（kerf）存在两套实现，填充侧是独立的

- 填充侧：`Engine/2D/Src/Algorithm/Fill/PolygonFill/EntityFill.cpp:665` 在生 hatch 之前，用 `Geo2DOffset::offsetContours` 按 `dMargin + 0.5*dKerf` 内缩外轮廓；`dKerf` 来自填充对话框自己的参数（不在图层 `ProcessParams` 里）。
- CAM 侧：`CAM/CAM/Src/GeometryTransform/KerfCompensator.cpp`，由 `CamCore.cpp:327` 按 `bucket.kerf.enabled` 调用；另有 `Engine/2D/Src/Cam/KerfCompensator.cpp` 被 `MotionPlanCompiler.cpp:409` 与 `KerfCompensatorBridge.h:133` 使用。

即 **三处 kerf 实现**（填充内缩 / CAM 补正 / 运动规划补正），彼此没有共享代码。这是 §9 的耦合热点之一：换填充策略时，如果新策略不做自己那份内缩，CAM 补正会补上，但两者叠加时的口径没人保证一致。

### 7.3 工艺链对填充结果无类型假设，但对"轮廓闭合性"有假设

`CAM/CAM/CMakeLists.txt` 只链 `Utility`（PUBLIC）与 `Log`、`Clipper2::Clipper2`（PRIVATE），零 Engine 依赖。所以工艺链（割缝/引线/穿孔/功率/共边）看到的是 `Cam::Path`，与填充无关——前提是 `CamInputBridge` 已经把填充结果转成了闭合轮廓。

## 9. 耦合热点（按传染性排序）

1. **`Geo2DBoolean` 是"根内核"** —— 被偏移、线填充、同心环、色块填充、布尔、排样准备层 6 处调用。它一变（例如 Clipper2 升级、精度口径调整），6 个算法的数值结果同时变。这是全仓传染性最强的一个点。
2. **`Geo2DOffset` 是"第二根"** —— 线填充的 kerf/margin 内缩（`EntityFill.cpp:665`）、同心环、螺旋、偏移命令全部依赖。它同时承载倒角/圆角，所以"删偏移"会连带删掉倒角命令。
3. **`EntityDiscretizer` 是"进入几何世界的唯一门"** —— 4 个算法实现 + 布尔公开头（`EntityBoolean.h:4`）+ 排样准备层都 include 它。它的图元覆盖表（10 类，`EntityDiscretizer.cpp:129-217`）决定了所有算法的输入上限。TEXT 不在表里，这是"文字要转曲线才能填/排"的根因。
4. **`FillGeometryUpdater` 是唯一算法间回调** —— 任何图元编辑都会触达色块填充。它把"编辑"与"填充"两条本来独立的链路缝在一起。
5. **三份 kerf 实现** —— 填充内缩 / CAM 补正 / 运动规划补正各写一份，没有共享口径。换填充策略时最容易在这里出"双重补偿/补偿缺失"。

## 10. 改造建议（按最小改动排序）

> 原则：用户已明确不喜欢复杂化。以下每条都能用一句话说清，且不新增抽象层。

### 建议 1（必须做，零代码）：把裁剪点从"算法"上移到"命令"

现状：四个填充样式共用一个 `FillTaskHandler` 和一个 `FillDialog`，把"线填充/色块/同心环"拆成独立算法是净负收益（要拆 handler、拆对话框、拆参数 POD，还改 vtable）。

替代做法：**样式级裁剪在对话框里做**——`FillDialog` 按授权隐藏样式页（现有 `initSpiralFillPage` 这类整页函数天然适合条件构造），引擎侧一个分支都不动。删的是"用户能选到的值"，不是算法。

一句话：**算法按族保留，裁剪按样式页做。**

### 建议 2（推荐，小改动）：真正的删除只对"独立分支"做，并保留 ABI 占位

适合删的只有两类：独立函数（螺旋的 `insetSpiralPaths`）与独立模块（Nesting/Engraving）。

删除时遵守仓库已有范式：参数结构体字段标 `[[deprecated]]` 保留（`ContourFillParameters.h:42-44/69-71` 的三个先例），ABI 基线的删行独立成一个提交。这样"删功能"不会变成"改布局"，其它未删功能的数值与 ABI 都不受影响。

一句话：**删函数可以，删字段不行；字段标 deprecated。**

### 建议 3（不建议）：不要为裁剪新增 `BUILD_FILL` / `BUILD_BOOLEAN` 开关

理由有实测支撑：

- Engine2D 是 `GLOB_RECURSE` 单 DLL，加开关只能靠 `#if` 包代码，不能少编一个目标；
- 填充/偏移/布尔互相依赖（§3），任何单独 OFF 组合都要额外维护 2^3 种编译态；
- 仓库已有的 `ENABLE_NESTING` 是 40 个守卫点换来的，填充面比排样大得多，守卫点数会翻倍；
- 编译期开关会产生 vtable/`sizeof` 不一致风险（`UI/Common/CMakeLists.txt:161-164` 已记录过这类 ABI 事故），运行期门禁没有这个问题。

一句话：**编译期开关只给"整模块"（Nesting/Engraving/Raster），不给"算法内部"。**

### 建议 4：给"删除"补一条护栏，而不是补一层框架

现状的失败模式是"注册了但没编进来 → 点了没反应"（`Main/CMakeLists.txt:177-179` 明文记录）。已有护栏是启动自检 `UiConfigSelfCheck`（JSON/CMake/License 三侧交叉核对）。

**不需要扩表**：自检的 `feature → BUILD_*` 映射表（`UiConfigSelfCheck.cpp:225-231`，只认 5 个）对表中没有的 feature 已经直接 `continue`（`:315-319`，视为"纯授权项"）。所以新增 `"feature": "fill"` / `"spiral"` 这类纯授权项时，自检天然免检、不会误报；"JSON 写了、命令不存在"的拼写错误由同一函数的命令可解析性检查（`:256-299`）负责，与表无关。

唯一要补的是**语义错配**：`relief3d` 被映射到 `BuildConfig::kEngraving`（`:229`），而 2D 的 `algo.relief_engraving` 实际由 `BUILD_RASTER` 决定（`ReliefEngravingOperation2D.cpp:6-9`、`:163-167`）。一个用户可见名字对应两个构建开关，详见姊妹篇 §3.1。

一句话：**自检不用扩枚举，只需修正已有的错配项。**

## 11. 注册码门禁落点

> 完整分发链与框架级证据见姊妹篇 §4、§7。这里只给算法相关的结论与代价。

### 11.1 三个候选落点

| 落点 | 覆盖范围 | 代价 | 结论 |
|---|---|---|---|
| A. 菜单 JSON 的 `feature` 字段 | 菜单项 + 快捷键（同一 QAction，`UiLayoutBuilder.cpp:433`）；**工作台自建工具栏目前漏门控**（`Workbench2D.cpp:1127-1133`、`Workbench3D.cpp:141-142`） | **零代码**，`UiFeatureGate` 已实现；现有 `client_b.json` 已在用（`nesting`/`relief3d`/`vision`）。补洞约 2 文件 12 行，见姊妹篇 §6 | **首选（先补洞）** |
| B. 任务注册层（`AlgorithmTaskRegistration2D` / `AlgorithmOperationMapping`） | 所有走任务链的入口 | 中：需要在 UI2D 可见 feature 表；已有 `#ifdef` 条件注册先例（`:1380-1387`） | 作为 A 的补强，可选 |
| C. 总线层（`OperationBusBase::runImpl`） | 入口全覆盖，但此时只剩 `OperationId`，feature 信息已丢 | 中偏高：需要新建 `OperationId → feature` 表（第三真相源）并把门禁搬进 UICommon | **不做**，详见姊妹篇 §5、§6.4 |
| D. 算法内部 | — | 高：Engine 目前零 License 依赖；每个算法都要改；破坏 ABI 裁剪自由度 | **不做** |

### 11.2 推荐组合

**A + 自检**，兜底留 C：

1. 客户配置里给算法菜单项/工具栏项加 `"feature": "fill"` / `"spiral"` / `"nesting"`；
2. `License` 的 feature 串里增删同名 token；
3. `UiConfigSelfCheck` **不需要**登记（`:315-319` 对未知 feature 直接跳过）；
4. **先把工作台自建工具栏的洞补上**（姊妹篇 §6，2 文件约 12 行），否则工具栏入口绕过门禁；
5. 只有出现"必须防程序化调用"的需求时，才在 `OperationBusBase::runImpl` 加一处判定。

代价：

- A：改 `base.json` + 客户 JSON，0 行 C++；
- 补洞：`Workbench2D.cpp:1105-1141`、`Workbench3D.cpp:124-165` 各加 2 个判断 + 1 个 include；
- 自检：0 行（修正 `relief3d` 错配除外）；
- C（可选）：`UiFeatureGate` 从 `Main/Src/UI/ClientConfig/` 迁到 `UI/Common/`，改 5 处 include，`runImpl` 加 1 个分支——**不建议**，理由见姊妹篇 §6.4。

### 11.3 为什么不能放算法内部

三条实测理由：

1. **依赖方向**：`grep -rn 'UiFeatureGate|License' Engine` 零命中；Engine2D 的 PUBLIC 依赖只有 Utility/EngineCommon/Boost/Log。加门禁等于让最底层几何库反向依赖授权组件。
2. **裁剪目标冲突**：算法层的裁剪是 ABI 级动作（基线 1329 行、`EntityContourFiller` 11 个符号）。在算法里加运行时开关，既删不掉代码，又增加了每次调用的分支。
3. **一致性风险**：编译期 feature（`ENABLE_*`）必须 PUBLIC 传播才能保证 vtable/`sizeof` 一致（`UI/Common/CMakeLists.txt:161-164`）。运行期开关没有这个约束，放在 UI 层最安全。

## 13. 未覆盖与被否决的方向

- **未验证**：`BUILD_NESTING=OFF` 的实际构建结果（按要求未占用任何构建目录）。本文以"源文件排除 + 40 处守卫 + 条件注册"三条静态证据判定其为可用裁剪路径，未经编译验证。
- **未量化**：CAM 共边规划（`CommonEdgePlanner`）在填充结果上的具体行为差异。已确认它只消费 `Cam::Path`，不感知填充策略，未做数值对比。
- **被否决**：为每个填充样式建独立 CMake 目标（`Engine2DFill` 等）。理由见 §10 建议 3：单 DLL + GLOB 的现状下，拆目标收益低于维护 2^N 编译态的成本。
- **被否决**：把 `FillStyle` 拆成策略类继承体系。现状的四分支 switch 只有 4 个分支、约 280 行，拆成多态会引入 vtable 与 ABI 风险，且与"少注册一个算法"的裁剪目标无关。
