## 0 结论摘要

### 0.1 Raster 是不是处理位图的

是。Raster 是一个**独立的位图处理库**，不是几何/CAM 库，也不是只服务雕刻的专用模块。实测依据：

- 纯 C ABI 的独立动态库：`Raster/Raster/CMakeLists.txt:5-8` 声明设计定位，`:98-117` 用工程封装的共享库宏导出 DLL，`:158-192` 提供可选 `install(EXPORT)` SDK 导出，`:47-53` 有 ABI 版本护栏。
- 依赖只有 OpenCV：`Raster/Raster/CMakeLists.txt:69-77` 只 `find_package(OpenCV)`，`:115-116` 只链接 OpenCV；顶层 `Raster/CMakeLists.txt:32-33` 明确不引入 Qt。全仓没有 Raster 链接 Qt 或 Engine2D 的证据。
- 导出面很宽：`Raster/Raster/Include/Raster/RasterApi.h:62-757` 共 92 个 `RASTER_CALL` 函数，覆盖位图 I/O、预处理、形态学、OCR/码检测、缺陷检测、图像对比、矢量化、扫描线、栅格割缝、统计。
- 目前产品里真正用到它的只有四处：`UI/2D/Src/Operation/RasterProcessOperation2D.cpp`（处理位图/位图矢量化对话框）、`Main/Src/CAM/CamInputBridge.cpp`（位图→扫描线，未接生产执行）、`Main/Src/Export/Writers/RasterExportHelper.cpp`（PNG/BMP 导出）、`UI/2D/Src/Operation/ReliefEngravingOperation2D.cpp`（位图→JSON 刀路旁路导出）。

### 0.2 现在能做什么（只列已在代码里跑通的）

- 读 PNG/BMP/TIFF/JPEG/WebP（OpenCV `imread`，`Raster/Raster/Src/Algo/RasterIO.cpp:45`），8bit 三通道/四通道、16bit 单通道保留，其余归一化到 8bit（同文件 `:13-40`）。
- 预处理：灰度、亮度/对比度、Gamma、反相、全局/固定阈值、Otsu、自适应阈值、11 种抖动、半调、去噪、锐化、CLAHE、Canny、去斑点、倾斜校正、骨架化。
- 位图→矢量：Otsu 反相二值 → `RETR_CCOMP` 轮廓 → 多边形拟合 → 孔洞方向 → 最小面积过滤 → 排序/简化/平滑 → 导出 SVG/DXF/G-code/PLT。
- 扫描线：任意角度旋转扫描、双向/单向、行距（像素）、过扫（像素）、多遍、按像素亮度调制功率、G-code 导出。
- 栅格割缝：椭圆核形态学膨胀/腐蚀（像素域）。
- 图像质检：二维码/条码检测、缺陷检测、图像差异、边缘/清晰度统计。

### 0.3 关键结论（每条都有代码证据）

| 编号 | 结论 | 证据 |
|---|---|---|
| K1 | **位图雕刻没有进入生产执行链路**。执行服务仍走 `MotionPlanCompiler`，该编译器把 Raster 实体判为不可加工；能编译位图的 `Cam::compile` 只剩测试与基准调用 | `Main/Src/Hardware/ProcessingJobService.cpp:446`；`Main/Src/Hardware/MotionPlanCompiler.cpp:232`；全仓 `Cam::compile`/`buildJobInput` 无生产调用者 |
| K2 | **存在两套互相相反的灰度极性约定**。扫描线/功率映射按「亮=大功率」，阈值/矢量化按「暗=待加工」；桥接层把透明像素合成到白色，注释却写「避免出光」，实际会满功率 | `Raster/Raster/Src/Engrave/RasterScanline.cpp:178-183`；`Raster/Raster/Src/Vector/RasterVector.cpp:481`；`Main/Src/CAM/CamInputBridge.cpp:216-220` |
| K3 | **DPI 完全缺失**：文件导入恒为 96 DPI，Raster 内部没有任何 DPI 概念，PNG `pHYs` / JPEG JFIF 密度从未解析。导入后的物理尺寸 = 像素/96 | `FileIO/FileIO/Src/ImageUtils.cpp:52-53,57-63,223`；`Raster/Raster/Include/Raster/RasterTypes.h:122-130`（`RasterImageInfo` 无 DPI 字段） |
| K4 | **线距精度只有整像素**，最小 1px；默认 0.1mm 在 96DPI 下实际变成 0.2646mm | `Raster/Raster/Src/Engrave/RasterScanline.cpp:148`；`Main/Src/CAM/CamInputBridge.cpp:154-161` |
| K5 | **多遍语义是「逐行重复 N 次」而非「整图 N 遍」**，因为遍次循环写在行循环内部 | `Raster/Raster/Src/Engrave/RasterScanline.cpp:255` |
| K6 | **过扫有实现但生产恒为 0**，且固定像素、不随速度百分比 | `Raster/Raster/Src/Engrave/RasterScanline.cpp:205-214`；`Main/Src/CAM/CamInputBridge.cpp:168` |
| K7 | **没有雕刻预览、没有可用时间估算**。现有位图对话框只在打开时显示一次原图缩略；`estimatedSeconds` 字段标注 deprecated 且全仓零读者 | `UI/2D/Src/Operation/RasterProcessOperation2D.cpp:290`；`CAM/CAM/Include/CAM/CamPlan.h:128-130` |
| K8 | **割缝存在两套实现但作用域不同**：Raster 是像素域形态学，矢量是 Engine2D 几何偏置；生产矢量化路径走后者 | `Raster/Raster/Src/Algo/RasterContour.cpp:172-200`；`UI/2D/Src/ProcessRouteRegistry.cpp:283-360` |

### 0.4 一句话结论

Raster 的「图像处理算法库」完成度不低，缺的是**产品化与产线化**：DPI/单位、图像雕刻工艺面板、预览/估算、执行链接线、以及极性语义统一。P0 不是继续加算法，而是把「导入 → DPI 正确 → 灰度/二值 → 扫描线 → 预览/估算 → 进 CamPlan → 执行」这条线打通。

**图像解码路线对比（回答「是否必须弃用 QImage」）**

核实结果：**Raster 当前没有用 QImage，用的是 OpenCV**；FileIO 用 stb_image；QImage 只出现在 UI 预览层。模块边界没有被违反。若将来需要读 DPI 元数据，候选对比如下：

| 方案 | 体积/编译开销 | 许可证（可商用） | 格式覆盖 | DPI 元数据 | 结论 |
|---|---|---|---|---|---|
| OpenCV core+imgcodecs（现状） | 大（数十 MB DLL，已编入） | Apache-2.0，可商用 | 全 | 不暴露 pHYs/JFIF | **保留**，仅补元数据解析 |
| stb_image（现状，FileIO 已用） | 极小（单头文件） | Public Domain/MIT | PNG/JPG/BMP/GIF/TGA/PSD | 不暴露 | 保留用于快速读取像素 |
| libjpeg-turbo + libpng | 中（两库） | BSD-like/zlib，可商用 | JPG/PNG | 需自行读块 | 仅为 DPI 引入不值得 |
| libtiff | 中 | libtiff License（可商用） | TIFF | 可读 Resolution 标签 | TIFF 若要做 16bit/多页再评估 |
| FreeImage | 中 | FIPL（可商用，但条款繁琐） | 全 | 可读 | 不推荐，重复现有能力 |
| Qt QImage | 已在 UI2D | LGPL/商业 | 全 | 可读 | **禁止进 Raster**，只留 UI 预览 |

**推荐**：不解码二次引入。P0 在 `FileIO/FileIO/Src/ImageUtils.cpp` 增加约 100 行的 PNG `pHYs` 与 JPEG APP0/JFIF 解析（自研，零新依赖），TIFF 分辨率列为候选待评估；Raster 只接收 `pixelPitchMm`，永不接 DPI 概念。

**C ABI 变更规则**（所有涉及 Raster 的条目通用）

- 已导出函数不改签名；新增能力用 `Raster_*Ex` 新函数，旧函数保留转发。
- 结构体只增不删，新字段一律追加到末尾，并提升 `RASTER_ABI_VERSION`；`Raster_GetAbiVersion` 供宿主校验。
- 内存归属：输入缓冲区由调用方分配；输出结构由 Raster 分配并提供 `Raster_*Free`；禁止 STL 容器跨 DLL。
- 失败表达：统一返回 `RasterStatus`（`RASTER_OK` / `RASTER_ERR_*`），错误文本英文，中文由 UI 映射。

**UI 公共约定**

- 所有错误文案英文，例如 `Image has no DPI metadata. Set a physical width.`、`Line spacing exceeds image height.`、`Raster exceeds work area by 12.4 mm.`。
- 所有位图雕刻参数集中在同一对话框页签，默认值写入 `ProcessParams`，不写死到 Raster。
- 撤销：一次参数确认 = 一次撤销记录；预览不写场景，不产生撤销。

## 4 分期

### 4.1 分期原则

- **P0 只做「打通」，不做「变强」**：算法层已有的（阈值、抖动、扫描线、功率映射）不重写，只补参数、修语义、接产线。
- **每一期都能独立验收**：P0 结束时必须能在一台真实/仿真设备上完成一次「导入位图 → 雕刻出件 → 时间可预估」；P1/P2 各自有退出判据。
- **不跨期欠债**：P0 引入的字段单位、极性、ABI 约定，P1/P2 直接沿用，不返工。

### 4.2 P0 最小可用闭环

范围 = 表内标记 P0 的条目 + 一条当前不存在的产线接线 + 最小可用时间估算（E-02 的 P0 子集）。

**P0 边界说明**：割缝（D-06）与「雕刻后切割」不在 P0。理由：位图雕刻的最小出件闭环不需要割缝；割缝是矢量切割域的能力，一旦在 P0 引入，会把 `Engine2D` 的 mm 偏置语义拖进 Raster 像素域（见 §5.3）。如果产品验收硬性要求「雕刻 + 外轮廓切割一次完成」，则把 D-06 与 F-04 提前为 **P0.5**，不并入 P0 主链。

## 5 约束与冲突检查

### 5.1 模块边界：Raster 无 Qt 是硬约束，当前没有被违反

实测：`Raster/Raster/CMakeLists.txt:69-77` 只 `find_package(OpenCV)`，`:115-116` 只链 OpenCV；`Raster/CMakeLists.txt:32-33` 明确不引入 Qt；全仓 Raster 源码无 `QImage`/`QWidget` 引用。图像解码现状是 **Raster 用 OpenCV `imread`，FileIO 用 stb_image**，`QImage` 只出现在 UI2D 的预览层（`RasterProcessOperation2D.cpp`）。

因此：

- 「图像解码用 QImage」这个假设**不成立**，模块边界没有被违反；不需要为此整改。
- **禁止**把 `QImage` 放进 Raster 或 FileIO 的解析层；DPI 元数据解析必须在 `FileIO` 用纯字节解析完成（C1）。
- Raster 新增能力一律走 `Raster.dll` + C ABI，不允许为了省事把位图算法搬进 UI2D（UI2D 允许 Qt，但会破坏「算法可被 Headless/自动化复用」的边界）。
- Raster 不允许依赖 Engine2D：`pixelPitchMm`、mm 单位、DPI 都由调用方（Main/UI2D）换算后传入，Raster 只认像素与 mm 数值，不认 DPI 概念。

### 5.2 CAM 分期与 `CamPlan` ABI

- `CamPlan` 是跨 DLL 的 ABI 结构，**字段只能追加、不能删除、不能改语义**；`estimatedSeconds` 已标记 deprecated，**保留字段、不删除**，也不在 P0 复活它。
- 现有分段属性（`powerPercent` / `speedMmPerSec` / `passIndex`）足够表达位图扫描段，P0 不新增 `CamPlan` 字段；只有 D-05 的 `zMm` 属于真正需要追加的字段，放 P2 且必须升版本。
- 时间估算不在 `CamPlan` 里做，也不新增第二个估算器：P0 用「段长度 + 段速度 + 跳转」计算，P1 并入统一估算器并交叉引用 [走刀模拟与时间预估规划.md](file:///c:/Users/xx/Documents/Cpp/CAD/Docs/走刀模拟与时间预估规划.md)。
- CAM 的 M0/M1 分期不变：M0 只保证「矢量 + 标刻」；位图扫描段作为 `CamPlan` 的段类型进入 M1，不抢跑 M0 的排序/引线工作。

### 5.3 割缝：只有一份几何偏置实现

- Raster 侧的 `Raster_KerfCompensate` 是**像素域形态学**（椭圆核、半径 = 割缝宽/2、像素单位），不是几何偏置；它不调用、也不应调用 `Geo2DOffset`。
- 矢量切割的 `KerfCompensator` 是 **Engine2D 的几何偏置（mm）**，生产矢量化路径走它（`ProcessRouteRegistry.cpp:283-360`）。两者作用域不同，**不合并实现**。
- 按「不得写第二份偏移/求交实现」的约束：
  - 矢量域一律复用 `Geo2DOffset` / `KerfCompensator`，禁止在 Raster 或 Main 里再造偏置；
  - Raster 形态学只允许生成「像素掩码/轮廓」，跨域时**必须先转 mm 再交给矢量侧**，不得在像素域做几何求交；
  - 同一割缝宽在两侧的差异只允许来自栅格化误差，验收按 D-06 的「面积差 ≤1 个像素周长」。
- 本轮**只读**：`Engine/2D/Src/Geometry/Geo2DOffset.cpp`、`Engine/2D/Src/Algorithm/EntityContourFiller.cpp`、填充参数默认值、取色链路均不改不碰；本流程只新增 `Docs/08-Raster/`。

### 5.4 执行链路：生产仍走 `MotionPlanCompiler`，改造点只有一个

- 现状：`ProcessingJobService.cpp:446` 调 `MotionPlanCompiler`；`MotionPlanCompiler.cpp:232` 把 `GeometryKind::Raster` 判为不可加工；能编译位图的 `Cam::compile` / `CamInputBridge::buildJobInput` 只有测试与基准调用者。
- P0 的设计选择：**在 `ProcessingJobService` 按 `GeometryKind` 分流**——矢量继续走 `MotionPlanCompiler`（零改动），位图走 `CamInputBridge → Cam::compile → CamPlanEmitter`。这样：
  - 不动 `MotionPlanCompiler` 的矢量语义，回归面最小；
  - 不改 `CamPlan` ABI，只消费现有段属性；
  - 位图任务与矢量任务共用 `MotionPlan` 出口，设备层只认一种计划。
- 风险：分流后两条路径的 `MotionPlan` 字段覆盖面可能不一致（例如进给率/快速移动标志）。验证用「同一矢量任务在分流前后逐字节一致」+「位图任务段属性字段非空」。

### 5.5 UnityBuild 与代码规范

- **不许关闭 UnityBuild**：不得新增 `set_target_properties(... UNITY_BUILD OFF)` 或 `SKIP_UNITY_BUILD_INCLUSION` 来回避符号冲突。新增 `.cpp` 一律用匿名命名空间或 `static` 内部链接；新增的 C ABI 函数保持全局唯一符号。
- 代码标识符、日志、错误文案、注释里的协议名一律英文；**注释中文**。UI 可见文案英文（与现有代码一致），中文翻译走 `tr()` 资源，不在源码里写中文字符串字面量。
- 新增第三方库若与 UnityBuild 冲突（同名单头实现、宏污染），必须先在 P1 评估中记录，不能带病合入。
