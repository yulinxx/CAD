# DLL 导出与 ABI 约定（2026-11-11）

> 定位：本文是 [DLL制作标准与现状.md](../01-当前架构/DLL制作标准与现状.md) 的**演进规则补充**。

## 1. 现状基线（先确认事实，再谈规则）

1. **所有模块都是动态库**：`apr_add_shared_library()` 统一生成 SHARED 目标（`CMake/Utils.cmake:230、475`），不存在"某些模块其实是静态库"的例外（`RenderAbstraction` 除外，见下）。
2. **符号默认隐藏**：根配置 `set(CMAKE_CXX_VISIBILITY_PRESET hidden)`（`Config.cmake:141`）。因此一个符号能不能跨 DLL 用，完全取决于是否被导出宏标记。个别目标在 `CMake/Utils.cmake:480` 显式设回 `default`，新增 DLL 时必须先确认自己属于哪一类。
3. **导出宏按模块独立定义**，命名不统一但形态一致：`ENGINE_API`（`Engine/Common/Include/Engine/EngineAPI.h:17-25`）、`ENGINE2D_API`（`Engine/2D/Include/Engine2D/Engine2DAPI.h:10-20`）、`ENGINE3D_API`（`Engine/3D/Include/Engine3D/Engine3DAPI.h:10-20`）、`FILEIO_API` + `FILEIO_C_API`（`FileIO/FileIO/Include/FileIO/FileIOAPI.h:36-63`）、`RENDERBRIDGE_API`（`RenderBridge/Include/RenderBridge/RenderBridgeAPI.h:10-19`）、`CAM_API`（`CAM/CAM/Include/CAM/CAMExport.h:22-27`）、`HARDWARE_API`（`Hardware/Hardware/Include/Hardware/HardwareAPI.h:8-20`）、`LOG_API`（`Log/Log/Include/LogAPI.h:8`）。
4. **`RenderAbstraction` 不是 DLL**：纯头文件 `INTERFACE` 库（`RenderAbstraction/CMakeLists.txt:12、48-51`），只提供 `IRenderDevice/IRenderSurface/...` 纯虚接口。它的"ABI"表现为**编译期契约**：谁实现这些接口（目前是 `RenderBridge`），谁就被 vtable 布局绑定。
5. **已有两种版本策略，成熟度不同**：
   - 严格版本：RenderX C ABI `RENDERX_ABI_VERSION = 5.6`，创建运行时必须传匹配值，否则 `rxRuntimeCreate` 失败（`Renderx/include/render/renderx.h:46-48、365`），并提供了"返回 DLL 编译期版本"的查询（同文件 `:895`）。这是**正面样板**。
   - 结构体大小协商：Nesting C ABI v2 用 `structSize` 做前向兼容（见 [DLL制作标准与现状.md](../01-当前架构/DLL制作标准与现状.md) §2）。
6. **C++ DLL 没有版本查询**：`Engine2D/Engine3D/FileIO/RenderBridge` 的公开头中检索不到 `ApiVersion/apiVersion`。这意味着"头文件版本与 DLL 版本不匹配"只能在运行期以诡异崩溃或静默失效出现。

### 1.1 公开接口分类

| 类别 | 典型模块 | 边界类型 | 兼容规则严格度 |
|---|---|---|---|
| A. C ABI | `Renderx`、`Nesting`、`FileIO` 的 `FILEIO_C_API` | 句柄 + POD + 错误码 | 最高：只允许追加，不允许改布局 |
| B. 纯虚 C++ 接口 | `RenderAbstraction`（IRenderDevice/IRenderSurface/IRenderScene） | 由 DLL 内部实现、外部调用 | 高：任何虚函数增删改都破坏实现方 |
| C. 跨 DLL 对象层次 | `EngineCommon/2D/3D` 的 `AprEntity` 体系 | 继承 + 虚函数 + 跨库 shared_ptr/unique_ptr | 高：vtable、typeinfo、成员布局都受约束 |
| D. 内部 C++ DLL 门面 | `UICommon/UI2D/UI3D`、`EnginePersistence`、`FileIO` C++ 部分 | 类方法、Qt 类型 | 中：同仓同版本发布，但插件/独立工具会消费 |
| E. 设备适配器 | `Hardware` 的 `IDevice` 与 `DeviceRegistry` | C++ 类 + 导出宏 + 外部 DLL 注册 | 中高：第三方适配器由外部编译，必须稳定 |

**判定口径**：只要某个头文件在 `Include/` 下且带导出宏，或出现在 `DeviceRegistry` 的注册签名里，就按"公开接口"对待；`Src/` 下的头文件一律视为私有，不受本文保护，也不得被其他模块 include。

## 2. 新增接口的 ABI 兼容规则

### 2.1 允许（不破坏已编译调用方）

| 做法 | 说明 | 前置条件 |
|---|---|---|
| 追加**非虚**成员函数 | 不进入 vtable，不影响对象布局 | 该函数不引入新的导出符号冲突 |
| 追加**新类/新头文件** | 新符号，不影响旧符号 | 命名带模块前缀 |
| 追加**重载**并保留旧签名 | 旧调用方仍链接旧符号 | 旧实现必须保留（转发到新实现） |
| 结构体**尾部**追加字段 + `structSize` | 旧调用方传旧 size，新实现按 size 判定字段是否存在 | 字段零值必须等价于旧行为 |
| 追加**新枚举值** | 不改已有值 | 枚举必须固定底层类型，且旧代码有 `default` 兜底 |
| 追加**错误码** | 不改已有语义 | 旧代码对未知错误码要有兜底文案 |
| 新增**可选**接口（`QueryInterface` 式） | 老实现返回 `nullptr`，调用方降级 | 接口 ID 稳定、全局唯一 |

### 2.2 禁止（对已发布接口）

1. 删除或重命名导出符号；改变调用约定。
2. 修改已有函数签名（参数类型、`const`、默认参数**不**构成 ABI 兼容——默认参数只在源码层生效，已编译的旧调用方仍指向旧符号）。需要加参数时：**新增重载**，旧重载保留并转发。
3. 修改类成员**顺序、类型、大小**，或改变继承关系/基类顺序。
4. 在已被外部实现的接口上新增、删除或重排**虚函数**（包括纯虚接口和 `IDevice`）。
   - 追加到 vtable 末尾对"只调用"的一方通常安全，但对"实现方"必然破坏——跨 DLL 接口默认按"有实现方"处理。
5. 修改枚举已有值或底层类型；修改结构体已有字段的语义（例如 0 从"默认"改成"关闭"）。
6. 改变所有权与销毁契约（谁分配、谁释放、是否需要同 DLL `Destroy()`）——这在 Windows 上会演变为跨 CRT 崩溃。
7. 让 `std::string/std::vector/QString/Qt 容器` 出现在新增的 C ABI 或跨 DLL 结构体中（C++ DLL 内部可用，但不得作为契约）。
8. 在公开头里新增 `inline` 函数且不带导出控制——多 DLL 各自生成弱符号，配合 `-fvisibility=hidden` 会重演"typeinfo 各自一份、`dynamic_cast` 静默失败"的事故（`CMake/AbiVisibilityGuard.cmake:1-35` 记录的 Engine3D/UI3D 真实故障）。

### 2.3 符号冲突规则

- 公开函数统一带模块前缀（`rx*`、`cam*`、`hw*`、`eg2d*` 或经导出宏的命名空间），避免不同 DLL 导出同名符号后由链接顺序决定行为。
- 内部 helper 一律放匿名命名空间或 `static`；不导出模板实例化。
- 公开头中的常量用 `constexpr`（C++17 起隐式 inline），不要用 `const` 全局变量。

### 2.4 跨库对象判型

- 禁止 `dynamic_cast`；统一 `eType` + `static_cast`（[DLL制作标准与现状.md](../01-当前架构/DLL制作标准与现状.md) §3.5）。
- 需要"能力扩展"时不要用 RTTI，使用稳定的能力 ID：
  ```cpp
  // 示例（文档约定，非现有代码）
  enum class CapabilityId : uint32_t { SurfaceMsaa = 1, ToolpathXray = 2 };
  // 实现方返回 nullptr 表示不支持；调用方必须降级而不是崩溃
  virtual void* queryInterface(CapabilityId id) noexcept = 0;
  ```
  该函数只能加在**新接口**上；已有接口不得再增虚函数。

## 3. 新增能力的落地模式（不破坏既有调用方与插件）

### 3.1 渲染表面采样数（MSAA）

- 不修改 `IRenderSurface` 的虚函数表。
- 在 `RenderBridge` 的中性 POD 配置结构体（`RenderBridgeTypes.h` 体系）尾部追加 `uint32_t msaaSamples;`，并保留 `uint32_t structSize;` 作为首字段。
- 创建路径按 `structSize` 判定：旧调用方字段不存在 → 取 0 → 后端使用默认值（当前行为不变）。
- 后端支持性由 RenderX 能力查询返回；请求值不被支持时**降级并记录警告**，不返回失败（除非客户显式要求严格模式）。

### 3.2 刀路穿透显示开关

- 这是显示选项，不是渲染 ABI：放在 `RenderBridgeTypes.h` 的显示选项 POD 中（尾部追加 `uint8_t toolpathXray;`），由 UI 设置 → 桥接层映射。
- 禁止把它加到 `UI3D` 的公开类成员（会改变对象布局），也禁止加进 `IRenderScene` 的虚接口。
- 旧版本桥接层收到未知字段时忽略，不报错。

### 3.3 设备能力（Hardware）

- `IDevice` 是对外注册的 C++ 接口，新增虚函数会破坏第三方适配器（外部 DLL 已编译）。
- 扩展方式：新增 `IDeviceV2`（继承 `IDevice`，只在末尾追加虚函数），注册表同时接受两种工厂；调用方通过能力查询探测，老适配器继续工作。
- 设备能力用**位掩码 + 稳定枚举值**表达，追加值只能在末尾。

### 3.4 通用模板

```text
新增能力请求
  ├─ 是"数据/选项"？ → 尾部字段 + structSize + 零值兼容
  ├─ 是"新操作"？     → 新增非虚方法（或新重载，旧签名保留）
  ├─ 是"新实现方能力"？→ 新接口（V2）+ 能力查询 + 老实现降级
  └─ 是"改已有语义"？ → 破坏性变更，走 §4 流程
```

## 4. 破坏性变更的判定与升级流程

### 4.1 判定条件（任一命中即破坏性）

1. 删除、重命名导出符号，或改变调用约定。
2. 修改已有函数签名（含参数、`const`、异常规格）。
3. 修改类成员顺序/类型/大小、基类顺序或继承关系。
4. 在已有接口上增删/重排虚函数（含纯虚）。
5. 修改枚举已有值或底层类型。
6. 修改结构体已有字段或错误码的语义。
7. 修改线程/所有权/生命周期契约。
8. 修改"零值/缺省值"的含义。

### 4.2 升级流程

1. **登记**：在变更单写清模块、符号、受影响方（仓内模块 / 外部插件 / 客户 SDK）、兼容窗口。
2. **版本**：
   - RenderX：`RENDERX_ABI_VERSION` 主版本 +1（`renderx.h:46-48`）。
   - 其他 C++ DLL：必须先补 `XxxApiVersion()` 与 `XxxBuildId()` 导出（当前缺失，见 §5），再按主版本 +1 发布。
3. **兼容层**：旧符号保留一个发布周期，内部转发到新实现；或提供 V1/V2 两套接口并存。
4. **同步调用方**：先改仓内全部调用方，再改外部插件 SDK；插件必须能在旧宿主上"拒绝加载并给出明确提示"，而不是崩溃。
5. **CI 拦截**：导出符号清单做基线（`dumpbin /exports`、`nm -gU`、`objdump -T`），PR 中新增/删除符号必须显式确认。
6. **弃用与移除**：弃用公告 + 至少一个发布周期，才能删除兼容层。

### 4.3 版本号语义（建议统一）

| 变化 | 处理 |
|---|---|
| 追加非虚方法、尾部字段、新枚举值 | 次版本 +1，旧 DLL 可被新调用方加载（缺失能力降级） |
| 新增接口（V2） | 次版本 +1，能力查询 |
| 上述任一破坏项 | 主版本 +1，且必须提供兼容窗口 |

## 6. 导出符号基线（四个外部链接库，已落地）

**目标**：把已发布 DLL 的导出符号集合钉进仓库，删除或改名在比对这一步就被点名，而不是等下游在链接期报 undefined symbol。

**覆盖面**：只收有外部消费者的四个库——Renderx（C ABI）、Engine2D、Engine3D、RenderBridge。其余模块没有外部链接方，刻意不建基线：Engine2D 单库就有 1619 个符号，铺到全部 25 个模块只会得到一堆没人看的文本。

| 项 | 位置 |
|---|---|
| 比对脚本（唯一一份，四库共用） | `Tools/Abi/check_exports.py` |
| 基线文件（按库名分开放） | `Tools/Abi/baseline/<target>.txt` |
| 符号来源 | `nm -gU libX.dylib`（macOS）/ `nm -D --defined-only libX.so`（ELF） |

当前基线规模：

| 库 | 符号数 | 说明 |
|---|---|---|
| Renderx | 66 | 含 `rxSessionGetGpuFrameTimeNs`、`rxPipelineEnsureVariant` |
| Engine2D | 1619 | 含本周新增的 `Eg::Detail::assertSceneThread` |
| Engine3D | 439 | 写接口 private 化后需按本节规则更新 |
| RenderBridge | 66 | 含 `createOffscreenRenderFactory` |

归一化时剥掉 Mach-O 的 C 前导下划线（`_rx...` → `rx...`、`__ZN...` → `_ZN...`），因此同一份基线在 macOS / Linux 通用。

**三种用法**：

```bash
# 1. 按库名比对：自动探测产物，使用 Tools/Abi/baseline/<target>.txt
python3 Tools/Abi/check_exports.py Renderx
python3 Tools/Abi/check_exports.py Engine2D

# 2. 显式指定产物（多构建目录，或打包前的正式产物）
python3 Tools/Abi/check_exports.py Engine2D -l <path>/libEngine2D.dylib

# 3. 显式接受当前导出集：只在该变更已按 §4 评审为向后兼容时执行
python3 Tools/Abi/check_exports.py Engine2D --update -l <path>/libEngine2D.dylib
```

**比对规则：只允许新增。**

| 情况 | 行为 | 退出码 |
|---|---|---|
| 新增符号 | 逐条打印 `added (allowed)` | 0 |
| 任一基线符号消失 | 逐条打印 `REMOVED: <name>`，末尾 `FAIL` | 1 |
| 符号改名 | 符号表中表现为"旧名消失 + 新名出现"，按删除处理 | 1 |

这样定，是因为下游（RenderBridge、宿主 DLL）都在链接期才用到符号：删一个导出，本模块自己照样编译通过，受害方是"别人编不过"。让删除方向硬失败、新增方向放行，`--update` 才能保持低频且必须人工过一遍。

**局限（必须同页记录）**：符号表只记名字，不记类型。**C 函数参数/返回值变化不会改符号名，`nm` 查不出来**——例如 `rxBufferCreate` 把 `uint32_t` 改成 `uint64_t`，基线比对照常通过，但已编译的调用方会传错参数。因此：

- 本脚本**不能替代** ABI 版本号协商（`RENDERX_ABI_VERSION` + `rxGetAbiVersion` 的兼容判定）；
- 它只是"防线之一"：符号集合不缩水 + 版本号语义 + PR 审查签名，三者缺一不可。

**尚未接入 CI**。当前是手工入口，时间一长就没人记得它在跑。接入时的约定：

- **放在哪个 job**：构建产物已生成、`libEngine2D/libEngine3D/libRenderBridge/libRenderX` 可定位的那个 job（即产出 `bin_Qt6/<Config>/` 之后），不占用纯静态检查 job；
- **按什么失败**：以 `check_exports.py <target> -l <产物>` 的退出码为准，非 0 即失败；job 日志必须保留 `REMOVED:` 行作为证据；四个库逐个跑，任一失败即 job 失败；
- 新增方向放行，因此不需要自动 `--update`；基线更新仍走人工提交与评审；
- 接入动作由正在修改 `ci.yml` 的线在落地后执行，避免同文件冲突。

## 7. PR 级检查清单（提交前逐条自问）

- [ ] 新增/修改的头文件在 `Include/` 下吗？在 `Src/` 下的东西有没有被别的模块 include？
- [ ] 新增符号是否带模块前缀、是否只通过导出宏暴露？
- [ ] 是否改了已有函数签名/成员顺序/虚函数表？如果改了，是否按 §4 走了流程？
- [ ] 跨 DLL 结构体是否尾部追加并保留 `structSize`？旧值零值语义是否保持？
- [ ] 新枚举值是否追加在末尾、底层类型是否固定？
- [ ] 是否引入了 `dynamic_cast`、`std::string/vector` 或 Qt 类型到公开边界？
- [ ] 对象由谁分配、由谁销毁？删除是否在同一 DLL 内完成？
- [ ] 新能力是否提供了"不支持时的降级路径"，而不是硬失败或崩溃？
- [ ] 若修改了 `Renderx/include/render/renderx.h`，是否同步了 `RENDERX_ABI_VERSION`？
