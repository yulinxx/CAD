# 工业级架构完备性评审（2026-11-11）

> 评审对象：`/Users/ms/Documents/CAD`（Qt 6 / C++ 激光加工 CAD/CAM 桌面软件，主仓 + Engine / UI / PyBindCore 等子模块）
> 评审方式：只读代码与构建配置，按维度取证；不修改代码、不提交。
> 结论口径：每条先给 **已达标 / 有缺口 / 不适用**，再给证据（`文件:行` 或 CMake 目标关系）。

---

## 0. 总体判断（先给结论）

**水平：B（工程化基础扎实、关键工业能力尚未闭环）。**

- 值得肯定的部分：模块分层不是文档口号，而是 **configure 阶段会硬失败的门禁**（依赖方向、include 棘轮、场景写面三道），这在中型 C++ 项目里属于少见且有效的做法；SQLite 访问层、异常到日志的落盘、安装包合规物也做得比多数同类项目扎实。
- 不能称为"工业级"的部分：**加工工艺链几乎空白（CAM 仍为 M0）、加工过程没有任何可追溯记录、文档没有自动保存/崩溃恢复、渲染与 3D 算法仍在 UI 线程、macOS 无构建与签名发布链、依赖版本不锁定**。

三项最关键的缺口（详见 §9）：**① 加工闭环与可追溯性；② 运行期可靠性（线程模型 + 数据恢复）；③ 交付工程（macOS CI / 签名 / 依赖可复现）**。

## 1. 模块分层与依赖边界

### 1.1 依赖方向门禁 —— 已达标

- 规则 1~6 在 configure 阶段执行，违规直接 `FATAL_ERROR`：`CMake/CheckDependencies.cmake:79-260`（失败点 `:245-250`）。
  - 规则 1：Engine* 不得依赖 UI*/Render*/Main；规则 2：Render* 不得依赖 UI*/Main；规则 3：UI* 不得直接链接 Engine*；规则 4：UI* 不得直接链接 RenderX（`:104-161`）。
  - 规则 5/6 专门堵"假解耦"：UI 的 include 目录不得出现 RenderX 头路径，UI 的 **INTERFACE 传递闭包**不得到达 RenderX（`:189-220`），判据用的是 `INTERFACE_LINK_LIBRARIES` 而不是 `LINK_LIBRARIES`（`:51-77`）——这一点很关键，否则 PUBLIC 转发会被误判为已收口。
- 渲染侧确实完成了收口：`RenderBridge` 对 `RenderX` 已改为 PRIVATE 链接（`RenderBridge/RenderBridge/CMakeLists.txt:84-89`），UI 只看到 `RenderAbstraction` 接口。
- 模块链接声明本身是干净的：Engine2D 只 PUBLIC `Utility/EngineCommon/Boost/Log`，PRIVATE `Freetype/Clipper2`（`Engine/2D/CMakeLists.txt:80-89`）；Engine3D 只 PUBLIC `Utility/EngineCommon/Log`（`Engine/3D/CMakeLists.txt:72-78`）；CAM 只 PUBLIC `Utility`、PRIVATE `Log`（`CAM/CAM/CMakeLists.txt:48-53`）；Hardware 只 PRIVATE `Log/Utility` + Qt Core（`Hardware/Hardware/CMakeLists.txt:49-54`）。

### 1.2 UI → Engine 的 include 面 —— 有缺口（已知取舍，但代价要认）

- 链接层收口、include 层**未**收口：`CMake/CheckDependencies.cmake:14-24` 明确写了这一点，`CMake/UiEngineAccessRatchet.cmake:118-199` 把存量冻结为白名单（UI/Common 13、UI/2D 45、UI/3D 17，共 75 个去重的 Engine 头）。
- 棘轮本身设计得很好：按"去重后的头文件集合"统计（`:20-24`）、剔除注释与 `#if 0`（`:37-113`）、**反向检查**保证白名单只减不增（`:256-268`）。
- 但结论要如实说：**UI 与 Engine 共享同一个领域模型，UI 公共头直接暴露 Engine 类型**，因此模块边界目前靠"CMake 目标 + 白名单"维持，而不是靠编译期不可见。新增 API 面必须改白名单——这是显式决策，但仍是持续成本。

### 1.3 2D 场景写入口 —— 已达标（3D 未同步，属于缺口）

- 写接口 private 化 + 窄 friend，并在 configure 阶段扫生产代码：`CMake/SceneWriteSurface.cmake:1-66`（命中 `SceneWriteGateway` 即失败）。扫描范围含 `UI/2D/Src`、`UI/Common/Src`、`Main/Src`、`PyBindCore/PyBindCore/Src`（`:22-28`）。
- **3D 侧完全没有对应收敛**：`Engine/3D/Include/Engine3D/SceneManager3D.h:174,178` 的 `addEntity` 仍是 public，且不存在 `SceneEditService3D`（`Engine/3D/Include/Engine3D/Edit` 下只有 `SceneUndoCommands3D.h`）。也就是说 3D 的"是否入撤销栈"仍由调用点自行决定。

### 1.4 门禁覆盖面 —— 有缺口

- 受依赖方向校验的目标只有：`EngineCommon/Engine2D/Engine3D/EnginePersistence`、`RenderX/RenderBridge`、`UICommon/UI2D/UI3D`、`April`、`CAM`（`CMake/CheckDependencies.cmake:80-84`）。**FileIO / Hardware / Nesting / Vision / Network / Engraving / GeoModelCore / PyBindCore / PythonHost / Raster 不在任何方向规则内**。例如 Hardware 今天若 `#include "UI2D/..."`，configure 不会报错。
- `Main`（`April`）直接链接 `RenderX`（`Main/CMakeLists.txt:358`），即应用层保留了一条绕过 `RenderAbstraction` 的直连。UI 侧的收口是真实的，但"整个应用只通过抽象层接触渲染后端"这一目标尚未成立。
- 工艺语义位于 UI 层：`UI/2D/Include/UI2D/ProcessRouteRegistry.h:1-30` 定义三条工艺管线与能力协商。这让 CAM / Engine 无法复用工艺路由，工艺知识被锁在 2D UI 里。

## 2. 错误处理与失败传播

### 2.1 命令层结果模型 —— 已达标

- 统一结构 `OperationResultBase{success, message, phase, flags}`：`UI/Common/Include/UI/Command/OperationTypes.h:44-65`。成功/失败、提示文案、生命周期阶段、是否改场景/可撤销，都在同一处表达，UI 侧无需猜。

### 2.2 引擎层异常契约 —— 有缺口

- Engine2D / Engine3D 生产代码里 **没有 catch 块**（全仓 `catch(...)` 共 115 处，集中在 CrashHandler 30、Vision 47、Engraving 25、FileIO 8、Main 7）。也就是说引擎层默认"不抛异常"，但 Clipper2 / OCCT / 文件解析器等第三方一旦抛出，只有上层边界能兜住。
- 全仓 `catch (...)` 中有 4 处**完全空实现**：`CrashHandler/CrashHandler/Src/CrashHandler.cpp:136-138、162-164、190-191、244-245`。崩溃处理路径吞异常可以接受，但没有注释说明"为什么可以吞"，后续维护者无法判断是有意还是遗漏。
- FileIO 是正面例子：异常类型与 `what()` 都落日志，同时给调用方 error buffer（`FileIO/FileIO/Src/FileIOManager.cpp:304-325`），并明确注释"errorBuffer 只回一句概括，排查时不够用"（`:306`）。

### 2.3 失败是否可见 —— 基本达标，但不统一

- UI/Main 非测试代码有 132 处 `QMessageBox::`，失败对用户可见是常态。
- 缺口在于**没有错误码 → 用户文案的统一映射层**：`OperationResult.message` 由各 handler 自填，缺少"空 message 即失败"的兜底；`operationPhaseToString` 只解决阶段枚举（`UI/Common/Include/UI/Command/OperationTypes.h:67`），不解决错误分类。
- CAM 的入口把 `result` 设计为可空（`CAM/CAM/Include/CAM/CamCore.h:45-50`），调用方可以只拿到 `ok=false` 而不拿错误码与统计——这为"只报失败不报原因"留了口子。

### 2.4 小结

| 子项 | 结论 |
|---|---|
| 命令层结果结构 | 已达标 |
| 引擎层异常边界与契约 | 有缺口（无 catch、无文档化契约） |
| 第三方异常兜底与日志 | 已达标（FileIO 范式） |
| 错误码到用户文案的统一映射 | 有缺口 |
| 空 catch 的可解释性 | 有缺口（4 处无注释） |

## 3. 持久化与数据完整性

### 3.1 文档格式与原子写 —— 已达标（耐久性差一步）

- 真实文档路径是 FileIO 的 `AprSerializer`（3D 仅换魔数 `AP3D`，见 `UI/3D/Src/Storage/SceneDocumentIO3D.cpp:6`）。写入流程：魔数/头 + 负载 + CRC32 尾（`FileIO/FileIO/Src/AprSerializer.cpp:640-656`）。
- 原子写做得对：**同目录**临时文件（避免跨卷 rename 退化）→ 写 → `flush` → `close` → 逐项检查 `good()/fail()` → `rename` 覆盖（`AprSerializer.cpp:660-721`），失败/取消删除临时文件（`:672-675`）。
- 缺口：**没有 `fsync`/`FlushFileBuffers`**（全仓仅在第三方 libdxfrw 中出现，`ThirdParty/libdxfrw/src/intern/dwg_dxf_output_transaction.cpp:292-308`）。`ofstream::flush` 只到内核页缓存，断电时 rename 后仍可能得到 0 字节文件；这是"看起来原子、实际不抗掉电"的典型形态。

### 3.2 SQLite 访问模型 —— 已达标

- WAL + `busy_timeout=5000`（`Engine/Persistence/Src/Database.cpp:196-198`），并针对 `SQLITE_BUSY / BUSY_SNAPSHOT` 做了指数退避重试（同文件 `:79-91`，重试点在 `:255/344/433/545`）。这一点比多数桌面项目成熟。
- 注入防护走"表名/列名白名单"而非字符串拼接（`Main/Src/Persistence/SharedDatabaseAdapter.h:81-84`、`Main/Src/Persistence/DatabaseBootstrapper.cpp:76-77`），参数化绑定用于值。
- 迁移是幂等的：`ensureColumn` 通过 `PRAGMA table_info` 判断后补列（`DatabaseBootstrapper.cpp:369、415`），版本不匹配时只重置 `schema_version` 并保留用户数据（`:86-97`）。
- 双连接问题有明确处理：设置侧通过 `SharedDatabaseAdapter` 复用业务连接，避免 WAL 下双写互撞（`SharedDatabaseAdapter.h:5-11`）。

### 3.3 崩溃不丢数据 —— 有缺口（最严重的一项持久化问题）

- **没有文档自动保存/恢复**：全仓 `autosave / AutoSave / recovery` 检索只命中视图捕获与无关代码；`workspace_snapshots` 表只存工作台布局（`DatabaseBootstrapper.cpp:283`、`Main/Src/Persistence/Repositories/WorkspaceSnapshotRepository.cpp:17-47`）。
- **没有 `.bak`/历史版本**：`AprSerializer` 覆盖写成功后旧文件即消失，误操作与坏盘都无退路。
- 归因：文件写是原子的，但"进程被杀/崩溃时未保存的编辑"没有任何恢复通道——这是工业现场最常见的投诉来源。

### 3.4 序列化抽象分叉 —— 有缺口

- `Engine/Persistence` 导出了 `ISceneSerializer` / `SceneManagerSerializer`（`Engine/Persistence/Include/Engine/Persistence/`），但**生产代码无调用方**（仅自身实现与测试）；Main/UI 对 `Engine/Persistence` 的实际引用全部是 `Database.h`（`Main/Src/Persistence/PersistenceService.cpp:20` 等 10 处）。
- 结果是同一件事存在两套抽象：一套在用（FileIO/AprSerializer），一套在库里有版本迁移逻辑但未接线（`SceneManagerSerializer.h:130、213` 的 `migrate/migrateV1ToCurrent`）。后续极易出现"改了一套以为生效"的错误。

### 3.5 小结

| 子项 | 结论 |
|---|---|
| 文档格式（魔数/CRC/版本） | 已达标 |
| 原子写（tmp+rename） | 已达标 |
| 断电耐久（fsync + 目录同步） | 有缺口 |
| SQLite 并发/重试/迁移 | 已达标 |
| 自动保存与崩溃恢复 | 有缺口 |
| 备份/历史版本 | 有缺口 |
| 序列化实现唯一性 | 有缺口（双抽象，一套未接线） |

## 4. 并发与线程模型

### 4.1 算法任务 —— 已达标

- 三段式契约写进了接口：`doPrepare/doApply` 在主线程，`doCompute` 在工作线程且**禁止触碰 Qt 控件与 SceneManager/SceneEditService**（`UI/Common/Include/UI/Algorithm/IAlgorithmTaskHandler.h:77-87`、`UI/Common/Include/UI/Algorithm/BackgroundAlgorithmTaskHandler.h:35-38`）。
- 取消是协作式的原子标志 + 轮询，嵌套求解器另有 watchdog 线程看护（`UI/Common/Src/Algorithm/NestingEngine.cpp:459`），并在锁下调用 `RequestCancel()`（`Nesting/Nesting/Src/Api/NestingApi.cpp:103-166`）。
- 主线程/工作线程归属有运行期断言（`UI/Common/Src/Algorithm/AlgorithmApplicationService.cpp:363-425`）。

### 4.2 渲染线程 —— 有缺口（结构性）

- 3D 视口是 `QOpenGLWidget`（`UI/3D/Include/UI3D/Render3D/RenderWidget3D.h:108`），2D 视口的上传路径同样直接 `makeCurrent()`（`UI/2D/Src/UI/ViewWidget/RenderWidget.cpp:309`）。**渲染与几何提交发生在 GUI 线程**，没有独立渲染线程。当前靠"16ms 节流 + 增量刷新"缓解（`Main/Src/UI/Render/SceneRefreshCoordinator.h:88-100`），但这是削峰，不是线程隔离——大图纸 + 相机连续操作时，帧预算与 UI 响应仍互相挤占。
- 渲染后端本身是上下文驱动而非线程驱动（`Renderx/src/rt/rxSession.cpp:7,271`：GL 后端在 `acquireNextImage` 内 `makeCurrent`），所以真正的约束来自宿主选择在哪个线程驱动帧循环。

### 4.3 3D 算法仍同步 —— 有缺口

- 2D 已统一走 `runAsync`（无后台能力时服务内部退化为同步，`UI/2D/Src/Operation/AlgorithmRunner.cpp:121-132`）；**3D 仍直接 `runSync`**（`UI/3D/Src/Operation/AlgorithmRunner3D.cpp:107`）。3D 布尔/编辑在大模型上会整段阻塞主线程。

### 4.4 共享状态 —— 有缺口（弱保证）

- `SceneManager` 没有任何互斥或原子保护（头文件内 mutex/atomic 检索 0 命中）。"只有主线程写场景"目前是**口头契约 + 代码评审**，没有类型或断言强制；一旦某个后台 handler 误写，就是数据竞争而非编译错误。

### 4.5 小结

| 子项 | 结论 |
|---|---|
| 算法任务线程契约与取消 | 已达标 |
| 渲染线程隔离 | 有缺口（GUI 线程渲染） |
| 3D 长任务异步化 | 有缺口 |
| 场景数据并发保护 | 有缺口（无锁、靠约定） |
| 设备通信线程 | 不适用/未见统一模型（Hardware 以 `IDevice` 抽象，线程归属未在头文件约束） |

## 5. 可观测性

### 5.1 日志 —— 已达标

- 六级（Trace/Debug/Info/Warn/Error/Critical）、异步队列、按 10MB × 10 轮转、30 天清理、错误日志独立文件（`Log/Log/Include/Log/AprLogger.h:61-87`）。
- 崩溃前先刷盘的设计是对的，并写清了"异步日志在硬崩溃时会丢失"的动机（`AprLogger.h:129-136`）。
- 宏携带 `__FILE__/__LINE__`（`AprLogger.h:194-196`），排查时不需要猜调用点。
- 跨模块 `traceId` 传播（`Log/Log/Include/Log/AprTraceContext.h:1-50`），把一次用户操作串起 UI → PythonHost/Network。

### 5.2 崩溃上报 —— 部分达标

- 三平台 Breakpad minidump：`CrashHandler/CrashHandler/Src/Platform/CrashHandlerWin.cpp:151`、`CrashHandlerMac.cpp:98`、`CrashHandlerLinux.cpp:110`；启动装配在 `Main/Src/Common/CrashHandlerBootstrap.cpp`。
- 缺口：**只有本地 dump，没有自动上传、符号表归档与堆栈聚合**（全仓无 sentry/crashpad/符号服务器配置）。工业客户现场的崩溃仍然要靠用户把 `.dmp` 发回来，且没有符号就无法快速定位。

### 5.3 加工过程可追溯 —— 有缺口（工业级硬要求）

- 全仓检索 `MachiningJob / JobRecord / 加工记录 / job_history` **零命中**。也就是说：没有"谁、在什么时间、用什么参数、加工了什么、结果如何"的持久化记录。
- 现有 `traceId` 只解决**同一次会话内**的日志串联，不产生可查询的历史；数据库有 `documents/recent_files/layers/settings`，没有作业维度表。

### 5.4 小结

| 子项 | 结论 |
|---|---|
| 日志分级/轮转/降噪能力 | 已达标（异步+轮转；`rateLimit` 默认 0，见 `AprLogger.h:84`） |
| 崩溃捕获与 dump | 已达标（本地） |
| dump 上报与符号化 | 有缺口 |
| 加工作业记录/审计 | 有缺口 |

## 6. 构建与发布

### 6.1 打包 —— 已达标（形态齐全）

- CPack 覆盖 NSIS / DragNDrop / DEB / RPM / AppImage（`CMake/Packaging.cmake:72-165`），安装目录固定以保证覆盖升级（`CPACK_PACKAGE_INSTALL_DIRECTORY "April"`，`CMake/Packaging.cmake:178`）。
- 合规物随包：libdxfrw（GPL-2.0）许可证全文、第三方声明、SBOM、本地修改记录（`Packaging.cmake:36-56`）。这在商用 CAD 里是必要的。
- 安装包冒烟覆盖安装/升级/卸载（`.github/workflows/package-smoke.yml:44-73`）。

### 6.2 CI —— 有缺口（平台不对称）

- Windows 作业是真实门禁：全量 Configure/Build 12 个测试目标 + `ctest --no-tests=error`（`.github/workflows/ci.yml:37-65`），另有独立 `/analyze` 作业（`:67-70`）。
- **主程序从未在 macOS/Linux 上构建**：`core-libs-macos-linux` 只构建 Nesting 与 GeoModelCore（`ci.yml:106-165`），workflow 注释也直说"全应用（Qt + 全套 vcpkg 依赖）的 mac/Linux 构建目前太重，留待后续单独开作业"（`ci.yml:104`）。也就是说，日常开发平台（macOS）的 `April.app` 构建与测试完全靠本地，无 CI 兜底。
- 无签名与公证：全仓 `codesign / notarytool / signtool` 检索零命中。macOS 产物无法直接分发给客户（Gatekeeper 拦截），Windows 产物无签名会被 SmartScreen 提示。
- 依赖不可复现：vcpkg 走 classic 模式 + 硬编码路径，Windows 默认值甚至留着占位符 `C:/Users/xx/vcpkg/`（`Config.cmake:26-34`）；CI 每次 `git clone --depth 1` vcpkg HEAD（`ci.yml:138`）。仓库没有 `vcpkg.json` / `builtin-baseline`，同一份源码在不同时间 configure，三方库版本可能不同。

### 6.3 构建系统本身 —— 已达标（有可维护性隐患）

- 目标划分清晰、模块开关（BUILD_xxx）完整，`add_subdirectory` 顺序与依赖一致（`CMakeLists.txt:147-289`）。
- 隐患：大量 `file(GLOB_RECURSE CONFIGURE_DEPENDS)` + unity build + 全局 `add_compile_options`。前者会让新增文件隐式进入构建（可接受），但 unity 合批导致的匿名命名空间冲突已在本轮实际发生过（若干"同名函数合并后重复定义"问题），属于需要持续维护的成本。

### 6.4 小结

| 子项 | 结论 |
|---|---|

## 7. 可扩展性

### 7.1 设备与机型 —— 已达标

- `Hw::DeviceRegistry` 用"字符串 ID → 工厂函数"注册，支持外部 DLL 注册第三方适配器，工厂只构造不碰硬件，硬件访问集中在 `open()`（`Hardware/Hardware/Include/Hardware/Device/DeviceRegistry.h:1-60`）。
- 已有 6 家厂商实现（Leadshine / Bjjcz 金橙子 / Zmotion / Aerotech / Scanlab RTC / Ruida），新增机型 = 新增适配器 + 一行注册，不改调用方。

### 7.2 工艺与后处理 —— 有缺口

- 位图/矢量工艺路由是注册式 + 能力协商，且明确"不支持就报原因，不静默降级"（`UI/2D/Include/UI2D/ProcessRouteRegistry.h:1-30`）——设计意图正确。
- 但 CAM 仍是骨架：`CamCore.h:26-29` 明示 M0 只做"输入校验 → 分层 → 轮廓 → 空移 → 长度统计"，**割缝补偿、引线、穿孔、功率曲线、拐角、共边切割均未实现**，且 `CAM/CAM/Src` 下只有 `CamCore.cpp` 一个实现文件。以工业激光加工的标准，这属于核心工艺能力缺失，而不是"可扩展性"问题。
- 工艺路由位于 UI 层（§1.4），意味着雕刻/3D/CAM 链无法共享同一套工艺知识。

### 7.3 客户化 —— 已达标

- 客户 ID 运行期解析而非编译期宏，同一二进制服务多个客户（`Main/CMakeLists.txt:370-374`）；UI 由 JSON 配置驱动装配（`base.json` + `UiLayoutBuilder`），工具栏与视图可配置。

### 7.4 小结

| 子项 | 结论 |
|---|---|
| 新增机型/设备 | 已达标（注册表 + 外部 DLL） |
| 新增工艺路由（位图/矢量） | 已达标（但位于 UI 层） |
| 新增后处理/工艺步骤 | 有缺口（CAM M0，挂载点未落地） |
| 客户化/白标 | 已达标 |

## 8. 测试体系与质量门禁

### 8.1 测试规模 —— 已达标（量足）

- 测试注册点 124 处；分模块测试文件数：Engine2D 60、Main 38、UI2D 21、UI3D 19、Engine3D 12、FileIO 12、UICommon 8、Hardware 3、CAM 1。
- CI 实际编译并运行 12 个测试目标（`ci.yml:48-65`），不是"写了不跑"。

### 8.2 覆盖空白 —— 有缺口

- **Engine/Persistence 没有 Test 目录**（`Engine/Persistence` 下只有 `CMakeLists.txt/Include/Src`）；文档序列化只被 FileIO 与 Main 的集成测试间接覆盖。
- CAM（1 个测试文件）与 Hardware（3 个）相对于其风险权重明显偏少；`build-and-test` 作业以 `-DBUILD_HARDWARE=OFF` 构建（`ci.yml:41`），`/analyze` 作业虽 `BUILD_HARDWARE=ON` 但只构建 `UICommon/UI2D/UI3D/April`、不跑测试（`ci.yml:81-93`），等于设备层长期没有自动回归。

### 8.3 质量门禁 —— 有缺口

- 编译告警：`-Wall -Wextra -Wpedantic`，同时显式关闭了 6 类告警（`CMake/CompilerOptions.cmake:46-58`），**没有 `-Werror`**。对本项目这种"注释极多、模板极多"的代码量，缺 `-Werror` 意味着新增告警不会被拦截。
- 无 sanitizer：全仓 `fsanitize` 只命中第三方 libdxfrw 自身配置，没有 ASan/UBSan/TSan 作业。对一个多线程 + 手写内存管理的 C++ 项目，这是明显的保护缺口。
- 性能：有基准（`Tools/PerfBenchmark`、Engine2D 的 `SnapBenchmarkTests`），但 CI 不运行、无阈值门禁，性能回退只能靠人肉发现。

### 8.4 小结

| 子项 | 结论 |
|---|---|
| 单元/集成测试数量与执行 | 已达标 |
| 持久化/设备层覆盖 | 有缺口 |
| 告警门禁（-Werror） | 有缺口 |
| Sanitizer | 有缺口 |
| 性能预算门禁 | 有缺口 |
| 覆盖率统计 | 有缺口 |

## 9. 综合判断与优先级建议

### 9.1 当前水平

| 维度 | 结论 | 一句话理由 |
|---|---|---|
| 模块分层与依赖边界 | **已达标（局部有缺口）** | 三道门禁真实生效；扩展模块与 3D 写面未覆盖 |
| 错误处理与失败传播 | 有缺口 | 命令层统一，引擎层无异常契约，无错误码→文案映射 |
| 持久化与数据完整性 | 有缺口 | 原子写到位，但无 fsync、无自动保存、双序列化抽象 |
| 并发与线程模型 | 有缺口 | 算法任务模型好；渲染与 3D 算法仍在 UI 线程 |
| 可观测性 | 有缺口 | 日志与 dump 扎实；无作业追溯、无 dump 上报与符号化 |
| 构建与发布 | 有缺口 | Windows 可交付；macOS 无 CI/无签名；依赖不锁定 |
| 可扩展性 | 有缺口 | 设备/路由优秀；CAM 工艺链未实现 |
| 测试与质量门禁 | 有缺口 | 量大但缺 sanitizer/-Werror/性能阈值 |

**总体：B。** 更准确地说：**"架构纪律 A-、工艺与交付闭环 C" 的混合体**。分层与门禁已经达到可以放心扩张代码库的程度；但以"工业级激光加工软件"衡量，它目前仍是"能设计、能编辑、Windows 上能演示与内测"的产品，距离"产线部署、客户现场连续生产、可审计可追责"还有明确差距。

### 9.2 最关键三个缺口

1. **加工闭环与可追溯性缺失。** CAM 仍是 M0 骨架（`CAM/CAM/Include/CAM/CamCore.h:26-29`），且没有任何作业记录（全仓无 `MachiningJob/JobRecord`）。工业客户要求"这批活用的什么参数、什么时候做的、结果合格与否、谁操作的"——现在一条都查不到。这直接决定售后成本与质量追溯能力。
2. **运行期可靠性不足。** 渲染在 GUI 线程（`UI/3D/Include/UI3D/Render3D/RenderWidget3D.h:108`）、3D 算法同步执行（`UI/3D/Src/Operation/AlgorithmRunner3D.cpp:107`）、文档无自动保存/恢复、写盘无 fsync（`FileIO/FileIO/Src/AprSerializer.cpp:699-717`）。大图纸 + 长时间连续加工场景下，卡顿与丢数据是必然风险。
3. **交付工程不闭环。** 主程序只 Windows 有 CI（`.github/workflows/ci.yml:14-65` vs `:106-165`）、无签名/公证（全仓零命中）、vcpkg 无 manifest 与 baseline（`Config.cmake:29-34`、`ci.yml:134-146`）。这意味着"稳定产出可交付安装包"目前依赖个人机器状态。

### 9.3 按投入产出排序的建议

**P0（低投入、直接消除交付与数据风险）**

1. **文档自动保存 + 崩溃恢复**：复用现有原子写，在临时目录/AppData 下周期落盘（如 60s + 空闲），启动时检测未正常关闭并提示恢复。改动集中在 Main + FileIO，不触碰引擎模型。
2. **macOS 构建/打包/签名公证进 CI**：新增 macOS 全量构建 + `cpack -G DragNDrop` + `codesign/notarytool` 作业；同时补 `vcpkg.json` + `builtin-baseline` 锁定依赖。这是"能不能交付"的问题，优先级高于任何新功能。
3. **保存路径补耐久性**：写入后 `fsync` 文件与目录，保留上一版本为 `.bak`。改动小、收益直接。

**P1（中期，解决稳定性与工业追溯）**

4. **线程模型**：把几何构建/提交与 GL 上传从 GUI 线程剥离（至少渲染提交走 worker + 上下文管理集中），3D 算法统一切到 `runAsync`，复用 2D 的 `BackgroundAlgorithmTaskHandler` 契约。
5. **加工作业记录**：新增作业表（参数快照、开始/结束时间、结果码、操作者、设备序列号、文档哈希），与 `traceId` 打通；这也是售后与质量体系的基础。
6. **错误契约统一**：定义引擎错误码枚举 + 统一"错误码→用户文案"映射，禁止空 message 的成功/失败歧义；清理 4 处空 catch 并注明理由。

**P2（长期，架构与质量加固）**

7. **序列化收敛**：确定唯一文档实现（当前生产是 FileIO/AprSerializer），把 `Engine/Persistence` 的 `ISceneSerializer/SceneManagerSerializer` 要么接线要么删除；补 Persistence 层测试。
8. **CAM 工艺链 M1**：割缝补偿、引线、穿孔、功率曲线、共边切割，配套数值测试——这是"激光加工软件"的立身之本，应尽早排期。
9. **门禁扩展**：把 FileIO/Hardware/Vision/Network/Engraving/GeoModelCore/PyBindCore 纳入依赖方向校验；3D 写入口按 2D 的方式收敛；增加 ASan/UBSan 作业、`-Werror` 分级启用、性能基准阈值。
