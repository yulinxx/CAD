## 1. 模块边界实测（链接层）

### 1.1 实测方法

只读三样东西：各模块 `CMakeLists.txt` 的 `apr_add_shared_library(... PUBLIC_LINK_LIBRARIES ...)`、`CMake/UiEngineAccess.cmake`、`CMake/CheckDependencies.cmake`。所有结论都可用 §7 的命令复现。

### 1.2 与裁剪相关的链接矩阵（不是全量）

| 模块 | PUBLIC 链接（会传播给下游） | PRIVATE 链接（不传播） | 证据 |
|---|---|---|---|
| EngineCommon | Utility、Boost::geometry | Log | `Engine/Common/CMakeLists.txt:70-75` |
| Engine2D | Utility、EngineCommon、Boost::boost、Log | Freetype、Clipper2 | `Engine/2D/CMakeLists.txt:80-88` |
| Engine3D | Utility、EngineCommon、Log | Boost::boost、GeoModelCore（条件） | `Engine/3D/CMakeLists.txt:72-77`、`:169` |
| FileIO | Log | EngineCommon、**Engine2D**、**Engine3D**、protobuf-lite、nanosvg、WebP、TIFF | `FileIO/FileIO/CMakeLists.txt:108-119` |
| CAM | Utility | Log、Clipper2 | `CAM/CAM/CMakeLists.txt:60-66` |
| Nesting | （无） | Clipper2、Threads、Log（可选） | `Nesting/Nesting/CMakeLists.txt:109-115` |
| Engraving | OpenCV、Clipper2、**Engine3D** | Log | `Engraving/Engraving/CMakeLists.txt:100-106` |
| Raster | （无） | OpenCV | `Raster/Raster/CMakeLists.txt:115-117` |
| UICommon | Utility、Log 等 | Nesting（条件） | `UI/Common/CMakeLists.txt:166-169` |
| UI2D | Utility、**UiEngineAccess**、RenderBridge、RenderAbstraction、UICommon、Log | FileIO、OpenGL | `UI/2D/CMakeLists.txt:159-171` |
| UI3D | UICommon、Utility、**UiEngineAccess**、RenderBridge、RenderAbstraction、Log | FileIO、OpenGL | `UI/3D/CMakeLists.txt:146-160` |
| Main | — | EngineCommon、Engine2D、EnginePersistence、RenderBridge、UICommon、UI2D、Log、FileIO | `Main/CMakeLists.txt:352-366` |

读法：**PUBLIC 列 = 删掉该模块时，所有下游都要重新链接的东西。** 裁剪角度只看两个：

- `UiEngineAccess`（`CMake/UiEngineAccess.cmake:32-55`）是一个 `INTERFACE` 目标，**把 EngineCommon/Engine2D/Engine3D/EnginePersistence 四个库一次性转发给所有 UI 模块**。想"只给 UI 2D 能力、不给 UI 3D 能力"，现在做不到——门面是打包的。
- `Engraving` 的 PUBLIC 里有 Engine3D，`FileIO` 的 PRIVATE 里有 Engine2D/Engine3D。这两条是 `CheckDependencies.cmake:223-224` 明文放行的既有设计，不是违规，但会让"删 Engine3D"这件事牵动 FileIO 与 Engraving。

### 1.3 三条"看着解耦、实际连在一起"的路径

1. **UI → Engine 的链接收口是唯一收口，include 没收口。** `CMake/UiEngineAccess.cmake:13-19` 自己写明：转发头只覆盖 Engine2D 的算法/填充/离散化子集，场景/实体/编辑仍由 UI 直接 `#include "Engine2D/..."`。所以"删某个 Engine 头"会直接打穿 UI 源码，而不是只改一个门面。
2. **UI2D 经 Engraving 间接拿到 Engine3D。** `UI/2D/CMakeLists.txt:218-221` 以 PRIVATE 链 `Engraving`，而 `Engraving` 以 PUBLIC 链 `Engine3D`（`Engraving/Engraving/CMakeLists.txt:100-106`）。规则 3 只查 `LINK_LIBRARIES` 直接项（`CheckDependencies.cmake:164-180`），因此这条"传递拿到 Engine3D"不会被判违规。
3. **Main 完全没有依赖规则。** `_app_targets April` 在 `CheckDependencies.cmake:83` 声明，只被塞进 `_all_checked_targets`（`:91-95`）用于统计"审计了几个目标"，**没有任何一条规则读取它**。Main 直接链 RenderX、直接链 Engine3D、直接绕门面，都不会失败。

### 1.4 `CheckDependencies.cmake` 已经管住的（不要重复做）

| 规则 | 断言 | 行号 |
|---|---|---|
| 1 | Engine* 不依赖 UI*/Render*/Main/UiEngineAccess | `:136-149` |
| 2 | Render 不依赖 UI*/Main | `:150-163` |
| 3 | UI* 不**直接链接** Engine*（只允许经 UiEngineAccess） | `:164-180` |
| 4 | UI* 不直接链 RenderX | `:181-194` |
| 4.5 | CAM 不依赖 Engine/UI/Render/门面，且 `INTERFACE_INCLUDE_DIRS` 不泄漏 | `:195-220` |
| 5 | UI* 自己的 include 目录里不得有 RenderX 路径 | `:272-290` |
| 6 | UI* 不得经传递闭包到达 RenderX | `:291-303` |
| 7 | 基础/服务模块（含 FileIO、Engraving、Nesting、Raster）不向上依赖 | `:221-253` |
| 8 | Engine/Render 不反向依赖基础服务 | `:254-271` |

判定口径本身是对的：规则 6 用 `INTERFACE_LINK_LIBRARIES` 算可达闭包（`:49-77`），专抓"PUBLIC 转发绕过规则 4"。

### 1.5 它漏掉的四处（与裁剪直接相关）

| 编号 | 缺口 | 证据 | 对裁剪的后果 |
|---|---|---|---|
| G1 | Main（April）无任何依赖规则 | `:83`、`:91-95` 之后再无引用 | Main 可以随意多链一个库，没人发现；"UI 硬链 5 个可选 DLL"这类问题只能靠人工审查（`模块边界与依赖审查.md` P1-01 已记录） |
| G2 | 规则 3 只看直接链接 | `:164-180` | 经 `Engraving`（PUBLIC Engine3D）传递拿到 Engine3D 不报错，见 §1.3 第 2 条 |
| G3 | `APR_STRICT_DEPENDENCY_AUDIT` 默认 OFF | `:46-47`、`:318-326` | 目标不存在时只打一行 STATUS，CI 不加 `-DAPR_STRICT_DEPENDENCY_AUDIT=ON` 就永远发现不了"某条规则整条没跑" |

## 2. UI 命令分发链：四条入口，三个收口

### 2.1 入口与真实调用点

| 入口 | 第一跳 | 第二跳 | 证据 |
|---|---|---|---|
| 菜单项 / 快捷键（JSON 构建） | `QAction::triggered` → `IUiCommandDispatcher::dispatch(commandId)` | `Workbench2D::dispatchCommand` → `OperationRouting::dispatch` | `UiLayoutBuilder.cpp:217-230`（connect）、`Workbench2D.cpp:168-208` |
| 右键菜单（JSON 构建） | 同上（`UiContextMenuService` 复用同一绑定） | 同上 | `UiLayoutBuilder.cpp:730-736`、`:742` 注释"条目构建完全复用主菜单路径" |

| 工具栏（**工作台自建**，`skippedByBuilder=true`） | `CommandActionHub` 的 QAction → 直接 `OperationRouting::dispatch` | 不经 `Workbench2D::dispatchCommand` | `CommandActionHubActions2D.cpp:187`、`:199`；`base.json:285-314`（2D 顶部栏）、`:320`、`:343`、`:355` |

第二跳之后统一收敛：

```
OperationRouting::dispatch              UI/2D/Src/Operation/OperationRouting.cpp:134-176
  ├─ 对话框类（Move/Rotate/Mirror）→ s_dialogDispatchFn   :149-153（绕过总线）
  └─ 其余 → OperationBus::run(opId, params, source)       :164-166

              └─ op->execute()                            OperationBus.cpp:86
```

### 2.2 结论：三处收口，各自覆盖什么

| 收口 | 覆盖 | 收口不到 |
|---|---|---|
| `MenuDispatcher::dispatch`（`MenuDispatcher.cpp:91`） | 全部 JSON 菜单/快捷键/右键（它们都绑到 `dispatcher->dispatch`） | **工作台自建工具栏**（hub 直连）、程序化 `bus->run` |
| `OperationRouting::dispatch`（`OperationRouting.cpp:134`） | 菜单 + 右键 + 工具栏（两种）+ 快捷键的**动作类**命令 | 工具激活类（`Workbench2D.cpp:202` 直接 `bus->run`）、对话框类（`:149-153`） |
| `OperationBusBase::runImpl`（`OperationBusBase.h:72`） | 所有最终执行 | —（唯一真正的技术收口） |

**关键事实：`feature` 字段只有 UI 构建层看得见。** 到了 `OperationRouting` 只剩 `MenuActionId`（`:142` 由 `CommandCatalog::operationForMenu` 换算），到了总线只剩 `OperationId`。因此"注册码门禁"如果不在 UI 构建层做，就必须在框架层重建一张 `OperationId → feature` 的表——那是第三个真相源（现有真相源是 JSON、`CommandCatalog`、`UiFeatureGate` 的许可证串）。

### 2.3 门禁现状覆盖面（实测）

`UiFeatureGate::instance()` 有 3 个生产消费点，不是"到处都是"：

| 消费点 | 覆盖的界面 | 行号 |
|---|---|---|
| `UiLayoutBuilder` | 菜单项、JSON 工具栏（整条 + 单项）、状态栏槽位、右键菜单（整条） | `:395-400`、`:461-469`、`:486-506`、`:680-686`、`:730-736` |

| `UiConfigSelfCheck` | 启动自检三侧交叉 | `:301-336` |

**唯一没被覆盖的界面是"工作台自建工具栏"**：`skippedByBuilder=true` 的 4 条（`base.json:289`、`:320`、`:343`、`:355`）。2D 在 `Workbench2D.cpp:1105-1141` 把 `ToolBarActionDef.feature` 丢掉，3D 在 `Workbench3D.cpp:141-142` 同样丢掉；两处都不检查 `tb.feature`。同时它们也**不检查 `skippedByBuilder` 之外的任何门控**——这是 §6 要补的洞。

## 3. 现有可裁剪能力盘点

### 3.1 `BUILD_*` 关掉之后：是"真少功能"还是"构建失败"

实测 5 个与本次目标相关的开关，全部是**真少功能**，代价是"源码排除 + `#ifdef` 注册 + 宏 PUBLIC 传播"三件套：

| 开关 | 关掉后实际发生 | 证据 |
|---|---|---|
| `BUILD_NESTING` | UICommon 排除 `NestingEngine/NestingPartPreparer`（`:108-115`）；UI2D 排除 `NestingProcessor/NestingDialog/NestingPreviewDialog` 三个 cpp（`:100-102`）；handler 不注册（`AlgorithmTaskRegistration2D.cpp:1380-1387`）；命令目录不登记（`CommandCatalog.cpp:1065-1067`）；总线不注册（`AlgorithmOperationRegistry.cpp:64-66`）；不链库（`Main/CMakeLists.txt:381-383`）。**构建通过，功能消失。** | 同左 |
| `BUILD_ENGRAVING` | UICommon 用 `ENABLE_ENGRAVING` 条件定义 `ReliefEngraving3DDialogParams`（`DialogParameters.h:508`），宏 PUBLIC 传播给 UI2D/UI3D（`UI/Common/CMakeLists.txt:174-176`）；UI2D/UI3D 各自条件链接 `Engraving`（`UI/2D/CMakeLists.txt:218-221`、`UI/3D/CMakeLists.txt` engraving 段）。**构建通过。** | 同左 |
| `BUILD_RASTER` | Main 链 Raster 并定义 `BUILD_RASTER`（`Main/CMakeLists.txt:386-389`）；2D 浮雕雕刻入口仍存在，只是走 `#else` 分支提示"Raster module is not available in this build"（`ReliefEngravingOperation2D.cpp:6-9`、`:163-167`）。**这是"可见但点击提示"的既有先例。** | 同左 |
| `BUILD_HARDWARE` | UI2D 只 PUBLIC 传播宏、不链库（`UI/2D/CMakeLists.txt:205-209`）；Main 条件链（`Main/CMakeLists.txt:399-405`）。 | 同左 |
| `BUILD_CAM` | Main 条件链 CAM + 定义 `BUILD_CAM`（`Main/CMakeLists.txt:392-395`）；CAM 自身零 Engine 依赖（`CAM/CAM/CMakeLists.txt:60-66`），是最容易拿掉的一块。 | 同左 |

反例（需要小心）：`ReliefEngravingOperation2D.cpp` **没有** `#ifdef ENABLE_ENGRAVING`，而 `UiConfigSelfCheck` 把授权 token `relief3d` 映射到 `BuildConfig::kEngraving`（`:229`）。结果是：`BUILD_ENGRAVING=OFF` 时自检会说"该构建没编进来"，但 2D 菜单项其实是由 `BUILD_RASTER` 决定的（`:6-9`）。**一个用户可见名字对应两个构建开关**，自检的对齐关系在这一点上是错的。

### 3.2 编译期宏的 PUBLIC 传播门禁

根 `CMakeLists.txt:447-509` 会对 5 对 `BUILD_* → ENABLE_*` 做"源头模块是否 PUBLIC 传播"的硬校验，失败即 `FATAL_ERROR`（`:502-505`）。注意它的动机是 **ABI 一致**（`:447-449`：公共头类型布局不同 → `sizeof` 不一致 → 堆越界），不是"功能可用性"。所以：

- 新增的裁剪宏若会改变任何**公共头里的结构体布局**（例如 `DialogParameters.h` 里那些 `DIALOG_PARAMETER_STRUCT`），必须加进这张表；
- 若只做"少注册一个命令"（不动结构体），**不需要**动这张表，也就不会触发 ABI 风险。

### 3.3 `EmergencyStopFeature`：单点开关的样板

`Main/Src/UI/Safety/EmergencyStopFeature.h:19-22` 只有一个 `inline constexpr bool kEnabled = false`，头注释把 5 处联动点写死在文件里（`:12-17`）。全仓 12 个引用点、7 个生产点（`EmergencyStopController.cpp:76/158/180`、`MenuDispatcher.cpp:162`、`WorkbenchWindow.cpp:1059`、`EmergencyStopOverlay.cpp:204`、`LaserOperationRegistry.cpp:106`），全部是 `if constexpr` / `if (kEnabled && ...)`。

**它的可复制性**：一个 bool + N 个"同一条判断"，删功能时只改 bool 和这 N 行。**它的不可复制性**：它门的是"一套还没交付的硬件链路"，不是"一个可选卖点"；而且它分散在 5 个文件里，靠头注释维持一致——这恰恰是用户不喜欢的"复杂化"。裁剪路径应更像 `BUILD_NESTING`（集中排除），而不是像它。

### 3.4 "少注册一个算法"要改几处（实测 7 处）

以新增/移除一个 `algo.*` 算法为例，必须同步的位置：

| # | 位置 | 作用 | 漏了会怎样 |
|---|---|---|---|
| 1 | `UI/2D/Src/Algorithm/AlgorithmTaskRegistration2D.cpp:1372-1387` | 注册 handler | 点了没反应（`:1371` 注释明说） |
| 2 | `UI/2D/Src/Operation/CommandCatalog.cpp:1064-1073` | 命令 id ↔ OperationId | 菜单项被 `isCommandRegistered` 判死 |
| 3 | `UI/2D/Src/Operation/AlgorithmOperationMapping.cpp:17-19` | 任务 id ↔ 算法 | 任务链找不到 handler |
| 4 | `Main/Src/Composition/AlgorithmOperationRegistry.cpp:62-77` | 总线注册 + 参数声明 | 命令可见但执行空转 |
| 5 | `Main/Src/UI/ClientConfig/configs/base.json` | 菜单/工具栏条目 | UI 里没有入口 |
| 6 | `UiConfigSelfCheck.cpp:225-231`（仅当有对应构建开关时） | 自检映射 | 自检误报/漏报 |
| 7 | `Tools/Abi/baseline/Engine2D.txt`（仅物理删除） | 导出基线 | ABI 门禁失败 |

**第 1~4 处是"注册"，第 5 处是"入口"，第 6~7 处是"护栏"。** 只做"按注册码禁用"的话只需 5 + 6（JSON 加 `feature`），**一行 C++ 都不用改**——前提是入口真的被门控（§6 的洞）。

**结论：Nesting 是"编译期裁剪"的满分样本（库零 Engine 依赖 + 集中排除 + 条件注册），但它的 34 处 `#ifdef` 是为了"少编一段代码"，不是为了"按注册码开关"。** 按注册码禁用 Nesting 只需要 1 处：`base.json`/客户 JSON 的菜单项加 `"feature": "nesting"`（`client_b.json:21`、`:47` 已在用）。

### 4.3 裁剪成本对比（同一功能，两种裁法）

| 裁法 | 改动量 | 何时用 |
|---|---|---|
| 编译期（`BUILD_NESTING=OFF`） | 上述 34 处维护 + 2 段源文件排除 + 5 处 CMake；删库还要同步 `Config.cmake` | 交付体积敏感、确定某客户永不需要 |
| 授权期（JSON `feature`） | 0 行 C++，1 行 JSON | 同一二进制卖多档 |

## 5. 门禁落点结论

在 06 篇 §11 的 A/B/C/D 四选一之上，框架层实测补充三点：

1. **A（JSON `feature`）是唯一"语义完整"的落点**：只有这一层同时知道 `commandId`、`feature`、`tb/ad` 级别、以及"该不该创建控件"。其余层都丢了其中至少一项（§2.2）。
2. **C（总线层）不是"全覆盖"**：`OperationBusBase::runImpl` 只看得到 `OperationId`，要判定就得在 UICommon 里再建一张 `OperationId → feature` 表。这张表与 `CommandCatalog`、与 JSON 三处必须人工同步——用户明确不喜欢复杂化，这张表就是复杂化的典型。
3. **B（任务注册层）只覆盖算法**，覆盖不到"删掉整个入口"（菜单项还在，点了 WARN）。它适合做"编译期裁剪"的注册侧，不适合做授权门禁。

**推荐：A + 自检，且把 A 的覆盖面补全（§6）。** 一句话：**门禁只做在"创建控件"这一层，算法层永远不知道自己被开关。**

代价（实测）：

- JSON：每个要卖的算法入口加一个 `"feature"` 字段，0 行 C++；
- 自检：**不用扩表**——`UiConfigSelfCheck.cpp:315-319` 对没有构建开关的 feature 直接 `continue`，纯授权项天然免检（06 篇 §10 建议 4 原先写"扩表"，按此处口径修正）；
- 补洞：2 个文件约 6 行（§6）。

> 注意 `licenseSideMeaningful` 分支（`:310`、`:320-326`）：无许可证 / 试用期时 `UiFeatureGate` 是 unrestricted（`LicensingBootstrap.cpp:118-123`、`:183-187`），自检会跳过授权侧比对。**这意味着开发机上"不装许可证"永远看不到受限行为**，验证必须用受限模式（§6.5）。

### 6.4 `OperationBus::run` 要不要同时加一道：**不加**

判断与理由：

1. **重复，不是双保险。** 算法命令当前唯一入口是菜单/工具栏/右键，三者都已被 UI 层门控；总线层再加一道，只会在"同一件事"上出现两个判定点，任何一个改口径（大小写、逗号分隔、通配符）都会让两边不一致。
2. **要在总线层判定，就必须造第三个真相源。** `runImpl` 手上只有 `OperationId`（`OperationBusBase.h:74`）。要么给 `CommandEntry2D` 加 `feature` 字段（改 `CommandCatalog` 公共结构），要么在 UICommon 里建 `OperationId → feature` 的 switch——两者都比"改 2 个文件 12 行"贵，且新增同步义务。
3. **"未注册 opId 只打 WARN"不需要升级。** 现在 `runImpl` 已经返回失败结果并调用 `onOperationCompleted(id, false, message)`（`:76-81`），只是没人展示 message：`Workbench2D.cpp:1354-1366` 的连接只处理 `success && (Undo||Redo)`，失败文案被丢掉。**这是"失败无反馈"的问题，不是"门禁"的问题**；升级成"显式拒绝并提示"要顺带改状态栏/消息表面的消费逻辑，属于另一条线。真要修，改的是那个 connect，而不是 `runImpl`。

一句话：**只在 UI 构建层做（§6.1），总线层保持现状。**
