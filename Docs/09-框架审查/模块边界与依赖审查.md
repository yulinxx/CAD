### 1.3 层归属判断

- **真正的叶子**：`Utility`、`Log`、`CrashHandler`、`Raster`、`Vision`、`Nesting`、`CAM`、`GeoModelCore`。它们不依赖任何兄弟 DLL（`Raster/CMakeLists.txt:108-117` 只有 PUBLIC 头目录与 PRIVATE 的 OpenCV，没有 PUBLIC_LINK_LIBRARIES）。
- **引擎内核**：`EngineCommon → Engine2D/Engine3D → EnginePersistence` 方向一致，Persistence 只向上，没有回链。
- **方向可疑但已“收口”的边**：`FileIO → Engine2D/Engine3D`。FileIO 是适配器层，解析产物必须是 Engine 实体，这个方向合理；文档也按此设计（[位图盘点](file:///c:/Users/xx/Documents/Cpp/CAD/Docs/08-Raster/位图激光雕刻能力盘点与实施规划.md) `:219` 明确“Raster 不允许 Qt、不允许 Engine2D”）。
- **反向头依赖**：`Engine3D` 不链接 `FileIO`，却把 `FileIO/Include` 放进 `PUBLIC_INCLUDE_DIRS`（`Engine/3D/CMakeLists.txt:72-74`），导致 Engine3D 的公共表面依赖上层模块的头类型。见 P1-08。

- 两者证明：**同一套代码库可以做到第三方零外溢**，Engraving/Persistence/Engine2D/Engine3D 的泄漏不是“技术必然”，而是缺少同一条门禁。

### 3.3 后果量化（为什么不是“只是 include 多了几行”）

1. **编译时间**：Engraving 的 OpenCV 头经 PUBLIC 进入 UI3D 与 Main 的所有 TU（`UI/3D/CMakeLists.txt:175`）。OpenCV 头会拉入 `windows.h` 与大量模板，单 TU 增量约 0.3–1 s 量级；UI3D 有上百 TU。
2. **部署顺序**：`SanYiCAD.exe` 启动前必须集齐 `opencv_*.dll`（含 OpenCV 自己的第三方）、16 个 `TK*.dll`、`libprotobuf*.dll`。缺任一个，Windows 加载器在 `SanYiCAD` 导入解析阶段失败——**整个应用起不来**，而不是“某个功能不可用”。
3. **DLL 版本绑定**：`HeightMap`/`LaserProcessingAPI` 的 `cv::Mat` 让 Engraving.dll 与消费方必须在同一 OpenCV 二进制、同一 CRT、同一迭代器调试级别；否则是堆损坏而非报错。
4. **崩溃半径**：`Raster.dll` 是 UI2D 的加载期依赖（`UI/2D/CMakeLists.txt:228`），而 `Raster.dll` 运行期又依赖 `opencv_*.dll`；Raster 的安装规则默认**不**分发 OpenCV 运行时（`Raster/CMakeLists.txt:208-212`，需显式 `-DRASTER_INSTALL_OPENCV_RUNTIME=ON`）。位图模块的任何部署缺失都会放大为“主程序无法启动”。

### 4.2 契约层结论

1. **`structSize` 只保护“入参”，不保护“出参可读性”**。全库统一缺一条：失败时必须把 out 清零。这是 P0-01 的根，也是 Vision/Nesting 同类接口的潜在雷。
2. **ABI 版本号存在，但生产路径不校验**。Raster/Vision/Nesting 的自检只出现在测试与示例；唯一在生产路径查询 ABI 的是 CAM（`CamInputBridge.cpp:57-67`），而且只打印日志、不与头文件常量比对，也不失败退出。这意味着“版本号”目前是文档承诺，不是运行时保障。
3. **门禁只验函数存在性，不验语义**。`CheckCApi.cmake:66-71` 只检查头文件里出现 `GetVersionString`/`GetVersion|GetAbiVersion` 字样；不检查 `structSize` 约定、不检查出参清零、不检查消费端是否调用。门禁消息本身还是中文（`:62/67/70/77`），与“构建日志一律英文”的项目规范不一致（P2-09）。
4. **`extern "C"` 边界覆盖完整**，`CheckCApi.cmake:13-57` 维护了 Raster/Vision/Nesting/Engraving/GeoModelCore/License/CrashHandler/Log/RenderX 的清单；新增模块有登记点。
5. **PIMPL 覆盖度两极分化**：`GeoModelCore` 全 PIMPL；`Raster/Vision/Nesting/CAM` 用不透明句柄；`Engraving` 导出类零 PIMPL 且成员是第三方类型；UI 模块是 Qt 类（合理的例外）。建议把 Engraving 作为第三批重构对象，而不是全库一刀切。
6. **`*_API` 宏的可见性守卫是真门禁**：`CMake/AbiVisibilityGuard.cmake:37-114` 检查 GCC/Clang 分支不再按 `*_EXPORTS` 分叉，并在 `:23-25` 记录了“Engine3D 建出的 SyMeshEntity 在 UI3D dynamic_cast 静默失败”的真实事故。这条应保留并扩大登记范围。

### 6.2 部署后果（加载期依赖，不是功能降级）

`UI/2D/CMakeLists.txt` 在默认（`BUILD_NESTING/VISION/HARDWARE=ON`）配置下让 `UI2D.dll` 链接 `Nesting`（`:181`）、`Vision`（`:202`）、`Network`（`:212`）、`Engraving`（`:223`）、`Raster`（`:228`）。Windows 加载器解析 `UI2D.dll` 导入表时要求这些 DLL **全部存在且 ABI 匹配**，否则 `SanYiCAD.exe` 在启动阶段直接失败。也就是说：

- 只想用矢量切割的用户，若 `opencv_*.dll` 缺失，**连主界面都进不去**；
- `Raster` 的 ABI 版本不匹配时，Windows 可能仍加载成功（DLL 名相同），随后在第一次位图操作崩溃；
- 关闭某个 `BUILD_*` 后必须同步重新部署，不能“热替换单个 DLL”。

### 9.1 建议的分层与允许/禁止矩阵

> 目标名按 CMake 实际名称；`→` 表示允许依赖，`✗` 表示禁止直接依赖。

| `FileIO → Engine2D/Engine3D` 向上依赖 | 解析产物必须是 Engine 实体，反向会形成真正的环 | 保持单向；把反向的 `FioTypes` POD 下沉，删除 Engine3D 的 FileIO 头路径 |
| `FileIO` `thread_local` 借用指针 | 避免解析大图时整份 IR 深拷贝 | 保留“同线程下一次解析前有效”的书面契约 + Debug 代次断言；禁止跨线程导入 |

**明确不建议改**

- 不建议把 UI 模块全部改成 C ABI：Qt 控件本身就是 C++ 对象，收益低、改造面大。
- 不建议为了“零第三方泄漏”把 `Raster`/`Vision` 的 OpenCV 换成自研：它们的公共头已经零泄漏，问题不在实现层。
