## 0. 结论（先回答核心问题）

**2D 链路：已达标，可以了。**
三层边界清晰，增量刷新/视口扩展替代了缩放全量重建，覆盖层与标尺按层独立提交且有 70 个回归用例，CPU 侧 5 千图元帧路径约 0.03 ms。

**3D 链路：不满足工业要求，不能算完。**
不是「架构错了」，而是有 5 个具体缺口集中在「看得全、看得清、出错能恢复」上；其中 3 个会直接影响加工前判读。

按风险排序的核心问题：

| 级别 | 问题 | 直接后果 | 关键证据 |
|---|---|---|---|
| P0 | 3D 刀路/参考线只有受深度遮挡的一种显示，没有穿透/X-ray 检查模式 | **看漏路径**：模型内部、背面、毛坯下方的刀路不可见，且无任何提示 | [RenderWidget3D.cpp:60](../../UI/3D/Src/Render/RenderWidget3D.cpp#L60)、[:843](../../UI/3D/Src/Render/RenderWidget3D.cpp#L843) |
| P0 | 全链路无 MSAA，实心线宽恒为 1 物理像素（Retina 上等效 0.5 pt） | **看错图形**：细线/密集曲线/相邻刀路在缩放时断裂、摩尔纹、间距视觉失真 | [main.cpp:41](../../Main/Src/main.cpp#L41)、[metalDevice.mm:452](../../Renderx/src/rhi/metal/metalDevice.mm#L452)、[rhiSurface.h](../../Renderx/src/rhi/rhiSurface.h)（无 sampleCount） |
| P0 | macOS 3D 右键菜单父窗口回归为视口控件（已修复过又被改回） | 配置化 3D 视口右键菜单可能静默不弹出，选中/编辑入口消失 | [Workbench3D.cpp:704](../../Main/Src/UI/Workbench/Workbench3D.cpp#L704)、修复提交 `4264f399` 被 `d5cc0d478` 覆盖 |

一句话：**2D 可以交付；3D 需要补「路径可见性 + 抗锯齿 + 菜单回归 + 设备恢复」四件事，才能作为加工前判读依据。**

## 1. 后端抽象与跨平台

### 1.1 三层职责划分 —— 已达标

- `RenderAbstraction` 是 **C ABI 隔离层**，不是可插拔后端抽象：头文件明确写了「对外 C ABI，内部 POD + 句柄；不追求可插拔后端抽象，避免抽象泄漏」。
  [IRenderScene.h:8-20](../../RenderAbstraction/Include/RenderAbstraction/IRenderScene.h#L8-L20)
- `RenderBridge` 负责会话宿主、持久几何仓、覆盖层、文本批次与适配器；Metal Runtime 进程级共享、瞬态预算首次生效等约束在头文件里写清楚。
  [RenderSessionHost.h:100-140](../../RenderBridge/Include/RenderBridge/RenderSessionHost.h#L100-L140)
- `Renderx` 负责 RHI 后端（Metal / OpenGL / Null）与 RT 运行时（session、draw list、增量装配、管线缓存）。
- 后端创建**不做静默回退**：请求 Metal 失败就返回空并说明原因，只有显式 `Auto` 才允许自动选择；Vulkan 明确返回不可用。
  [rhiFactory.cpp:1-11](../../Renderx/src/rhi/rhiFactory.cpp#L1-L11)、[:65-89](../../Renderx/src/rhi/rhiFactory.cpp#L65-L89)

结论：抽象泄漏控制得比多数自研渲染层好；UI 层没有出现 Metal/GL 类型或头文件泄漏。

### 1.2 后端差异是否散落 —— 基本达标，但边界靠约定

- UI 侧只有一处平台分支：2D 在 `APR_ENABLE_METAL_VIEWPORT` 下把后端设为 Metal 并传 NSView，否则走 GL 默认路径；无 `#ifdef METAL` 散落在绘制逻辑里。
  [RenderWidget.cpp:401-418](../../UI/2D/Src/UI/ViewWidget/RenderWidget.cpp#L401-L418)
- 默认后端由构建选项派生：Apple=METAL，其它=OPENGL；非 Apple 强制关闭 Metal 视口，避免无法解析的分支。
  [Config.cmake:187-193](../../Config.cmake#L187-L193)、[CMakeLists.txt:368-396](../../CMakeLists.txt#L368-L396)

有缺口：**能力差异只能靠调用方自觉**。例如线宽上限由 RHI 能力决定并被钳制，UI 完全不设线宽，因此今天看起来一致；但抽象层没有「线宽语义 = 设备像素」的契约测试，后续一旦有人设 `lineWidth=2`，Metal 仍是 1px、Windows GL 可能变粗，视觉直接分叉。
[rxRuntime.cpp:1414-1416](../../Renderx/src/rt/rxRuntime.cpp#L1414-L1416)、[metalDevice.mm:452](../../Renderx/src/rhi/metal/metalDevice.mm#L452)

### 1.3 非 Metal 平台是否真能跑 —— 有缺口（能编译，图形正确性未验证）

- Windows/Linux 使用 GL 后端，CI 会构建三平台客户端；GL 后端函数加载与 FBO 缓存有实现。
- 但**像素级验证只存在于 Metal**：`RenderxMetalTests.mm` 有 14 个真实 GPU 回读用例（清屏色、三角形覆盖、纹理采样、深度遮挡、双面光照、线框填充等）；GL 侧只有 `RhiCoreTests`/`RxRuntimeTests`（Null 后端契约）和 `GlFboCacheTests`（用桩函数，不建真实上下文）。
  [RenderxMetalTests.mm:649-1260](../../Renderx/Test/RenderxMetalTests.mm#L649-L1260)、[GlFboCacheTests.cpp:1-18](../../Renderx/Test/GlFboCacheTests.cpp#L1-L18)
- 结论：**「非 Metal 能启动、能跑契约测试」成立；「非 Metal 画得对」没有证据。** Windows 是实际出货平台，这条不能算达标。

## 2. 2D 链路

### 2.1 场景环境 / 图元批次 / 离屏缓存 —— 已达标

- 帧入口：先同步视口与相机，再判定离屏场景缓存命中，未命中才整场景重画。
  [RenderWidget.cpp:1050-1203](../../UI/2D/Src/UI/ViewWidget/RenderWidget.cpp#L1050-L1203)
- 缓存目标尺寸/DPR 自愈；创建失败保持脏标记下一帧重试；后端缺少 `ScreenTextured` 管线时永久降级为直接重画，不会黑屏。
  [RenderWidget.cpp:1113-1123](../../UI/2D/Src/UI/ViewWidget/RenderWidget.cpp#L1113-L1123)、[:1328-1361](../../UI/2D/Src/UI/ViewWidget/RenderWidget.cpp#L1328-L1361)
- 相机变化会标记场景环境脏（进而使缓存失效），不会出现「平移后还显示旧画面」的陈旧像素。
  [RenderViewport2D.cpp:942-966](../../Main/Src/UI/Render/RenderViewport2D.cpp#L942-L966)

### 2.2 增量刷新与视口扩展 —— 已达标（这是 2D 做得最好的一块）

- 首载/换场景做一次全量；相机仍在已装配范围内只推进曲线 LOD；移出范围走**增量视口扩展**（补入 + 回收），跨帧由队列消费，而不是整场景重建。
  [SceneRefreshCoordinator.cpp:595-663](../../Main/Src/UI/Render/SceneRefreshCoordinator.cpp#L595-L663)
- 只有矩阵退化拿不到可视盒时才回退全量重建，属于兜底而非常态。
  [SceneRefreshCoordinator.cpp:641-647](../../Main/Src/UI/Render/SceneRefreshCoordinator.cpp#L641-L647)
- 回收逻辑避免长时间平移导致 GPU 几何无限增长。
  [SceneRefreshCoordinator.cpp:654-665](../../Main/Src/UI/Render/SceneRefreshCoordinator.cpp#L654-L665)
- 回归用例充分：`Main/Src/UI/Test/ViewportRefreshRegressionTests.cpp` 70 个用例覆盖增量更新不丢数据、扩展队列先于 LOD 队列消费、批量失败回退游标与指数退避等；曲线 LOD 另有 `LodValidationTests`。

### 2.3 覆盖层（选择框 / 夹点 / 标尺）—— 已达标

- 覆盖层不进离屏缓存，每帧单独提交：先场景，再世界文本，再覆盖层，最后标尺 HUD 与 FPS。
  [RenderWidget.cpp:1171-1203](../../UI/2D/Src/UI/ViewWidget/RenderWidget.cpp#L1171-L1203)、[:1259](../../UI/2D/Src/UI/ViewWidget/RenderWidget.cpp#L1259)
- 选择框/夹点用屏幕定尺寸常量与 `P3O2C4` 管线，缩放时手柄不跟着变大；命中区按 2 倍半径判定，与视觉一致。
- 选择轮廓有预算兜底：超出轮廓预算时只画包围盒 + 起点标记，**并保持本体可见**，不会出现「选中了但什么都没画」。
  [SelectTool.cpp:240-270](../../UI/2D/Src/UI/DrawTools/SelectTool.cpp#L240-L270)、[:430-450](../../UI/2D/Src/UI/DrawTools/SelectTool.cpp#L430-L450)
- 文字块不会被「隐藏本体」策略吃掉，始终留在世界层。

### 2.4 无深度测试、依赖提交顺序的隐含约束 —— 已文档化，达标

2D 不启用深度（`cfg.enableDepth=false`，[RenderWidget.cpp:405](../../UI/2D/Src/UI/ViewWidget/RenderWidget.cpp#L405)），层次完全由提交顺序决定，代码与设计文档双处写明了这一点：

- 头文件注释：「谁在上由提交顺序决定 —— 文字在图元之后提交，因此永远压在几何之上」。
  [RenderWidget.cpp:49-56](../../UI/2D/Src/UI/ViewWidget/RenderWidget.cpp#L49-L56)
- 标尺必须单独一批提交，「提交顺序压过 sortKey」。
  [RenderWidget.cpp:1263](../../UI/2D/Src/UI/ViewWidget/RenderWidget.cpp#L1263)
- 位图与图元合批时靠提交先后保证底图在下，「分两次提交会让 sortKey 失去意义（提交顺序压过排序键）」。
  [RenderWidget.cpp:1393-1396](../../UI/2D/Src/UI/ViewWidget/RenderWidget.cpp#L1393-L1396)
- 设计文档同步：`Docs/03-渲染主链/新渲染架构.md` 帧提交顺序与「深度测试无处可写，模型按提交顺序互穿」章节。

结论：这是本体系里最容易腐化的一条隐式约束，目前文档化到位，算达标；代价是后续新增层时必须人工维护提交顺序，没有编译期保护。

## 3. 3D 链路

### 3.1 批次提交与几何仓 —— 已达标

- 每帧顺序：模型批次 → 选中高亮（线框）→ 刀路覆盖层 → 预览/瞬态。
  [RenderWidget3D.cpp:1440-1545](../../UI/3D/Src/Render/RenderWidget3D.cpp#L1440-L1545)
- 几何仓一次性配置容量、粒度、绘制列表初值，开启合批与剔除；每实体带 `BoundsAabb3` 用于视锥剔除。
  [Mesh3DBuilder.cpp:81-103](../../UI/3D/Src/Render/Mesh3DBuilder.cpp#L81-L103)
- 半透明网格按视距排序，避免透明互相穿插。
- 无 GL 单测覆盖较充分：`UI3DRenderPipelineTests.cpp` 共 24 个用例，其中 17 个 `Mesh3DBuilder`（增量重写、容量扩展先分配后释放、分配失败保留旧几何、高亮线框只释放一次等）+ 7 个场景几何/覆盖层用例；该文件注释明确「renderScene 的提交顺序不在单测断言范围内」。

### 3.2 LOD 判定与脏 ID 装配 —— 2D 成立，3D 不成立

- 仓库里真正跑起来的是 **2D 曲线 LOD**：`RenderSubmitScheduler` 挂在 2D 的 `RenderWidget` 上，按缩放滞后判据重新收集曲线，批次预算 6 ms，失败回退游标 + 指数退避。
  [RenderSubmitScheduler.h:43-79](../../Main/Src/UI/Render/RenderSubmitScheduler.h#L43-L79)、[RenderSubmitScheduler.cpp:131-233](../../Main/Src/UI/Render/RenderSubmitScheduler.cpp#L131-L233)
- **3D 没有 LOD**：`DisplayCache3D` 只被 Engine 自身和文档引用，没有任何生产代码接线；文档中「3D 已有 DisplayCache3D」与实现不符。
- 结论：3D 侧所有 mesh 始终全精度提交，只靠视锥剔除与绘制列表合并；大装配/大三角面模型没有降级路径。**有缺口。**

### 3.3 拾取 —— 已达标

- CPU 射线拾取：R 树空间索引取候选，`Geo3DParallel::pickFromCandidates` 做三角形级求交并按 t 排序取最近；不依赖 GPU 深度回读。
  [RenderWidget3D.Picking.cpp:40](../../UI/3D/Src/Render/RenderWidget3D.Picking.cpp#L40)、[SpatialIndex3D.cpp:279-288](../../Engine/3D/Src/SpatialIndex/SpatialIndex3D.cpp#L279-L288)
- 夹点命中用同一射线与逻辑视口尺寸，与屏幕投影一致；`worldToScreen` 批量收集也使用同一相机。
- 风险提示：精度按整数像素构造射线，Retina 上存在亚像素舍入，但不会造成系统性偏移。

### 3.4 手势与右键菜单 —— 手势达标，菜单不达标

- pinch-to-zoom 走 `QEvent::NativeGesture` 的 `ZoomNativeGesture`，不依赖 wheel。
  [RenderWidget3D.Gestures.cpp:515-535](../../UI/3D/Src/Render/RenderWidget3D.Gestures.cpp#L515-L535)
- **右键菜单回归**：`Workbench3D` 把 `m_renderWidget3D` 作为 `QMenu` 父窗口传给配置化菜单；而提交 `4264f399` 曾把该处改为顶层 `m_workbenchWindow` 并注明「修复 macOS 下静默不弹」，随后 `d5cc0d478` 重构时改回具体视口，当前 HEAD 仍是回归后的写法。
  [Workbench3D.cpp:689-706](../../Main/Src/UI/Workbench/Workbench3D.cpp#L689-L706)、`git show 4264f399 -- Main/Src/UI/Workbench/Workbench3D.cpp`
- 这条不是「画错」，但会让用户在 3D 视口找不到选中/编辑入口，属于加工前操作链断裂，必须优先复验。

### 3.5 视口裁剪 —— 已达标

- 主场景绘制列表开启剔除，按实体 AABB 与视锥平面求交；瞬态覆盖层刻意关闭剔除（刀路可能跨视野），避免把被裁剪的线段拼接错。
  [RenderWidget3D.cpp:1414-1434](../../UI/3D/Src/Render/RenderWidget3D.cpp#L1414-L1434)

### 3.6 刀路预览 —— 功能有，但缺少「检查模式」

- 刀路走 3D 线批次，受深度测试、不写深度，物理上正确地被模型遮挡；没有「置顶/穿透/半透明」查看模式。
  [RenderWidget3D.cpp:60](../../UI/3D/Src/Render/RenderWidget3D.cpp#L60)、[:843](../../UI/3D/Src/Render/RenderWidget3D.cpp#L843)
- 对浮雕表面刀路基本够用；对减材/内部路径、被毛坯包裹的路径，用户无法在加工前确认「路径到底有没有走到」，这是**看漏路径**的直接来源。

## 5. 性能

### 5.1 实测数据（Release / Null 后端 / 1280×720 / 20 预热 + 120 帧）

`AprRenderBenchmark` 测的是**帧路径 CPU 侧**（几何收集、剔除、排序、合批、命令构建），不含 GPU 光栅与提交，因此是性能下限而非整帧。

| 场景 | 5,000 图元 p50 | 50,000 图元 p50 |
|---|---|---|
| 全场景视野（zoom fit） | 0.0343 ms | 0.3799 ms |
| 平移视野 | 0.0169 ms | 0.2166 ms |
| 每帧改 1 千个包围盒 | 0.0901 ms | 0.4532 ms |
| 每帧改 1 万个包围盒 | 0.9430 ms | 3.8020 ms |
| 每帧重排 1 万条排序键 | 0.2690 ms | 3.8346 ms |
| 瞬态环全量重传 1 万条 | 0.1874 ms | 0.3596 ms |

合批结果：5k 全场景 `visible=5000 / draws=2 / 合批率 83.3%`；50k 全场景 `visible=50000 / draws=10 / 合批率 100%`（按连续块分段合批）。合批契约有真实断言：连续块 + 同材质同管线才合并，材质编号不同即不合并，合批不丢图元。
[DrawListBatchMeasurementTests.cpp:190-204](../../RenderBridge/Test/DrawListBatchMeasurementTests.cpp#L190-L204)

结论：**数千图元目标在 CPU 侧大幅达标**（差两个数量级）。50k 的脏包围盒/重排约 3.8 ms，仍可接受，但余量开始变小。

### 5.2 缩放/平移是否触发全量重建 —— 已达标

见 2.2：常态是增量扩展，全量只在首载/换场景/矩阵退化时发生。`ViewportRefreshRegressionTests` 里甚至有「平移视野不得触发全量重建」的回归断言。

### 5.3 顶点缓冲重分配 —— 已达标

- 几何仓按 256 字节粒度分配，3D 容量扩展先分配新块再释放旧块；`Mesh3DBuilderTests` 有对应断言。
- 批量导入前预留容量（`prepareForBulkAdd`），避免逐图元 realloc。
- 3D 瞬态环固定 64 MB，溢出走临时缓冲，不静默回绕覆盖（`IRenderScene` 头注释）。

### 5.4 主线程阻塞点 —— 有缺口

1. Metal 获取 drawable 时 `dispatch_semaphore_wait(..., DISPATCH_TIME_FOREVER)`，GPU 真卡住时 UI 线程会无限期阻塞，没有超时降级。
   [metalDevice.mm:315](../../Renderx/src/rhi/metal/metalDevice.mm#L315)
2. 3D 每帧全量提交所有 mesh（无 LOD），大网格的 GPU 时间不可控。
3. 50k 图元、1 万条排序键变更时全量重排 3.8 ms，虽然仍在帧预算内，但没有分批/增量排序。
4. **GPU 时间不可观测**：Metal/GL/Null 的 `timestampQueries` 均为 false，FrameStats 只有 CPU 计数与 draw/tri 数，无法区分 CPU-bound 与 GPU-bound。

## 6. 稳定性与资源

| 项目 | 结论 | 证据 |
|---|---|---|
| 句柄式资源生命周期 | 已达标 | 纹理由 session 拥有、显式 `destroyTexture`；场景缓存目标释放有独立函数（[RenderWidget.cpp:1363-1375](../../UI/2D/Src/UI/ViewWidget/RenderWidget.cpp#L1363-L1375)）；GL 设备析构删除 surface 并释放资源 |
| 生命周期顺序 | 已达标 | 2D 关闭顺序 `scene → device → surface` 有注释约束；Metal Runtime 进程级共享，不随单个视口销毁 |
| 泄漏检测 | 有缺口（低） | Metal 设备析构只对未销毁 surface 报错，不负责释放；GL 会主动清理。没有资源计数/预算告警，长期运行只能靠 Instruments |
| 管线状态 | 已达标 | `CommandEncoder::execute` 开头重置当前管线状态；管线缓存键包含颜色格式/深度格式/拓扑/混合/深度写等（`Mesh3DPipelineVariantIsKeyedByDepthFormat`） |
| 着色器编译失败 | 基本达标 | Metal 着色器编译期产出 metallib，运行期只建管线；管线缺失时逐命令 `warn + skip`，不崩溃（[rxSession.cpp:499-507](../../Renderx/src/rt/rxSession.cpp#L499-L507)）；但默认管线整体缺失时表现为整帧空白，仅日志可见 |
| 表面/设备丢失 | 不满足工业要求 | `acquireNextImage` 失败返回 `ErrorDeviceLost`（[rxSession.cpp:278-290](../../Renderx/src/rt/rxSession.cpp#L278-L290)）；2D/3D 只做一次 resize 重试后 `return false`，没有重建 device/session，也没有用户提示（[RenderWidget.cpp:1186-1196](../../UI/2D/Src/UI/ViewWidget/RenderWidget.cpp#L1186-L1196)、[RenderWidget3D.cpp:1171-1182](../../UI/3D/Src/Render/RenderWidget3D.cpp#L1171-L1182)） |
| 交换链过期 | 已达标 | 表面尺寸自愈；`minimized` 时返回 `OutOfDate` 而非黑屏渲染；Metal 对残留 drawable 做恢复（[metalDevice.mm:300-320](../../Renderx/src/rhi/metal/metalDevice.mm#L300-L320)） |
| 透明排序 | 已达标 | 3D 半透明按视距排序；2D 透明位图按提交顺序，规则已文档化 |

## 7. 可验证性

### 7.1 能覆盖到的（无 GL 或真实 GPU 自动化）

- Renderx：152 个非 Metal gtest（Arena/SlotMap/Mat4、Null 后端契约、后端选择、surface 最小化、draw list slot 映射、批量删除、GLSL 管线错误、FBO 缓存键）+ 14 个 Metal 像素用例。
- RenderBridge：10 个 gtest（持久几何仓、真实合批计数与断言）。
- Metal：14 个真实设备像素用例，覆盖清屏、屏幕三角形覆盖、纹理采样、深度测试、双面光照、线框。
- 2D：`ViewportRefreshRegressionTests` 70 个用例、`RenderViewport2DRegressionTests`、`LodValidationTests`。
- 3D：`UI3DRenderPipelineTests` 24 个用例（17 个 `Mesh3DBuilder` + 7 个场景几何/覆盖层）、`SceneRefreshCoordinator3DTests` 10 个用例；`renderScene` 的层间提交顺序明确未纳入断言。

### 7.2 只能靠肉眼的

1. 2D 最终像素（`captureFrameRGBA` 可截图，但没有任何 golden image 测试；场景缓存命中/失效也没有专门的像素回归）。
2. GL 后端的任何像素行为（Windows/Linux 出货路径）。
3. 抗锯齿/线宽/文字在 Retina 与多屏缩放下的实际观感。
4. 选中态对比度（蓝色虚线在蓝色图形上是否可辨）。
5. 3D 刀路被遮挡的程度、大模型帧率、设备丢失后的恢复行为。
6. GPU 帧时间（没有 timestamp query），性能回归没有任何 CI 门限；`1M 图元缩放` 基准用例是 `DISABLED_` 状态，且注释明确「没有真机 GPU 全链路测量前不在用例里锁死」。

**结论：CPU 侧逻辑可验证性良好；「画出来对不对」几乎完全依赖肉眼。** 对工业软件，这是最大的过程性风险。

## 8. 风险排序与建议

### P0（必须修，直接影响加工前判读）

1. **给刀路/参考线增加「穿透查看」模式**
   - 方案：刀路覆盖层增加显示模式（正常 / 置顶不测深 / 半透明置顶），默认保持现状；切换到置顶时给出显式提示，避免被当作真实遮挡关系。
   - 验收：3D 用例复用 `Mesh3DDepthTestRejectsFarQuadDrawnAfterNearQuad` 的像素断言方式，新增「置顶线在近面之后仍可见」的 Metal 用例。

2. **抗锯齿与线宽**
   - 短期：`SurfaceDesc` 增加 `sampleCount`（ABI 变更需版本号），离屏 MSAA + resolve；3D 同时接回 `msaaSamples`。
   - 备选：线/多边形改用屏幕空间带 shader AA 的三角形带（工作量更大，但不改 ABI）。
   - 同时明确「线宽 = 逻辑像素」契约，2D 在 Retina 上传 `dpr` 倍线宽。
   - 验收：Metal 与 GL 各一条像素用例，断言 45° 线的覆盖率呈渐变而非硬边。

3. **修复 macOS 3D 右键菜单父窗口回归**
   - 改回顶层窗口（`m_workbenchWindow` 或 `m_renderWidget3D->window()`），补一条 3D 视口右键菜单冒烟用例（否则同类回归还会发生）。

### P1（必须修，影响可用性与误判概率）

4. **3D LOD/分块或明确的容量上限**
   - **已落地「明确的容量上限」**（2026-11-11）：`Mesh3DBuilder` 新增网格顶点总驻留预算，默认取 `min(单仓推荐上限, 2 GiB)`，可用 `setGeometryBudgetBytes()` 覆盖。超限时不再静默丢模型：新图元拒绝入账、已有图元保留上一帧几何，并通过 `geometryBudgetExhausted()` / `droppedEntityCount()` 暴露；`RenderWidget3D` 用独立的黄色英文角标 `geometryBudgetBadge` 提示「有对象未显示」，与 `Render error` 失败语义分开。
   - **LOD/分块仍未接入**：`DisplayCache3D` 仍是离线缓存，不参与逐帧提交；真正的多级细节/按屏幕误差分块需要数据层提供 LOD 源，排入后续。本轮只保证「容量有明确契约且超限可见」，不声称已解决超大模型的逐帧成本。
   - **GPU timestamp 已落地**：GL/Metal 双后端的 `timestampQueries`、`rxSessionGetGpuFrameTimeNs`、RenderBridge 转发、FPS HUD 的 CPU/GPU 分列耗时均已完成；CI 门限尚未设置（需要真机 GPU 基准数据）。
   - 验收：`UI3DRenderPipelineTests` 的 `DefaultBudgetIsExplicitAndBounded`、`RejectsNewEntityAndKeepsUploadedGeometryVisible`、`RejectsGrowthButKeepsPreviousBlock`、`RemovingEntitiesFreesBudgetAndAllowsNewUploads` 可自动断言预算裁决、旧几何保留与释放后恢复；角标在真实超大模型下的可读性与布局只能真机肉眼确认。

5. **渲染失败可恢复、可感知**（已完成）
   - surface/device lost：`RenderWidget` / `RenderWidget3D` 在取帧失败后标记 lost，下一次 `paintGL`/`paintEvent` 触发有上限（3 次）的自动重建；重建成功后 `requestFullRefresh()` 重新装配几何，失败显示英文红色角标 `renderErrorBadge`，不再静默白屏。
   - Metal 信号量等待已加超时，超时返回 `ErrorDeviceLost` 而非冻结 UI。
   - 验收：`CommandUiWiringTests` 的 `RenderErrorBadgeShowsReasonAndClears2D/3D` 可自动断言角标显示与清除。

### P2（有缺口，建议排期）

6. 选中态对比度：提高轮廓不透明度/宽度，或在深色与浅色图形上使用双色描边；补充暗色主题下的可视性验证。
7. 场景缓存与 2D 最终像素的 golden image 回归；GL 后端的离屏像素用例。
8. 清理残留配置与文档漂移：`msaaSamples`/`nearPlane`/`farPlane` 无消费者；「瞬态环回绕覆盖」文档已过时（实现改为溢出临时缓冲）；`DisplayCache3D` 文档声明与接线不符。
9. 选择色两份头文件副本（`UI/Common/Include/Render/ColorSchemes.h` 与 `SelectionColors.h`）内容几乎一致，后续调色存在只改一处的漂移风险。
