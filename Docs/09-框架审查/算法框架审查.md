### 线程与事务边界小结

| 阶段 | 线程 | 事务 |
|---|---|---|
| 参数收集 / prepare | 主线程 | 无 |
| compute | 工作线程（每任务一个 `std::thread`） | 无 |
| apply | 主线程 | 单事务 `runAsSingleUndoStep`（可嵌套，最终合并为 1 条撤销） |
| 进度回调 | worker 写 `ProgressTracker`（内部加锁），主线程 100ms 定时器读 | 无 |
| 取消 | 主线程置标志 → worker 轮询 | 无 |

已核实为**正确**的两点，避免误报：
1. 嵌套 batch 不会产生多条撤销记录：`UndoRedoManager::beginBatch` 内层只累加深度（`UndoRedoManager.cpp:242-257`），`pushExecutedCommand` 在批次内直接进 `m_vBatchCmds`（`:343-360`）。因此 handler 外层 `runAsSingleUndoStep` + 内层 `runAsSingleUndoStep`/`pushExecutedChange` 最终仍是一条。
2. `runSync` 只对「非后台 handler」包撤销（`AlgorithmApplicationService.cpp:187-192`），后台 handler 由 `applyBackgroundRun` 自己包（`BackgroundAlgorithmTaskHandler.cpp:141-148`），没有把对话框吞进事务。

## 3. 框架层缺陷清单

### P0-1 进度对话框裸指针跨异步边界，对话框被销毁后回调仍会解引用（**本批已修复，见 §7**）

- 证据：
  - `AlgorithmApplicationService.cpp:342` 主线程 lambda 捕获裸 `dialog`，`:352` `dialog->beginApplyPhase()`、`:388` `dialog->endApplyPhase()`。
  - 同一指针还被 `ctx.progressCallback` 捕获（`:291-305`），在 worker 线程里通过 `QMetaObject::invokeMethod(dialog, ...)` 使用。
  - 对话框生命周期独立于该 lambda：`WA_DeleteOnClose`（`:279`）、`QTimer::singleShot(800, this, &QDialog::accept)`（`ProgressDialog.cpp:382`）、父窗口销毁（Qt 子对象级联析构）、`ProgressDialog::~ProgressDialog`（`:51-71`，析构只 cancel+join，不通知服务）。
  - 连接的接收者上下文是服务 `this`，不是 `dialog`（`AlgorithmApplicationService.cpp:342`），对话框析构不会自动断开该连接；已投递的 `QMetaObject::CallEvent` 仍会在主线程执行该 lambda。
- 影响：workerd 完成瞬间或取消/关闭窗口时，若对话框先被销毁，主线程 lambda 解引用悬空指针 → 访问冲突崩溃；Windows 上表现为随机闪退，日志停在 `apply begin`。
- 严重级别：**P0**（崩溃）。
- 建议修法：所有跨线程引用 `dialog` 的位置改 `QPointer<ProgressDialog>`，并在 lambda 首行判空；或把 `taskFinished` 连接的 context 改为 `dialog` 本身，让 Qt 在析构时自动断开。代价：小（局部类型替换 + 空判），需回归“关闭主窗口时任务中途退出”。

### P1-1 apply 阶段不校验“是否取消 / 计算是否成功”，正确性完全依赖派生类自觉

- 证据：`AlgorithmApplicationService.cpp:342-343` `Q_UNUSED(success)`，随后无条件调用 `applyBackgroundRun`；`BackgroundAlgorithmTaskHandler.cpp:131-167` 的 `applyBackgroundRun` 也不检查 `m_cancelRequested` / `m_computeCompleted`。
- 现状：现有 5 个后台 handler 都自查（Fill `AlgorithmTaskRegistration2D.cpp:269-282`、Offset `:573-586`、Boolean `:732-745`、Array `ArrayProcessor.cpp:175-190`、Nesting `:980-996`），所以当前不会写半成品；但这是**契约靠人**。
- 影响：任何新 handler 漏写一行就变成“取消后仍写回结果 / 计算异常后写半成品”，且框架层无日志可追溯。
- 严重级别：P1（数据一致性，潜在加工事故）。
- 建议：基类 `applyBackgroundRun` 入口统一判断 `computeCompleted()==false || isCancelled()` → 直接以失败/取消收尾，派生类只处理业务；`ProgressDialog::taskFinished` 的 `success` 参数应传入并参与决策。代价：小。

### P1-2 退出/关闭路径存在固定 3s 与 5s 阻塞

- 证据：`AsyncPipelineExecutor::shutdown` 无条件 `sleep_for(3s)` 后再 join（`AsyncPipelineExecutor.cpp:37-50`）；`ProgressDialog` 析构同理 5s（`ProgressDialog.cpp:51-71`）。
- 事实：注释写“正常毫秒级返回”，但代码是**无条件睡眠**，不是“最多等 N 秒”。worker 早已结束时也会白等 3s/5s。
- 影响：关窗/退出时界面卡 3-8s；用户体感为“无响应”。任务卡在阻塞 I/O 时 join 还会无限延长。
- 严重级别：P1（体验/关闭可靠性）。
- 建议：改用 `wait_for` 条件变量（worker 完成时 notify），或 `join` + 心跳标志轮询，超时才记 WARN。代价：小。

### P1-3 `AsyncPipelineExecutor` 的 owner 空分支不 join，下一次启动会 `std::terminate`

- 证据：`AsyncPipelineExecutor.cpp:156-167` owner 为空时直接 `m_busy=false; return;`，跳过 `:192-196` 的 `m_worker.join()`。
- 触发条件：`startPipeline(..., owner=nullptr)`（头文件默认值 `:140`）或 owner 在 worker 完成前被销毁。当前两处生产调用均传 `&inst`（`RasterProcessOperation2D.cpp:422`、`:507` 附近），所以是潜伏路径。
- 影响：一旦触发，`m_worker` 保持 joinable，下一次 `m_worker = std::thread(...)` 对 joinable 线程赋值 → `std::terminate` 直接杀进程。
- 严重级别：P1（当前潜伏；触达即 P0）。
- 建议：把 join 抽成唯一的收尾函数，所有退出路径（含 owner 空、异常、取消）都走它；或 `owner` 改为必填并断言。代价：小。

### P1-4 prepare 段无异常保护，异常会留下“交互永久禁用”状态

- 证据：`AlgorithmApplicationService.cpp:270-273` 先 `m_interactionControlCallback(false)`，`:320-335` 直接调用 `prepareBackgroundRun`，无 try/catch；只有“返回 false”分支恢复交互（`:328-332`）。
- 影响：`doPrepare` 内抛异常（对话框代码/场景访问）→ 异常穿透 `runAsync` → 交互回调保持 disabled，界面按钮灰死，直到下一次算法任务成功收尾；`finishRun` 也不会被调用，OperationBus 收不到完成信号。
- 严重级别：P1（可用性）。
- 建议：prepare 包 try/catch，异常路径与 `return false` 合并为同一收尾（恢复交互 + finishRun）。代价：小。

### P2-1 框架存在两套互不相通的异步执行器

- 证据：`AlgorithmApplicationService` + `ProgressDialog`（`UI/Common`）与 `AsyncPipelineExecutor`（`UI/2D`）各自 `std::thread`、各自取消标志、各自收尾；Raster 三条 route 完全绕过 `AlgorithmTaskId`/handler 注册（`RasterProcessOperation2D.cpp:389-422`、`:495-525`）。
- 影响：Raster 长任务没有统一进度框/取消入口（与 `Docs/08-Raster/位图激光雕刻能力盘点与实施规划.md:1106-1108` 已记录一致）；两套的 join/取消语义还在分叉（见 P1-2/P1-3）。
- 严重级别：P2（结构债）。
- 建议：Raster 侧改为 `IAlgorithmTaskHandler` 三段式（已有框架），删除 `AsyncPipelineExecutor` 或把它降为纯工具类（不持线程）。代价：中。

### P2-2 参数体系没有 schema，范围校验只在对话框里

- 证据：`declareParam` 实际定义见 `Main/Src/Composition/OpRegistryTypes.h:170-175`（仅注册 ParamLambdaOperation）；`AlgorithmTaskRequest::params` 为裸 `QVariantMap`（`AlgorithmTaskTypes.h:94-103`）；范围只写在 `QSpinBox::setRange`（`UI/2D/Src/UI/Dlg/FillDialog.cpp:429-741`）；`booleanOp` 直接强转枚举（`AlgorithmTaskRegistration2D.cpp:693`）。
- 影响：任何非 UI 入口（脚本/Python、批量、未来 API）都能传非法值；引擎侧越界行为不可预期（例如 offset=0、maxLayers=0）。
- 严重级别：P2。
- 建议：在 handler 的 `doPrepare` 统一做参数 clamp + 错误码；不建议新建反射框架。代价：小。

### P2-3 注册表覆盖与调试校验

- 证据：重复 taskId 静默覆盖（`AlgorithmApplicationService.cpp:76-80`）；`validate()` 仅 `#ifndef NDEBUG` 且只查 5 个 id（`:460-481`）。
- 影响：漏注册/错注册只能靠“菜单点了没反应”发现（文件头注释 `AlgorithmTaskRegistration2D.cpp:11-13` 已自述）。
- 严重级别：P2。

### 4.2 契约表

| 算法 | 输入单位/精度前提 | 输出结构 | 幂等 | 复杂度/实测 | 内存峰值来源 | 线程/取消 | 重复实现 |
|---|---|---|---|---|---|---|---|

### 4.3 2D / Raster 缺陷

#### P1-5 偏移与填充链路完全没有取消能力，取消延迟等于整次计算

- 证据：`Geo2DOffset` 全部公开函数签名无 cancel 参数（`Engine/2D/Include/Engine2D/Geometry/Geo2DOffset.h:33-114`）；`insetRingLayers` 循环 `Geo2DOffset.cpp:645-716` 无中断点；`EntityFill` 无线程中断检查（`Engine/2D/Src/Algorithm/Fill/PolygonFill/EntityFill.cpp` 全文无 cancel）；`FillTaskHandler::doCompute` 只在调用前后检查（`UI/2D/Src/Algorithm/AlgorithmTaskRegistration2D.cpp:212,262` 附近）。
- 影响：0.05mm 步距、100mm² 区域约 2000 条扫描线，取消响应要等到整段完成；用户连续点取消只会看到进度条不动。
- 严重级别：P1。
- 建议：给 `Geo2DOffsetParams`/`FillParameters` 增加 `const std::atomic<bool>* cancelFlag`（或 `std::function<bool()>`），在每层/每 64 行检查；代价小，但要改公开头（ABI 兼容需加默认参数）。

#### P1-6 Raster 矢量化与轮廓追踪是两份实现，极性相反

- 证据：`Raster/Raster/Src/Algo/RasterContour.cpp:101-105`（`Raster_TraceContours` 假设亮=保留，不做反相）；`Raster/Raster/Src/Vector/RasterVector.cpp:479-481`（`Raster_Vectorize` 固定 `THRESH_BINARY_INV+OTSU`，暗=加工）；两者都做 `findContours + approxPolyDP`，但输出类型与 epsilon 语义不同。
- 影响：同一张位图，走“轮廓追踪”与走“矢量化”得到互补区域；若未来某处接错入口，会加工背景而不是图形（P0 级事故的潜因）。当前 UI 只接了 `Raster_Vectorize`（`ProcessRouteRegistry.cpp:319`），`Raster_TraceContours` 无生产调用。
- 严重级别：P1（潜在加工事故，需合并）。
- 建议：保留一份，统一“暗=加工”极性并在 API 名称中显式；删除另一份或改为薄包装。代价中（需回归矢量化测试）。

#### P1-7 矢量化容差写在像素域，物理精度随 DPI 漂移

- 证据：`UI/2D/Src/ProcessRouteRegistry.cpp:449-454` 硬编码 `tolerance=1.0`、`minArea=10.0`，注释明确“10 平方像素”；随后才做像素→世界映射（`:360-375`）。
- 影响：600DPI 下简化误差≈0.042mm，150DPI 下≈0.169mm；同一几何在不同分辨率位图上结果不同，且与 2D 其它算法的 mm 容差体系不可比。
- 严重级别：P1（精度契约不一致）。
- 建议：UI 侧按 `mm/px` 换算后传入（epsilon_mm = 1px × mm/px），参数面板暴露 mm；代价小。

#### P1-8 Raster 处理链丢弃返回码，失败仍报成功

- 证据：`ProcessRouteRegistry.cpp:146-155` 调 `Raster_Threshold` 未判返回值，只判输出非空；后续抖动/反相同样只判指针（`:200-246`）。若 OpenCV 处理失败而输出缓存仍非空，route 继续走完并置 `outcome=Success`。对照：矢量化路由反而检查了返回码（`:319-328`），说明这是 bitmap 路由的实现疏漏，不是框架缺能力。
- 影响：用户得到未二值化/未抖动的图直接进入雕刻，属“静默错误输出”。
- 严重级别：P1。
- 建议：每个 `Raster_*` 调用检查 `RasterStatus`，非 OK 立即 `outcome=Failed` 并回填 `Raster_StatusText`；代价小。

#### P2-4 填充族分裂：旧扫描线填充与环/螺旋填充并存

- 证据：线填充走 `EntityFiller → EntityFill/BowFill`（0.1µm 整数网格，无取消），环/螺旋走 `EntityContourFiller → Geo2DOffset`（ClipperD(2)，无取消）。同一 `FillTaskHandler` 按 `FillStyle` 分派（`AlgorithmTaskRegistration2D.cpp:210-263`）。
- 影响：两套精度/取消/进度行为不一致，后续优化要改两处；已记录于 `Docs/轮廓偏移填充设计.md`（环/螺旋替换旧实现的方向），此处只更新“仍并存”。
- 严重级别：P2。

#### P2-5 位图内存峰值未做上限保护

- 证据：route 一次持有 `SnapshotImage`（RGBA）+ 灰度 + 二值 + 输出（`ProcessRouteRegistry.cpp:110-246`）；无分辨率/像素数上限检查，`AsyncPipelineExecutor` 的 3s join 也挡不住大图。
- 量化（估算，未实测）：A3 420×297mm@600DPI = 9921×7016 ≈ 69.6M px；RGBA8 单缓冲 278MB，灰度 70MB，二值 8.7MB；峰值 ≥350MB，若抖动/反相各留一份则 ≈600MB。
- 影响：32 位进程易 OOM；与 `Docs/08-Raster/位图激光雕刻能力盘点与实施规划.md:1106-1108` 记录的“600DPI UI 假死”同源。
- 严重级别：P2（有文档记录，补充量化）。

#### 精度差异的静态结论（未实测）

- `Geo2DOffset` 与 `PolygonOffset` 的差异点：网格 10µm vs 1µm；JoinType 可配 vs 硬编码 Miter/2.0；输出 double 环 vs float 环；是否每轮 Union 归一化（两者都做，但 Engraving 用 `EvenOdd`，Engine2D 也是 `EvenOdd`）。
- 期望差异量级：单顶点 ≤5µm vs ≤0.5µm；在 0.1mm 割缝、50 层填充上，前者可能让最内层残余面积判定提前 1-2 层触发最小面积终止。**未实测，需同一输入的 A/B 对比才能定量**。

### 5.2 3D / Vision / CAM 缺陷

#### P1-9 “位图能否加工”仍是三个互斥结论源（已记录，复核仍成立）

- 证据：
  - `Engine/2D/Src/Cam/GeometryExtractor.cpp:859-863`：`SyImage` → `GeometryKind::Raster`，`reason="raster engraving engine not implemented yet"`，不作为轮廓提取。
  - `Main/Src/Hardware/MotionPlanCompiler.cpp:232-245`：`GeometryKind::Raster` → `Unsupported`，`unmachinableEntityCount++`，返回 false。
  - `Main/Src/CAM/CamInputBridge.cpp:429-451` + `CAM/CAM/Src/CamCore.cpp:589-643`：Raster 且有 `scanlines` 时**能生成刀路**（`Raster_ScanlineJobs`），仅当 `BUILD_RASTER` 关闭或无 scanlines 时才标 `Unsupported`。
- 影响：同一张位图，硬件前处理判“不可加工”，CAM API 判“可加工”。用户看到的预检结论与实际下发能力不一致；若有人把 `Cam::compile` 接到生产链，会绕过前处理的拒绝，直接按未经确认的扫描线参数加工。
- 严重级别：P1（当前生产链 fail-safe；接错即 P0）。
- 建议：把“可加工性”收敛到单一判定函数（`GeometryExtractor` 输出 `Machinability`），`CamCore` 只消费该结论；`BUILD_RASTER` 不应改变语义。代价中（跨 Main/CAM 两模块，需契约测试）。
- 去重：`Docs/08-Raster/位图激光雕刻能力盘点与实施规划.md:37`（K1）已记录，本处只补精确行号与“第三源”证据。

#### P1-10 CAM 与硬件前处理是两套独立刀路编译器

- 证据：`Cam::compile`（`CAM/CAM/Src/CamCore.cpp:470-643`）与 `MotionPlanCompiler`（`Main/Src/Hardware/MotionPlanCompiler.cpp:210-262`）各自做实体分类、跳过、排序、pass 展开；两者的单位/坐标都是用户坐标 mm（`CAM/CAM/Include/CAM/CamPlan.h:18-22`），但可加工性规则不同。
- 影响：同一场景“预检结果”和“导出结果”可能不同；修一处 bug 要改两处。
- 严重级别：P1（一致性/维护）。
- 建议：保留 `Cam::compile` 为唯一编译入口，`MotionPlanCompiler` 退化为“预检适配器”只做校验；代价中。

#### P1-11 3D 切片 C API 默认补弦闭合，外部调用会切到不该切的区域

- 证据：`MeshSlicer.h:47-54` `allowChordClose` 默认 true；`EngravingCAPI.cpp:717-719` 调 `connectSegmentsToContours(sliceSegments, eps)` 未传第三参 → 走 true（开口链首尾直连）。生产内部路径（`VolumeProcessing.cpp:576,678,744,751,824,829,978`）均显式传 false。
- 影响：通过 C API（外部/脚本/未来语言绑定）走 `SliceMesh → ConnectContours` 时，破面缺口会被补一条直线弦，G-code 可能穿过工件内部（加工事故）。当前 C API 无生产调用，属潜伏。
- 严重级别：P2 潜伏（触达即 P1）。
- 建议：C API 增加显式 `allowChordClose` 参数或默认改为 false；代价小。

#### P2-6 3D 精度全部用 float，而 2D 已用 double

- 证据：`Engraving/Engraving/Include/Engraving/VolumeProcessing.h:31-41` `Point3D` 为 float；`MeshSlicer.h:37,53` 参数 float。
- 量化：1000mm 处 float ulp≈6.1e-5mm（0.06µm），叠加焊接 1e-4mm 容差，对激光切割够用；但在 2000mm 幅面、多次累加后误差可达 0.5µm 量级，仍小于 10µm 网格。**当前不构成 P1**，记录为结构债：3D→2D 传递需显式 double 化。
- 严重级别：P2。

#### P2-7 Vision 与 CAD/CAM 没有数据契约

- 证据：`Vision/Vision/Src/Service/VisionService.cpp:34-35`（线程全在内部）、`:1199`（worker 池）；Vision 输出停在 `VisionHost` C ABI，未接入 `SceneManager`/`CamInputBridge`（AUDIT 检索 Main 侧仅见 `VisionHostBridges`，无算法/场景消费）。
- 影响：视觉定位结果无法直接驱动套料/加工；且 Vision 的 Fixed/Otsu/Adaptive 阈值与 Raster 的阈值各一套（`Vision/Vision/Src/Algo/BuiltinOperators.cpp:2238-2259` vs `Raster/Raster/Src/Algo/RasterPreprocess.cpp:222-275`），极性约定不同（Vision 可配 `markIsDark`，Raster 矢量化固定反相）。
- 严重级别：P2（能力缺口+结构债）。
- 建议：定义 `VisionResult` → 场景/坐标系的显式适配层；阈值语义统一到“前景区/加工区”两个命名。代价中。

#### P2-8 CAM 静默跳过不可加工图元

- 证据：`CamCore.cpp:488-493` 对 `isEntityExcluded` 的图元 `continue`，只在 `failOnUnmachinable=true` 时整体失败（`CamInputBridge.cpp:320` 由 `spec.failOnUnmachinableEntity` 决定）。
- 影响：默认配置下部分图元不加工，但任务仍算成功；用户可能不知道有零件被漏掉（只靠 `unmachinableDetails` 展示）。
- 严重级别：P2（若 UI 不展示即 P1）。
- 建议：返回结果强制携带“被跳过清单”，UI 必须弹确认；代价小。

## 7. P0-1 修复记录（本批）

### 7.1 生命周期规则（已写入代码注释，`AlgorithmApplicationService.cpp:279-286`）

1. **拥有者**：`ProgressDialog` 由 `AlgorithmApplicationService::runAsync` `new` 出来，父对象是 `ctx.parentWidget`，同时设置 `WA_DeleteOnClose`。它有三种先死方式：父窗口级联析构、800ms 自动关闭、用户/系统关闭。服务**不独占**它的生命周期。
2. **谁可能先死**：对话框可能先于 worker 收尾、也可能先于已排队的完成回调派发而析构。工作线程本身由对话框独占（`ProgressDialog::runAsync` 在对话框内部建 `std::thread`），因此对话框死亡时 worker 仍会跑完并 join（`ProgressDialog.cpp:51-71`），但 `taskFinished` 连接会被移除。
3. **主线程回调**：`taskCanceled` / `finished` / `taskFinished` 三个回调只经 `QPointer<ProgressDialog>` 访问对话框，每次使用前判活；对话框已销毁时跳过纯 UI 动作（`beginApplyPhase/endApplyPhase`），但 **apply、结果写回、交互恢复必须继续执行**。
4. **worker 侧**：`ctx.progressCallback` 只允许写线程安全的 `ProgressTracker`，禁止直接或经 `invokeMethod` 触碰任何 QWidget；界面刷新全部由对话框自己的 100ms 定时器在主线程读 tracker 完成。worker 侧**不读 QPointer**（判活只在主线程，避免与析构构成数据竞争）。

### 7.2 改法选择

- **采用 QPointer 主线程判活**（规则 2/3），并把 worker 侧对 UI 的唯一触点彻底移除。
- 放弃 “把 `taskFinished` 连接 receiver 改成 dialog”：Qt 会在对话框析构时静默断开，**apply 与结果写回也随之丢失**，等于用“丢结果”换“不崩”，不符合契约。
- 放弃 “禁止 `WA_DeleteOnClose` + 服务独占生命周期”：对话框与父窗口是子对象关系，父窗口销毁仍会级联析构，独占只能挡住自动关闭这一种情况，挡不住真正的 P0 路径；且会改变现有 UI 行为。
- 明确不做“再判一次裸指针非空”：对已析构对象判非空是伪保护。
