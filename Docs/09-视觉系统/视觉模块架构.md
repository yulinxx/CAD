# 视觉模块架构（Vision v2）

> 状态：设计定稿；P0–P3 已落地，P4 前置缺口已修完并接入首个非仿真相机（UVC）；读码补齐 ZXing-C++（可选依赖），自动对焦活体扫描落在 `VisionService`
> 适用范围：`Vision/Vision`（git submodule），工业激光 2D 加工软件的视觉子系统
> 关联文档：`Docs/05-硬件与设备/硬件抽象层架构.md`（本文的 ABI 与设备范式沿用其约定）

---

## 0. 为什么重写

旧 Vision 的问题是结构性的，不是缺功能：

- **无抽象**：22 个头文件全是并列的具体类（`ShapeDetector`、`BarcodeDetector`、`ImageEnhancer`…），零虚接口、零 pimpl、零注册表。新增一个算法就是新增一个类，上层必须硬编码类名。
- **接口是"文件路径进、PNG 出"**：`VisionUIAPI::detectShape(const std::string& imagePath)` 内部读盘、写 `./output/*.png`、返回路径字符串。真机产线上没有磁盘往返的余量，也拿不到亚像素坐标。
- **无坐标系概念**：识别结果停留在像素，没有 像素 → 相机 → 平台 → 图纸 的标定链路，因此"看到了"无法变成"打在正确位置"。
- **无设备层**：相机就是 `cv::VideoCapture`，工业相机（海康/Basler/大恒/迈德威视/GenICam）一个都接不进来；无触发、无曝光同步、无帧时间戳。
- **公开头文件泄漏 OpenCV 与 STL**：`cv::Mat`、`std::string`、`std::vector` 直接出现在 `VISION_API` 签名上，头文件自己写了"沙箱型模块，不承诺跨 DLL ABI"——等于放弃了跨 DLL。
- **无流程编排**：视觉是"配出来的"，不是"编译出来的"。旧代码没有作业/步骤/参数 schema，工艺工程师无法在界面上组流程。
- **测试从未构建**：`Vision/Test/` 5 个文件不在任何 CMake 目标里。
- 死依赖与残留：`PUBLIC Log` 但全模块不用 Log；`HAVE_TESSERACT` / `decodeWithZbar` 声明但从未定义；源码树里提交了 `CMakeFiles/`、`Vision.dir/` 构建产物。

结论：保留任何一个旧类都会把"文件路径 + cv::Mat + 无坐标系"的假设带进新框架。**旧代码整体归档到 `Legacy/`，只为 `UI/2D` 的既有调用点续命，新功能一律走 v2。**

## 1. 设计目标与硬约束

### 1.1 目标

1. **跨 DLL 干净**：Vision 的公开头文件里不出现 OpenCV、Qt、STL、异常。厂商相机适配器与第三方算子可编译成独立 DLL。
2. **分层单向**：`Core → Device → Calib → Algo → Pipeline → Service`，下层不认识上层，同层不互相引用。
3. **可配置而非可编译**：视觉流程 = 作业（JSON） + 算子注册表。工艺工程师在界面上组流程，不改代码。
4. **坐标系是一等公民**：任何测量结果都带坐标系标签，跨坐标系必须经过标定过的变换，缺标定则报错（`FrameNotLinked`），不静默按像素当毫米用。
5. **宁可报错，绝不静默降级**：沿用 HAL 的价值观。相机不支持硬触发就报 `NotSupported`，不悄悄退化成软触发。
6. **可测**：不依赖真实相机即可跑全链路（`SimulatedCamera` + `FileReplayCamera` + 手动推进的时钟/事件泵）。

### 1.2 硬约束（与 HAL 一致，逐条对齐 `硬件抽象层架构.md`）

| 约束 | 做法 |
|---|---|
| 接口签名只用 POD | 定长 `char[N]`、指针 + 数量、枚举、`double`；禁 `std::string/vector`、`QString`、`cv::Mat` |
| 谁分配谁释放 | 所有接口对象提供 `destroy()`，虚析构 `protected`，编译期堵死跨 DLL `delete` |
| 禁 `dynamic_cast` | 根 CMake 开了 `CMAKE_CXX_VISIBILITY_PRESET hidden`，改用 `queryInterface(InterfaceId) -> void*` + `visQuery<T>()` |
| 禁异常穿越边界 | 统一返回 `VisResult{ VisError, vendorCode, message[256] }` |
| 实现的 STL 成员藏进 pimpl | 避免 MSVC C4251，也保证头文件布局与实现解耦 |
| 公开头文件禁 `emit/signals/slots` 标识符 | Vision 完全不用 Qt；事件用纯虚 sink，宿主侧转 Qt 信号 |
| 常量定义在头文件 | `constexpr` 上限（缓冲数、最大点数、最大步骤数）必须在头里，否则各 DLL 各取默认值 |
| 单位统一 | 长度 mm、角度 度、时间 微秒、像素 px、曝光 微秒、增益 dB、温度 ℃ |
| 日志文本英文，代码注释中文 | 沿用项目既有约定 |

### 1.3 依赖边界

```
Vision  ──依赖──>  Log（日志）
        ──内部依赖（仅 .cpp / Internal/*.h）──>  OpenCV
Vision  ──不依赖──>  Hardware / Engine / UI / Renderx / Qt
```

Vision 需要"平台运动"和"振镜出光"来做手眼标定与场镜标定，但**不能反向依赖 Hardware**。做法是 Vision 定义宿主要实现的回调接口（`IStagePoseProvider` / `IStageController` / `IGalvoController` / `ILightControl`），由 `Main` 在装配期用 Hardware 的 `IMotionCard` / `IGalvoCard` / `IIoModule` 桥接注入。这样 Vision 与 Hardware 互不认识，装配点唯一且在 `Main`。

OpenCV 只出现在 `Src/**` 与 `Src/Internal/**`。`Include/**` 一旦出现 `#include <opencv2/...>` 视为架构违规，由 CI 脚本 grep 拦截。

### 2.1 分层职责一句话

- **L0 Core**：定义"话怎么说"——错误码、几何、图像视图、参数、事件。不做任何事。
- **L1 Device**：把"任意厂商相机"变成一个接口。只管取图，不认识算法。
- **L2 Calib**：把像素变成毫米，把相机看到的变成机床能走到的。
- **L3 Algo**：把图像变成测量值与位姿。不认识相机，只吃 `ImageView`。
- **L4 Pipeline**：把算子按配置串起来跑，产出结果与耗时。
- **L5 Service**：对宿主只暴露一层，句柄式 API，内部管线程。

## 3. L0 契约层关键决策

### 3.1 图像怎么跨 DLL 传

两个类型分工：

```cpp
// 非拥有视图，按值传递，用于同步调用（算子入参）
struct ImageView {
    const uint8_t* data;   int32_t width, height, strideBytes;
    PixelFormat format;    int32_t bitDepth;      // 有效位深，Mono12 打包在 Mono16 里时为 12
    int64_t timestampUs;   uint64_t frameId;
};

// 引用计数缓冲，用于异步传递（相机线程 → 算法线程 → UI 显示）
class VISION_API IFrameBuffer {
public:
    virtual void addRef() = 0;
    virtual void release() = 0;                  // 归还给产出它的 FramePool
    virtual ImageView view() const = 0;
    virtual const FrameMeta& meta() const = 0;
protected:
    virtual ~IFrameBuffer() = default;
};
```

理由：`ImageView` 解决"算子不该拿所有权"，`IFrameBuffer` 解决"帧要活过相机回调"。都不涉及跨 DLL 的堆所有权转移——释放走 `release()`，实际 delete 永远发生在产出方模块内。

`FrameMeta` 携带 **曝光时刻的平台位姿**（`Pose2D stagePose; bool stagePoseValid;`）、曝光值、增益、触发序号、本帧之前的丢帧数。这一条是飞拍与手眼标定能不能做对的关键：位姿必须和帧绑定，不能事后去问"现在在哪"。

### 3.2 错误码分段

沿用 HAL 的分段风格，便于现场按段定位：

- 1–7 通用（`NotImplemented` / `InvalidArgument` / `InvalidState` / `Timeout` / `Busy` / `NotSupported`）
- 20–23 SDK 装载（`SdkNotFound` 最常见：现场没装相机驱动）
- 40–44 连接
- 60–64 取流（`GrabTimeout` / `GrabIncomplete` / `BufferOverflow` / `TriggerLost`）
- 80–82 图像（`ImageEmpty` / `ImageFormatUnsupported` / `RoiOutOfRange`）
- 100–104 标定（`CalibNotReady` / `CalibInsufficientData` / `CalibNotConverged` / `CalibResidualTooLarge` / `FrameNotLinked`）
- 120–123 算子（`OperatorNotFound` / `SlotNotFound` / `SlotTypeMismatch` / `ModelNotTrained`）
- 140–143 判定（`MatchNotFound` / `LowScore` / `AmbiguousMatch` / `VerifyMismatch`）
- 160–161 配置与持久化

### 3.3 参数自描述

与 HAL 的 `ParamSchema` 同构：`{ key, label, unit, description, type, min, max, defaultNumber, defaultText, enumValues, required, advanced }`，取值一律字符串承载（最终要落 JSON）。

收益：相机参数面板、算子参数面板、标定向导的参数区**全部由 schema 自动生成**，UI 不为任何一个具体相机或算子写代码。新增算子 = 注册 + 声明 schema，界面自动出现。

## 4. L1 相机抽象层

### 4.1 接口形状

```cpp
class VISION_API ICameraDevice {
public:
    virtual void destroy() = 0;
    virtual const CameraDescriptor& descriptor() const = 0;

    virtual int32_t paramSchemaCount() const = 0;
    virtual const ParamSchema* paramSchemaAt(int32_t index) const = 0;

    virtual VisResult open(const ParamSet& params) = 0;
    virtual VisResult close() = 0;
    virtual DeviceState state() const = 0;
    virtual VisResult reset() = 0;
    virtual VisResult selfTest() = 0;

    virtual VisResult startStream(AcquisitionMode mode) = 0;
    virtual VisResult stopStream() = 0;
    virtual bool isStreaming() const = 0;
    virtual VisResult grab(int32_t timeoutMs, IFrameBuffer** outFrame) = 0;   // 同步单帧
    virtual void setFrameSink(IFrameSink* sink) = 0;                          // 异步流
    virtual void setEventSink(IVisionEventSink* sink) = 0;

    virtual VisResult setFeature(const char* key, double value) = 0;          // 键值式，见 CameraFeatureKeys.h
    virtual VisResult getFeature(const char* key, double* outValue) const = 0;
    virtual VisResult setFeatureText(const char* key, const char* value) = 0;
    virtual VisResult getFeatureText(const char* key, char* out, size_t outSize) const = 0;
    virtual VisResult setRoi(const RectI& roi) = 0;
    virtual VisResult setPixelFormat(PixelFormat format) = 0;

    virtual void* queryInterface(InterfaceId id) = 0;
protected:
    virtual ~ICameraDevice() = default;
};
```

**为什么参数用 `setFeature(key, value)` 而不是 `setExposure()/setGain()/...`**：工业相机的可调项有几十到几百个（GenICam 特征树），逐个开虚函数会让接口在接第三家相机时就必须改，而改虚函数表就是 ABI 破坏。键值 + schema 声明能力，接口永久稳定；不支持的键返回 `NotSupported`。常用键在 `CameraFeatureKeys.h` 里定为 `constexpr const char*`，避免拼写漂移。

### 4.2 能力位与子接口

`CameraCapability` 位掩码声明能力（`HardwareTrigger` / `SoftwareTrigger` / `Roi` / `Binning` / `AutoExposure` / `Gain` / `WhiteBalance` / `LineScan` / `Focus` / `Light` / `ChunkTimestamp`…），**能力必须按实际解析到的 SDK 符号收窄**，不允许"声明支持、第一次用就失败"。

可选面通过 `queryInterface` 取：`ITriggerControl`、`IFocusControl`、`ILightControl`。实现侧多重继承时必须 `static_cast<T*>(this)`，禁 `dynamic_cast`。

### 4.3 厂商 SDK 运行期加载

`CMake 不链接任何厂商 lib`。沿用 HAL 的 `DynamicLibrary` 范式（`QLibrary` 藏在 pimpl 里，Vision 侧改为 `LoadLibraryW`/`dlopen` 的薄封装以保持零 Qt）：`setSearchNames(primary, fallback)` → `load()` 幂等 → `bind<Fn>(&fn, "symbol")` 类型安全绑定 → `lastResult()` 指出缺哪个符号。缺 DLL 报 `SdkNotFound`，DLL 在但缺符号报 `SdkSymbolMissing`——现场"没装驱动"和"驱动版本不对"是两条完全不同的处理路径。

### 4.4 兼容目标（本期只定义接口，不写实现）

海康 MVS(`MvCameraControl`)、Basler Pylon、大恒 GxIAPI、迈德威视 MindVision、GenICam/GenTL 通用、USB/UVC。每家一个 `Vendors/<Brand>Camera.{h,cpp}`，形状固定为：

```cpp
class VISION_API HikvisionCamera final : public CameraDeviceBase, public ITriggerControl {
public:
    static ICameraDevice* create();               // 就是 CameraFactoryFn
    void* queryInterface(InterfaceId id) override;
protected:
    VisResult doOpen(const ParamSet&) override;   // 只需实现钩子
    VisResult doClose() override;
    VisResult doStartStream(AcquisitionMode) override;
    VisResult doGrab(int32_t timeoutMs, IFrameBuffer** out) override;
    ...
};
```

内置两个非厂商相机，测试与离线调试全靠它们：

- `SimulatedCamera`：程序化生成带噪声的图（可放 Mark 点、二维码、缺陷），支持指定帧率与丢帧率。
- `FileReplayCamera`：按目录里的图片序列回放，可回放现场抓的 NG 图，用于回归。

### 4.5 线程与背压

- 每台相机一个采集线程，由 Vision 拥有；`IFrameSink::onFrame` 在该线程调用，回调里禁止碰 UI，宿主必须投递到主线程。
- `FramePool` 定容（默认 8 帧，可配）。池满时按策略处理：`DropOldest`（实时预览）或 `Block`（不许丢帧的检测流程）。丢帧计入 `FrameMeta::droppedBefore` 并发 `FrameDropped` 事件，**不静默丢**。
- 事件另有拉模式：`VisionService::pollEvents(VisionEvent* out, int32_t maxCount)`，宿主在自己的 tick 里 drain，测试不用 sleep（对齐 `DeviceHost::tick` 的约定）。

## 5. L2 标定与坐标系（本设计的核心）

### 5.1 坐标系枚举与变换中枢

```cpp
enum class Frame : int32_t {
    Pixel = 0,      // 原始像素（含畸变）
    Image = 1,      // 去畸变后的理想像素
    Camera = 2,     // 相机坐标，mm（像素当量已知）
    Tool = 3,       // 工具/激光头坐标，mm
    Galvo = 4,      // 振镜场坐标，mm
    Stage = 5,      // 机床/平台坐标，mm
    Document = 6,   // 图纸/场景坐标，mm（Engine 的世界坐标）
};

class VISION_API CoordinateHub {
public:
    VisResult setTransform(Frame from, Frame to, const Mat3& m);   // 自动登记逆变换
    bool hasPath(Frame from, Frame to) const;
    VisResult compose(Frame from, Frame to, Mat3* out) const;      // BFS 求链路
    VisResult transformPoint (Frame from, Frame to, const PointF& in, PointF* out) const;
    VisResult transformPoints(Frame from, Frame to, const PointF* in, int32_t count, PointF* out) const;
    VisResult transformPose  (Frame from, Frame to, const Pose2D& in, Pose2D* out) const;
    VisResult save(const char* path) const;
    VisResult load(const char* path);
private:
    struct Impl; Impl* m_impl;      // 固定 7×7 邻接矩阵，无 STL 出现在头里
};
```

**没有标定过的链路一律返回 `FrameNotLinked`。** 这条规则把"像素当毫米用"这类现场事故挡在编译-运行边界上，是旧代码最缺的东西。

### 5.2 标定器统一接口

```cpp
enum class CalibKind : int32_t {
    Intrinsic = 0,      // 内参 + 畸变（棋盘/圆点/非对称圆点；支持远心镜头）
    Scale = 1,          // 单像素当量（一次平移标定，最常用的轻量标定）
    HandEyeInHand = 2,  // 相机装在运动头上
    HandEyeToHand = 3,  // 相机固定，工件随平台动
    GalvoField = 4,     // 振镜场镜畸变（九点/网格 + 桶形校正）
    Homography = 5,     // 平面单应（斜视安装的透视矫正）
};

class VISION_API ICalibrator {
public:
    virtual void destroy() = 0;
    virtual CalibKind kind() const = 0;
    virtual int32_t paramSchemaCount() const = 0;
    virtual const ParamSchema* paramSchemaAt(int32_t) const = 0;
    virtual VisResult configure(const ParamSet& params) = 0;
    virtual VisResult addSample(const CalibSample& sample) = 0;   // 图 + 位姿（+可选人工点对）
    virtual int32_t sampleCount() const = 0;
    virtual void clearSamples() = 0;
    virtual VisResult solve() = 0;
    virtual const CalibStats& stats() const = 0;                  // rmsPx / maxErrPx / converged
    virtual VisResult writeTo(CoordinateHub* hub) const = 0;      // 结果直接注入坐标中枢
    virtual VisResult save(const char* path) const = 0;
    virtual VisResult load(const char* path) = 0;
protected:
    virtual ~ICalibrator() = default;
};
VISION_API ICalibrator* createCalibrator(CalibKind kind);
```

### 6.3 测量结果与判定

```cpp
struct Measure {
    char name[kNameLen];
    double value;
    double nominal;                        // 标称值（设计值）
    bool hasNominal;
    double lowerLimit, upperLimit;
    bool hasLowerLimit, hasUpperLimit;     // 上下限各自可缺省
    bool pass;
    char unit[16];
};
enum class Verdict : int32_t { Unknown = 0, Pass = 1, Fail = 2, Warn = 3 };
```

把公差带进结果结构，而不是让上层各自写 `if (value > 0.5)`：这样 OK/NG 判定、报表导出、SPC 统计都有唯一数据源。

上下限用两个独立标志而不是一个 `hasLimits`：单边公差是工业测量的常态（"残差 ≤ 0.05mm"、"匹配分数 ≥ 0.8"）。缺失的那一侧完全不参与判定，也不参与 Warn 的"接近边界"比例计算 —— 给另一侧编个假限值会让残差趋近 0（找正最好的时候）被误判成贴着下限的预警。

**Warn 基准点规则（已定案，不要当 bug 改）**：预警比例需要一个"满行程"，基准点优先取 `nominal`，缺失时双边取公差带中心、单边退回 0。由此产生一个有意的后果 —— 形如 `score >= 0.8`（只有下限且下限为正）的量，0 落在下限外侧，行程无从定义，该量**只有 OK / NG 两态，不产生 Warn**。要让这类量具备预警，正确做法是在配方里填 `nominal`（如满分 `1.0`），而不是让代码替用户假设一条他从未声明的公差带 —— 在虚构刻度上报预警比不报更坏。实现见 `Src/Algo/Measure.cpp` 的 `toleranceReference()`，行为由 `JobPipelineTests.cpp::ALowerOnlyToleranceWarnsAgainstTheNominalAsReference` 锁定。

#### 读码依赖（不糊假实现）

当前 OpenCV 4.12.0（vcpkg，无 contrib）实测能力，靠扫 `opencv_objdetect4.dll` 符号 + 合成码实跑确认：

- **能解**：EAN-13 / EAN-8 / UPC-A / UPC-E（`cv::barcode::BarcodeDetector`）、QR 含 Structured Append（`cv::QRCodeDetector::detectAndDecodeMulti`）。
- **仍不能解**：OCR（需 Tesseract）、ISO/IEC 15415 符号分级（需专门分级库）。这两项一律返回 `NotSupported` 并在消息里点名缺失的依赖，**不返回"看起来合法的空成功"**。`vis.read.ocr` 尤其如此：手糊的"切字+模板相关"在示教样张上准确率很高、现场笔画一粘就崩，而它错的方式是交出一个合法字符串（把 8 读成 B 照样往下走），内容防错读错一个字符的代价是整批报废。`grade_quality` 同理——恒返回满分会毁掉这个参数存在的唯一意义：在码还能解出来之前就发现激光在缓慢衰减。
- **已由 ZXing-C++ 2.3.0 补齐**：Code128 / Code39 / ITF / Codabar 与 DataMatrix。**可选依赖**：CMake `option(VISION_WITH_ZXING)` 默认跟随 `find_package(ZXing 2.3.0 EXACT CONFIG)` 的发现结果，源码侧用 `VISION_HAS_ZXING` 门控（与 `VISION_HAS_LOG` 同样的 `#ifndef/#define 0` 写法，缺失即定义为 0 而不是未定义符号）。没装 ZXing 时 Vision 照样独立构建，两个读码算子返回与从前**逐字节相同**的 `NotSupported` 消息。注意 `VISION_WITH_ZXING=ON` 而 ZXing 不在，是配置期 `FATAL_ERROR`——静默降级成"编译过了但没功能"正是当年 `HAVE_TESSERACT` 的失败方式。vcpkg 上的 port 名是 `nu-book-zxing-cpp`，只提供静态库。
- **一个符号体系只走一个后端，不做回退。** ZXing 也能解 EAN/UPC 和 QR，而且可能更好，但刻意不让它接手：两个后端对同一个符号的**报告方式不同**，而这个差异在配方里是承重的——首位为 0 的 EAN-13 从 OpenCV 出来是 `UPC_A` 且去掉前导零，从 ZXing 出来是 13 位的 `EAN-13`，于是"只勾 Ean13"的配方会剔掉前者、接受后者。`min_module_px` 的"长边 ÷ 标称模块数"算法同样只对定长族成立。让 ZXing 兜底会使判定结果取决于构建机器上恰好装了什么库。这条是实测撞出来的，不是推理出来的：第一版确实做了回退，把既有的符号筛选用例弄红了，现在有一个专门的用例（`TheEanFamilyStillGoesThroughOpenCv`）当闩。
- 另一条实测坑：**ZXing 的 `tryInvert` 只作用于矩阵类符号，不作用于一维码**，于是 `polarity=LightOnDark` 在 Code128 上会静默失败。两个算子改为自己反转 ROI 并传 `setTryInvert(false)`，与 OpenCV 路径同一套机制，`polarity` 在两个算子里语义一致。
- `score` 仍恒为 1.0。ZXing 有两个看着像置信度但不是的东西：`ecLevel()` 是**打印时**选的纠错等级（对这一枚符号退化到什么程度一无所知），`lineCount()` 是几条扫描线取得一致、取决于条高与采样且无法归一化。都不是分级置信度，所以什么都不发布，不编一个像置信度的小数。

- 一条实测坑：OpenCV 的一维码检测器在**合成的完美条码**上会直接漏检，实现里靠"按整个 ROI 四角再解一次"兜底救回；现场配方通常已用 ROI 框住码，这条兜底不是可选优化。另外首位为 0 的 EAN-13 会被 OpenCV 报成 `UPC_A` 并去掉前导零（规范行为，两者是同一个符号），意味着配方只勾 Ean13 时这种码会被符号筛选剔除。

#### 对焦执行端缺口

`vis.focus.autofocus` 只实现了「对宿主已采好的 (位置, 分数) 曲线寻峰」这一半：三点抛物线亚步长拟合（用差商，不等距同样成立）、平坦度拒收、端点告警。**实时驱动焦轴 + 重新取帧这一半返回 `NotSupported` 并点名 `IFocusControl`。**

原因是算子在运行期确实拿不到执行端：`IVisionContext` 的全部能力是插槽读写 / `appendMeasure` / `coords()` / `frameMeta()` / `cameraIntrinsics()` / `workingDirectory()` / `cancelRequested()` / `reportProgress()` / `log()`，没有任何设备入口；`HostBridges.h` 里也没有焦轴桥接，且桥接只注入到 `VisionService` 与标定器，从不流向 `IVisionContext`；`IFocusControl` 唯一的获取路径是 `ICameraDevice::queryInterface`，而算子拿不到 `ICameraDevice`。

**已按"把扫描整体上移到服务层"关闭。** `VisionService` 上新增 `setFocusControl(IFocusControl*)` / `autoFocus(const FocusSweepRequest&, FocusSweepResult*)` / `cancelAutoFocus()`，两个结构体皆 POD。理由：「动 → 拍 → 算」本质是编排，编排是服务/流程层的职责而不是算子的；`VisionService` 本来就同时握着相机与桥接注入点。另两个方案（在 `IVisionContext` 上开 `focusControl()` + `regrab()`，或在 `HostBridges.h` 加 `IFocusAxisProvider`）都会把「一次 run = 一帧」这条流程不变式打破，或让每个第三方算子的测试桩都得跟着实现新方法。

`cancelAutoFocus()` 是超出"一个 setter + 一个编排器"的第三个方法，但它是必需的：`autoFocus` 是同步的、跑几秒的调用，取消标志只能从另一个线程抬起，而 `cancelJob(RunHandle)` 不适用（扫描不是 job，没有 run handle）。`setFocusControl` 返回 `VisResult` 以便在扫描进行中用 `Busy` 拒绝——扫描途中换轴会得到一条前半在 A 轴、后半在 B 轴测出来的曲线，而它看起来和正常曲线一模一样。

实现上刻意不复制任何算法：每个探测点把图写进插槽后调既有的 `vis.focus.score`，寻峰把整条 (位置, 分数) 列表喂进 `vis.focus.autofocus` 的 `focus_samples` 插槽——那个插槽就是为此存在的。指标与抛物线拟合各自只有一份实现。

四种 `fine_strategy` 现在全部可用：`CoarseOnly` / `ParabolicFit` 不额外动轴；`HillClimb`（从粗扫极大值出发逐次折半试探）与 `GoldenSection`（在括住区间内黄金分割收缩）在服务层才成立，算子的离线路径对这两个仍返回 `NotSupported`，这是对的——固定样本集上它们本来就无法工作。

一个必须记住的语义：**在这一层 `fineStrategy` 决定"下一个点测在哪儿"，不决定"最终峰位怎么定"**。四种策略都把完整曲线交给 `vis.focus.autofocus` 做最终寻峰。若寻峰也按策略分叉，就会出现"同一条曲线因为配方里写了不同的策略名而得出两个不同焦面"。

`limits()` 的取舍是**夹取 + WARN**，并置 `rangeClamped`：镜头经常正好停在行程端点，而那恰恰是最需要对焦的时候，在那里失败等于"越靠近限位开关，自动对焦越不工作"。扫可达的那一段仍然有用，真焦面若在区间外，`peakOnEdge` 会说出来而不是让结果安静地撒谎。三种情况反而失败得很响：可达点少于 3 个 → `ConfigInvalid`（括住一个峰至少要 3 点）；`coarseStepMm < minStepMm` → `ConfigInvalid`（相邻采样是同一个物理位置，"曲线"纯是噪声）；未回零而设备要求回零 → `InvalidState`。只有 `fineToleranceMm < minStepMm` 是抬高而不是拒绝（它只是停止判据，分辨率就是能给出的最好答案；留得更细会造成"命令了但没动、分数不变"的死循环）。


#### P1 遗留限制的现状（已部分关闭）

`CoordinateHub` 的链路只承载 `Mat3`，而镜头畸变是非线性映射，`Mat3` 表达不了。因此 `IntrinsicCalibrator::doWriteTo()` 只在**畸变可忽略**时才注册 `Pixel↔Image`（把 9×9 网格过一遍正向畸变取最大位移，落在 `max_rms_px`、未启用验收时退回 0.5 px 之内才写入），超出则返回 `NotSupported` 且**什么都不注册**——宁可报错，也不能把恒等变换伪装成"像素已经是理想像素"。

这条限制已通过 `IVisionContext::cameraIntrinsics()` 关闭了主要部分。`vis.pre.undistort` 现在的取数优先级：

1. `intrinsics_path` 非空 → 配置期加载文件，非线性 `cv::remap`。显式配置永远优先，配方跨机器可复现。
2. 否则 `ctx->cameraIntrinsics()` 非空 → 同样的非线性 `remap`，**不需要文件**。
3. 否则退回 hub 的线性 `Pixel→Image`；链路也缺则 `CalibNotReady`。**任何情况下都不透传。**

设计要点：接口返回 `const CameraIntrinsics*`（POD）而不是 `LensModel`（含非 POD 内部，不得跨接口），算子自己用 POD 构造 `LensModel`；`nullptr` 即"未注入"，转成 `CalibNotReady`。内参存在 pipeline 而不是 `FrameMeta` 上——`stagePose` 挂在帧上是因为平台真的会在两次曝光之间移动，位姿只有绑定那一次曝光才有意义；内参恰好相反，是相机+镜头+分辨率的属性，整轮运行恒定，挂帧上等于给节拍路径上每一帧增加约 120 字节纯冗余，而且在 `run(image, nullptr)`（`frameMeta()` 为 `nullptr`）这个最需要离线复现的场合反而拿不到。

仍未关闭的两点：`CoordinateHub` 没有内参槽位，所以 `autoLoadCalibration` 恢复变换但**不恢复内参**，宿主每次加载后必须重新注入；多相机作业下访问器是「每 pipeline 一份」，与 `runJob(jobName, camera, ...)` 的单相机模型一致，真要支持一作业读两相机需要给访问器加键。两者都是公开头文件改动。

#### P4 前置缺口（四处**已修完**，保留原因分析备查）

本机与仓库内**不存在任何厂商 SDK**（`C:\Program Files` 全列、环境变量、vcpkg、`ThirdParty/`、`CMake/` 全部查过），所以 P4 仍然阻塞在"给哪家、哪些机型、许可怎么处理"这些输入上。但接口层原有四处缺口真实适配器绕不过去，其中两处 ABI 可见——头文件自己论证过"给 `ICameraDevice` 加虚函数会让已发布的适配器 DLL 失效"——**这四处已在写第一个适配器之前一次性改完**。下面保留原始缺口分析作为设计依据，每条后面标注落地结果。


- **A（ABI 硬冻结）无特性范围内省，且 `ParamSchema` 在构造期就冻结。** 真实范围要 `open()` 之后才知道，而且会动（曝光上限随帧率、`Width` 步进常为 8、增益上限随增益模式）。于是自动生成的参数界面对每台真相机都显示错误范围，`setFeature` 再把界面刚展示为合法的值拒掉。`SimulatedCamera` 掩盖了这一点，因为它的范围真的是静态的。最小修法：加 `featureInfo(key, min, max, inc)` 虚函数 + 基类非虚 `updateParamSchema()` + `SchemaChanged` 事件。同批一起做的还有两处同样 ABI 可见的：`ICommand` 类特性（`TriggerSoftware` / `UserSetLoad` / `DeviceReset`）没有执行通道；`CameraDescriptor::nativeFormat` 只有一个值而 `setPixelFormat` 收十种枚举，上层无法生成正确下拉框。
- **B（非 ABI，但每个适配器的取流路径都要重写）`FramePool` 自己持有内存，逼出逐帧 `memcpy`，而头文件写的是「零拷贝取流」。** 目前只有 `SimulatedCamera` 真零拷贝（它就地合成像素）。5 MP 单色 60 fps ≈ 300 MB/s 纯拷贝还能扛，12 MP 彩色或线扫就占主导。GenTL `DSAnnounceBuffer` 与 pylon 自定义 buffer factory 都能接受**我们的**内存，而两条好路径都缺同一个能力：**取流前暴露稳定的槽位基址**。最小修法：加 `slotCount()` / `slotBase(i)` / `slotBytes()`，并把「零拷贝」这句改成实际保证的内容。另外两条必须写进文档的既有事实：`DropOldest` 的 steal 路径是**追加**引用而不是重置计数（刻意如此，防止下游 release 释放掉生产者正在写的槽），代价是消费者可能在读一个正被覆写的槽——这是 `DropOldest` 的定义，但适配器在背压下撞上时，撕裂帧看起来会像 SDK 的 bug；`bytesPerFrame` 在 `initialize` 时固定，适配器必须按最大分辨率×最大像素字节预留，12 MP 彩色 × 8 buffer ≈ 288 MB 常驻，即使当前 ROI 很小。`SimulatedCamera` 与 `FileReplayCamera` 现在用的是两种不同策略（前者一次按最大预留，后者中途重新 `initialize`），**必须先定一种再写适配器**。
- **C（非 ABI）`doGrab` 是纯虚且同步，真实 SDK 的线程模型是反的。** 两个参考适配器都是 pull 模型：自己起线程循环调 `doGrab`。而 MVS `MV_CC_RegisterImageCallBackEx` / Daheng `GXRegisterCaptureCallback` / pylon `CImageEventHandler` / GenTL `EventGetData` 全是 push：SDK 持有线程回调你。基类**没有「一帧到了」的钩子**，于是每个厂商适配器都要重新发明同一个队列——正是 `CameraDeviceBase` 存在的意义所在。注意任何新增的基类帮手必须是**非虚**的（给导出基类加虚函数会破坏别的 DLL 中派生适配器的 vtable）；把 `doGrab` 从 `= 0` 改成有默认实现是安全的，vtable 槽位不变。
- **D** Vision 不能复用 Hardware 的 `DynamicLibrary`（它返回 `HwResult`、实现在 `QLibrary` 上，而 Vision 只链 Log + OpenCV 且 ABI 守卫禁 Qt），需要自己的 `Src/Internal/VisDynamicLibrary`。`VisError` 里 `SdkNotFound=20` / `SdkSymbolMissing=21` / `SdkVersionMismatch=22` / `PlatformUnsupported=23` 早已预留，`open()` 的契约也已强制使用它们。

**落地结果（A–D 已全部修完）**

- **A** `ICameraDevice` 一次性补了两个纯虚：`featureInfo(key, outMin, outMax, outInc)` 与 `executeCommand(key)`。**此后不再给 `ICameraDevice` 加虚函数。** 基类补非虚 `updateParamSchema(key, min, max, inc)` 与 `updateParamSchemaEnum(key, values, count)`，`VisEventType` 追加 `SchemaChanged = 19`（message 存变化的键，空串表示整表），`ParamSchema` 追加 POD 字段 `incNumber`。枚举值表是**整表覆写而非追加**——留着旧候选项等于把设不上的格式继续摆在下拉框里；若覆写后 `defaultText` 失效则改指向新的首个候选并记日志，否则 `applyDefaults` 会注入一个 `validateParams` 保证会拒的值。`incNumber` 是**建议值**，`validateParams` 仍只校验范围与枚举成员，量化的裁判是设备自己的 `setFeature`——在 L0 强制步进会改变所有既有 schema 的行为。刷新只能从配置路径（`doOpen` / `doSetFeature`）调，绝不能从采集线程调，这条约束写进了 `Impl`。A3 的多格式问题走同一套刷新机制解决，**没有动 `CameraDescriptor` 的 POD 布局**。
- **B** `FramePool` 追加非虚 `slotCount()` / `slotBase(i)` / `slotBytes()` / `acquireSlot(index, outFrame)`，零拷贝路径 A 打通：开流前把槽位基址登记给 GenTL `DSAnnounceBuffer` / pylon BufferFactory，SDK 回调说"我填了第 N 个槽"时用 `acquireSlot(N, &frame)` 闭环。`acquireSlot` **不参与任何 `PoolFullPolicy`**——槽位是 SDK 选的，没有仲裁余地，去抢它意味着 SDK 与下游持有者同时写同一块内存（那是垃圾数据而不是撕裂）；槽位不空闲时返回 `Busy` 而不是 `BufferOverflow`（前者是"池里可能还有空位，但 SDK 点名的这个还被人拿着"，后者是"整池无空位"，这个区别直接告诉现场是容量不够还是适配器 requeue 时序不对），并照规矩记一次丢帧。头文件的"零拷贝取流"改成了实际保证：**池只承诺取流路径零分配**，是否零拷贝取决于谁写这块内存。
- **B 附带修掉两个真问题**：`meta()` 原来无锁读、而 `handOutLocked` 在被征用时清空 meta，是 UB 不只是脏读——改成每槽 `FrameMeta metaSlots[2]` + `atomic<int32_t> metaActive`，写方在锁内写非活动副本再 release 翻转，`meta()` 一次 acquire 读、**完全不上锁**（给 `meta()` 加锁根本无效：调用方是在函数返回、锁已释放之后才读字段的）。`publish()` 也改成在栈上装配完整 `FrameMeta` 一次翻转，消掉了"`frameId` 已对而 `droppedBefore` 未写"的半patch窗口。另外 `Block` 策略下 `shutdown()` 唤不醒停在 `cv.wait` 的线程（等待谓词里没有 stopping 标志），停流会挂——加 `stopping` / `waitingAcquires` / 独立 `drainCv`，被唤醒者返回 `InvalidState` 而不是 `GrabTimeout`（后者会让适配器以为相机不出图而重试）。用**独立** CV 是因为 `recycle()` 每帧都 `notify_one`，两类等待者混在一把 CV 上会丢唤醒。
- **C** `doGrab` 从 `= 0` 改成有默认实现（vtable 槽位不变，ABI 安全），默认实现从基类槽位取帧；新增非虚 `submitFrame(IFrameBuffer*)` 供厂商回调在 SDK 线程上调用，一个槽位同时喂 sink 与后续的同步 `grab()`。**没有 `FrameMeta` 参数**——meta 已由 `publish` 挂在帧上并且只有 `publish` 会算 `droppedBefore`，再传一份就是第二个真相来源。线程纪律：先 `addRef` 再插入、sink 回调**在锁外**发（sink 可能反入设备）、被顶掉的帧在锁外 release（`release()` 会重入池的锁）、**任何失败路径都消费掉这个引用**（厂商回调没有合理的错误处理，让它判断"我还持有吗"必然漏或双放）。槽位深度是 1、新的顶掉旧的：池本身已提供 N 级缓冲，再叠一层 N 级队列会让同步 `grab()` 返回任意旧的帧，而 `grab()` 的语义是"现在给我一帧"；被顶掉记 `FrameDropped` 并说明 sink 已经收到过。`doGrab` 默认实现刻意区分两种失败：槽空**且在取流** → `GrabTimeout`，槽空**且未取流** → `InvalidState`——"没人在生产"和"帧还没到"在现场是完全不同的诊断。
- **C 的一个判断**：两个参考适配器**都没有**改走 push 路径。`FileReplayCamera` 的"SDK"是文件系统，它不回调任何人，改过去只是把帧塞进一个自家线程里的队列，买不到真实性；更糟的是它在 `SoftwareTrigger`/`SingleShot` 模式下**根本不起线程**，帧是在 `doGrab` 里同步解码的，把 `doGrab` 交给基类会让 `grab()` 卡在永远空的槽上。改用测试专用适配器 `PushModelCamera` 验证 push 路径：它故意不覆写 `doGrab`，回调从设备不拥有的线程走完整的厂商路线（`acquire → mutableView → memcpy → publish → submitFrame`），**测的是基类里那份唯一的实现**而不是适配器自己的代码。
- **D** 新增 `Src/Internal/VisDynamicLibrary`（内部头，不进 `Include/`，与 `VisionLog.h` 同理）：`setSearchNames(primary, fallback)` / 幂等 `load()` / `bind<Fn>(fn, "symbol")` 由目标变量推导签名 / `setWindowsOnly()` / `lastResult()` 点名缺失符号。只用 `LoadLibraryW`，UTF-8 路径过 `MultiByteToWideChar(CP_UTF8, MB_ERR_INVALID_CHARS, ...)`——带 `MB_ERR_INVALID_CHARS` 是刻意的：配置的路径若其实是 GBK，转换失败并报"path is not valid UTF-8"，而不是悄悄替成 U+FFFD 再误报"SDK not found"。`loadedPath()` 走 `GetModuleFileNameW` 回程，日志打的是 OS 解析出的完整路径——装了多个 SDK 版本时"到底加载了哪个文件"是唯一有用的那行。析构**不** `FreeLibrary`（与 Hardware 版同样的取舍：厂商 SDK 有内部采集线程和内核句柄，进程退出路径上卸掉它们的代码会让那些线程跳进未映射内存，崩在没有符号的地址上），需要提前释放的显式调 `unload()`。**一处仍未覆盖**：`SdkVersionMismatch = 22` 加载器天生产不出来（它只能区分"文件加载不了"和"符号不存在"），"加载成功、符号齐全、但版本不对"必须调厂商自己的版本查询接口比对，是逐适配器的事。

#### 首个非仿真适配器：`UvcCamera`（以及它暴露出的设计问题）

`Include/Vision/Device/Vendors/UvcCamera.h` + `Src/Device/Vendors/UvcCamera.cpp`，建在 `cv::VideoCapture` 上，**零新依赖**（OpenCV videoio 本来就在）。它的价值一半是支持 USB 相机，另一半是**在一个不是我们合成的设备上验证整条设备层契约**。

关键取舍：

- **能力位声明为 `CameraCapability::None`，一个都不declare。** 触发、ROI、Binning、AutoExposure、Gain、WhiteBalance、ChunkTimestamp、FocusControl、LightControl 逐条都有具体理由。举两个：把 `CAP_PROP_FRAME_WIDTH/HEIGHT` 当 ROI 卖是错的，它选的是整帧模式而不是开窗传感器；`CAP_PROP_POS_MSEC` 对相机是流位置而不是曝光时刻的设备时钟，拿它做飞拍时序会错得极难发现。不声明的好处是基类的能力闸自动拒掉 `startStream(HardwareTrigger)`，适配器一行代码都不用写。`queryInterface(TriggerControl/FocusControl/LightControl)` 全返回 `nullptr`。
- **只有 `FeatureKey::kFrameRate` 诚实可映射，且只读。** 写 `CAP_PROP_FPS` 会重新协商流模式、画幅可能随之改变，而池是定容的，所以允许写就是允许运行期越界。改帧率意味着重开。`featureInfo` 在后端不报帧率时返回 `NotSupported` 而不是一个看起来合理的范围。
- `kExposureUs` / `kGainDb` / `kExposureAuto` / `kGainAuto` 一律 `NotSupported` 并给出可操作的消息。原始值走**明确带后端前缀**的 `uvc.raw.exposure` / `uvc.raw.gain` / `uvc.raw.auto_exposure`，文档写明单位由驱动定义。这三个键**刻意不声明 `ParamSchema`**，正是为了让基类的 schema 回退找不到范围、只能回答 `NotSupported`——声明一个 Double schema 等于把我编的范围变成权威。没有任何一张按相机的换算表。
- 走 push 路径，**不覆写 `doGrab`**：自有线程阻塞在 `read()`，然后 `acquire → mutableView → 行拷贝 → publish → submitFrame`。`cv::VideoCapture` 持有自己的内部缓冲，这里的拷贝无法避免也不假装避免。背压选 `DropNewest` 而不是 `DropOldest`：后者会把撕裂帧交给消费者，而算子拿撕裂图算出一个错结果，比记一次丢帧糟得多。

**这个适配器暴露出的设计问题**（都不是它自己能绕的）。第 1、4 条已修 —— 它们是 GenTL 适配器必然第一个撞上的两条，所以先修；其余四条记在这里等后续处理：


1. ~~`updateParamSchema*` 的收窄是单向的、没有恢复途径~~ —— **已修**。基类在 `Impl` 里存一份构造期快照（`schemaBaseline`），新增非虚 `resetParamSchema(key)` / `resetAllParamSchemas()`，并且 **`close()` 自动整表回正**（设备已经不在了，构造期值是唯一诚实的状态；让适配器记得自己回正正是这个陷阱本身）。`open()` 的失败路径也回正 —— `doOpen` 是一个键一个键收窄的、没有事务，收窄了分辨率再在像素格式上失败会留下半收窄的表，而设备此刻已经是 `Closed`；GenTL 适配器要读十几个 GenICam 节点，几乎必然撞上。快照由一次性的 `ensureSchemaBaseline()` 在 `open()` 开头与两个 updater 开头取（`addParamSchema` 按契约只在构造期调用，而且必须如此：`paramSchemaAt` 交出的是指向 vector 的指针，构造后 `push_back` 会让已交给界面的指针失效——所以这两个入口跑到时表一定已经定型，且收窄只可能发生在 `doOpen` 及更晚，快照抓不到被收窄的值）。恢复**按键查找而不是按下标**，构造函数里插入一个 schema 不会把 A 的范围写到 B 上。恢复只覆盖收窄 API 能改的字段（`minNumber`/`maxNumber`/`incNumber`/`enumValues`/`enumCount`/`defaultText`），不整体拷贝结构体——`label`/`description`/`type`/`required` 运行期从不改，拷回去等于悄悄抹掉合法改动。**`defaultText` 必须一起恢复**：收窄枚举时若旧默认值落表外会被改指向新首项，只恢复候选表不恢复默认值，`applyDefaults` 就会注入一个 `validateParams` 保证拒绝的值，现象是"我一个参数都没设，`open` 却说我参数非法"。`UvcCamera::widenSchemaAfterClose()` 及其重复的静态数组已删除，`FileReplayCamera` 的 `pixel_format` 隐患免费消失（有用例证明）。

2. **没有办法表达"未知"。** `updateParamSchema` 只收 `(min, max, inc)`。后端不报帧率时，要么留着构造期的粗范围（界面会当真），要么写一个退化区间。现在是留着范围、同时让 `doFeatureInfo` 回答 `NotSupported`——也就是 schema 与 `featureInfo` 对这个键**刻意不一致**。范围查询契约有办法表达"不可知"，`ParamSchema` 没有。
3. **`doFeatureInfo` 的消息恰好在最需要它的地方被丢掉。** 基类把 `doFeatureInfo` 返回的 `NotSupported` 当作"适配器没意见，回退到 schema"，于是"`CAP_PROP_EXPOSURE` 是 log₂ 秒标度，请用 `uvc.raw.exposure`"这句解释被替换成通用的"key 'x' is not supported by this device"。适配器唯一能解释**为什么**某个键不可映射的地方，正是解释传不出去的地方。`setFeature`/`getFeature` 会转发消息（基类只是委托），所以现在只能在那两处重复写一遍解释。基类应当区分"没意见，用 schema"和"确定不支持，这是原因"。
4. ~~`submitFrame` 没有"未在取流"的闸~~ —— **已修**，改成显式的**接收窗口**（`std::atomic<bool> acceptingFrames`）而不是从状态枚举推断。开关次序是这条修复的全部内容：

   - **在 `doStartStream()` 之前开窗**：MVS 的 `MV_CC_RegisterImageCallBackEx` + `MV_CC_StartGrabbing`、GenTL 的 `DSStartAcquisition` 都可能在启动调用**内部**就投递第一个回调。放在之后开窗会丢掉每条流的第一帧真实图像，现象是"`startStream` 之后第一次 `grab()` 总是超时"，极难诊断且容易错怪相机。`doStartStream()` 失败则关窗并清空。
   - **在 `doStopStream()` 之前关窗**：MVS / 大恒 / pylon / GenTL 没有任何一家承诺"停止调用返回时没有回调在飞"，而那个线程是它们的。先关窗意味着与厂商停流赛跑的回调被拒绝，而不是排进槽里活到下一条流。
   - **`startStream` 里也要清空一次**（这条不是防御性的，是必需的，而且是另一扇门）：采集线程调 `raiseFault` 后状态变 `Fault`，`stopStream` 会提前返回 `Ok` 而**不**关窗、**不**清空；`reset()` → `Open` → `startStream()` 就会把故障前那一帧交给第一个 `grab()`。同理 `close()` 也要显式关窗清空，否则 `Fault`/`Open` 状态下 `close()` 走不到 `stopStream` 的关窗点，回调能在清空之后重新填满槽位，让 `doClose` 里的 `framePool().shutdown()` 以"仍有帧在用"失败。
   - 被拒的帧仍然**先 `release()` 再返回** `InvalidState`（与 `doGrab` 既有的划分一致：`InvalidState` = 没有流在跑，`GrabTimeout` = 在跑但还没到）。计数走内部 `submitOutsideWindowTotal`（`PoolCore::slotBusyTotal` 的先例，不动任何公开 POD 结构），加一条 `visLogDecade` 收敛的 WARN。**刻意不发 `FrameDropped`**：那个事件的含义是"这条流内部丢了一帧"，把流外的帧算进去会污染丢帧率。
   - 旧的 `state == Closed` 闸是**删掉**而不是并存 —— 窗口严格覆盖它（开窗蕴含 `startStream` 成功，`close` 必定关窗），而"两个闸表达同一条规则"正是后人删错那一个的方式。

   顺带把 push 路径上"从回调线程无同步读 `state`"的洞补了：`submitFrame` 不再用 `state` 做任何控制决策，仅在收敛后的日志里读它取名字。其余位置（`isStreaming` / `requireOpen` / `requireNotStreaming` / `doGrab` / `setState`）仍是无同步读写，那是既有实践且调用方都在宿主线程，改它要动类里每一处状态迁移，不作为一次 bug 修复的副作用来做。

5. **`FrameDropped` 事件分不清两件完全不同的事。** 槽位顶替（`value = 1.0`，sink 已经收到过，什么都没丢）与池拒收（一张图真的没进系统）都是 `VisEventType::FrameDropped` + `value = 1.0`。消费者无法区分"我们在丢产品图"和"只是 `grab()` 跟不上"。UVC 适配器只能自己另记一个 `poolFullCount()`。事件上加一个判别字段就能解决。
6. **"不做每帧工作"通过这条路径其实做不到。** `submitFrame` → `dispatchFrame` 对每一帧都发 `FrameArrived` 事件，发在采集线程上，没有关闭开关。60 fps 且挂了 UI 事件 sink 时，那是每秒 60 次额外的 sink 回调，适配器无权干预。

剩余的 P4 次序：**下一步是 GenICam/GenTL 通用适配器**（海康、Basler、大恒都出 GenTL producer，一个适配器覆盖三家）→ 只在 GenTL 确实不够时才写厂商原生。已完成的 UVC 适配器（`cv::VideoCapture`，零新依赖）是这条路上的第一步，它真实跑通了回调/拷贝/线程这条路径，见上一节。

## 10. 构建与工程约定

### 10.1 独立构建（脱离主程序）

Vision 必须能**脱离主程序单独编译**，同时**继续复用主仓的配置**——两者不矛盾：

```powershell
# 配置（生成器按本机实际情况填）
cmake -S Vision -B Vision/build -G "Visual Studio 18 2026" -A x64
# 带测试
cmake -S Vision -B Vision/build -G "Visual Studio 18 2026" -A x64 -DBUILD_VISION_TESTS=ON
# 构建
cmake --build Vision/build --config Release
# 跑测试
.\Vision\build\bin_Qt6\Release\VisionTests.exe
```

复用的主仓配置（不另立一套，避免两份配置漂移）：

- `Config.cmake` —— Qt / vcpkg / 模块开关等全局配置，独立入口 `Vision/CMakeLists.txt` 直接 `include`；
- `CMake/SanYiPaths.cmake` —— 依赖模块的源码路径。独立构建时用 `${SANYI_LOG_DIR}` 定位 Log，**不写 `../Log/Log` 这类相对路径**，否则目录结构一调整就静默失效；
- `CMake/Utils.cmake` —— `sanyi_add_shared_library` 统一创建 DLL，保证独立构建与主工程构建出来的 Vision.dll 在导出宏、CRT、可见性、PDB 策略上完全一致。

依赖的其它 DLL 以源码方式加入本次构建，产物与 `Vision.dll` 落在同一输出目录，因此独立构建出的 DLL 可直接运行、直接被测试加载：

- `Log`（源码，来自 `SANYI_LOG_DIR`）
- `OpenCV`（vcpkg，仅 `Src/` 内部使用）

刻意**没有**引入的依赖：Qt、Hardware、Engine、UI。Vision 只硬依赖 Log 与 OpenCV，这是它能独立构建的根本原因；任何要往 Vision 里加 Qt 或上层模块依赖的改动，都会同时破坏独立构建与跨 DLL 插件承诺。

唯一的**可选**依赖是 ZXing-C++ 2.3.0（`option(VISION_WITH_ZXING)`，默认跟随 `find_package` 的发现结果），只补读码能力；没装照样配置、构建、链接，两个读码算子退回点名依赖的 `NotSupported`。可选依赖必须保持这个形状：**缺失时降级到明确报错，而不是降级到"编译过了但功能悄悄没了"**。`VISION_WITH_ZXING=ON` 而库不在时是配置期 `FATAL_ERROR`，因为"要求开却静默关"是当年 `HAVE_TESSERACT` 的确切失败方式。

独立构建下 `BUILD_VISION_TESTS` 默认 **OFF**（只想拿一个 DLL 的人不该被 GTest 依赖卡住）；主工程里跟随 `BUILD_VISION` 默认 **ON**。

### 10.2 ABI 守卫

`sanyi_vision_abi_guard()` 在配置期扫描 `Include/Vision/**`（豁免 `Legacy/`），命中禁用模式即 `FATAL_ERROR`。

为什么必须由构建系统强制：这类违规**加进去的时候不会报任何错**，只会在某个客户用不同编译器构建相机适配器插件时炸掉，那时已经很难回溯是哪次提交引入的。旧 Vision 就是这么烂掉的——头文件里写 `cv::Mat` / `std::string`，最后只能在头注释里写"不承诺跨 DLL ABI"来承认失败。

实现上有一个关键点：**必须先剥掉注释再匹配**。v2 头文件的注释里大量出现"不要用 `std::string`""禁用 `dynamic_cast`"这类说明文字，直接对原文匹配会把说明本身报成违规。

临时放行用 `-DVISION_ABI_GUARD=OFF`，但不要提交这个配置。

### 10.3 编译警告策略

`C4251`（导出类含非导出的 STL 成员）**只对 `Src/Legacy/*.cpp` 关闭**，不全局关闭：

C4251 恰恰是"公开头文件出现了不该跨 DLL 的类型"的编译器级警报，v2 代码必须继续受它保护。Legacy 头文件把 `std::string` 放进了导出结构体，会刷一片警告，但那部分已冻结、不再演进，因此只对它豁免。

### 10.4 日志

Vision 通过 `Src/Internal/VisionLog.h` 接入 Log 模块。封一层的三个理由：

1. **收敛依赖面**：整个 Vision 只有这一个文件 `#include "Log/SyLogger.h"`；
2. **统一前缀**：所有消息自动加 `[Vision] `，总日志里可按模块筛；
3. **可裁剪**：`VISION_HAS_LOG=0` 时全部退化为空操作，Vision 可在不链接 Log 的环境下编译（日志不应变成新的硬依赖）。

规约：

- **日志文本一律英文，代码注释一律中文**；
- `VIS_LOG_RESULT(level, context, result)` 把 `VisResult` 的三要素一次打全（错误名 + 厂商原生码 + 描述）。缺任何一样都会导致"现场只能再跑一次"：缺错误名不知道归哪类，缺 vendorCode 无法对厂商文档，缺 message 不知道是哪台设备哪个参数；
- **日志不得进入热路径**（逐帧 grab、逐点坐标变换）。可能高频的位置必须做频率收敛，用 `visLogDecade(count)`：只在第 1、10、100… 次打一条。丢帧、事件队列溢出、过期句柄、坐标系缺链路这四类问题一旦发生就会连续发生上万次，每次一行会直接吃掉产线节拍，并把首次那条有用记录淹掉；精确数值一律由各自的 `stats()` 提供，日志只负责提醒去看 `stats()`。

当前落点（59 处）：设备 open/close/取流与状态迁移、帧池初始化与丢帧、回放解码失败（**带出文件路径**）、坐标变换登记与缺链路、标定结论与残差、流程 build/逐步失败/结束（含最慢步骤）、服务初始化与句柄拒绝、C ABI 边界异常。
