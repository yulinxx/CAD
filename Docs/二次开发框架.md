## 1. 结论摘要

### 1.1 总体判定

> **当前架构"够做白标定制"，但"不够做二次开发平台"。**

这两件事经常被混为一谈，但工程要求完全不同：

| 目标 | 交付物 | 客户能做什么 | 现有架构 |
| --- | --- | --- | --- |
| **白标定制**（已达成） | 换一个品牌、改菜单布局、加几个面板 | 换皮 + 摆 UI | ✅ 已具备 |
| **二次开发**（未达成） | 一套可长期依赖的 SDK | **写业务逻辑**：读写图元、注册命令、响应事件、扩展格式、批处理 | ❌ 关键能力缺失 |

具体地，现有三条扩展通道都存在**结构性上限**：

| 通道 | 现状 | 结构性上限 |
| --- | --- | --- |
| **C++ 客户插件** | `IClientUiPlugin` 只能注册 QWidget 面板 | **只能做"展示"**，不能读写场景、不能注册命令、不能订阅事件 |
| **JSON 配置** | 菜单/工具栏/Dock/快捷键/状态栏/右键菜单 | **只能做"布置"**，配置项是封闭枚举，不是可扩展 schema |
| **Python 绑定** | `Document` + 6 个值类型 | **只能做"离线几何"**：`open`/`save` 未实现，无图层/撤销/选择/命令/事件 |

### 1.2 分维度评分

工业级 SDK 的判据见 §3。评分：**5 = 可直接交付客户并长期依赖；1 = 完全缺失**。

| 维度 | 现状 | 目标 | 差距 |
| --- | :---: | :---: | --- |
| 稳定公共 ABI（跨编译器/跨 CRT） | ⬜ 1 | 5 | **G1 阻塞** |
| 插件能力广度（命令/数据/事件/格式） | 🟨 2 | 5 | **G2 阻塞** |
| Python API 完备度 | 🟨 2 | 5 | **G3 阻塞** |
| 事件与通知机制 | ⬜ 1 | 5 | G4 |
| 跨平台二次开发可行性 | 🟨 2 | 5 | **G5 阻塞** |
| SDK 打包与分发 | 🟨 2 | 5 | G6 |
| 版本治理与兼容承诺 | 🟨 2 | 5 | G6 |
| 文档与示例 | 🟨 2 | 5 | G7 |
| 配置 schema 版本化 | ⬜ 1 | 4 | G8 |
| 插件隔离与崩溃归属 | 🟨 2 | 4 | G9 |
| 商业化（授权/许可/条款） | 🟨 2 | 4 | G10 |
| 测试与质量门禁 | 🟨 2 | 4 | G9 |

**综合：18/60 ≈ 30%**。距"可交付工业级二次开发平台"约需 **P0+P1 两个阶段**（约 12~16 人周，不含 SDK 文档与示例）。

### 1.3 三句话行动纲领

1. **先立 ABI，再谈功能**：把 `Engine2D/Engine3D/UICommon` 内部 C++ 接口与"对外 SDK"彻底分开，新建 `sy_abi` 纯 C 门面层。现有 C-ABI 风格约定已把规范写好，缺的是**实现与分发**。
2. **插件接口从"面板"扩到"能力"**：`IClientUiPlugin` v2 增加命令注册、场景访问、事件订阅、格式扩展四个 sink，让客户插件能真正干业务。
3. **跨平台二次开发的正确答案是"SDK 而非插件"**：客户不要编译 C++ DLL（会被 MSVC/Qt/CRT 锁死），而是写 **Python 脚本 / 配置 / 独立进程程序**，通过 SDK 调用主程序。这需要在主程序内**内嵌 Python 运行时**，而不是当前的子进程 worker。

### 2.2 通道 A：C++ 客户插件（现状详解）

```text
<AppDir>/plugins/clients/<clientId>/*.dll
$SANYI_CLIENT_PLUGIN_DIR/*.dll          # 开发调试，优先级最高
```

宿主加载流程（`UiClientPluginHost::loadForClient`）：

```text
QLibrary 打开 DLL
   ↓ resolve "createClientUiPlugin"  → IClientUiPlugin*
   ↓ resolve "destroyClientUiPlugin"
   ↓ plugin->clientId() 匹配当前客户（或返回空串表示通用）
   ↓ plugin->registerPanels(sink)
       └ sink.registerPanel(id, factory)  → 存入 UiPanelRegistry
   ↓ UiLayoutBuilder 读 JSON 的 widgetType → registry.createPanel(id, parent)
```

**插件接口全文**（`Main/Src/UI/ClientConfig/IClientUiPlugin.h`）：

```cpp
class IClientUiPlugin {
public:
    virtual QString id() const = 0;
    virtual QString clientId() const { return {}; }
    virtual void registerPanels(UiPanelRegisterSink& sink) { Q_UNUSED(sink); }
};
```

**可做的**：在 Dock / 状态栏里显示自定义 QWidget。
**不可做的**：

- ❌ 读写当前文档的图元（拿不到 `Eg::SceneManager`）
- ❌ 注册菜单命令（`ICommandPlugin` 的 sink 是空壳，且仅 3D 接线，见白标方案 §5.3）
- ❌ 响应选择变化、文档修改、撤销栈变化
- ❌ 参与 Undo/Redo 事务
- ❌ 扩展导入/导出格式
- ❌ 弹模态对话框后拿到用户选择结果（面板工厂只返回 widget）

模板插件（`Clients/_template/src/ClientPlugin.cpp`）恰好印证了这一点——它创建一个 `QLabel`，**没有任何业务逻辑**。

### 2.3 通道 B：JSON 配置 + 品牌（现状详解）

配置结构（`UiClientConfigBase.h`）覆盖：

| 节 | 结构体 | 说明 |
| --- | --- | --- |
| `meta` | `UiConfigMeta` | `clientId/clientName/version/extends` |
| `menus` | `MenuDef` | 树形菜单（Action/SubMenu/Separator 三态 variant） |
| `toolBars` | `ToolBarDef` | 工具栏 + 位置 + 归属工作台 |
| `docks` | `DockDef` | Dock 面板 + 位置 + `widgetType` |
| `shortcuts` | `ShortcutDef` | 命令 → 快捷键 |
| `statusBar` | `StatusBarDef` | 状态栏槽位（Left/Permanent 对齐） |
| `contextMenus` | `ContextMenuDef` | 右键菜单 + `dynamicSections` 动态段 |
| `themeStyle` | `QString` | 主题标识或 QSS 路径（**当前解析了但无消费者**） |

这套模型的工程成熟度高（继承合并、字段校验、feature 门控、可见域 `shared/2D/3D`、自检），**但它是封闭的**：

- 菜单项类型是 C++ 枚举 `MenuItemType`，无法在不改主程序的情况下引入新类型；
- `commandId` 指向主程序内置命令，客户**无法注入新命令**；
- 没有 `schemaVersion`，无法判断配置文件是旧版还是新版。

### 2.4 通道 C：Python 绑定（现状详解）

```
PythonHost/sanyi/__init__.py        ← Python 包门面
    └ from . import _sanyi_core     ← pybind11 扩展（PyBindCore 构建产物）
         └ PyFacade::DocumentFacade ← 内部持有 Eg::SceneManager
```

`PyBindCore` 的边界设计**方向是对的**——`FacadeTypes.h:3-5` 明确：

> FacadeTypes.h 定义 PyFacade 值类型，用于隔离 Engine C++ 类型与 Python 绑定层。
> Eg::EntityId / Eg::EType 仅在内部类型转换中使用，不直接暴露到 Python。

Python 侧**永远拿不到** `SyEntity*` / `SceneManager*`，只拿 `EntityRef(id)` 句柄和 DTO 快照。这是正确的做法，工业级 SDK 也应如此。

**但覆盖面极小**（`py_types.cpp` + `py_document.cpp` 全量）：

```python
class Vec2, BBox2, EntityRef
class Document:
    create() / open()        # open 未实现
    add_point / add_line / add_circle
    remove_entity / query_box
    export_snapshot / apply_changes
    entity_count / get_entity
    save() / close()          # save 依赖未实现的 FileIO 集成
```

**没有**：图层、选择集、撤销重做、命令执行、文档格式、单位/坐标系、参数化约束、事件回调、错误码体系（只有 `last_error` 字符串）。

### 2.5 三条通道的能力边界汇总

| 客户需求 | L0 配置 | L1 C++ 插件 | L2 Python |
| --- | :---: | :---: | :---: |
| 换品牌/logo/主题 | ✅ | ❌ | ❌ |
| 改菜单/工具栏布局 | ✅ | ❌ | ❌ |
| 加一个显示数据的面板 | ✅（需 DLL） | ✅ | ❌ |
| 加一个业务命令 | ❌ | ❌ | ❌ |
| 读写图元 | ❌ | ❌ | 🟡 仅离线 |
| 响应选择/文档事件 | ❌ | ❌ | ❌ |
| 扩展导入导出格式 | ❌ | ❌ | ❌ |
| 批处理自动化 | ❌ | ❌ | 🟡 仅离线 |
| 参与 Undo 事务 | ❌ | ❌ | ❌ |

## 3. 工业级判据与逐条自评

### 3.1 判据清单

一套能长期依赖、跨平台、可商业分发的二次开发平台，必须满足：

| # | 判据 | 判定方式 |
| --- | --- | --- |
| **J1** | **ABI 稳定**：客户用任意编译器/任意 CRT 都能链接，不因主程序升级而重编 | 用 GCC/Clang 编译的 `.so` 能被 MSVC 构建的主程序加载并正常调用 |
| **J2** | **能力完备**：能读写数据、注册命令、订阅事件、扩展格式 | 客户能独立实现一个"批量圆角标注"功能插件 |
| **J3** | **版本协商**：运行时能问出主程序支持哪些能力 | `sy_abi_Capabilities()` 返回能力位图 |
| **J4** | **前向兼容**：主程序升级后旧插件不崩 | 插件用 v1 SDK 编译，能在 v2 主程序上运行 |
| **J5** | **跨平台一致**：同一份 SDK 源码能在 Win/mac/Linux 编译运行 | CI 矩阵三平台编译同一 SDK 示例 |
| **J6** | **隔离与归属**：插件崩溃不拖垮主程序，日志能区分归属 | 插件段错误后主程序仍可用，崩溃报告标注插件 ID |
| **J7** | **错误可诊断**：失败有明确错误码和可读消息，不是 `bool` | 全部 API 返回 `sy_status` 枚举 + `sy_status_text()` |
| **J8** | **线程模型明确**：哪些 API 必须在主线程调用，写在文档和头文件里 | 头文件标注 `SY_THREAD_UI` |
| **J9** | **SDK 可独立获取**：客户只拿 SDK 就能编译，不下载整个源码仓库 | 一个 zip：`include/ lib/ cmake/ samples/ docs/` |
| **J10** | **文档齐全**：概念指南、API 参考、示例、迁移指南 | 客户不看源码能完成开发 |
| **J11** | **版本治理**：主程序版本、SDK 版本、插件兼容矩阵清晰 | 文档化兼容矩阵 + 自动校验 |
| **J12** | **商业条款**：许可协议、第三方库许可（SBOM）、支持策略 | LICENSE + SBOM + 支持 SLA |

## 4. 缺口清单与根因分析

### G1 稳定公共 C ABI 层缺失【阻塞】

**现象**：所有对外可见的模块（`EngineCommon/Engine2D/Engine3D/EnginePersistence/UICommon/UI2D/UI3D`）都是"内部 C++ DLL"，公共头大量暴露 STL：

```cpp
// Engine/2D/Include/Engine2D/Engine2DAPI.h:3-4
// 模块级 ABI 声明：Engine2D 为内部 C++ DLL，公共头大量使用 STL 类型
// （std::vector/std::string/std::unique_ptr/std::function/std::unordered_map），
// 仅限同编译器/同 CRT 体系内部使用，不承诺跨编译器稳定 ABI。
```

**根因**：这些模块是**主程序的内部实现**，从来不承担"对外契约"职责；`DLL制作标准与现状.md` §3.1 明确"跨 DLL 接口只用必要函数"，但那是**主程序内部 DLL 之间**的约束，不是**对客户**的约束。客户要的是"我写一个插件，编译进我的工具链"，这需要第三条约束。

**具体后果**：

| 场景 | 后果 |
| --- | --- |
| 客户用 MinGW/GCC 编译插件 | C++ 标准库 ABI 不同（libstdc++ vs MSVC STL）→ 传 `std::string` 跨界直接崩 |
| 客户用 `/MT` 编译，主程序用 `/MD` | 堆分配/释放跨 CRT → 释放后崩溃（Windows 上最难查的一类 bug） |
| 客户 Qt 版本与主程序不同 | 链接失败，或 ABI 布局差异导致 `QWidget` 虚表错位 |
| 主程序升级 Qt 大版本 | 所有插件必须重编 |

**必须做**：新建 `SyAbi` 模块，对外只暴露 C ABI。

### G2 插件能力只有"面板"【阻塞】

**现象**：`IClientUiPlugin` 唯一可覆写的方法是 `registerPanels`。

**旁证**：既有的通用命令插件接口 `UI/Common/Include/UI/Plugin/ICommandPlugin.h` 已经预留了 2D/3D 共用的注册入口，但两个 sink 是**纯空壳**：

```cpp
class ICatalogRegisterSink  { public: virtual ~ICatalogRegisterSink()  = default; };  // 无方法
```

**必须做**：把这两个 sink 做实，并扩成 4 能力（命令/场景/事件/格式）。

### G3 Python API 单薄 + 进程模型错位【阻塞】

**现象 A（单薄）**：绑定类型仅 6 个，`open`/`save` 未实现。

**现象 B（错位，更根本）**：`PythonHost` 是**子进程 worker**。

```text
┌────────────────────┐         ┌────────────────────────┐
│  GUI 主进程         │  pipe   │  PythonHost 子进程     │
│  (SceneManager 在这)│◀───────▶│  (Python 解释器在这)   │
└────────────────────┘         └────────────────────────┘
        场景数据在这里                  脚本在这里
```

Python 进程里的 `Document` 持有的是**它自己创建的** `Eg::SceneManager`（`DocumentFacade.h:56`），**不是 GUI 里用户正在编辑的那份文档**。后果：

- ❌ 脚本改不了 GUI 里的当前文档
- ❌ 脚本无法触发 GUI 刷新
- ❌ 脚本无法弹模态对话框做交互式拾取
- ❌ 脚本无法响应选择变化
- ✅ 只能做**离线批处理**（读文件 → 算 → 写文件）

**这是定位问题，不是功能缺失问题。** 必须先决定 Python 二次开发的定位：

| 定位 | 能力 | 实现 |
| --- | --- | --- |
| **离线批处理**（现状） | 跑批任务、处理文件 | 子进程 worker（保持现状） |
| **内嵌脚本**（新增） | 操作当前 GUI 文档、交互、事件 | 主进程内嵌 CPython |
| **两者都要** | — | 内嵌为主，worker 复用为"隔离执行环境" |

**工业级 CAD（如 AutoCAD LISP、ZWCAD .NET、Onshape App）一律是"内嵌 + 可选外部进程"双轨**，因为客户真正要的是"在软件里跑我的逻辑"。

## 6. L1 公共 C ABI 层规范（sy_abi）

### 6.1 设计原则

继承 `C-ABI风格约定.md` 的全部约定，并追加针对"对外 SDK"的强化：

| # | 原则 | 说明 |
| --- | --- | --- |
| 1 | **纯 C99** | 公开头不出现任何 C++ 构造；`extern "C"` 仅作为 `#ifdef __cplusplus` 包装 |
| 2 | **零第三方依赖** | 不依赖 Qt、不依赖 STL、不依赖 STL 的 `stdint.h` 之外的任何东西 |
| 3 | **不透明句柄** | 所有跨边界对象用 `typedef struct sy_xxx_s* sy_xxx;` |
| 4 | **POD 结构 + `structSize`** | 每个结构体首字段是 `uint32_t structSize`，宿主按 `structSize` 决定读多少字段（前向兼容） |
| 5 | **错误码枚举** | `sy_status`（`int32_t` 底层），成功 = 0 |
| 6 | **静态存储期字符串** | 只读、不释放；动态消息走 `sy_get_last_error()` |
| 7 | **能力协商** | 运行期查能力位图，而非编译期版本号硬编码 |
| 8 | **回调签名固定** | 回调 typedef 固定，不允许客户自定义结构体布局 |
| 9 | **线程亲和性标注** | 每个 API 标注 `SY_THREAD_UI` / `SY_THREAD_ANY` / `SY_THREAD_MAIN_ONLY` |
| 10 | **符号可见性统一** | Windows `__declspec(dllexport)`，ELF/Mach-O `visibility("default")`（与 `Engine/EngineAPI.h` 一致，**不按 EXPORTS 分叉**，否则跨 DLL `dynamic_cast` 静默失败） |

### 6.2 头文件组织

```c
/* sy_abi.h — 总入口 */
#ifndef SY_ABI_H
#define SY_ABI_H

#include <stdint.h>
#include <stddef.h>

#ifdef __cplusplus
extern "C" {
#endif

#if defined(_WIN32)
    #if defined(SY_ABI_EXPORTS)
        #define SY_ABI_API __declspec(dllexport)
    #else
        #define SY_ABI_API __declspec(dllimport)
    #endif
#elif defined(__GNUC__) || defined(__clang__)
    #define SY_ABI_API __attribute__((visibility("default")))
#else
    #define SY_ABI_API
#endif

/* 版本 */
#define SY_ABI_VERSION_MAJOR 1
#define SY_ABI_VERSION_MINOR 0
#define SY_ABI_VERSION_PATCH 0
#define SY_ABI_MAKE_VERSION(major, minor, patch) \
    (((uint32_t)(major) << 16) | ((uint32_t)(minor) << 8) | (uint32_t)(patch))

#ifdef __cplusplus
}
#endif
#endif /* SY_ABI_H */
```

> **注意**：这里刻意**不使用** `ENGINE_API` 那套"按 EXPORTS 分叉"的做法在 Linux/macOS 上——`Engine/EngineAPI.h:9-23` 已经踩过并记录了这个坑（弱符号无法合并 → 跨镜像 `dynamic_cast` 返回 nullptr）。`SY_ABI` 必须遵守。

### 6.3 句柄与生命周期

```c
/* 不透明句柄 */
typedef struct sy_document_s*  sy_document;
typedef struct sy_layer_s*     sy_layer;
typedef struct sy_transaction_s* sy_transaction;

/* 宿主拥有的实体 ID（不是指针，跨进程/跨镜像安全） */
typedef uint64_t sy_entity_id;
#define SY_ENTITY_ID_INVALID ((sy_entity_id)0)

/* 实体类型 —— 与 Engine 内部 EType 解耦，只做语义子集 */
typedef int32_t sy_entity_type;
#define SY_ENTITY_TYPE_UNKNOWN   0
#define SY_ENTITY_TYPE_POINT      1
#define SY_ENTITY_TYPE_LINE       2
#define SY_ENTITY_TYPE_CIRCLE     3
#define SY_ENTITY_TYPE_ARC        4
#define SY_ENTITY_TYPE_POLYLINE   5
#define SY_ENTITY_TYPE_POLYGON    6
#define SY_ENTITY_TYPE_BEZIER     7
#define SY_ENTITY_TYPE_TEXT       8
#define SY_ENTITY_TYPE_IMAGE      9
#define SY_ENTITY_TYPE_GROUP     10
#define SY_ENTITY_TYPE_MESH      11
```

**生命周期规则（必须写进文档和头文件注释）**：

1. 句柄由**宿主创建**、宿主销毁；客户代码**不得**自行 free/malloc。
2. 文档句柄在 `sy_document_close()` 后失效；关闭前必须 `sy_document_close` 所有子句柄。
3. 实体 ID 在文档未保存前有效；保存/重载后**可能失效**，需重新查询。
4. 所有 `sy_*_create` 失败时返回 `NULL` 并设置 last error。

### 6.5 版本与能力协商

```c
/* packed 语义版本（沿用既有约定） */
SY_ABI_API uint32_t sy_abi_get_version(void);
SY_ABI_API const char* sy_abi_get_version_string(void);

/* 能力位图：运行期查询主程序支持什么 */
typedef uint64_t sy_capability;
#define SY_CAP_DOCUMENT         (1ull << 0)
#define SY_CAP_ENTITY           (1ull << 1)
#define SY_CAP_LAYER            (1ull << 2)
#define SY_CAP_SELECTION        (1ull << 3)
#define SY_CAP_UNDO             (1ull << 4)
#define SY_CAP_COMMAND          (1ull << 5)
#define SY_CAP_EVENT            (1ull << 6)
#define SY_CAP_FORMAT           (1ull << 7)
#define SY_CAP_PYTHON_EMBEDDED  (1ull << 8)
#define SY_CAP_HARDWARE         (1ull << 9)
#define SY_CAP_UI_PANEL         (1ull << 10)

SY_ABI_API sy_capability sy_abi_capabilities(void);
SY_ABI_API int sy_abi_has_capability(sy_capability cap);
```

**为什么必须有能力协商而不是只有版本号**：主程序会按构建选项裁剪功能（工程已有 `BUILD_HARDWARE / BUILD_VISION / BUILD_ENGRAVING / BUILD_GEOMODELCORE / SANYI_PYTHON_HOST` 等开关，`Main/CMakeLists.txt:117-125` 已把这些开关镜像成 `BuildConfig.h` 运行期镜像）。**能力位图能准确反映"这个包里到底有什么"**，比版本号精确得多。

### 6.6 结构体前向兼容

```c
typedef struct sy_bbox2_s {
    uint32_t structSize;   /* 必填：sizeof(sy_bbox2) */
    double   minX, minY;
    double   maxX, maxY;
} sy_bbox2;

typedef struct sy_entity_info_s {
    uint32_t structSize;   /* 必填 */
    sy_entity_id id;
    sy_entity_type type;
    int32_t    layerIndex;
    uint32_t   flags;      /* SY_ENTITY_FLAG_* */
    double     bbox[4];    /* minX,minY,maxX,maxY */
    uint32_t   pointCount;
    const double* points;  /* 可为 NULL；长度 = pointCount */
} sy_entity_info;
```

**规则**：

1. 客户填 `structSize = sizeof(结构体)`；
2. 宿主**只读**前 `min(structSize, 宿主sizeof)` 字节；
3. 宿主写入时总是写满自己知道的字段，并把自己的 `structSize` 写在第一个字段；
4. 客户读到 `structSize` 大于自己版本时，多出来的字段忽略；
5. **新增字段只能追加在末尾**，且必须给默认值语义。

> 既有工程已在 `Nesting` 模块用过这个模式（C ABI v2，`structSize` 前向兼容，见 `DLL制作标准与现状.md` §2 表）。**SDK 层应复用同一套机制，不另造。**

### 6.7 回调与线程模型

```c

                             sy_event_type type,
                             const sy_event_payload* payload,

/* 命令执行结果 */
```

**线程模型（写进每个头文件）**：

| 标注 | 含义 |
| --- | --- |
| `SY_THREAD_UI` | 必须在主线程（GUI 线程）调用；其他线程调用返回 `SY_ERROR_WRONG_THREAD` |
| `SY_THREAD_ANY` | 任意线程可调用；内部保证线程安全 |
| `SY_THREAD_CALLBACK` | 仅在事件回调内有效，不得跨调用保存 |
| `SY_THREAD_MAIN_ONLY` | 仅在主线程，且**回调期间**有效 |

> 现有 `ImportService::importAsync` 已经在做"Phase 1-2 后台线程、Phase 3-5 回主线程"的分段（`ImportService.h:117-123`），这套模型可以直接映射到 `SY_THREAD_UI` 语义。

## 7. L1 插件能力扩展设计

### 7.1 插件接口 v2

保留 `IClientUiPlugin` 的向后兼容，同时新增能力接口：

```cpp
// Main/Src/UI/ClientConfig/IClientUiPlugin.h （v2，保持 v1 源码兼容）
class IClientUiPlugin
{
public:
    virtual ~IClientUiPlugin() = default;
    virtual QString id() const = 0;
    virtual QString clientId() const { return {}; }
    virtual void registerPanels(UiPanelRegisterSink& sink) { Q_UNUSED(sink); }

    // ── v2 新增（全部带默认空实现，v1 插件二进制不受影响）──
    virtual void registerCommands(Cmd::ISyCommandSink& sink) { Q_UNUSED(sink); }
    virtual void registerEvents(SyEventSink& sink) { Q_UNUSED(sink); }
    virtual void registerFormats(SyFormatSink& sink) { Q_UNUSED(sink); }
    virtual sy_status onInitialize(SyPluginContext* ctx) { Q_UNUSED(ctx); return SY_OK; }
    virtual void onShutdown() {}
};
```

> **ABI 策略**：只加带默认实现的虚函数会**改变 vtable 布局**，破坏二进制兼容。因此正确做法是：
> - v1 插件：保持 `SANYI_CLIENT_UI_PLUGIN_ABI = 1`，宿主按 v1 路径调用（只 `registerPanels`）；
> - v2 插件：走**新的导出符号** `createClientPluginV2()`，宿主检测到就按 v2 路径；
> - 两者可共存于同一 DLL，宿主按符号存在性决定。
>
> 这比"加虚函数然后 bump ABI"更安全——**老插件永远不需要重编**。

### 7.2 命令注册

把 `UI/Common/Include/UI/Plugin/ICommandPlugin.h` 里的两个空壳 sink 做实，并与 L1 对齐：

```cpp
{
```

### 7.3 场景访问

插件通过 **L1 C ABI** 访问场景（不走 Engine C++ 类）——这是保证 J1（ABI 稳定）的关键：

```cpp
// 插件内部
sy_document doc = sy_document_current();
sy_entity_id ids[256];
uint32_t n = 0;
sy_selection_get(ids, 256, &n);

sy_entity_info info{};
info.structSize = sizeof(info);
sy_entity_get_info(doc, ids[0], &info);
```

**为什么不让插件直接 include `Engine2D/Include/Engine2D/Core/SceneManager.h`**：那样就绑死了同编译器同 CRT（同 G1 的根因）。**唯一例外**是"同 ABI 的 C++ 插件"（客户愿意接受工具链约束），此时可以提供**可选的** `SyAbiCpp` 便利层（header-only 的薄封装，把 L1 C 调用包装成 RAII C++ 类），但**不是必需的**，也不是文档的主推路径。

### 7.4 事件订阅

## 8. L2 Python 二次开发框架

### 8.1 定位澄清：双轨制

| 轨道 | 运行时位置 | 用途 | 隔离性 |
| --- | --- | --- | --- |
| **内嵌脚本**（新增） | GUI 主进程内 | 操作当前文档、交互、事件、命令 | 与主程序同生共死（需异常隔离） |
| **子进程 worker**（现有 `PythonHost`） | 独立进程 | 批处理、离线计算、沙箱化执行 | 强隔离，崩溃不影响 GUI |

两者**共用同一套 Python API 表面**（`sanyi` 包），但能力集不同：

```python
import sanyi

# 内嵌模式：绑定到当前 GUI 文档
doc = sanyi.document.current()          # ← 内嵌模式返回 GUI 的当前文档
# worker 模式：doc 为 None（无 GUI 上下文）
```

### 8.2 内嵌脚本运行时设计

**关键决策：内嵌 CPython 还是进程内解释器？**

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **内嵌 CPython**（`PythonHost` 已有 libpython 依赖） | 完整 Python 生态、性能好、已有基础 | GIL 与主线程交互需小心；崩溃会带走主程序 |
| **进程内轻量解释器** | 隔离好、性能可控 | 生态缺失，客户写不了通用 Python |

**选内嵌 CPython**，理由：

1. 客户要的是"用 Python 写业务逻辑"，需要 numpy / shapely / 客户自己的库；
2. `PythonHost` 已经有 libpython 依赖与 `TaskExecutor` / `RuntimeManager` 基础；
3. 隔离问题通过"异常捕获 + 插件级子解释器"缓解（见 §8.4）。

**线程模型**：

- 脚本在**主线程**执行（保证能操作 GUI 与文档）；
- 长耗时脚本必须主动让出：`sanyi.sleep_ms(16)` 或 `sanyi.process_events()`；
- 提供 `sanyi.run_in_background(fn)` 包装，把纯计算丢到线程池（但线程池内的脚本**不能**访问文档）。

**崩溃隔离**：为每个脚本执行创建**子解释器**（`Py_NewInterpreter`），脚本崩溃只毁掉子解释器，主解释器与主程序存活。这与 CPython 的 sub-interpreter 机制契合（Python 3.12+ 官方支持）。

> Python 版本：CI 里用的是 vcpkg 的 3.12（`PyBindCore/README.md:39`）。3.12 的 sub-interpreter 支持是官方稳定状态，够用。

### 8.3 Python API 分层设计

```text
sanyi/
├── __init__.py          # 门面，导出全部公开符号
├── document.py          # Document：文档读写
├── entity.py            # Entity, EntityRef, 几何构造
├── layer.py             # LayerManager
├── selection.py         # SelectionService
├── command.py           # CommandRegistry
├── event.py             # 事件订阅
├── transaction.py       # 事务 / Undo
├── ui.py                # 对话框、消息、拾取
├── format.py            # 自定义格式读写

├── log.py               # 日志
└── runtime.py           # 运行时信息（版本、能力、平台）
```

**关键 API 形态**：

```python
# ── 文档 ──────────────────────────────────────────────
doc = sanyi.document.current()          # 内嵌模式：当前 GUI 文档
doc = sanyi.document.open("a.dxf")       # 独立文档
doc.save()
doc.path
doc.entity_count
doc.bounds

# ── 实体 ──────────────────────────────────────────────
line = doc.add_line(sanyi.Vec2(0, 0), sanyi.Vec2(100, 0))
circle = doc.add_circle(sanyi.Vec2(50, 0), 5)
info = line.info                       # EntityInfo dataclass
found = doc.query_box(sanyi.BBox2(0, 0, 100, 100))

# ── 事务（参与 Undo）─────────────────────────────────
with doc.transaction("批量圆角") as tx:
    for e in doc.query_box(box):
        doc.set_layer(e, layer_id)
# 异常自动回滚；正常退出自动提交 → 可撤销

# ── 事件 ──────────────────────────────────────────────
def on_sel(selection):
    print("选中了", len(selection.entities), "个图元")

sanyi.event.subscribe(sanyi.event.SELECTION_CHANGED, on_sel)
sanyi.event.unsubscribe(sanyi.event.SELECTION_CHANGED, on_sel)

# ── 命令 ──────────────────────────────────────────────
sanyi.command.execute("acme.roundCorners")

# ── UI 交互 ──────────────────────────────────────────
if sanyi.ui.confirm("确定要执行吗？"):
    sanyi.ui.message("完成", sanyi.ui.MessageType.Information)
path = sanyi.ui.open_file("选择 DXF", "*.dxf")

# ── 授权 ──────────────────────────────────────────────
if sanyi.license.has_feature("acme"):
    ...

# ── 运行时信息 ────────────────────────────────────────
sanyi.runtime.version          # "1.0.0"
sanyi.runtime.abi_version      # 1
sanyi.runtime.capabilities     # set of str
sanyi.runtime.platform         # "windows" / "macos" / "linux"
sanyi.runtime.is_embedded      # True = 内嵌模式
```

**设计要点**：

1. **Python 侧一律用 dataclass / 不可变快照**，不暴露 C++ 指针（延续 `FacadeTypes.h` 的正确方向）；
2. **事务用 `with` 上下文管理器**——这是 Python 生态最自然的 Undo 表达；
3. **事件用回调 + 显式退订**，同时提供 `weakref` 支持避免循环引用；
4. **所有会失败的调用抛异常**（`sanyi.SyError`），而不是返回 `None`——Python 生态的期望；
5. **禁止把 `SceneManager*` 之类泄漏到 Python**（现有 `FacadeTypes.h` 已经做到，保持）。

### 8.4 Python API 版本与兼容

```python
sanyi.runtime.abi_version       # int，SDK ABI 版本
sanyi.runtime.api_version       # str，Python API 语义版本
sanyi.runtime.has_capability("SY_CAP_EVENT")
```

**兼容策略**：

- `abi_version` 与主程序 C ABI 一致（打包时同步）；
- Python API 遵循 **SemVer**：
  - patch：修 bug，不改签名
  - minor：加功能，不改已有签名
  - major：允许改签名（但仍提供 `sanyi.v1` 兼容模块至少一个大版本周期）
- 提供 `sanyi/__init__.py` 的 `__all__` 稳定列表 + 契约测试（见 §12）。

### 9.1 平台矩阵

| 平台 | 主程序 | L1 C ABI SDK | L2 Python | L0 配置 |
| --- | --- | --- | --- | --- |
| **Windows x64** (MSVC 2022) | ✅ 稳定 | ✅ | ✅ | ✅ |
| **macOS arm64** (Metal) | 🟡 构建可用，CI 未覆盖 | ✅ | ✅ | ✅ |
| **macOS x86_64** | 🟡 | ✅ | ✅ | ✅ |
| **Linux x64** | 🟡 构建可用，CI 未覆盖 | ✅ | ✅ | ✅ |
| **Linux arm64** | ⬜ 未验证 | ✅ | ✅ | ✅ |

> L1/L2 的跨平台性是**设计出来的**：L1 纯 C99 无依赖，L2 只依赖 CPython。三者（Win/mac/Linux）天然一致。

```text
│   └── linux-x64/libsy_abi.so
├── cmake/sy_abi-config.cmake     # find_package(sy_abi) 支持
├── samples/
├── docs/
└── VERSION
```

**CMake 集成**（客户侧）：

```cmake
find_package(sy_abi 1.0 REQUIRED)
target_link_libraries(my_plugin PRIVATE sy_abi::sy_abi)
```

**不要**要求客户链接主程序的其他 DLL——那会重新引入 CRT/Qt 耦合。**L1 必须是自包含的**（它自己链接 Engine 需要的部分，但**对客户暴露的导入库只导出纯 C 符号**）。

> **实现要点**：Windows 上 `sy_abi.dll` 内部仍然会链接 `Engine2D.dll` / `Qt*.dll`，这没问题——因为客户只调用 `sy_abi.dll` 导出的 C 函数，**跨边界的只有 C ABI**。客户进程里不会有多份 Qt。

### 9.3 跨平台 CI 矩阵（必须新增）

```yaml
# .github/workflows/sdk.yml
name: SDK Build & ABI Conformance
on: [push, pull_request]
jobs:
  sdk:
    strategy:
      matrix:
        os: [ubuntu-22.04, macos-14, windows-latest]
    steps:
      - uses: actions/checkout@v4
      - name: Build SyAbi only (no Qt, no vcpkg)
        run: cmake -S SyAbi -B build -DBUILD_SANYI_ABI_SDK=ON && cmake --build build
      - name: ABI conformance test
        run: ctest --test-dir build -R abi_conformance
      - name: Build samples against SDK
        run: cmake -S Samples -B build-samples -Ds SDK_DIR=$PWD/build/sdk && cmake --build build-samples
```

**关键点**：`SyAbi` 的 SDK-only 构建**不依赖 Qt、不依赖 vcpkg**，因此 CI 极快（秒级），三平台可高频运行。这与 `ci.yml:91` 说的"全应用 mac/Linux 构建太重"形成对比——**轻量的 SDK CI 是可以立刻做的**。

**SDK 兼容性测试**（`abi_conformance`）：用固定的一组"黄金二进制"插件（每个平台一份），验证新版本 SDK 仍能加载并调用。这是 J4（前向兼容）的自动化保障。

### 9.5 路径、编码、换行约定

跨平台二次开发的高频坑，必须写进 SDK 文档并在 API 层抹平：

| 问题 | 约定 |
| --- | --- |
| 路径分隔符 | SDK **只接受 UTF-8 字符串**；内部统一转 `std::filesystem::path`；客户在 Windows 上传 `C:\a\b.dxf` 可用，SDK 内部规范化 |
| 中文文件名 | Windows 用 `std::filesystem::u8path` / `QString::fromUtf8`；禁止 `fopen` 直接传 UTF-8 路径 |
| 换行 | 文件 I/O 一律 `\n`；Windows 文本模式差异在 SDK 内部处理 |
| 编码 | 客户 JSON / 脚本文件统一 UTF-8 **无 BOM**；Python 源码 UTF-8（Python 3 默认） |
| 大小写 | Linux 文件系统区分大小写 → SDK 内所有路径查找做**大小写不敏感回退**（Windows 语义） |
| 分隔符 | 客户配置里的模块路径用 `/` 统一，不用 `\` |

## 10. SDK 交付、版本与生命周期

### 10.1 SDK 目录结构

```text
sdk/
├── include/sy/            # 公开头（C99）
├── lib/<platform>/        # 导入库 / 动态库
├── cmake/                 # find_package 支持
├── samples/               # 可编译示例（含 CMakeLists）
├── docs/                  # PDF/HTML 文档
├── CHANGELOG.md
├── VERSION
└── COMPATIBILITY.md       # 兼容矩阵
```

### 10.2 版本号体系

**四个版本号，各司其职**：

| 版本 | 位置 | 含义 | 变更规则 |
| --- | --- | --- | --- |
| **应用版本** | `Main/VersionInfo.h` / `brand.json` | 产品版本（如 `1.0.0`） | 发版时变 |
| **SDK ABI 版本** | `sy_abi_get_version()`（packed） | **二进制兼容**版本 | 破坏性 ABI 变更才变 major |
| **SDK 语义版本** | `VERSION` 文件 | SDK 自身版本 | 每次发布变 |
| **Python API 版本** | `sanyi.runtime.api_version` | Python 表面版本 | SemVer |

**ABI 版本规则（继承 `C-ABI风格约定.md` §2）**：

- **major +1**：删除/改变任何已有函数的签名或语义；改变结构体已有字段的含义；改变枚举已有值。
- **minor +1**：新增函数；结构体**末尾**新增字段；新增枚举值（追加在末尾）。
- **patch**：仅修 bug，不改任何签名。

> **枚举值追加规则要特别注意**：C 的枚举值一旦发布就是 ABI。新增枚举值**必须追加在末尾**，不能插入中间。

### 10.3 兼容性承诺

| 承诺 | 内容 |
| --- | --- |
| **C1** | SDK major 版本不变时，客户用 SDK 编译的插件/程序，在任何 minor/patch 的主程序上**二进制兼容**，无需重编 |
| **C2** | 运行时可通过 `sy_abi_capabilities()` 得知主程序实际支持的能力；不支持的能力**不会**出现在位图里 |
| **C3** | 破坏性变更（major +1）**至少提前 2 个次版本**在 CHANGELOG 中声明，并提供迁移指南 |
| **C4** | 旧 major 的 SDK 至少维护 12 个月，并在 SDK 下载页标注 EOL 日期 |
| **C5** | Python API 遵循 SemVer；major 变更时保留 `sanyi.v1` 兼容层至少一个大版本周期 |

### 10.4 发布流程

```text
1. 改动 SyAbi 公开头
     ↓
2. CI 自动跑：
     ├─ ABI 黄金二进制兼容性测试（abi_conformance）
     ├─ 三平台 SDK 构建
     └─ 符号导出审计（abi_symbols_audit）
         · 检查无 STL/Qt 符号泄漏
         · 检查导出符号数量与上次一致（增量审计）
     ↓
3. 人工确认 CHANGELOG 条目 + ABI 版本号
     ↓
4. 打 tag: sdk/v1.2.0
     ↓
5. 流水线产出 4 个平台 zip + 文档站
     ↓
6. 主程序构建脚本记录本次 SDK 版本（写进 abi.txt / VERSION 文件）
```

**符号审计**是 ABI 稳定性的自动化守卫：

```bash
# 检查 sy_abi.dll 导出的符号里不含 STL/Qt
nm -D --defined-only libsy_abi.so | grep -E 'std::|__cxa|_ZN.*Qt' && exit 1
```

## 11. 稳定性、安全与隔离

### 11.1 插件崩溃隔离

| 层级 | 机制 |
| --- | --- |
| **加载期** | `QLibrary` 打开失败 / 符号缺失 → 记 `SY_ERROR` + 跳过，不影响主程序（已实现） |
| **注册期** | `registerPanels` / `registerCommands` 抛异常 → `try/catch` 包裹，该插件的注册全部丢弃（**待实现**） |
| **调用期** | 命令 handler 抛异常 → 捕获 + 标记事务回滚 + 上报错误（**待实现**） |
| **运行期崩溃** | 崩溃处理器记录"当前活跃插件链"（见 §11.2） |
| **Python 脚本崩溃** | 子解释器隔离，主进程存活（**待实现**） |

### 11.2 崩溃归属

在 `CrashHandler` 的崩溃上下文里追加：

```json
{
  "loadedPlugins": [
    { "id": "acme", "path": "plugins/clients/acme/AcmeUi.dll",
      "abi": 1, "version": "1.2.0", "loadedAt": "..." }
  ],
  "activePlugin": "acme",
  "pythonScript": "batch_task.py:42"
}
```

现有的 `Tools/crash_server.py` / `crash_analyze.py` / `crash_handler.h` 已有完整的符号化链路（`Main/CMakeLists.txt:336-338` 链接 dbghelp 做 Windows 栈符号化），只需扩展上下文结构。

### 11.3 沙箱与权限

客户插件运行在主程序进程内，**天然有全权限**。工业级做法是明确声明边界而非假装隔离：

- 文档中明确写："插件与主程序同权限，可访问文件系统/网络。插件代码被视为客户自有代码。"
- 提供 `sy_log_*` 让插件写进统一日志（便于现场排查）。
- 对**高风险**场景（客户要求强隔离）提供"外部进程插件"模式：插件是可执行文件，通过管道通信（L1 复用同一套 API，跨进程用序列化传递）。

### 11.4 输入校验

所有 L1 入口必须校验：

- 指针非空；
- `structSize` 合法（不小于最小必需值）；
- 字符串是合法 UTF-8（跨平台编码问题的最大来源）；
- 实体 ID 在当前文档内有效；
- 调用线程符合 `SY_THREAD_*` 标注。

违反时返回明确 `sy_status`，**绝不崩溃**。

## 15. 风险登记册

| # | 风险 | 影响 | 概率 | 缓解 |

| R4 | **主程序升级破坏客户插件** | 客户信任崩塌 | 高 | C1 兼容性承诺 + ABI 黄金二进制 CI 测试 |
| R5 | **macOS/Linux 主程序构建长期不达标** | 跨平台承诺落空 | 中 | P3-1 先把"构建绿"作为 P1 的准入条件之一 |
| R6 | **SDK 与内部实现漂移**（内部改了 Engine，L1 没跟上） | L1 能力落后 | 中 | L1 的每个 API 都有对应内部实现映射；季度审查 |
| R7 | **客户用 Python 做了性能关键的事**（大文件百万图元） | 卡顿 | 中 | 文档明确性能边界；提供 `sanyi.perf` 基准工具；引导用 C++ 插件或外部进程 |
| R8 | **授权绕过**：客户插件绕过 feature 门控 | 商业损失 | 中 | L1 暴露 `sy_license_has_feature`；宿主在命令执行时二次校验（不信任插件自检） |
| R9 | **SDK 文档腐化**（代码改了文档没改） | 客户踩坑 | 高 | 文档一致性 CI 检查（§12.1 最后一行） |
| R10 | **Windows CRT 混用**（客户 `/MT`，主程序 `/MD`） | 随机崩溃 | 低 | L1 无堆分配跨界（句柄由宿主持有）；即使混用也不会跨界释放 |

### A. 术语

| 术语 | 含义 |
| --- | --- |
| **SDK** | 二次开发套件：头文件 + 导入库 + 示例 + 文档 |
| **ABI** | 应用二进制接口：已编译代码之间的接口契约 |
| **C ABI** | 用 C 语言函数/类型定义的 ABI，可跨编译器 |
| **能力协商** | 运行期查询宿主支持哪些功能，而非编译期硬编码版本 |
| **句柄（handle）** | 指向宿主内部对象的、不透明指针；只能由宿主创建与销毁 |
| **前向兼容** | 新宿主能运行旧 SDK 编译的插件 |
| **白标** | 换品牌但不改功能的定制 |
| **二次开发** | 客户编写新逻辑的功能扩展 |
| **L0/L1/L2** | 本文定义的三层扩展模型：配置 / C ABI / 语言绑定 |
