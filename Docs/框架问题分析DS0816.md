# 框架问题分析 DS0816

> 日期：2026-08-16
> 范围：全框架体检（SanYiCAD 根工程 + 17 个 git 子模块）
> 性质：**只分析、不改动**。本文仅描述问题定位、影响评估与改造思路，供后续立项排期参考。

---

## 1. 总体评估摘要

SanYiCAD 是一个约 **30 万行 C++17** 的工业级激光 CAD/CAM 框架（根工程 + 17 个 git 子模块）。工程在架构演进上做了大量正确的事：P5/P8 系列重构（命令内核模板化、刷新协调、场景树数据模型、DI 组合根）、跨 DLL 纯 POD 契约约束、`unique_ptr` 所有权迁移、Renderx 相机相对精度管线等，代码整体纪律性较好（100% `#pragma once`、命名空间统一、错误处理水平中上）。

但体检发现以下 **7 类高危问题**，按"伤害立即性"排序：

| 级别 | 问题域 | 一句话概括 |
|------|--------|-----------|
| 🔴 P0 | 构建可复现性 | **新克隆无法 configure**——全部 `*.cmake` 被 `.gitignore` 排除，`Config.cmake`/`CMake/*.cmake` 未入库 |
| 🔴 P0 | 许可证 | **生产环境许可校验从未生效**——默认关闭、无人开启、可被公开 API 直接标记为有效 |
| 🔴 P0 | 文件解析 | **ASCII STL 解析栈缓冲区溢出**（恶意文件可内存破坏）；SVG NaN → UB |
| 🔴 P0 | 引擎核心 | **无图纸持久化**（CAD 引擎无法保存/加载文档）；事务删除撤销失效（undo 坏链） |
| 🟠 P1 | 渲染框架 | Vulkan/Metal 后端"编译通过但结构残缺"（缺 render pass/信号量/着色器阶段），3D 实例化路径不可用 |
| 🟠 P1 | 渲染性能 | 每帧阻塞式 GPU 可见性回读、选中即全量重建、屏幕文字每帧重建 VB |
| 🟠 P1 | UI 层 | `UI2D.h` 聚合头已损坏；全局单例泛滥（ServiceLocator3D/OperationBus）；新旧两代视口栈并存 |

本文第 3 节逐条给出 **问题定位 → 根因 → 影响 → 改造思路**，第 4 节给出**分阶段实施路线图**。

---

## 2. 严重度定义

| 级别 | 含义 | 判定标准 |
|------|------|---------|
| **P0** | 阻断性/安全危害 | 无法构建、可被外部利用（内存破坏/越权）、核心功能失效（如撤销坏链、无法保存文档） |
| **P1** | 高危架构债 | 数据竞争/悬挂指针风险、声明与实现不符、性能退化到不可接受、维护双轨长期共存 |
| **P2** | 中危债务 | 重复代码、死代码、文档与代码失配、测试缺失 |
| **P3** | 低危/清理 | 编码问题、注释过期、命名/格式类 |

## 3. 分域详细问题分析与改造思路

---

### 域 A：构建与工程化（P0 最高危）

#### A1.【P0】构建配置层整体未纳入版本控制，新克隆无法 configure

**问题定位：**
- `.gitignore:19` 一条 `*.cmake` 把所有 CMake 配置文件全部排除。
- `git ls-files` 证实：`Config.cmake`、`CMake/SanYiPaths.cmake`、`CMake/Utils.cmake`、`CMake/Packaging.cmake`、`CMake/StandaloneInit.cmake` **均未入库**。
- 但 `CMakeLists.txt:10` `include(Config.cmake)`、`:25-26` include 两个 CMake 模块、`:380` include Packaging——**任何新克隆在 configure 第 10 行即报错**。

**根因：** 早期为了"本地私有路径不入库"的诉求，用一刀切 `.gitignore *.cmake` 实现，把公共构建逻辑也一并排除了。

**影响：** 工程事实上只在本机可构建；换人、换机、CI 全部不可用。这是当前**最严重**的工程问题。

**改造思路：**
1. 拆分配置语义：
   - **入库**（公共逻辑）：`CMake/` 下所有 `.cmake` 重命名保留并 `git add -f`（或改用 `*.local.cmake` 类忽略模式，仅忽略带 `local` 后缀的）。
   - **不入库**（机器私有）：新建 `Config.local.cmake`（gitignore），顶部 `CMakeLists.txt` 改为：
     ```cmake
     if(EXISTS "${CMAKE_SOURCE_DIR}/Config.local.cmake")
         include(Config.local.cmake)
     endif()
     # 其余路径用 find_package / 环境变量 / 默认值兜底
     ```
2. 提供 `CMake/Config.example.cmake` 模板入库，含三平台注释示例。
3. 将 `Config.cmake` 中的硬编码路径改为 **CMake 变量 + 环境变量回退**（`SANYI_VCPKG_DIR` / `SANYI_QT_DIR`），未设置时 `find_package(Qt6)`/`find_path(vcpkg)` 自动探测。
4. `.gitignore` 改为仅忽略 `*.local.cmake`、`CMakeUserPresets.json`，删除宽泛的 `*.cmake`。

#### A2.【P0】`Config.cmake` 用 `FORCE` 强制缓存变量，模块开关命令行失效

**问题定位：** `Config.cmake:61-70`
```cmake
set(BUILD_HARDWARE    ON  CACHE BOOL "..." FORCE)
set(BUILD_ENGRAVING   ON  CACHE BOOL "..." FORCE)
set(BUILD_VISION      ON  CACHE BOOL "..." FORCE)
set(BUILD_GEOMODELCORE ON CACHE BOOL "..." FORCE)
set(BUILD_UI3D        ON  CACHE BOOL "..." FORCE)
set(BUILD_NETWORK     OFF CACHE BOOL "..." FORCE)
```
`BUILD_GEOMODELCORE=ON` 又连带 `CMakeLists.txt:174` `find_package(OpenCASCADE CONFIG REQUIRED)`——无 OCCT 的机器连 configure 都过不了。

**影响：** `-DBUILD_VISION=OFF` 等任何命令行开关被静默覆盖；新开发者无法裁剪依赖树。

**改造思路：**
- 删除所有 `FORCE`。顶部用一次 `option()` 声明默认值，用户可用 `-D` 覆盖：
  ```cmake
  option(BUILD_GEOMODELCORE "..." ${SANYI_DEFAULT_CORE})
  option(BUILD_VISION "..." ${SANYI_DEFAULT_OPTIONAL})
  ```
- 默认值本身用一份**可入库的 profiles**（如 `--sanyi-client=minimal/standard/full` 预设）表达，而非在 cmake 里硬编码 ON/OFF。
- OCCT/Vision/OpenCV 改为 `find_package(... QUIET)`，未找到时自动降级 `BUILD_*=OFF` 并打印提示。

#### A3.【P1】configure 阶段执行 `git submodule update --init --recursive`

**问题定位：** `CMakeLists.txt:55-73` 在 configure 中拉取全部子模块。

**影响：** ①configure 需要网络 + SSH 私钥；②子模块有未提交改动时（当前 Engine/UI 即 dirty）update 失败只打 WARNING，产出"配置成功但子模块不一致"的假象；③configure 修改工作区是副作用。

**改造思路：**
- 删除该段。改为：`git submodule update --init --recursive` 写入 `README` 的**前置步骤**，并在 configure 时仅 `find_path` 校验各子模块的 `CMakeLists.txt` 是否存在，缺失则 `message(FATAL_ERROR)` 提示先执行更新命令。

#### A4.【P1】子模块 CMake 引用兄弟子模块路径（依赖方向错乱）

**问题定位：**
- `Engine/CMakeLists.txt:3` `include(../Config.cmake)`；`:38-39` `add_subdirectory(../Log/Log ...)`、`add_subdirectory(../Utility/Utility ...)`。
- `Renderx/CMakeLists.txt:5`、`:182` 同样 `../Config.cmake`、`../Log/Log/Include`。
- `UI/2D/CMakeLists.txt:141` 直接编译 `../../ThirdParty/QrCodeGen/qrcodegen.cpp`。
- `FileIO/FileIO/CMakeLists.txt:30-32,76-78` 直接 glob 编译 `ThirdParty/libdxfrw`。
- `PyBindCore/PyBindCore/CMakeLists.txt:5,38-42` 引用 `../../CMake/Utils.cmake`、`../../Engine/...`。

**根因：** 子模块未自洽，构建只能以"固定在根工程目录树内"为前提成立；`add_subdirectory` 对外部目标反复 `add_dependencies` 造成重链、命名空间污染和重复编译。

**影响：** 任何模块无法单独出包/复用；一旦目录布局调整即大面积断裂。

**改造思路：**
- 中期（低风险）：各子模块 CMakeLists 剥离外部 `add_subdirectory`，改为 `find_package(SanYiLog)`、`find_package(SanYiUtility)` 式的 CONFIG 包发现，由根工程负责构建顺序并提供 `CMAKE_PREFIX_PATH`。
- 长期：子模块作为独立仓库，通过 `FetchContent` 或安装包消费；根工程只保留 `Main/` 与 `CMake/`。
- `ThirdParty/QrCodeGen`、`libdxfrw` 建议随子模块**复制或 fetch**，消除跨子模块源码编译。

#### A5.【P1】`BUILD_NESTING` 从未定义，Nesting 被静默丢弃

**问题定位：** `CMakeLists.txt:117,191,278` 及 UI 各 CMake 均引用 `BUILD_NESTING`，但 Config.cmake 与根 CMakeLists 均未 `option()` 声明。未定义变量在 `if()` 中按 OFF 求值 → **Nesting 从未被构建**，`libNesting_d.dylib` 是残留旧物。

**影响：** 排样功能实际不可用，且无人察觉（编译全绿）。

**改造思路：** 根 CMakeLists 顶部补 `option(BUILD_NESTING ... ON)`；删除构建目录中残留的 Nesting 产物；在安装规则中同步保留其条件分支。

#### A6.【P2】CMake 版本要求与文档失配

**问题定位：** 全部 CMakeLists `cmake_minimum_required(VERSION 4.3)`（本机 CMake 4.4.0，前沿版本），`README.md:222-224` 却宣称 "CMake 3.20+"。若真按 README 用 3.20 会直接失败。

**改造思路：** 统一文档与代码。建议文档改标 4.3。

#### A7.【P1】无 CI；多模块测试从未接入

**问题定位：**
- `.gitignore:184` 连 `.github/` 都忽略，仓库无任何 CI 工作流。
- 测试目标未接线：`Hardware/Test/`、`Vision/Test/`、`Network/Test/`、`GeoModelCore/Test/`、`Engine/Persistence/Test/`（710 行测试无人构建）；`Utility`/`Log` 测试默认 OFF；CrashHandler/PythonHost/PyBindCore 零测试。
- 当前 ctest 实际运行约 2137 条，主要来自 Engine2D(964)/MainTests(728)/FileIO(120)，覆盖面严重不均。

**改造思路：**
1. 先修 A1（构建可复现）→ 再上 CI。
2. CI 最低配置：Ubuntu + macOS 双矩阵，Debug 全量构建 + `ctest --output-on-failure`；Release 只编 `SanYiCAD` 与安装目标。
3. 逐个补齐未接线测试目录的 `add_subdirectory(Test)`，并修复其依赖（Nesting 需 A5 先修）。
4. 测试目标策略问题见 A8。

#### A8.【P2】`MainTests` 重编译约 60 个生产源文件

**问题定位：** `Main/CMakeLists.txt:458-545` 把 Main/UI 生产 `.cpp` 直接编译进测试二进制（15.8MB），`UI/2D/Test` 亦以 Stub 头替换真实头、编译源副本。

**影响：** ①测试测的是"源文件的另一份拷贝"而非发货 DLL，存在"测试绿、产品挂"的分叉风险；②编译耗时巨大。

**改造思路：** 逐步迁移为对公开 DLL 的接口测试（POD 契约已支持）。至少为 `Main` 层优先补齐"进程内冒烟测试"（启动→导入→保存→退出）以覆盖集成路径。

#### A9.【P3】其他构建卫生问题

- `.gitmodules` 残留 `[submodule "Render"]` 项（无对应 gitlink）；README 依赖表提到已删除的 `Render/` 目录。
- `Engine2D` 的 `SANYI_FILEIO_DIR` include（`Engine/2D/CMakeLists.txt:67`）是**反向依赖残留**：引擎包含 FileIO 目录但源码从未 include——属于潜伏的依赖循环掩体，应删除。
- 源树中残留 Windows 生成的 `UI3DOperationTests[1]_include-*.cmake` 等（含 `C:/Users/xx/...` 硬编码路径）。
- 死文件：`Renderx/original.cpp`（2287 行）、`Renderx/original_frame.cpp`（0 字节）、`Nesting/Nesting/Test/`（与 `Tests/` 重复）、根 `Testing/`。
- `BUILD_SHARED_LIBS` 在 `Engine/CMakeLists.txt:36`/`Renderx/CMakeLists.txt:57` 声明但被 `sanyi_add_shared_library` 显式 SHARED 架空。

### 域 B：许可证与安全（P0）

#### B1.【P0】生产环境许可校验从未生效

**问题定位：**
- `License/Src/LicenseInternal.cpp:8`：`std::atomic<bool> g_checkEnabled{ false };`——**默认关闭**。
- 全仓库 grep 证实：没有任何生产代码调用 `License_SetCheckEnabled(true)`（仅测试）。
- `Main/Src/Runtime/CADApplicationRuntime.cpp:71`：`if (License_IsCheckEnabled()) { ... }` 门控整段校验，恒为 false → 启动直接跳过。

**影响：** 商业软件的授权系统是**纯摆设**：任何用户免激活运行。这是商业风险层面的 P0。

**改造思路：**
1. 明确的启用策略：由客户配置/编译期宏（如 `SANYI_ENABLE_LICENSE=ON`）决定生产开关，`Config.local.cmake` 或构建参数注入，禁止在代码里硬编码。
2. 理顺启动顺序：`CADApplicationRuntime` 先 `License_ConfigInit`（含 enableCheck 生效）再 `License_IsCheckEnabled`，当前 `:71` 在 `:76` 之前判断，顺序本身就是反的。
3. 补一条 CI/集成测试：`SANYI_ENABLE_LICENSE=ON` 下，无注册码启动必须进入激活对话框。

#### B2.【P0】`License_GuardMarkValid()` 作为公开 C API 导出

**问题定位：**
- `License/Src/LicenseDLL.cpp:372-376` `License_GuardMarkValid()`：任何进程内调用即可把散射态标记为有效，完全击穿 `LicenseGuard` 防 patch 设计。
- `License_SetCheckEnabled`（`:125-128`）同样公开导出，是全局开/关。

**影响：** 散射态防护形同虚设；攻击者（或普通用户注入）一行调用即绕过。

**改造思路：**
- 从导出符号表移除：`RENDER_API`/`LICENSE_API` 宏改为仅导出必要符号；内部函数 `__attribute__((visibility("hidden")))` 或移入匿名命名空间。
- `GuardMarkValid` 只保留给**内部测试**用：放 `#ifdef SANYI_UNIT_TEST` 或独立测试库。
- 强化：校验态标志由 `License_Create` 之后的**不可变上下文**持有，不提供外部写路径。

#### B3.【P1】Keygen（签名）代码打进发货 DLL，私钥明文落盘

**问题定位：**
- `License/CMakeLists.txt:23-28` 用 glob 编入全部 `Src/*.cpp`，含 `KeygenTool.cpp` 与 `LicenseKeygenDLL.cpp`；导出 `LicenseKeygen_GenerateKeyPair`、`LicenseKeygen_GenerateRegCode`。
- `KeygenTool.cpp:76-81` 生成私钥直接明文写盘。

**影响：** 攻击者即使拿不到私钥文件，也可调用导出的生成函数自行产新私钥签发任意注册码——授权体系被从根上瓦解。

**改造思路：**
- 拆分目标：`KeygenTool` 与 `LicenseKeygenDLL` 从 `License` DLL 编译源中剔除（`list(REMOVE_ITEM)` 或按目录分层），单独生成可选工具（`Tools/KeygenTool`，默认 OFF）。
- 私钥落盘加口令派生加密（AES-GCM + PBKDF2），或要求从外部安全介质注入。

#### B4.【P1】`.sy` 原生格式"加密"是异或混淆

**问题定位：** `FileIO/.../SyCryptoProvider.h:104` 默认密钥 `"SanYiDefaultKey2024"`；`XorCryptoProvider::encrypt` = `plain[i] ^ key[i%len] ^ (i&0xFF)`（`SyCryptoProvider.cpp:40-46`），trivially 可逆。

**改造思路：** 若确需加密，升级为 AES-256-GCM（密钥由机器指纹派生 + 随机 IV）；若仅需防误改，改校验和/签名。与 B1 的密钥管理统一。

#### B5.【P1】许可有效期无防回拨；features 未校验

**问题定位：**
- `LicenseManager.cpp:539-556` 仅本地时间比较过期日；未检查 `issueDate` 晚于当前时间（未来签发）；无时间戳回拨检测。
- `LicenseManager.cpp:838-867` features 字符串被原样拷贝，应用从未解析为权限检查。

**改造思路：** 补"签发时间 ≤ 当前 ≤ 过期时间"双界校验 + 本地最近校验时间戳持久化（防止整体回拨）；features 解析为枚举集合，在功能入口执行 `hasFeature()` 检查（与 B1 联动）。

#### B6.【P1】硬编码口令 + 权限函数忽略操作参数

**问题定位：** `Hardware/Src/SafetyManager.cpp:16-17` 明文 `admin/admin123`、`operator/operator123`；`:263-267` `hasPermission(操作)` 忽略传入操作直接放行。

**改造思路：** 口令改为配置化 + 加盐哈希存储；`hasPermission` 实现基于"角色×操作"矩阵；默认拒绝（fail-closed）。

#### B7.【P2】网络令牌明文落盘 / 空令牌登录

**问题定位：** `Network/Src/ConfigManager.cpp:63-95` 用 QSettings 明文 INI 存 access/refresh token；`LoginManager.cpp:115-121` 空 token 也登录成功。

**改造思路：** token 存 `SecureStorage`（见 C10 改造）；空 token 视为未登录。

### 域 C：引擎核心（Engine，P0/P1）

#### C1.【P0】引擎无文档持久化——CAD 引擎无法保存/加载图纸

**问题定位：**
- `Engine/Persistence` 只是**设置/参数键值存储**（Settings/WindowSettings/Secure/Material/ProcessParameter），不含任何 `SyEntity`/`SceneManager` 序列化。
- 全引擎仅有的导入是 3D OBJ/STL 加载器；2D 图纸没有任何 save/load 能力。
- 原生 `.sy` 格式由 `FileIO/Proto/SanYiDocument.proto` 定义，`NativeParser/NativeWriter` 存在，但**与 Engine 场景模型之间没有正式桥梁**（UI 层手工转换）。

**影响：** "保存/打开"是 CAD 的基本功能；当前只能靠 UI 层各自为政的 protobuf 转换，Engine 侧无统一契约。这是架构层面最大的功能空洞。

**改造思路：**
1. 在 Engine 定义**正式文档序列化层**：`Engine/Persistence` 新增 `ISceneSerializer` 接口，实现基于 **Protobuf**（复用/扩展 `SanYiDocument.proto`）的 `SceneManagerSerializer` / `SceneManager3DSerializer`。
2. 序列化契约：`SyEntity` 各子类注册 `serializeTo(doc)`/`deserializeFrom(doc)`；层、组、选择、undo 栈不序列化，文档只含内容。
3. 版本化：文档头带 schemaVersion + 逐字段 forward-compat（proto 天然支持）。`DatabaseMigration` 模式可迁移到文件头。
4. 收敛路径：废除 UI 层"两套转换"（`FioEntityConverter` 与 `NativeParser` 各转一遍），统一走 `SceneDocumentIO`（Engine 序列化）→ `FileIO` 只负责格式外壳（容器/加密/压缩）。
5. 补充 round-trip 测试：构造场景 → 保存 → 加载 → 几何/属性比对（含 undo 后保存）。

#### C2.【P0】事务删除的撤销是坏链——`DeleteEntitiesCommand` 拿到空 ID 列表

**问题定位：** `Engine/2D/Src/Core/DocumentTransaction.cpp:382-433`
```cpp
std::vector<std::unique_ptr<SyEntity>> removedEntities; // 收集了 beforeState 克隆
...
case ChangeType::Delete:
    removedEntities.push_back(...beforeState->clone());   // :398-403 认真收集了
...
if (!removedEntities.empty())
    m_undoManager->executeCommand(
```

- 实现 `AttributeChange` 的 apply/revert（已有 before/after 快照数据，补齐应用逻辑即可）。
- 为 `DocumentTransaction` 补测试套件（当前该文件无直接测试）。

#### C3.【P1】场景核心非线程安全，却内建并行

**问题定位：**
- `SceneManager`/`SceneManager3D`/`UndoRedoManager`/`LayerManager`/`SelectionManager`/`EntityContainer` 均**无锁**。
- 但 `EngineParallel`（共享 BS 线程池）与 `ArrayAlgorithm` 的并行区会并发读取同一批实体对象；`dirtyEntities()`/`deletedEntityIds()` 以 const 引用返回，UI 线程改动与后台读取**数据竞争**。
- `getAllEntities()` 返回内部存储裸指针，调用方可绕过 generation 随意改。

**影响：** 竞态窗口真实存在（拖拽编辑期间后台重绘/量化读取），是"偶发闪错/崩溃"类问题的头号嫌疑。

**改造思路：**
1. 明确并发契约：**场景为 UI 线程单线程独占**；并行只允许在"不可变几何算法层"（纯函数，不触场景容器）。
2. 若确需后台渲染/量化：引入 `SceneSnapshot`（不可变副本）供工作线程消费，主线程用 dirty set 增量更新快照（copy-on-write）。
3. 为 `dirtyEntities` 等接口改为值返回（避免外部持有引用期间被 `markClean` 清空的竞态）。
4. 用 TSAN 在 CI 跑一轮 Engine2D/Main 测试抓现行竞态（改造 A7 时一并上）。

#### C4.【P1】`EntityContainer` 删除 O(N) + 索引翻腾

#### C5.【P1】`Geo2DTolerance` 旧 API 与新 `GeometryContext` 双轨并存（108 个 deprecated 重载）

#### D1.【P1】Vulkan 后端"编译通过、结构残缺"，一运行即失效/崩溃

**问题定位（`Renderx/src/rhi/rhi_vulkan.cpp`）：**

- `endFrame`（:1606-1655）提交 `imageAvailableSemaphores[]`/`renderFinishedSemaphores[]`——**全文件无 `vkCreateSemaphore`**，未初始化句柄进 `vkQueueSubmit`。
- `createPipeline`（:1134-1302）创建图形管线时 **shader 阶段为零**（`m_shaderStages` 从未填充，源码自述 :1139-1140 未实现 shader 编译）。
- `setUniform*`（:1833-1913）写入局部 `m_pushConstants`，**从未 `vkCmdPushConstants`**，pipeline layout 也未声明 push-constant 范围。
- descriptor set（:1721-1738）bind/update 但 **从未从 pool allocate**。
- `resize`（:2023）`// TODO: Recreate swapchain and frame resources`。
- `memoryBarrier`（:1965-1982）把 GL 访问标志位当 `VkAccessFlags` 用。

**影响：** 后端只是"存在"而非"可用"；`render_types.h:205-215` 声称"仅 OpenGL 已实现"，而 README 却声称四后端"已实现"——对外表述与事实矛盾。任何选择 Vulkan 的宿主会立即失败。

**改造思路：**
1. **二选一决策**：(a) 若 Vulkan 是真实目标 → 成立专项，按官方教程级顺序补齐：swapchain+image views → render pass → framebuffers → 描述符池/集 → 管线（含 shader 编译）→ command buffer 录制 → 同步原语 → resize 重建，并对齐 RHI 语义（access mask 转换函数）。每步加验证层 + CI 冒烟；(b) 若近期无实际客户 → 显式标记 `EXPERIMENTAL_NOT_RENDERABLE`，`renderCreateDevice` 对 Vulkan 返回明确错误码并阻止其成为默认。
2. 至少在 CMake 上让非 GL 后端**不参与 Release 构建**（`#ifdef SANYI_ENABLE_VULKAN`），避免"编了不能用"。

#### D2.【P1】Metal 后端同样不可渲染（且从未编译过）

**问题定位（`rhi_metal.mm`）：**
- `m_framebufferOnly` 被当作多用途临时指针：:164 存 `CAMetalLayer`，:202 又被 `createDepthBuffer` 覆写为 depth texture，:232 `updateDrawable` 再强转回 `CA::MetalLayer*` → **首帧类型错乱/崩溃**。

- `metalLayer->setPixelFormats(...)`（:154）`CAMetalLayer` 无此 API，macOS 下应属编译错误——该文件从未进过编译。

**改造思路：** 与 D1 同策略：不开金属后端即从构建移除；若要做，先修复句柄复用冲突（引入独立 `m_layer`/`m_depthTexture` 字段）、补 MSL shader、接通编译（`*.metal` 入 Xcode/CMake 编译步骤）。在可用前，README/类型注释明确标注"占位"。

#### D3.【P1】3D 清屏色失效——先清后设色

**问题定位：** `render_c_api_frame.cpp:597` `rhi->beginFrame()` 即执行 ClearColor+Clear（`rhi_gl.cpp:797-798`）；3D 模式的 `FrameSetup3D` 随后才 `setClearColor(0.12,0.14,0.20,...)`（`:848`）且**不再 clear**。3D 场景永远用最后一次 2D 的清屏色。

**改造思路：** clear 逻辑后移到"各模式首个 pass 内"，或 beginFrame 仅清 stencil/depth，颜色清理由模式代码显式触发。

#### D4.【P1】3D 实例化路径结构性不可用（GL）

**问题定位：** `mesh_3d_instanced.vert:5` 把 `aModelMatrix` 声明为**逐实例顶点属性**，但 `MeshManager::render` 把实例缓冲绑为 **uniform buffer**（`mesh_manager.cpp:593`），且全工程无 `glVertexAttribDivisor`（`rhi_gl` 无 divisor API）；`rhi_gl.cpp:1027,1046-1050` 的 `draw/drawIndexed` **忽略 firstInstance/vertexOffset**。所有实例坍缩到原点。

**改造思路：** 补 `VertexAttribDivisor`/实例步长支持；实例缓冲改绑 VBO + divisor=1；`draw*` 参数透传。鉴于当前无生产调用方，也可**冻结该 API 并隐藏**（从 `render.h` 摘除或标记 unstable），集中精力在 2D 主路径，避免维护一个不可用的 3D 面。

#### D5.【P1】每帧阻塞式 GPU 可见性回读

**问题定位：** `persistent_entity_manager.cpp:431-478` 每帧 `mapBuffer`（阻塞）读回 GPU 剔除结果，`:172-174` 注释自认双缓冲方案被放弃。

- `OperationBus::instance()`：`std::atomic<OperationBus*>` 裸指针，深埋在 `SelectTool.cpp:661-746` 等工具代码里；未注册时为 nullptr。

**改造思路：**
1. 冻结新增调用点：grep 列出全部 `ServiceLocator3D::instance()/OperationBus::instance()` 调用，用**依赖注入**迁移：工具/服务构造时通过参数或 context 传入所需服务引用。
2. `OperationBus` 的实例引用从"全局单例"改为"UI 会话上下文持有"，由 `WorkbenchWindow`/`CompositionRoot` 注入。
3. 过渡期内给单例加"已 shutdown"断言（Debug 下使用悬垂即崩，提前暴露），而不是静默返回。

#### E4.【P1】`clearWorkbenchContent()` 全局冲刷 DeferredDelete

**问题定位：** `WorkbenchWindow.cpp:849-854` 切换工作台时执行 `QCoreApplication::sendPostedEvents(nullptr, QEvent::DeferredDelete)`，冲刷**进程内所有**待删对象，可能在工作台切换事件中途销毁无关对象。

**改造思路：** 只 flush 目标工作台的子对象（`QObject::childEvent` 追踪或按对象树局部 `deleteLater`），必要时改为同步 `delete` 受控对象。

#### E5.【P1】选中即全量重建（与增量渲染宣传相悖）

**问题定位：**
- `SceneRefreshCoordinator.cpp:196-203` `onSelectionChanged → requestFullRefresh()`：每次单击/悬停选择变化都触发**整场 gather+tessellate+submit**。
- 叠加 `Renderx` 的增量路径（`EntityToVertices`）时，本应走 add/modify/remove，但选择变化绕过了它。
- 渲染引擎宣称支持百万级图元；悬停在大 DXF 上会持续卡顿。

**改造思路：**
1. 选择态变化 → 增量路径：选择高亮是"每个被选/取消选中实体"的 modify，而不是全场重建。给 `SceneRefreshCoordinator` 增加 `RefreshLevel::Selection` 分支。
2. 高频场景（拖拽框选）用 16ms 节流合并脏集（`onSceneChanged` 已有节流，选择变化同样纳入）。
3. 用 `RenderWidget` 的 `modifyRenderEntity`（重传几何/样式）实现高亮，避免重 tesellation。

#### E6.【P1】场景树去抖被同步刷新击穿

**问题定位：** `UiWorkbench.cpp:983-989` 场景树刷新去抖 150ms，但 `:966-973` 在 `undoStateChanged` 与每次 `operationCompleted` 同步调 `refreshSceneTree()`——批量操作每步一次，O(N) 去抖失效。

**改造思路：** 统一走节流定时器；操作完成事件只发"需要刷新"标记，树刷新收敛到单定时器。

#### E7.【P1】`releaseGLResources()` 置空 `m_device` 未销毁设备 → 重显永久空白

**问题定位：** `RenderWidget.cpp:436-441`：隐藏时 `m_device=nullptr` 但不调用 `renderDestroyDevice`（GPU 资源悬挂至 QOpenGLWidget 析构）；`m_glResourcesReleased` 又阻止再次 `initializeGL`——**隐藏后重新显示的小部件永久空白**。

**改造思路：** 隐藏时完整 `renderDestroyDevice` + 允许重新 `renderCreateDevice`；或相反，隐藏时**保留**设备与上下文资源（仅停止渲染），恢复显示直接可用。二选一并补回归测试（显示→隐藏→显示）。

#### E8.【P1】`closeEvent` 保存是异步的，失败静默丢失

**问题定位：** `WorkbenchWindow.cpp:561-583`："保存后关闭"走 `File_Save` 操作但不等待结果；保存失败窗口照常关闭，未保存数据静默丢失（`Docs/01-当前架构` 有多张相关截图的既有记录）。

**改造思路：** 关闭流程改为同步三态：执行保存 → 收到 result（成功/失败/取消）→ 成功才退出；失败弹对话框提供"重试/另存/放弃"。

#### E9.【P2】Workbench/工具神类

### 域 F：文件导入导出（P0 安全 + P1 健壮性）

#### F1.【P0】ASCII STL 解析栈缓冲区溢出

**问题定位：** `FileIO/FileIO/Src/Parsers/StlParser.cpp:164-209`
```cpp
float v[9];
...
else if (lower.find("vertex") != std::string::npos) {
    ... v[vertRead * 3] = x;      // 无 vertRead<3 守卫
    ... v[vertRead * 3 + 1] = y;
    ... v[vertRead * 3 + 2] = z;
    ++vertRead;
}
```
一个 facet 内超过 3 个 `vertex` 行 → `vertRead>=3` → `v[9..]` 越界写**栈**。

**影响：** 恶意 STL 文件可直接栈破坏/任意代码执行（打开文件即触发，无交互）。

**改造思路：** `if (vertRead >= 3) { 跳过或告警 }`；并给 ASCII STL 增加顶点数上限与 facet 数上限。补 fuzz 测试（畸形/超长 facet）。**这是全仓库最优先修复项。**

#### F2.【P1】SVG NaN 坐标 → 未定义行为

**问题定位：** `SvgParser.cpp:452-479,643-677` 路径点/变换未做 `std::isfinite` 校验，`computeAdaptiveSegments` 对 NaN 计算后 `static_cast<int>(NaN)` 为 UB，可产生越界数组索引。

**改造思路：** 入口统一 `sanitizeGeometry`（坐标/半径/角度全量 finite 校验，非法点跳过+警告）；所有 `static_cast<int>` 前 clamp。补 NaN 输入单测。

#### F3.【P1】解析无实体/内存上限（DoS）

**问题定位：** DXF/SVG 解析循环无实体总数上限；`Engraving/MeshSlicer.cpp:505` 扫描线填充对极小 `lineSpacing` 无界。PLT 有 100 万上限（`PltParser.cpp:109`），但 DXF/SVG/STL-ASCII 没有。

**改造思路：** 建立 `ParseLimits`（实体数、顶点数、字节数、深度），超限报错并回滚；UI 层显示"文件过大"。DXF 各类段各设计数。

#### F4.【P1】文本编码不做转换（GBK/ANSI→UTF-8 缺失）

**问题定位：** `DxfParser.cpp:262,494` 的 TEXT/MTEXT 字节原样透传；无 `$DWGCODEPAGE`/`$INSUNITS` 处理。中文 DXF 到 UTF-8 UI 必乱码。

**改造思路：** 引入 codepage→UTF-8 转换（Windows codepage 映射表，可复用 Qt `QStringDecoder` 或自带映射）；MTEXT 转义（`\P \H` 等）同步处理。写 round-trip 测试（GBK 文本 → 中文实体 → 内容比对）。

#### F5.【P1】`$INSUNITS`/单位完全忽略，`FioParseResult.sourceUnit` 从未填充

**问题定位：** 全 FileIO/Main grep 无 `INSUNITS`；`FioTypes.h:206` 声明 `sourceUnit` 但无解析器写入；`readImageInfo` 硬编码 DPI 96（`ImageUtils.cpp:32-33`）。所有导入都当毫米处理。

**改造思路：** DXF `$INSUNITS`、SVG `width/height`+单位、PLT 头文件单位解析进 `FioParseResult`；Main 转换层按"源单位→毫米"换算并记录文档元数据（C1 文档格式一并携带）。

#### F6.【P1】`parseToIR` 返回 thread_local 缓冲指针

**问题定位：** `DxfParser.cpp:1066-1071`、`SvgParser.cpp:750-757`、`StlParser.cpp:261-288` 的 IR 指针指向 `thread_local` 向量，同线程下次解析即失效。头文件有注释，但任何存储结果的调用方都是潜伏 use-after-free。

**改造思路：** 改为值语义（`std::vector` 返回 + move），或返回 `shared_ptr<const FioParseResult>`；API 层面禁止"返回缓冲指针"模式。

#### F7.【P1】确定性临时文件名 + 无 O_EXCL（TOCTOU/投毒）

**问题定位：** `FileIOUtils.h:86-104` `sanyi_<前缀>_<fnv哈希><ext>` 无随机性无 `O_EXCL`；`PdfToSvgConverter.cpp:545-586` 的 PDF→SVG 缓存 `sanyi_pdf_<hash>.svg` **永不清理**、可被预创建文件投毒。

**改造思路：** 临时文件用 `std::filesystem` + 随机后缀 + `O_CREAT|O_EXCL`（失败重试）；缓存文件加内容指纹校验并定期清理；改为进程内存缓存优先。

#### F8.【P1】Windows 中文路径断裂

**问题定位：** `UgParser.cpp:113` `std::ifstream(filePath,...)`、`ImageUtils.cpp:54,71,157` `std::fopen`/`stbi_load` 用裸 UTF-8 `char*`——Windows 下中文/空格路径失败。其余解析器已正确用 `std::filesystem::u8path`。

**改造思路：** 统一为 `std::filesystem::path`（u8path）贯穿 FileIO；OpenCV/stb 读取用 wide API 包装或读入内存再解析。

#### F9.【P1】回调在操作开始前即报"成功"

**问题定位：** `FileIOManager.cpp:121-124,241-244` 导入/导出回调在操作**执行前**就 `success=true` 触发；异常路径（`:167-171`）`catch(...)` 后不写错误缓冲也不回调——UI 无感知静默失败。

**改造思路：** 成功回调移到操作完成点；异常路径统一写错误码 + 失败回调。

#### F10.【P2】纯填充 SVG 被丢弃 → 合法文件导入失败

**问题定位：** `SvgParser.cpp:566-572` 丢弃无描边 shape；`FileIOManager.cpp:286-294` 把 `entityCount==0` 一律视为失败——合法空文档/纯填充图误报解析失败。

**改造思路：** 失败判定改为"解析错误标志"而非实体计数；纯填充 shape 转 `SyFillRegion`。

#### F11.【P2】`DxfConverter` 与 `DxfIrConverter` 重复约 400 行转换逻辑

**改造思路：** 删除旧实体直转路径（`DxfParser::parse` 的 legacy 分支），只保留 IR 路径（parseToIR→FioEntityConverter）；历史兼容由 `FileImporter` 死代码一并清理。

#### F12.【P2】IR 扩展 blob 越界读

**问题定位：** `Main/Src/Import/FioEntityConverter.cpp:146-148,341-350` NURBS/扩展点读取未校验 `blob.data` 非空、`offset+size<=blob.size`——畸形 IR 可 OOB。

## 5. 改造原则与验收红线

1. **先测后改**：每个改造先补/跑失败用例（bug 复现用例），再改实现，再回归。
2. **保持增量路径有效**：任何渲染改动不得引入全量重建回退（性能红线：选择/悬停无全量 gather）。
3. **DLL 契约先行**：涉及跨 DLL 类型/接口变更，先更新 `render_types.h`/`FioTypes.h` 等 POD 契约与 `static_assert`，再改实现。
4. **一轨推进**：每类重复实现（容差、undo、选择、命令总线）只能保留一条主线，新代码禁止走旧轨。
5. **构建可复现是最高红线**：从阶段 0 起，任何"换机/新克隆不可构建"回归一律视为 P0。
6. **删除优先于注释**：死代码直接删除并记入 git 历史，不保留"备份文件"（如 `original.cpp`）。
