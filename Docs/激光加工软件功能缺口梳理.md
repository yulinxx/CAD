# SanYi CAD 作为激光加工软件的功能缺口梳理

> 基准参考：LightBurn、EZCAD、RDWorks、CypCut 等主流激光切割/雕刻软件
> 分析日期：2026-11-03
> 范围：仅限仓库现有源码/文档的只读核对，不涉及运行时行为验证

> **历史快照（截至 2026-11-03）**：本文记录的是当时的盘点结论，正文保持原样。构建开关默认值与 CAM 模块状态已被后续提交改变，本文不再作为现状依据；阅读现状请以当前工作区代码为准。

**与现状冲突清单**（按 2026-11-05 工作区代码核对）：

1. 前 5 项缺口第 1 项、第 4 节末「CAM 层缺失的根因」、第 6 节 CAM 行、总结第 1 条：仓库已有 `CAM/CAM` 模块，`BUILD_CAM` 默认 ON（`Config.cmake:226`），根脚本 `CMakeLists.txt:257` 已接入 `add_subdirectory`。但执行路径仍是 `MotionPlanCompiler`（`Main/Src/Hardware/ProcessingJobService.cpp:446`），尚未调用 `Cam::compile`，因此"端到端未闭合"仍成立，"完全缺失"不成立。
2. 前 5 项缺口第 2 项及第 6 节整体判断「Hardware 默认关闭」：`BUILD_HARDWARE` 实际默认 ON（`Config.cmake:229`）。
3. 第 6 节构建开关默认值表：实际 `BUILD_HARDWARE`/`BUILD_VISION`/`BUILD_RASTER`/`BUILD_NETWORK`/`BUILD_CAM` 均为 ON（`Config.cmake:225-233`），`BUILD_NESTING`/`BUILD_ENGRAVING` 亦为 ON。
4. 第 9 节整体判断与风险表 R11「Vision 默认 OFF」：`BUILD_VISION` 实际默认 ON（`Config.cmake:225`）。
5. 根因描述「根 CMakeLists.txt 第 200-203 行明确注释仓库里暂时没有 CAM 模块目录」：当前 `CMakeLists.txt:200-201` 已改为「CAM/CAM 已落地，由 BUILD_CAM 开关控制」。
6. 第 2 节「Hardware 默认关闭 + 设备适配器为桩」与第 6 节设备发现行「只有 `SimulatedDevice`」：`Hardware/Hardware/Src/Device/DeviceRegistry.cpp:213-222` 已注册 6 类厂商适配器（BJJCZ、SCANLAB、雷赛、正运动、Aerotech、Ruida），不再只有仿真设备；真机验证状态另计。

---

## 最关键结论（前 5 项缺口）

| # | 缺口 | 严重度 | 影响 |
|---|------|--------|------|
| 1 | **CAM 层完全缺失**（路径生成到设备指令之间的工艺层） | P0 | 有几何→无加工：光有图元和位图处理，无法产出可下发设备的 G-code / 运动指令 |
| 2 | **Hardware 默认关闭 + 设备适配器为桩** | P0 | 即使打开 BUILD_HARDWARE，硬件模块只有 SimulatedDevice 和接口定义，无真机协议适配 |
| 3 | **位图处理→场景→工艺的 UI 链路断裂** | P1 | Raster C API 非常完整，但没有工作台入口把位图处理面板、参数对话框、结果入场景、Undo 串起来 |
| 4 | **缺共边切割、穿孔参数、功率曲线（速度调功）、断点续雕** | P0 | 这些是厚板/高速加工的必备工艺，缺失直接导致无法商用 |
| 5 | **作业队列、加工时间预估（完整版）、走刀模拟缺失** | P1 | 多批次生产场景无法支撑；单批加工也缺少事前估算和可视化校验 |

**整体判断**：仓库的底层算法资产（2D 几何、布尔、偏移、阵列、Raster、Nesting、Engraving 路径规划）**远超竞品平均水平**，但**从"几何处理"到"实际加工"的最后一公里几乎全断**。CAM 层缺失是最硬的天花板。

## 二、最短商用路线：再做 5 件事就能对外交付

> 假设目标是"给中小激光切割厂/广告标识厂一套可用的切割软件"（ezCAD/RDWorks 级定位），以下 5 件事按顺序做。

### 1. 建 CAM 层（几何→G-code 运动指令）— **P0**
**为什么第一？** 这是整个加工链的断点。现在仓库有：图元 → Raster → Engraving 路径 → MotionPlanCompiler 薄壳，但 MotionPlanCompiler 只做了基础 LineTo/ArcTo 编译。需要补：

- **共边切割**：相邻零件的共享边只走一次刀，是厚板/批量加工节省时间的关键
- **穿孔参数 + Ramp**：厚板需要先穿孔再穿过去，穿孔位置、时间、功率曲线独立配置
- **功率曲线（速度→功率映射表）**：高速切薄板时功率跟不上会断，低速切厚板会过烧
- **拐角处理**：尖角减速 + 圆角过渡 + 过切补偿
- **空移优化 + 反补偿（先加工内轮廓）**：减少空移和过烧
- **G-code 导出 + 运动卡指令**：至少支持 3~5 种主流运动卡协议

**工作量**：核心 3~4 周（有 Raster 和 Engraving 路径规划资产可复用），协议适配每种 1~2 周。

### 2. 位图处理工作台 UI — **P1**
**为什么第二？** Raster C API 的完整度已经超过 LightBurn，但没有工作台面板把"导入→预览→参数→入场景→Undo→加工"串起来。需要补：

- 位图导入 + 在视口里定位/缩放/旋转的交互
- 处理参数面板（模式：二值化/抖动/半调/功率图/高度图；阈值/网屏角度/功率范围）
- 预览 + 参数实时刷新
- 结果输出为 SyEntity（矢量轮廓）或标记为位图层
- Undo 压栈

**工作量**：UI 工作台入口 + 对话框 ≈ 2~3 周，Raster C API 不用改。

### 3. 真机设备适配器（先做 1~2 种主流协议）— **P0**
**为什么第三？** Hardware HAL 接口已经完备，DeviceHost 也写好了装配流程。只需要实现 1~2 种主流协议：

- **直线电机**（如雷赛、正运动、Aerotech）：至少覆盖 1 款主流
- **振镜卡**（如 CY2000、Scanlab RTC5/6）：至少覆盖 1 款主流
- 实现回零、红光预览、急停、暂停/恢复、断点续雕

**工作量**：HAL 接口已经对齐，每个协议适配器 ≈ 2 周。

### 4. 套料工作台入口 + 排版预览 — **P1**
**为什么第四？** Nesting 算法层已经很完整，API 稳定。需要的是：

- 套料工作台面板：零件列表 + 板材设置 + 启动求解
- 排版预览：在视口里可视化看到零件摆放和利用率
- 一键将套料结果转回场景（坐标变换 + 自动生成图元 + Undo 压栈）

**工作量**：Nesting API 已稳定，UI 层 ≈ 1~2 周。

### 5. 走刀模拟 + 加工时间预估 — **P1**
**为什么第五？** 这是"让用户敢下手"的最后一块拼图。操作员在正式加工前必须能看到：

- 走刀顺序动画（哪些先切、哪些后切）
- 空移路径和距离
- 激光开关时刻
- 预估总时间（切削时间 + 空移时间 + 穿孔时间）

**工作量**：依赖 CAM 层的刀路输出，≈ 1~2 周。

## 四、总结

SanYi CAD 的**算法资产**在同类产品中属于上游水平——2D 几何引擎、布尔运算、Raster 位图处理（含 Vectorize、割缝补偿、引入引出线、空移优化）、Nesting 套料、Engraving 路径规划、Vision 视觉都做到了可用以上的程度。

**致命短板只有两个**：
1. **CAM 层完全缺失**——几何处理的终点和硬件执行的起点之间，没有做工艺编译
2. **UI 集成层断裂**——Raster/Nesting/Vision 这些模块各自 API 很完整，但工作台入口、参数面板、Undo 链都没接上

好消息是，这两个短板都是**纯软件职责**，不依赖硬件协议。硬件侧（设备适配器）确实需要真机配合，但 HAL 接口已经对齐，只要选定 1~2 款主流协议就能在 2~3 周内打通。

**5 件事补完后**，就能对标 LightBurn 的 2D 切割+雕刻场景。3D 打印/扫描、高端视觉引导、云端协同是后续增量。
