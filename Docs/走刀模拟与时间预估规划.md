## 1. 定位与边界

### 1.1 推荐分层

| 子能力 | 归属层 | 理由 |
|--------|--------|------|
| **时间预估（TimeEstimator）** | CAM 模块内部 `Estimate/` 子目录 | 纯算法、纯 C++17、不依赖 Qt/OpenGL/UI，是 `Cam::compile` pipeline 的最后一段 |
| **时间轴构造（TimeAxisBuilder）** | CAM 模块内部 `Estimate/` 子目录 | 把 CamPlan 翻译成"每秒采样一次的刀具位置序列"，纯数据 |
| **播放控制（PlaybackController）** | UI 侧新建 `CamSimulatorService`（在 Main/Src/CAM/ 或 Main/Src/Hardware/） | 依赖 QTimer 做驱动，属于 UI 生命周期管理 |
| **渲染动画** | UI 侧，复用 RenderBridge / 视口画线 | 已有 OverlayScene + PersistentGeometryStore 足以表达 |

### 1.2 权衡说明

**为什么不把播放控制塞进 CAM 模块**：
- CAM 模块的设计约束是"纯 C++，不依赖 Qt"（见 CAM 层架构规划 §1.2 的 CMake 配置）。播放需要 QTimer、需要与 UI 命令中枢对接，必须在 UI 侧。
- 如果强行把播放做成 CAM 内部的 C++ 虚接口 + UI 侧实现，反而引入不必要的间接层，收益为零。

**为什么不把时间预估放进 UI 层**：
- 时间预估需要 CamPlan 的完整上下文（图层工艺参数、穿孔参数、功率曲线），这些都在 CAM 编译阶段内部可得。如果放到 UI 层，UI 就得反向 include CAM 的内部头 → 破坏边界。
- 预估的结果（estimatedSeconds）要写回 CamPlan 和 MotionPlanHeader，供 ProcessingJobService 的进度条使用。在 CAM 内部做，编译完立刻可得，零额外通信。

### 1.3 硬约束（与 CAM 层架构规划对齐）

1. **只消费中性数据**：走刀模拟和时间预估的唯一输入是 `CamPlan`（CAM 工具级输出），**不直接读 `Eg::SceneManager`、`Eg::SyEntity`、`LayerManager`**。如果某些调用点手头只有 `MotionPlanView`（设备 IR），可以额外提供一条从 MotionPlan 反推时间轴的路径，但必须在文档里明确标注为"降级模式"——IR 不含 sourceEntityId、不含穿孔语义、不含工艺参数名称，预估精度会下降。
2. **不依赖任何设备协议**：模拟不调 `IMotionCard` / `IGalvoCard` 的任何方法，不需要真机就能跑完整动画。
3. **UI 不持有 CAM 内部对象**：UI 侧通过 `CamSimulatorService`（Main 侧服务，持有 CamPlan 的只读副本）发起模拟，不直接调用 CAM::Estimate 命名空间下的函数。
4. **不重排刀序**：模拟的轨迹顺序必须严格来自 CamPlan 的 `layers[] → contours[] → segments[]` 序列（已由 Cam::compile 的 Order 子模块排好），不得自行重排。

## 2. 走刀模拟

### 2.1 播放模型：状态机

```
                    start() / compile 完成 + CamPlan 就绪
  [Idle] ──────────────────────────────────────────────▶ [Ready]
                                                           │
                                              play() ──────┤
                                                           ▼
                          seek(t) ──▶ [Playing] ◀──────────┤
                           （任何时刻）      │              │
                                             │ pause()      │
                                             ▼              │
                                          [Paused]          │
                                             │              │
                                    reset()  │  seek(0)     │
                                             ▼              │
                                          [Idle]            │
                                                           │
                                    所有段执行完毕 ──────▶ [Completed]
```

| 状态 | 含义 | 允许的操作 |
|------|------|-----------|
| Idle | 未编译 / 已关闭 | start → Ready |
| Ready | CamPlan 已加载，未开始播放 | play → Playing / seek → Paused / reset → Idle |
| Playing | 动画推进中 | pause → Paused / seek → 跳转 / 速度倍率调整 / 播放结束 → Completed |
| Paused | 暂停在某个时间点 | play → Playing / step → 单步 / seek → 跳转 / reset → Idle |
| Completed | 完整走完一遍 | play → 从头重放 / seek → 任意点 / reset → Idle |

### 2.2 时间轴与播放进度

**CAM 侧产出的时间轴数据结构**（放在 CAM/CAM/Include/CAM/Estimate/TimeAxis.h，属于 CAM 的 C++ 内部 ABI；不含 `structSize`，字段变更递增 `CAM_ABI_VERSION`）：

```cpp
namespace Cam
{
    /// 时间轴上的单个采样点（中性值类型）
    struct TimeAxisSample
    {
        double timeSec = 0.0;       ///< 累计时间（相对于计划开始）
        double posX = 0.0;
        double posY = 0.0;
        bool laserOn = false;       ///< 当前是否出光
        bool isRapid = false;       ///< 当前段是空移还是切削
        int32_t layerIndex = 0;
        int32_t passIndex = 0;
        int32_t contourIndex = 0;   ///< 当前轮廓在 CamPlan.layers[layerIndex].contours 内的索引
        uint64_t sourceEntityId = 0;///< 追溯用：高亮、报错定位
        bool isPierce = false;      ///< 当前是穿孔停留阶段
    };

    /// 时间轴查询接口（CAM 内部纯数据，无 UI 依赖）
    struct TimeAxis
    {
        double totalSeconds = 0.0;
        double cuttingSeconds = 0.0;
        double rapidSeconds = 0.0;
        double pierceSeconds = 0.0;
        double dwellSeconds = 0.0;
        std::vector<TimeAxisSample> samples;  ///< 按 timeSec 升序
        // 后续：可以加分段索引，让 UI 能快速跳到某个轮廓起点
    };

    /// 从 CamPlan 构造时间轴（纯函数，可后台线程调用）
    TimeAxis buildTimeAxis(const CamPlan& plan, const ProcessParamsMap& paramsByLayer);
}
```

**关键参数说明**：
- `samples` 密度：默认每 1mm 一个采样点 + 穿孔点 + 起停延时点，再加上匀速补采样把最长段控制在 10mm 以内。**超过上方段**（例如一条 2m 直线空移）的情况，按每 50mm 一个点自动降密度，避免十万级图元场景下 samples 爆炸。
- 加速/减速段：当前 S0/S1 阶段**不做** S 曲线离散，用匀加速模型近似，采样点按速度线性插值。S2 真机标定后再升级。
- `ProcessParamsMap`：`std::unordered_map<int32_t, ProcessParams>`（按 layerId 查速度/快速速度），由 UI 侧从 ToolpathJobInput 复制过来，CAM 侧不反向 include Engine2D 的 ProcessParams 头。

**UI 侧播放进度**：
- 当前时间 = 当前帧的 elapsed 毫秒 × 速度倍率。
- 通过 `TimeAxis::samples` 的二分查找定位当前段 + 线性插值精确坐标。
- 进度条显示"当前时间 / 总时间"（秒），同时显示"当前轮廓 / 总轮廓数"。

### 2.3 速度倍率

| 倍率 | 说明 | 实现 |
|------|------|------|
| 0.1× / 0.25× / 0.5× / 1× / 2× / 5× / 10× | 加速 / 减速 / 慢动作观察 | UI 侧 QTimer tick 间隔固定（如 16ms ≈ 60fps），每次 tick 推进的 `deltaSec` = `0.016 × 倍率`。 |
| 单步模式 | 每按一次前进一段 | 从当前位置跳到下一个 contour 的起点（即轮廓间的 RapidTo 结束点），而不是下一个像素。这样才能看到"跳刀顺序"这一对操作员最关键的信息。 |
| 跳到指定时间 | 进度条拖动 | 直接设 `currentTimeSec` 到目标值，内部重新二分定位。 |

### 2.4 视觉语义（RenderBridge 复用）

| 视觉元素 | 颜色 / 样式 | 说明 |
|----------|------------|------|
| **已加工轨迹** | 实线，颜色 = 图层色（从 CamPlan::layers[].params 映射） | 已走过的段，直接复用现有视口画线 |
| **当前刀具 / 激光头位置** | 实心圆点（半径 3px），激光出光时红色、空移时蓝色 | 每帧刷新位置 |
| **未加工轨迹** | 虚线，颜色 = 浅灰（globalColor） | 整份计划开始加载时一次性画好，播放过程中逐步擦除或改实线 |
| **空移路径** | 细虚线（宽度 1px，颜色偏蓝） | 与切削轨迹视觉区分，让操作员一眼看出哪些是空走 |
| **穿孔点** | 黄色圆点，略大于刀具点 | 标注穿孔位置，停留时间 > 300ms 时旁边显示穿孔毫秒数 |
| **引入 / 引出线** | 与所属切削段同色但略浅 | 走刀顺序的重要组成，必须显示 |
| **激光开关时刻** | 当前位置激光出光时，刀具点变为红色 + 外围一个 200ms 渐隐光圈 | 让操作员看到"激光什么时候亮的" |

**大规模路径（上方段）绘制与刷新策略**：
- 未加工轨迹**不在每帧重绘**。加载 CamPlan 时一次性用 `PersistentGeometryStore::upsert` 画好所有虚线（可分块：按图层分 group，按需可见性切换）。
- 已加工轨迹**每帧 append 一个 segment**，用 overlay 的临时 buffer 逐段追加，累积到 100 段时 flush 一次（避免每帧调一次 GPU）。
- 刀具点**每帧 update 一个 marker**，复用 `PinnedMarkerGeometry` 或类似机制，只更新位置坐标，不重建几何体。
- **可选优化**：当当前段已过且下一段是 Rapid（空移），刀具点短暂变为蓝色，动画过程中不刷激光圈——这能让操作员清晰区分切削 vs 空移阶段。

### 2.5 与真实刀序一致性的保证

**CamPlan 的轮廓顺序就是加工顺序**，走刀模拟**不得自行重排**。保证方式：

1. TimeAxisBuilder 严格按 `plan.layers[layerIndex].contours[contourIndex] → segments[segmentIndex]` 顺序展开，不做任何 reorder。
2. 对每个 contour 内的 segments，顺序即 `compiler` 输出顺序——由 KerfCompensator、LeadInOut、PiercePlanner、CornerProcessor 等子模块依次追加。
3. 跨图层空移：第 N 层最后一个 contour 的结束点到第 N+1 层第一个 contour 的穿孔点之间，TimeAxisBuilder **自动补一条 Rapid 段**（速度 = rapidSpeedMmPerSec），时间 = 距离 / rapidSpeed。
4. **验收手段**：对黄金文件 CamPlan，跑 TimeAxisBuilder 后 `TimeAxis.samples` 的第一个非穿孔点的 sourceEntityId 必须等于 CamPlan.layers[0].contours[0].sourceEntityId。单元测试里直接断言这个。

### 2.6 交互入口与边界

```
UI（菜单/工具栏点击"走刀模拟"）
    │ 或（加工前确认对话框点击"预览走刀"）
    ▼
LaserOperationRegistry 注册的新命令（如 Laser_StartSimulation）
    │
    ▼
命令处理器（Main/Src/CAM/CamSimulatorService）
    │① 检查 CamPlan 是否已编译（未编译则先触发 Cam::compile，复用编译服务缓存）
    │② 调 Cam::buildTimeAxis(plan, paramsMap) → TimeAxis
    │③ 创建 PlaybackController（持有 TimeAxis + 当前时间 + 状态）
    │④ 发信号通知 UI：onSimulationReady(timeAxis)
    ▼
UI 视口接收信号 → 绑定 overlay → 启动 QTimer 播放
```

**UI 不持有内部对象**：
- UI 侧**不能** new `Cam::TimeAxis`、**不能**遍历 `CamPlan::contours[]`。
- UI 侧只能通过 `CamSimulatorService` 的公共接口（`play/pause/seek/setSpeedMultiplier`）和信号（`positionChanged(x,y,laserOn)`、`stateChanged(state)`、`progressChanged(curSec,totalSec)`）驱动动画。
- `CamSimulatorService` 是 `QObject`，持有 `CamPlan` 的只读副本（编译时拷贝，编译结束后不依赖 CAM 内部任何对象）。

### 2.7 中断与恢复

| 场景 | 处理 |
|------|------|
| 模拟中途用户点击"停止"或切换到其他命令 | PlaybackController 进入 `Idle` 状态，overlay 的模拟图层立即 clear，但 CamPlan 副本保留（下次 start 时可立即进入 Ready）。 |
| 用户关闭包含 CamPlan 的文档 | `CamSimulatorService` 监听 `documentClosed` 信号，自动 reset 所有状态 + 释放 CamPlan 副本。 |
| 用户切换工作台（3D ↔ 2D） | 模拟只在 2D 视口有实际意义；3D 工作台自动 pause + 进入 Ready 状态，避免跨视口坐标错乱。 |
| 编译完成后设备直接 startJob（真机加工开始） | **真机加工 ≠ 走刀模拟**，两者状态机独立。模拟如果在播放中被打断，不影响真机执行——但 ProcessingJobService 应在 `startJob` 时发一个 `simulationInterrupted` 信号，让 UI 同时停止播放。 |
| 切文档 → 再切回来 | CamPlan 副本已在文档关闭时释放，切回来时服务处于 Idle，用户需重新点击"开始模拟"。 |

## 3. 加工时间预估

### 3.1 计算模型

**时间 = 切削时间 + 空移时间 + 穿孔时间 + 延时**，分项计算后求和。

| 项 | 如何取得 | 公式 | 缺失时如何保守估计 |
|----|----------|------|-------------------|
| **切削段时间** | CamPlan.layers[].contours[].segments[] 的 PathSegment（Line/Arc）+ ProcessParams.speedMmPerSec | Line：`length / speed`<br>Arc：`arcLength / speed`，arcLength 由 radius + 扫掠角算 | 速度字段缺失 → 用 ToolpathJobInput 的全局默认（200 mm/s），并在预估结果里标 `confidence = low` |
| **空移段时间** | Rapid 段由 TimeAxisBuilder 在 contour 之间自动补（距离从当前 contour 终点到下一个 contour 穿孔点）+ ProcessParams.rapidSpeedMmPerSec | `distance / rapidSpeed` | rapidSpeed 缺失 → 用默认 300 mm/s；且**保守假设**空移距离是直线（不考虑 TSP 实际路径），所以如果将来引入 CoEdgeFinder 或更复杂的 TravelOptimizer，空移时间可能比这个估计短。这是**已知误差源** |
| **穿孔时间** | PierceParams.pierceCount × (pierceDelayUs + dwellUs) + 穿孔前的空移段（rapid） | 总穿孔时间由 PierceParams 直接给出，不在 CamPlan.segments 里——TimeAxisBuilder 在 contour 起点前插入 pierce 的 rapid + dwell 序列 | PierceParams.enabled = false → 穿孔时间 = 0；PierceParams 字段缺失 → 用默认值（pierceCount=1, pierceDelayUs=500, dwellUs=200） |
| **起停延时** | 激光器开关延时（固定值，配置在 MachineProfile 或 ProcessParams 的扩展字段里，如 `laserOnDelayUs`/`laserOffDelayUs`） | 每次激光开关事件累加 | 字段缺失 → 用保守默认（on=100us, off=50us）。对总时间的贡献通常 < 1%，影响可忽略 |
| **层切换时间** | 换层时的空移 + 可能的激光器复位 | 层间距离 / rapidSpeed + 起停延时 × 2 | 同空移时间 |
| **加速度影响（详细档）** | 匀加速模型：起速段 `v² = 2·a·s`，求出 s = v²/(2a)；减速段对称。段长 < 2s 时速度达不到设定速度 | 详细档 S1 阶段引入；快速档 S0 不考虑加速度，直接 length/speed 匀速近似 | 加速度参数缺失 → 保守假设加速度 = 设定速度（极端保守：永远能瞬间达到目标速度，会**低估**总时间），标 `confidence = low` |
| **拐角限速（详细档）** | cornerParams.strategy=2（尖角减速）或 strategy=1（圆角过渡）时，在拐角处根据夹角大小乘一个 slowdownFactor | 尖角（<30°）：速度 × 0.5<br>钝角（>150°）：速度 × 1.0<br>中间：线性插值 | cornerParams 缺失 → **不做**拐角减速，等同快速档。这会**低估**尖角密集件（如锯齿形轮廓）的真实加工时间——可能差 20%-50% |
| **功率调制的间接影响** | 功率曲线（PowerCurve）影响激光能量，理论上影响切割质量和可能的返工，但**不直接影响运动速度**，所以对加工时间预估的贡献为 0 | 不计入 | — |

### 3.2 两种精度档

| 维度 | 快速估算（QuickEstimate） | 详细估算（DetailedEstimate） |
|------|--------------------------|------------------------------|
| **适用场景** | 作业队列排序、粗量级告知 | 加工前确认对话框、导出面板最终时间 |
| **输入** | 仅 CamPlan 路径长度 + 每层一个速度值 | CamPlan + 完整 ProcessParams + PierceParams + CornerParams + 加速度参数 |
| **计算成本** | O(contours)，一次遍历累加 | O(segments) × 拐角检测 × 加速减速段展开 |
| **误差预期** | ±30%（保守低估，因忽略加速度和拐角限速） | ±10%~15%（S1 阶段），±5% 以内（S2 真机标定后） |
| **CAM 编译后耗时** | < 1ms（一次累加） | ~5ms（十万图元量级） |
| **是否后台线程安全** | 是（纯累加） | 是（纯计算，不依赖 Qt/OpenGL） |
| **在 Cam::compile 内的位置** | S0 阶段就可放在 CamCore 末尾 | S1 阶段引入 CornerProcessor 和 PiercePlanner 后才能完整 |
| **输出里的置信度标注** | 固定标 `confidence = low` | 根据输入参数完整度动态标 `low / medium / high` |

### 3.3 真机偏差标定（S2 阶段）

**问题**：匀加速模型 vs 真机的 S 曲线加减速、拐角限速参数、空移 TSP 优化后的实际路径——这些都在快速/详细档里做了近似，与真机有系统偏差。

**最小实施路径**：

```
真机实际切割一批样本件
    ↓
ProcessingJobService 记录 jobStartTs / jobFinishTs + CamPlan
    ↓
Main/Src/CAM/CalibrationDatabase（纯 SQLite 表）
    ↓
CalibratorService.fit()：用最小二乘拟合
    - 加速度系数：让匀加速模型的时间 × k_acc 逼近实测时间
    - 拐角系数：让拐角限速的 slowdownFactor 矩阵 × k_corner 逼近实测
    - 空移修正系数：让 rapid 时间 × k_rapid 逼近实测
    ↓
CalibrationProfile 写入 SQLite，下次 TimeEstimator 自动加载
    ↓
预估时间 = 详细档原始结果 × k_acc × k_corner × k_rapid
```

**数据结构草案**：

```cpp
namespace Cam
{
    /// 校准系数（中性值类型）
    struct CalibrationProfile
    {
        double accelMultiplier = 1.0;    ///< 加速度修正：真机加速比模型慢则 > 1.0
        double cornerMultiplier = 1.0;   ///< 拐角限速整体修正
        double rapidMultiplier = 1.0;    ///< 空移时间修正
        double laserSwitchExtraUs = 0;   ///< 激光器开关延时额外补偿
        char lastCalibrated[32] = {};    ///< ISO8601 时间戳
        int32_t sampleCount = 0;          ///< 拟合时用了多少条真机记录
    };

    /// 校准样本（供 UI 录入或自动采集）
    struct CalibrationSample
    {
        char sampleId[64] = {};
        double estimatedSeconds = 0.0;    ///< 本次预估时间
        double actualSeconds = 0.0;       ///< 真机实测时间
        double totalLengthMm = 0.0;
        double rapidLengthMm = 0.0;
        double pierceCount = 0;
        char machineId[64] = {};          ///< 哪台设备切的（多机场景关键）
    };
}
```

**关键设计约束**：
- **每台设备一份独立 profile**，因为不同型号的加减速曲线差异巨大。`CalibrationProfile` 必须绑定 `machineId`。
- 用户可以手动触发"重新拟合"，也可以关闭校准功能（此时所有 multiplier = 1.0）。
- S0/S1 阶段先**不做**标定，TimeEstimator 用纯模型输出，误差接受 ±30% 即可。

### 4.3 线程与生命周期

| 任务 | 线程模型 | 取消/进度 | 防重入 |
|------|---------|----------|--------|
| `Cam::estimateQuick` / `estimateDetailed` | 后台线程安全（纯函数、只读输入） | 无进度（< 10ms 无需） | 天然可重入 |
| `Cam::buildTimeAxis` | 后台线程安全（同上） | 可在 samples 追加过程中检查 `Progress.cancelled`（参考 CAM 层架构规划 §4.3 的 Progress 机制） | 天然可重入 |
| `CamSimulatorService` 播放循环 | **必须主线程**（QTimer 驱动） | UI 直接 pause/reset，无取消语义 | UI 侧单例 + `isRunning()` 检查 |
| 真机标定 `CalibratorService.fit()` | 后台线程（SQLite 读写 + 拟合） | 可加取消标志 | 单例 + fit 期间锁 |

**关键线程约束**：
- CAM 侧的 `TimeEstimator`、`TimeAxisBuilder`、`toolPositionAt`、`segmentsInRange` 都是**无状态纯函数**，任何线程都能调用，不需要锁。
- UI 侧的 `CamSimulatorService` 继承 QObject，**只能在主线程构造和使用**——因为 QTimer 的 timeout 事件在主线程派发。
- 播放时不直接访问 CamPlan：`CamSimulatorService::loadPlan` 时已经把 CamPlan 拷贝进来了，后续播放循环只读 TimeAxis 副本，与 CAM 模块解耦。

## 5. 依赖与排期

### 5.1 与 CAM M0~M3 的前置关系

| 阶段 | 依赖 CAM 输出 | 具体依赖字段 |
|------|-------------|-------------|
| **S0 快速估算**（CAM M1 同步） | CamPlan.layers[].contours[].segments[] | `PathSegment.length`（或 line: ptStart→ptEnd 距离、arc: 扫掠角 × radius）+ `ProcessParams.speedMmPerSec` |
| **S1 详细估算 + 时间轴模拟**（CAM M1~M2 之间） | CamPlan + PiercePlanner 输出 + CornerProcessor 输出 | 除 S0 外，还需要 PierceParams（穿孔点位置、pierceCount/dwell）、CornerParams（slowdownFactor 按转角大小插值） |
| **S2 真机标定**（CAM M3 同步） | CamPlan + ProcessingJobService 真机实际耗时日志 | 真机必须已落地，否则校准数据为零 |

**不依赖 CAM 的阶段**：
- S0 快速估算只需要 CamPlan 的路径长度，CAM M0 产出的骨架 CamPlan 即可满足。
- 如果当前只有 MotionPlanView（设备 IR）而没有 CamPlan（CAM 模块尚未创建），也可以**从 MotionPlanView 反推时间轴**——用 LineTo/ArcTo 的 target 距离 + SetFeedRate 的速度 + Dwell 的 durationUs 累加。但这是降级模式：IR 里没有 sourceEntityId、没有 pierce 参数（Dwell 是什么场景下的停留）、没有图层工艺参数覆盖。降级模式的预估误差会再大 10%~15%。

### 5.2 与其他模块的先后

| 模块 | 先后关系 | 原因 |
|------|---------|------|
| **作业队列** | 本规划 S0/S1 → 作业队列 | 作业队列需要预估时间做排序，先有预估才有队列 |
| **套料预览** | 独立 | 套料是排版，模拟是走刀，互不依赖 |
| **位图加工（Raster 模块）** | 本规划依赖 CAM M0 的 RasterEngraveCompiler 骨架 | 位图加工的 CamPlan 可能先只产出 contour 路径，无 raster fill segment——模拟时跳过 raster segment 即可 |
| **真机适配器** | 本规划 S0/S1 不依赖，S2 强依赖 | S0/S1 纯软件验证，S2 标定必须真机 |

### 5.3 分阶段路线

#### S0 —— 快速估算（CAM M1 同步，3~5 天）

| 范围 | 可验证产出 | 验收标准 | 粗略工作量 |
|------|-----------|----------|-----------|
| CAM `Estimate/TimeEstimator.cpp` 骨架 + `estimateQuick` | 给定 CamPlan（手工构造），返回 TimeEstimateResult（totalSeconds > 0） | 单元测试：正方形轮廓 100mm 边长 + speed=200mm/s → expected = 4×100/200 = 2.0s（忽略角点加速），断言误差 < 5% | 2~3 天 |
| CamCore::compile 末尾自动调 estimateQuick | 编译完的 CamPlan 自动带 estimatedSeconds 字段 | 单元测试：compile 完断言 plan.estimatedSeconds ≈ estimateQuick(plan).totalSeconds | 1 天 |
| MotionPlanHeader 写入 estimatedSeconds | ProcessingJobService.startJob 拿到的 MotionPlanView.header.estimatedSeconds 有值 | ProcessingJobService 已有 `progressFraction()` 依赖这个值；跑端到端 → 进度条能推进 | 0.5 天 |

**风险**：CamPlan 骨架在 CAM M0 阶段才能生成。如果 CamPlan 结构中途调整，TimeEstimator 里 contour/segment 的访问路径要跟着改。

#### S1 —— 详细估算 + 时间轴模拟数据（CAM M1~M2 之间，5~7 天）

| 范围 | 可验证产出 | 验收标准 | 粗略工作量 |
|------|-----------|----------|-----------|
| `estimateDetailed`（含匀加速模型 + 穿孔时间 + 拐角限速） | 给定完整 ToolpathJobInput（含 PierceParams/CornerParams）的 CamPlan → 返回分项秒数 | 单元测试：含 5 个 50mm 角点锯齿形轮廓 → 详细估算 > 快速估算（因拐角减速），误差 < 15% | 3 天 |
| `Estimate/TimeAxis.h` + `TimeAxisBuilder` | `buildTimeAxis(plan, paramsMap)` 产出 TimeAxis，samples 按 timeSec 升序，首个非穿孔 sample 的 sourceEntityId = CamPlan 首 contour 的 sourceEntityId | 单元测试断言顺序一致性 | 2 天 |
| `toolPositionAt` + `segmentsInRange` | 给定任意 timeSec，返回正确的 ToolPositionSnapshot | 单元测试：时间轴的末端 timeSec → posX/posY ≈ 计划最后一个 contour 的终点 | 1 天 |

**风险**：拐角限速的 slowdownFactor 模型需要和 CornerProcessor 的实现保持一致。如果 CornerProcessor 没做拐角减速（策略=0），TimeEstimator 里不能凭空加——需要从 CamPlan 的 contour 上读取是否有 corner 标记。这要求 CamPlan 在 M1 阶段 contour 上附加 cornerFlags 字段（见 CAM 层架构规划 §2.3 的 CamPlan::Contour，需补充 cornerFlags）。

#### S2 —— UI 播放器（CAM M2 同步，6~8 天）

| 范围 | 可验证产出 | 验收标准 | 粗略工作量 |
|------|-----------|----------|-----------|
| `Main/Src/CAM/CamSimulatorService.{h,cpp}` | 继承 QObject + QTimer 驱动 | 单元测试（无事件循环）：手动调 `loadPlan` → `play` → `poll` 模拟时钟推进 → 断言 `positionChanged` 信号顺序正确 | 3 天 |
| 激光加工命令中枢新增命令 | LaserOperationRegistry 注册 `Laser_StartSimulation` / `StopSimulation` | 单元测试：模拟命令触发 → CamSimulatorService 收到 loadPlan | 1 天 |
| 视口 overlay 渲染 | overlay 画出未加工虚线 + 已加工实线 + 当前刀具点 | 视觉验收：正方形 CamPlan 加载 → 看到灰色轮廓虚线 → 播放中虚线逐步变红实线 → 刀具点从起点走到终点 | 2~3 天 |
| 分段统计 UI | 右侧面板显示分项时间（切削/空移/穿孔/延时） | UI 验收：走刀模拟播放时分段统计实时更新 | 1 天 |

**风险**：RenderBridge 的 overlay 接口如果缺少"批量画线"能力，需要先在 RenderBridge 里补一个 bulk upsert（一条命令塞多段 line segment），避免每帧逐段调 GPU 导致卡顿。预计 RenderBridge 补这个能力需要 0.5~1 天。

#### S3 —— 真机标定闭环（CAM M3 同步，5~7 天，**必须真机**）

| 范围 | 可验证产出 | 验收标准 | 粗略工作量 |
|------|-----------|----------|-----------|
| SQLite 表 + CalibratorService | 每次真机加工结束，ProcessingJobService 把 CamPlan + 实际耗时 + machineId 写入 calibration_samples 表 | 跑一次真机加工 → 查表有新行 | 1 天 |
| CalibratorService.fit() | 用已有样本拟合 → 产出 CalibrationProfile（每台 machineId 一份） | 构造 10 个样本（estimated=100, actual=115 的比例） → fit 后 accelMultiplier ≈ 1.15 | 2 天 |
| TimeEstimator 应用 CalibrationProfile | 预估时间 × calibration multipliers | 真机实测：5 台不同的轮廓，每台跑预估 → 真机 → 预估，fit 后误差 < 5% | 2~3 天 |

**风险**：真机数量太少（例如只有 1 台），拟合 profile 的泛化能力差。应在 UI 里明确提示"校准基于 N 台设备、M 个样本拟合，新机型请重新校准"。

### 6.1 无硬件依赖的测试（全部阶段）

## 7. 风险与反模式

### 🔴 高风险反模式（必须防）

| # | 反模式 | 后果 | 约束写法 |
|---|--------|------|----------|
| 1 | **模拟器自行重排刀序**（例如"为了动画更顺眼"把跳刀变成连续轨迹） | 操作员看到的走刀顺序与真机实际顺序不符，可能在"空移时碰撞干涉"类场景下给出危险误导 | TimeAxisBuilder 的输出顺序**必须**是 `plan.layers → contours → segments` 的纯遍历，单元测试里断言 samples[0].sourceEntityId == plan首contour.sourceEntityId |
| 2 | **预估模型里写死某款设备的加速度/拐角系数** | 换一台真机（或未来同时支持运动卡 + 振镜卡），预估系统误差 > 50% 无法标定 | TimeEstimator 的输入里**绝不能**出现厂商名、SDK 类型、或设备型号。加速度等参数必须从 EstimateProcessParams 里读；字段缺失时用保守默认 + confidence=low |
| 3 | **UI 直接遍历 CamPlan 内部结构**（例如 UI 侧自己写个 for 循环画 contour） | 未来 CamPlan 增加字段（如 cornerFlags、rasterFillSegments），UI 就得跟着改多处，CAM 和 UI 解耦失效 | UI 侧画线**只能**通过 CamSimulatorService.segmentsAdded 信号拿 segments 批量画；ToolPositionSnapshot 是中性值类型，UI 不依赖 CAM 的任何内部结构 |
| 4 | **把模拟做成 MotionPlan 的截图回放**（例如 MotionPlanEmitter 执行一段录一段坐标，然后回放） | MotionPlan 可能被设备适配器离散成更多段（例如圆弧离散成 100 条直线），回放的不是"走刀顺序"而是"适配器内部轨迹"，与 CamPlan 里的轮廓顺序脱节 | 模拟必须从 CamPlan 构造时间轴，**不从 MotionPlan 回放**。MotionPlanView 反推只是降级路径，不是主路径 |
| 5 | **模拟播放循环依赖 Qt** 写进 CAM 模块 | CAM 模块就会被迫 link Qt，破坏 CAM 层架构规划 §1.2 "纯 C++" 的边界 | CAM 的 Estimate/ 子目录的头文件**不得 include Q* 任何头**。播放循环必须在 UI 侧 CamSimulatorService 里做 |

### 🟡 中风险反模式

| # | 反模式 | 后果 | 约束 |
|---|--------|------|------|
| 6 | **TimeAxisBuilder 自己算转角**（而不是从 CamPlan 读 cornerFlags） | 转角检测算法和 CornerProcessor 可能不一致，导致拐角限速在预估和真实加工里算两次或一次都没算 | CornerProcessor 在 contour 上附加 cornerFlags；TimeAxisBuilder **只读**标记，自己不算转角 |
| 7 | **空移时间用直线距离近似，但 TravelOptimizer 将来可能做共边或路径绕回** | 预估的空移时间偏小（TSP 后实际路径更长）或偏大（共边后某些 Rapid 段被消除），造成预估偏差 | 空移时间在 S1 阶段先明确标注为"直线近似，误差 ±20%"；将来 TravelOptimizer 产出实际空移段路径时再升级 |
| 8 | **忽略 raster fill segment 的时间**（假设位图加工未来才做） | 对已启用 raster engraving 的项目，预估严重偏低 | TimeAxisBuilder 里遇到 contour.kind=Raster 时，用段数 × scanAngle + lineSpacing 折算扫描线数量，每条扫描线按 speed 算时间。先做近似，M1 raster fill 完整实现后升级 |
| 9 | **CalibrationProfile 不绑定 machineId** | 多台不同型号的真机共用一份校准 profile，校准失效 | CalibrationProfile 结构体必须含 machineId 字段；拟合结果存入 SQLite 时按 machineId 分表或分 key |

### 🟢 低风险

| # | 反模式 | 后果 |
|---|--------|------|
| 10 | 模拟不显示激光开关时刻 | 操作员看不到"激光什么时候亮"的关键信息，失去走刀模拟的一半价值 |
| 11 | 进度条只显示"已处理轮廓数/总轮廓数"不显示时间 | 操作员无法判断加工还剩多少秒，对 job queue 排序无帮助 |

## 附录 B：需要用户拍板的关键决策点

| # | 决策点 | 选项 | 推荐 | 理由 |
|---|--------|------|------|------|
| D1 | 时间预估快速档的默认输出位置 | ① 编译完成后自动在 UI 状态栏显示<br>② 只在加工前确认对话框显示 | ① 自动显示，作为即时反馈；详细估算只在加工前确认时触发 | 快速估算 < 1ms，零成本；让操作员随时看到"这批大概烧多久" |
| D2 | 是否引入真机标定闭环（S3） | ① **必须做**（CAM M3 同步）<br>② 先跳过，后续视用户反馈再加 | ① 必须做 | 匀加速模型的系统偏差在真机上普遍 15%~30%，不做标定就无法给用户可靠的"预计时间"；加工前确认对话框里如果显示的时间与实际差 30% 以上，会导致用户不信任软件 |
| D3 | 模拟是否支持逐帧回放导出视频 | ① 支持（Qt Multimedia 录制 overlay）<br>② 暂不支持 | ② 暂不支持 | 功能成本 ≥ 3 人天（编码库选择、帧同步、UI），且走刀模拟本身还没做稳就加视频导出，属于典型的过早优化 |
| D4 | TimeAxisBuilder 的 samples 密度策略 | ① 按距离（每 1mm 一个点）<br>② 按时间（每 20ms 一个点）<br>③ 动态（距离为主，时间过短的段合并） | ③ 动态 | ① 上方段（2m 直线）会产生 2000 个点冗余；② 1mm/s 慢速会产生巨量点；③ 在两者之间取最优 |
| D5 | 是否在模拟里显示 Raster fill（位图雕刻的扫描线） | ① 是，和 contour 走刀一样动画推进<br>② 暂不显示 raster segment | ② 暂不显示，等 raster engraving 完整实现后再评估 | S0/S1 阶段 RasterEngraveCompiler 还是骨架，实际 contour 产出的 raster fill segment 数量和路径都未确定 |
