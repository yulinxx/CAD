# 项目 / 任务模型设计草案

## 1. 文档目的

本文用于设计工业激光加工软件中的项目与任务模型，目标是把单纯的图形编辑、工艺定义和路径生成，进一步组织成可保存、可复用、可批处理、可执行的工程体系。

本草案重点回答以下问题：

- 项目模型和任务模型为什么必须独立
- 它们需要哪些核心对象和字段
- 如何与工艺数据模型、路径系统和仿真系统衔接
- 如何为后续硬件执行预留统一入口

---

## 2. 系统定位

项目 / 任务模型位于工艺数据模型、路径系统和仿真系统之上，用于组织整个加工流程的工程结构。

### 2.1 项目模型的职责

项目模型负责：

- 组织整份工程数据
- 管理多个工件、多个工艺层和多个任务
- 保存全局配置和设备能力信息
- 作为保存、加载和版本管理的顶层容器

### 2.2 任务模型的职责

任务模型负责：

- 描述一段可执行的加工批次
- 组织多个工艺对象与路径对象
- 管理加工顺序与执行状态
- 支持排队、暂停、恢复和重试

### 2.3 与工艺和路径的关系

- 工艺模型决定“怎么加工”
- 路径系统决定“如何运动”
- 项目 / 任务模型决定“先加工什么、后加工什么、整体如何执行”

---

## 3. 总体结构

建议采用如下层级：

```text
ProjectModel
    ├── ProcessDocument
    ├── MaterialProfile
    ├── MachineProfile
    ├── ProcessLayer[]
    ├── TaskGroup[]
    └── TaskJob[]
```

### 3.1 组织原则

- 项目是顶层容器
- 任务是执行单元
- 任务组用于批处理或工序分组
- 文档保存图形、工艺、路径与任务的关联

---

## 4. 核心对象设计

### 4.1 ProjectModel

项目模型是整个工程的顶层对象。

#### 职责
- 保存项目元数据
- 组织文档、任务和工艺配置
- 保存全局材料和设备默认配置
- 支持工程版本管理

#### 建议字段
- `id`: QString
- `name`: QString
- `description`: QString
- `version`: QString
- `createdAt`: QDateTime
- `updatedAt`: QDateTime
- `documentId`: QString
- `materialProfileId`: QString
- `machineProfileId`: QString
- `defaultProcessPresetId`: QString
- `taskGroupIds`: QStringList
- `taskIds`: QStringList
- `metadata`: QVariantMap

---

### 4.2 ProjectDocument

文档承载项目内的所有数据。

#### 职责
- 保存几何数据
- 保存工艺数据
- 保存路径数据
- 保存任务数据
- 提供序列化与反序列化入口

#### 建议字段
- `id`
- `projectId`
- `name`
- `revision`
- `geometryEntities`
- `processObjects`
- `toolPaths`
- `simulationResults`
- `metadata`

---

### 4.3 TaskJob

任务是实际执行顺序中的最小可管理单元。

#### 职责
- 组织一个加工批次
- 绑定工艺对象和路径对象
- 保存执行顺序和状态
- 提供仿真和设备输出入口

#### 建议字段
- `id`: QString
- `name`: QString
- `projectId`: QString
- `groupId`: QString
- `processObjectIds`: QStringList
- `toolPathIds`: QStringList
- `priority`: int
- `status`: QString
- `progress`: double
- `createdAt`: QDateTime
- `updatedAt`: QDateTime
- `startedAt`: QDateTime
- `finishedAt`: QDateTime
- `metadata`: QVariantMap

---

### 4.4 TaskGroup

任务组用于批量组织任务。

#### 职责
- 将多个任务归类
- 支持工艺阶段划分
- 支持批量启用、禁用、排序

#### 建议字段
- `id`: QString
- `name`: QString
- `projectId`: QString
- `taskIds`: QStringList
- `enabled`: bool
- `priority`: int
- `metadata`: QVariantMap

---

### 4.5 TaskStep

任务步骤用于描述任务内部的执行顺序。

#### 职责
- 表示任务中的一个加工步骤
- 绑定具体工艺对象或刀路对象
- 支持分步执行和暂停恢复

#### 建议字段
- `id`: QString
- `taskId`: QString
- `sequenceIndex`: int
- `processObjectId`: QString
- `toolPathId`: QString
- `operationType`: QString
- `status`: QString
- `metadata`: QVariantMap

---

## 5. 状态设计

### 5.1 TaskState

```cpp
enum class TaskState
{
    Idle,
    Ready,
    Running,
    Paused,
    Completed,
    Failed,
    Cancelled
};
```

### 5.2 状态说明

| 状态 | 说明 |
|------|------|
| Idle | 未准备 |
| Ready | 已准备，可执行 |
| Running | 正在执行 |
| Paused | 已暂停 |
| Completed | 执行完成 |
| Failed | 执行失败 |
| Cancelled | 被取消 |

### 5.3 ProjectState

项目层也可拥有整体状态，但它更多是“工程状态”，例如：

- 是否有未保存修改
- 是否已校验
- 是否已生成路径
- 是否已完成仿真

---

## 6. 任务执行流程

### 6.1 标准流程

```text
选择项目
    → 打开文档
    → 配置材料和设备
    → 创建/修改工艺
    → 生成路径
    → 进行仿真校验
    → 生成任务
    → 排序任务
    → 执行任务（后续硬件）
```

### 6.2 任务内部流程

```text
TaskJob
    → TaskStep 1
    → TaskStep 2
    → TaskStep 3
    → ...
```

### 6.3 任务执行策略

- 顺序执行
- 条件执行
- 批量执行
- 失败重试
- 暂停恢复

---

## 7. 与工艺数据模型的关系

### 7.1 引用关系

项目和任务不应直接复制工艺数据，而应引用工艺对象。

#### 推荐关系
- `TaskJob` 引用 `ProcessObject`
- `TaskStep` 引用 `ToolPath`
- `ProjectModel` 汇总任务与文档

### 7.2 优势

- 避免数据重复
- 方便工艺修改后重算路径
- 支持撤销重做
- 便于版本管理

### 7.3 失效机制

当工艺对象或几何对象变化后：

- 相关路径失效
- 相关仿真结果失效
- 相关任务进入待重算或待校验状态

---

## 8. 与路径系统的关系

### 8.1 任务如何使用路径

任务本质上是路径的调度单位。

#### 典型依赖
- 一个任务可绑定多个路径
- 一个路径只属于一个工艺上下文
- 一个任务可拆成多个步骤

### 8.2 路径变化后的影响

如果路径重新生成：

- 任务步骤顺序可能变化
- 任务状态可能需要回到 Ready
- 仿真结果需要重新生成

---

## 9. 与仿真系统的关系

### 9.1 仿真对象来源

仿真应基于项目或任务进行，而不是孤立针对单个实体。

### 9.2 关系方式

- 项目级仿真：检查整体工程
- 任务级仿真：检查单个执行单元
- 步骤级仿真：检查某一步的路径和工艺

### 9.3 仿真结果写回

建议项目和任务对象保存以下字段：

- `simulationState`
- `lastSimulationResultId`
- `lastValidatedAt`
- `lastValidatedBy`

这样可以在 UI 中清楚展示当前工程是否通过校验。

---

## 10. 与 2D / 3D 框架的衔接

### 10.1 2D 视口中的展示

2D 视口可用于：

- 显示项目中的几何结构
- 显示当前任务所关联的工艺对象
- 显示路径预览和任务顺序
- 高亮当前步骤

### 10.2 3D 视口中的展示

3D 视口可用于：

- 显示工件在空间中的布置
- 显示任务执行顺序
- 显示仿真刀路动画
- 显示设备姿态与参考坐标

### 10.3 状态中心衔接

建议状态中心保存：

- 当前项目 ID
- 当前文档 ID
- 当前任务 ID
- 当前任务组 ID
- 当前步骤 ID
- 当前任务状态

---

## 11. 命令系统衔接

项目与任务的编辑、生成和执行应由命令系统驱动。

### 11.1 典型命令

- `CreateProjectCommand`
- `OpenProjectCommand`
- `SaveProjectCommand`
- `CreateTaskCommand`
- `GenerateTaskCommand`
- `RunTaskCommand`
- `PauseTaskCommand`
- `ResumeTaskCommand`
- `CancelTaskCommand`
- `RebuildTaskCommand`

### 11.2 职责边界

命令负责：
- 收集用户意图
- 修改项目/任务模型
- 触发校验或仿真
- 更新状态中心

命令不负责：
- 直接操作硬件
- 直接绘制 UI
- 直接承担复杂调度算法实现

---

## 12. 撤销重做衔接

项目 / 任务模型必须支持撤销重做，尤其是：

- 新建或删除任务
- 调整任务顺序
- 修改任务绑定的工艺对象
- 修改任务组结构
- 修改项目默认参数

### 12.1 撤销对象建议

撤销对象至少要保存：

- 修改前的任务快照
- 修改后的任务快照
- 关联工艺对象 ID
- 关联路径 ID

---

## 13. 为硬件层预留的接口

虽然硬件最后做，但项目与任务模型必须预留输出入口。

### 13.1 预留能力

- 将任务转成执行队列
- 将路径转成设备指令集
- 将任务状态转成设备状态映射
- 将报警和中断回写到项目/任务状态

### 13.2 设备适配前不要做的事

- 不要在任务模型里写具体控制卡协议
- 不要在项目模型里写某品牌设备特有字段
- 不要把设备状态当成工程的唯一状态来源

---

## 14. 数据流建议

### 14.1 工程编辑流

```text
ProjectModel
    → ProcessDocument
    → ProcessObject
    → ToolPath
    → TaskJob
```

### 14.2 任务执行前流

```text
TaskJob
    → SimulationResult
    → Ready / Failed
    → 后续设备执行
```

### 14.3 任务状态流

```text
Idle → Ready → Running → Completed / Failed / Paused / Cancelled
```

## 15. 开发建议

### 15.1 第一阶段：项目结构

先建立：
- `ProjectModel`
- `ProcessDocument`
- `TaskJob`
- `TaskGroup`
- `TaskStep`

### 15.2 第二阶段：状态与引用

实现：
- 状态流转
- 引用关系
- 失效机制
- 数据一致性检查

### 15.3 第三阶段：任务编排

实现：
- 顺序组织
- 批处理
- 暂停/恢复
- 重试

### 15.4 第四阶段：仿真与执行入口

接入：
- 仿真系统
- 任务预览
- 设备预留接口

---

## 16. 推荐错误码

建议采用以下错误码前缀：

- `project.*`
- `task.*`
- `job.*`

### 示例

- `project.invalid`
- `project.load_failed`
- `project.save_failed`
- `task.empty`
- `task.invalid_state`
- `task.rebuild_failed`
- `job.cancelled`
- `job.queue_failed`

---

## 17. 总结

项目 / 任务模型是工业激光加工软件从“单次图形编辑”走向“可组织、可批处理、可执行工程”的关键一步。

它应当做到：

- 组织整份工程数据
- 管理加工任务与步骤
- 与工艺、路径、仿真紧密衔接
- 为后续硬件执行提供统一出口
- 保持 UI 和设备层解耦

如果这一层设计稳定，后续无论是多工件、多任务还是多设备兼容，系统都能保持清晰的工程结构，不会失控。
