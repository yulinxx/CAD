01

全局分层架构

一句话：EXE 只做编排，框架库做装配，客户模块提供控件与命令，契约头是三者唯一共同依赖。默认动态库交付，shell 与客户模块各自导出接口；关闭 UI_BUILD_SHARED 后合并成静态单 EXE。

读图顺序：从顶部薄入口往下看依赖，底部契约是所有层的公共底座。默认动态模式下 shell 与客户模块各自编成 DLL 并在编译期链接；关闭 UI_BUILD_SHARED 后合并进单 EXE，不按名称运行期加载。

框架负责什么

  • 解析并校验 profile，生成纯数据装配信息 AssemblyInfo
  • 创建容器级控件：区域、槽位、布局、标题栏、菜单
  • 按 id 向注册表索取面板 / 对话框工厂并挂载

客户负责什么

  • 实现 IWidgetFactory 返回真正的业务面板
  • 实现 ICommandCatalog/Invoker 提供命令语义
  • 实现 customerBuildFingerprint() 与 createCustomerModule()，只依赖契约
02

依赖方向与构建产物

一个客户一个 EXE。默认动态链接，交付 MantiSoft.exe + shell DLL + 客户 DLL；切换客户改 UI_CUSTOMER（A/B/C）重新配置。需要单 EXE 时使用 -DUI_BUILD_SHARED=OFF。

注意大小写：include/UiShell/ 是目录，UiShell 是库目标；默认产物是 UiShell.dll 与 UiCustomerX.dll，关闭 UI_BUILD_SHARED 后才变成静态库并合并进 MantiSoft.exe。

03

启动到装配的时序

翻译必须先装，否则客户显示名停在源语言；attachWindow() 必须在窗口 show() 之前。启动由 main.cpp → AppBootstrap::start() 编排，加载失败通过明确退出码返回。

2. 翻译初始化TranslationSetupcreate() + installFromArguments(--lang/系统语言)创建失败退出码 5

04

从配置到界面：装配流水线

AssemblyInfo 是不含 QWidget 的纯数据快照，所以解析、校验、排序、功能开关过滤都能脱离 GUI 单测。props 从 profile 解析一路透传到工厂。

requiredFeatures 不满足的面板在装配阶段静默跳过；菜单命令在 catalog 中找不到时丢弃并记 warning；菜单项 enabled 在渲染时按 requiredFeatures 计算。
细化流程覆盖失败分支与空壳回退策略。首次加载与运行期刷新共用同一套装配/通知机制，但刷新粒度不同（全壳重建 / 仅 chrome / 视结构变化）。
05

区域 · 槽位 · 面板布局模型

7 类区域是产品语义，不随客户变化；客户能改的是区域的可见性、顺序、槽位划分和面板归属。

面板只声明 slot id，由 planner 的反查索引确定所属区域；区域隐藏时其下所有面板一起不装配。
每个槽位是一个独立布局容器；面板挂载时先落位再按计划设置可见性，避免默认可见状态闪出。
06

扩展点：两个注册表

加新面板或新对话框只需要 append 一条绑定，不改 ShellServices、CustomerModule 的结构或 RuntimeBuilder 的代码。

两个注册表对称：都按字符串 id 查一个纯虚接口。对话框注册表不做类型擦除（没有 void* 与类型键），所有对话框都实现 IDialogFactory。
07

跨模块规则：不传标准库对象、谁创建谁释放

EXE、UiShell.dll、UiCustomerX.dll 是三个独立链接的模块，各自内联了一份标准库模板。跨模块只传「两边布局一定相同」的东西；完整规则写在 include/UiShell/Export.h 顶部，并由检查与编译期断言兜底。

原先跨模块的两处 std::function（ShellServices::languageChanged、IFeatureFlagStore::subscribe）已改为观察者接口；对话框注册表的 void* + 类型键已改为直接存 IDialogFactory*。
08

运行期刷新的三条路径

语言切换重建 chrome 但保留面板；皮肤切换只应用 QSS/Palette 并刷新菜单勾选态；功能开关变化先重规划并比较 structureKey，结构变了才重建 shell，否则只刷新 chrome。三者复用同一组扩展点与刷新入口。

菜单文字与勾选态在创建时一次性写入 QAction，所以皮肤切换也需要重建菜单（MenuController 按 ShellServices.strThemeId 设 checked）；面板和其他控件靠 QSS 自动刷新。功能开关变化走第三条路径：FeatureFlagStore 通知 → 重规划 → structureKey 比较 → 结构变化则全量重建，否则 refreshShell + 菜单 enabled 刷新。客户可用 ShellServices.customStylePrefix 只覆盖 light/dark 其中一套，另一套自动回退框架默认。
09

ABI 校验与导出面（动态模式）

默认动态链接下 shell 与客户模块都是独立 DLL，这一节的约束默认生效；-DUI_BUILD_SHARED=OFF 静态链接时没有跨 DLL 边界，可忽略。EXE、shell DLL、客户 DLL 必须来自同一次构建：宿主先检查 Qt 运行时版本，再分别比较客户与 shell 的构建指纹（只经 const char* 返回），一致后才让 CustomerModule 按值返回、才创建运行期。指纹已包含契约代际 kUiApiVersion、Qt、编译器、CRT、客户与提交，运行期不再做结构体版本 / 大小校验。

Qt5 与 Qt6 二进制不兼容：两者不能共用同一个构建目录，需分别配置。导出表检查仅在 Windows 且 UI_BUILD_SHARED=ON 时注册，macOS 本机不可验证，需 Windows CI 覆盖。

导出工厂（允许）

  • createTranslationService / createQtTextProvider
  • createTitleBar
  • createShellRuntime / createWidgetFactoryRegistry
  • createDialogRegistry / createFeatureFlagStore
  • shellBuildFingerprint

具体类（禁止导出）

  • ShellRuntime / ShellView / RegionContainer / ProfilePipeline
  • ProfileParser / ProfileValidator
  • AssemblyPlanner
  • TranslationService / QtTextProvider / TitleBar
  • WidgetFactoryRegistry / DialogRegistry / FeatureFlagStore
  • TitleBarHostAdapter / Jsonc
  • 内部函数 createWindowFrame / createWindowCapabilities / textContextForKey（由 ctest 导出表检查自动扫描）
10

部署链

部署集中在一处。默认动态模式把 shell/客户库和 EXE 分别传给 windeployqt；静态模式只分析 EXE。工具只分析命令行里二进制的导入表，所以每个需要部署的二进制都必须显式列出。

Qt5 的 qml 模块落在 QtQuick.2，Qt6 落在 QtQuick；自检对两种都接受。
11

现状与演进路线

骨架方向正确，但离"客户完全可控的数据驱动 UI + 多业务对话框"还有几步。下表是本轮审查的结论。

已具备

  • 契约 / profile / 装配信息 / 运行时分层，分层检查自动守边界
  • Region → Slot → Panel 配置驱动，顺序与可见性可配
  • 默认动态库交付（EXE + shell DLL + 客户 DLL）；可关闭切换静态单 EXE，并保留 ABI + 构建指纹校验
  • 两个扩展注册表；面板 props 完整透传
  • 翻译按模块分组，语言/皮肤切换保留面板实例
  • widget 与 QML 面板共用工厂注册点

待建设（按建议顺序）

  • 命令 → 对话框的结构化入参 / 结果回传协议
  • Windows x64 + Qt5.15 / Qt6 双版本的 CI 覆盖（部署与导出表检查）
  • 运行期换客户（目前一客户一 EXE）
