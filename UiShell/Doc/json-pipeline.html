01

总览：从 ui.json 到 ProfileModel

整个管道是一条线性的数据生产线，中间节点只追加不回退。出错时尽早返回，避免无效计算浪费在坏数据上。

整条管道都在 ProfileParser::loadFromJson 内完成，返回值是扁平的 ProfileLoadResult。只有入口阶段的失败（文件超限 / JSONC 语法错误 / JSON 语法错误 / 根节点不是对象）会提前返回；version 与字段级 Error 会继续解析并累积诊断，最后仍执行 ProfileValidator。Warning 始终累积。

输入约束

  • UTF-8 编码（BOM 可选）
  • JSONC 格式（允许 // 和 /* */ 注释）
  • 文件大小上限由 ProfileLimits::maxProfileBytes 硬编码

输出约束

  • 只含纯数据结构，不含 QWidget
  • model 是 std::optional，仅无 Error 时有值
  • diagnostics 始终完整返回

不负责什么

  • 不读文件（调用方自己读入 QByteArray）
  • 不创建控件
  • 不解析 props 内部结构
  • 不按能力过滤面板
02

入口与接口边界

Model 层是 shell 内部静态库（UiShellModel），没有接口和工厂：ProfilePipeline 直接调用静态函数 ProfileParser::loadFromJson() 与自由函数 planAssembly()；测试同样直接调用，并可单独调用 stripJsoncComments() / jsoncLineColumn()。ProfileParser 在字段解析完成后调用 ProfileValidator。

原先的 Model 层接口与 createXxx() 工厂已删除：它们只有一个实现、从不跨 DLL，接口只增加了一层间接（其中的 validate 也从未被调用）。
03

JSONC：带注释 JSON 的预处理

注释处理是整个管道最精巧的一步，且已经吸收了 BOM 剥离。关键设计：用空格替换而非删除，保证字节偏移与行号完全对齐。

优化变更：BOM 剥离已合并进 stripJsoncComments——复制完 buffer 先判断 BOM 再进入状态机，调用方只需一次拷贝。BOM 只有 3 字节且不含换行，删掉后 size 用处理后的长度，blockStart 的行号计算仍正确。

为什么用空格替换而非删除？

  • QJsonParseError.offset 是字节偏移
  • 删除注释会让后续所有 token 的 offset 前移
  • 空格替换让 offset 与原文件完全对齐
  • → jsoncLineColumn(offset) 可以直接在原文件上计算行列号

错误：未闭合块注释

  • 走到文件末尾仍在 BlockComment 态
  • 扫描 blockStart 到文件头的换行，算出起始行号
  • 返回 JsoncStripResult.ok = false
  • 错误消息："unterminated block comment starting at line N"
04

Qt 解析器与错误定位

JSONC 预处理完成后，直接喂给 Qt 自带的 QJsonDocument::fromJson。出错时把字节偏移转换成人类可读的行列号。

注意顺序：先检查 QJsonParseError，再检查 isObject()。后者是因为 profile 根节点必须是 object——如果用户写了 [1,2,3] 或 "hello"，虽然 Qt 能正常解析，但不符合 profile schema。
05

顶层字段逐层解析

每个字段独立处理，Unknown 字段只告警不报错（保留前向兼容），已知字段按类型强校验。

递归解析的关键防御：menuNodeCount 跨所有递归调用共享，超限后只报一次错，后续节点返回空节点且不再展开子节点；递归参数 depth 达到 ProfileLimits::maxMenuDepth 时停止展开，防止深层嵌套爆栈。
06

二次校验：ProfileValidator

字段解析阶段只做类型、必填与上限检查，交叉引用在解析全部完成后统一校验——此时所有数据都在 ProfileModel 里。

Validator 里用两个 QSet 做 O(1) 查重：regionIds 收集所有 region.id，paneSlotIds 收集所有 slot.id（含自动生成的）。Panel 校验时直接 paneSlotIds.contains(panel.paneSlotId) 即可判断引用是否合法。

Warning vs Error

  • Error：阻断产出，model 不赋值
  • Warning：记录但继续，model 正常产出
  • CenterView 缺失只告警——某些纯对话框式界面不需要
  • 未知顶层字段只告警——为未来新增保留前向兼容

自动 slot 生成

  • Region 没写 slots？→ 自动生成 {regionId}.main
  • CenterView 区域 → stretch = 1（吃剩余空间）
  • 自动生成的 slot 也参与唯一性校验；若 id 与其它 region 的 slot 冲突，只报错且不追加该自动 slot，不会覆盖显式声明
  • 冲突时只报错，不追加自动 slot，也不会覆盖任何显式声明
07

Diagnostic 诊断体系

所有错误和警告都被收敛成统一的 Diagnostic 结构，strJsonPath 使用点分路径格式（$.regions[0].slots[1]），方便用户和 IDE 直接定位。

jsonPath 的构造规则：顶层字段 → $.fieldName；数组元素 → $.fieldName[index]；嵌套字段 → $.a.b.c。这不是标准 RFC 6901 JSON Pointer（标准用 / 而不是 .），而是项目自定义的点分路径，语义直观、对人类更友好。
08

ProfileLoadResult：最终产出

Model 内部的扁平结构体（不跨 DLL，因此可以用 std::optional）。std::optional 的 has_value() 直接充当"是否成功"的标志。

为什么用 std::optional 而不是裸指针或 bool + model？因为 optional 的状态（有值/空值）和 isOk() 天然一一对应，不存在"model 有值但 isOk=false"的歧义。

09

错误定位实战

常见错误类型和诊断消息长什么样，一目了然。

Warning 的"陷阱"：拼写错误（少字母）会被当成未知字段只告警，用户可能以为配置生效了实际被忽略。这就是为什么 IDE 插件和 schema 校验很重要——在用户编辑阶段就拦住。
10

时序图：三条典型路径

把"谁在什么时候调谁"说清楚。一个正常解析、一个 JSONC 错误提前返回、一个 Warning 继续产出——对比三个分支的消息流。

三条路径一目了然：场景 A（上半）正常走完整条管道直到 AssemblyPlanner；场景 B（左下）JSONC 错后直接在 Parser 层 return，QJsonDocument 和 Validator 都没机会执行；场景 C（右下）Warning 被追加但不影响后续步骤继续跑完。

为什么场景 B 能那么早返回？

  • stripJsoncComments 在 BOM+注释挖空时发现 /* 没闭合
  • 此时 Qt 解析器还没启动，省了 QJsonParseError 那一步
  • Parser 内部 return result 直接带出已收集的 diagnostics

激活条含义

  • 深色竖线 = 类的 active 阶段
  • 不同层用不同颜色：装配层紫色、Model 层青/橙、Qt 层灰
  • ProfileValidator 只在 Parser 末尾被调一次，生命周期最短

Pipeline 和 Parser 的边界

  • Pipeline 持 profile 原文 / 模型 / 计划 / 诊断缓存；ShellServices 按调用传入
  • Parser 是纯函数：QByteArray → ProfileLoadResult
  • 两者之间只有一个 loadFromJson() 调用，零依赖
11

UML 类图：类与依赖关系

类图回答"谁依赖谁、谁持有谁、谁是接口"。Model 层不依赖 Assembly 层是低耦合的关键——Parser/Validator 完全不知道 ShellRuntime 和 Pipeline 的存在。

三层清晰：Assembly 层（ShellRuntime / ProfilePipeline / AssemblyPlanner）→ Model 层（ProfileParser / ProfileValidator / stripJsoncComments / planAssembly）→ 数据结构（ProfileLoadResult / Diagnostic / ProfileModel / 各 Spec）。Model 层不反向依赖 Assembly 层，低耦合的关键保证。

关键耦合规则

  • ShellRuntime 只知 Pipeline，不知 Parser
  • Pipeline 只调 ProfileParser::loadFromJson + planAssembly，不知 Jsonc/QJson
  • Parser 知 Jsonc/QJson/Validator，但完全不知道 ShellServices/AssemblyInfo
  • ProfileModel 只被消费，不持有任何类引用

为什么是静态方法而非实例？

  • ProfileParser::loadFromJson 是 static
  • ProfileValidator::validate 是 static
  • stripJsoncComments 是内部自由函数（JsoncInternal.h，不导出）
  • 全部无状态，天然可单测、可重入、无线程安全问题

为什么没有接口

  • Model 层是内部静态库，只有一个实现，从不跨 DLL
  • 直接调用静态 / 自由函数，测试与 shell 走同一条路径
  • 规划器实现类在 AssemblyPlanner.cpp 的匿名命名空间里
  • 不属于公开 ABI：结构体可随版本自由调整
